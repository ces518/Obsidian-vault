## 개요

**HTTPS = HTTP + TLS** 구조에서, 한 IP에 여러 도메인을 호스팅할 때 발생하는
**닭과 달걀 문제(순환 의존성)** 와 이를 해결한 **SNI(Server Name Indication)** 의 동작 원리를 다룬다.
또한 SNI의 트레이드오프(평문 노출), 한국의 SNI 차단, 그리고 차세대 표준인 **ECH**까지 정리한다.

---

## 1. TLS의 계층 위치 — 모호한 중간 계층

> [!important] TLS는 OSI에 깔끔히 매핑되지 않는다
> 통념상 **L5 (세션 계층)** 이라 부르지만, 실제로는 **L4(TCP)와 L7(HTTP) 사이의 중간 계층**.

```
┌──────────────────┐
│  L7  HTTP        │  ← 애플리케이션
├──────────────────┤
│  ?   TLS         │  ← L4와 L7 사이의 보안 계층
├──────────────────┤
│  L4  TCP         │  ← 전송
├──────────────────┤
│  L3  IP          │
└──────────────────┘
```

> [!tip] 핵심 사실
> **TLS 핸드셰이크는 HTTP 통신보다 먼저 끝나야 한다.**
> → 이 순서가 SNI 문제의 출발점이 됨.

---

## 2. 닭과 달걀 문제 — 순환 의존성

> [!important] 문제 상황
> 한 서버 IP에 여러 HTTPS 사이트를 호스팅하려 할 때, **인증서 선택**과 **호스트명**이 서로를 필요로 하는 순환 의존성이 발생.

![[Pasted image 20260510194836.png]]

### 순환 의존 구조

```
┌─────────────────────────────────────┐
│ 서버: "어떤 인증서 보내지?"           │
│       → 호스트명을 알아야 함         │ ◀──┐
└────────────┬────────────────────────┘    │
             │                              │
             ▼ 필요                         │ 필요
┌─────────────────────────────────────┐    │
│ 호스트명은 HTTP Host 헤더에 있음      │    │
│ → TLS가 끝나야 볼 수 있음            │ ───┘
└─────────────────────────────────────┘
```

### SNI 이전의 회피책

> "한 IP = 한 사이트" 정책 → IP 하나당 사이트 하나만 호스팅
> → **IPv4 고갈 가속의 한 원인**이 됨

## 3. SNI의 역할 — 의존성 사슬 절단

> [!important] SNI (Server Name Indication)
> **ClientHello 단계에서 호스트명만 평문으로 미리 흘려보내는 우회로**
> 정확히 **순환 의존 사슬 중 한 곳을 끊는** 역할.

### Before vs After

```
[원래 의존성 — 순환]
인증서 선택 ← 호스트명 ← HTTP Host ← TLS 완료 ← 인증서 선택 (순환 ❌)

[SNI 이후 — 일직선]
SNI(호스트명) → 인증서 선택 → TLS 완료 → HTTP 통신 ✅
```

### TLS 핸드셰이크에서 SNI의 위치

```
Client                                  Server
  │                                       │
  │ ① ClientHello                          │
  │    - TLS 버전, 암호 스위트              │
  │    - SNI: "www.example.com" ◀── 평문!  │
  │ ──────────────────────────────────────▶│
  │                                       │ ② SNI 보고 인증서 선택
  │                                       │
  │ ③ ServerHello + 인증서 (해당 도메인)    │
  │ ◀──────────────────────────────────── │
  │                                       │
  │ ④ Key Exchange + Finished              │
  │ ──────────────────────────────────────▶│
  │                                       │
  │ ⑤ 암호화 채널 위에서 HTTP 통신 시작      │
```

## 4. 트레이드오프 — SNI는 평문이다

> [!caution] SNI의 본질적 한계
> SNI는 **암호화 키 협상 이전**에 보내야 하므로 **평문일 수밖에 없다**.

### 결과

| 보호 여부 | 항목 |
|---------|------|
| **노출됨** ❌ | "어느 도메인에 접속 중인지" (호스트명) |
| **보호됨** ✅ | 페이지 내용, 요청 본문, 응답 데이터 |
| **보호됨** ✅ | URL 경로, 쿼리 파라미터, 헤더 |

### 한국의 SNI 차단

> [!note] 망 차단의 도구
> 한국의 SNI 차단은 정확히 이 **평문 SNI 필드를 검사**하는 방식.
> HTTPS 자체는 못 깨도 "어디 접속 중인지"는 검열 가능.

```
ISP/방화벽이 ClientHello 패킷을 가로채서:
  ① SNI 필드 추출 (평문)
  ② 차단 도메인 목록과 비교
  ③ 일치 시 RST 패킷 송신 → 연결 끊김
```

## 5. ECH — 차세대 표준

> [!important] ECH (Encrypted Client Hello)
> SNI의 평문 노출 문제를 해결하기 위해 **ClientHello 자체를 암호화**하는 방향으로 진화 중.

### 동작 원리 (요약)

```
1. 서버는 DNS HTTPS 레코드(RFC 9460)에 ECH 공개키를 게시
2. 클라이언트가 DNS로 공개키를 받음
3. 진짜 ClientHello를 그 공개키로 암호화
4. 외부 ClientHello에는 더미 호스트명만 표시
5. 서버만이 진짜 호스트명을 복호화 가능
```

→ ISP/방화벽은 **어떤 도메인인지 더 이상 볼 수 없음**.

## 6. 역사적 맥락

| 시기 | 방식 | 결과 |
|------|------|------|
| **SNI 이전** | 사이트마다 별도 IP 할당 | IPv4 고갈 가속 |
| **SNI 이후** (RFC 6066, 2006) | 한 IP에 다수 사이트 | **CDN/가상호스팅 시대 개막** |
| **ECH 도입 중** (RFC 9460) | 호스트명까지 암호화 | SNI 기반 차단/감시 무력화 |

## 7. 실무에서 만나는 지점

### CDN 라우팅의 토대

> [!tip] CDN의 동작 원리
> Cloudflare, CloudFront 같은 CDN은 **SNI를 보고 어떤 origin으로 보낼지 결정**.
> 한 IP(엣지 노드)에서 수백만 도메인을 처리하는 게 가능한 이유.

### OkHttp 등의 SNI 미스매치 에러

흔한 원인:
- **DNS가 잘못된 IP를 반환**한 경우
- HTTP/2의 **Connection Coalescing** — 같은 IP를 사용하는 다른 도메인의 연결을 재사용하려다 SNI와 인증서가 맞지 않음

### 브라우저 ECH 활성화

- **Chrome / Firefox** 모두 설정에서 ECH 활성화 가능
- DNS-over-HTTPS(DoH) + ECH 조합 시 호스트명 완전히 비공개

### 국가별 망 정책

```
SNI 검사로 차단 (한국 등)
        │
        ▼
ECH 도입 시 차단 무력화
        │
        ▼
일부 국가는 ECH 자체를 차단하는 흐름
```

## 8. 한 줄 요약

> [!summary] 핵심
> **TLS 핸드셰이크와 HTTP Host 헤더 사이의 순환 의존성을 끊기 위해,
> 호스트명만 ClientHello에 평문으로 미리 흘려보내는 우회 기법.**
> CDN의 토대이자 망 차단의 도구이며, ECH로 가려지는 중.

---

## 핵심 요약

> [!summary]
> 1. **TLS는 L4와 L7 사이**의 중간 계층 — 통념상 L5라고 부르지만 모호함
> 2. **TLS 핸드셰이크가 HTTP보다 먼저** 끝나야 한다 → SNI 문제의 출발점
> 3. **닭과 달걀**: 인증서 선택은 호스트명 필요 ↔ 호스트명은 HTTP Host에 있음 ↔ HTTP는 TLS 완료 후
> 4. SNI 이전 회피책 = "한 IP = 한 사이트" → **IPv4 고갈** 가속
> 5. **SNI** = ClientHello에 호스트명을 **평문**으로 미리 보냄 → 순환 의존 절단
> 6. SNI는 키 협상 전이라 **평문일 수밖에 없음** → 도메인은 노출, 내용은 보호
> 7. 한국의 SNI 차단 = 이 평문 필드를 ISP가 검사하는 방식
> 8. **ECH (Encrypted Client Hello)** = ClientHello 자체를 암호화 → SNI 차단 무력화
> 9. **CDN의 토대**: Cloudflare, CloudFront 등이 SNI로 origin 라우팅
> 10. RFC 6066 (2006, SNI) → RFC 9460 (ECH) — HTTPS의 진화 흐름
