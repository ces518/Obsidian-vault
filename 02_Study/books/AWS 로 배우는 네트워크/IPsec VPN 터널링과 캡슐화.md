# IPsec VPN 터널링과 캡슐화

## 개요

[[사설망과 가상 사설망(VPN)]] 후속편 — **IPsec VPN이 패킷 수준에서 어떻게 터널링(암호화)** 하는지 구체적으로 본다.
- **터널링 ≒ 암호화** — 터널에 들어가면 안 보이듯, 암호화하면 데이터 내용을 알아볼 수 없다
- **IPsec 3대 구성**: 키 교환(**ISAKMP/IKE**) + 무결성(**AH**) + 기밀성(**ESP**)
- 기반 지식 **PKI**: 대칭키 vs 비대칭키(`PUBLIC_KEY`/`PRIVATE_KEY` 쌍), 인증서(X.509)
- **SSL/TLS는 소켓(L7) 수준**, **IPsec은 패킷(망) 수준** 암호화 → 앱 종류와 무관하게 전부 암호화
- 동작: **원본 IP 패킷을 통째 암호화·캡슐화**하고 게이트웨이 간 **새 IP 헤더**를 덧붙임
- 부작용: 헤더가 늘어 **MTU 초과 → 단편화** → 망 불안정 → **MSS/MTU를 미리 줄여** 회피

## 한 줄 요약

> IPsec VPN은 원본 IP 패킷을 통째로 암호화한 뒤 게이트웨이 주소로 된 새 IP 헤더를 씌워(캡슐화) 보내는 **패킷 수준 터널링**이다. 키 교환(IKE)·무결성(AH)·기밀성(ESP)으로 구성되며, SSL/TLS(소켓 수준)와 달리 망 수준에서 앱 무관하게 보호한다. 헤더가 추가되어 **MTU를 넘으면 단편화**가 생기므로 MSS/MTU를 미리 줄이는 게 핵심이다.

---

## 1. 터널링이란? — 결국 "암호화"

> [!important] 터널링 = 암호화
> SSH 터널링 등 자주 등장하는 "터널링"은 거의 대부분 **암호화한다는 뜻**. 대단한 개념이 아니다.

> [!tip] 비유 — 터널에 들어간 차
> 헬기가 도주 차량을 추격하다가 차가 **터널에 진입**하면 더 이상 보이지 않는다.
> 암호화하면 데이터가 무슨 내용인지 **알아볼 수 없게 되는 것**과 같다.

- 인터넷상에서 정보가 보이지 않도록 암호화해 **로컬 LAN처럼** 통신하게 하는 방법론이 VPN
- 그중 대표 프로토콜이 **IPsec**

---

## 2. IPsec 프로토콜 배경

> [!note] IPv4의 보안 한계 → IPsec → IPv6에 포함
> IPsec은 IPv4의 보안적 한계를 극복하려 고안되었고, 이후 **IPv6 표준에 포함**되어 범용적으로 쓰인다.

- (강의 여담) IPv6는 "차세대"로 불린 지 30년 가까이 지나도 본격 시대가 오지 않음
- 그래도 IPsec 자체는 광범위하게 사용됨

---

## 3. IPsec 3대 구성요소 + 보안 3요소

> [!important] IPsec 내부는 세 갈래
> 키 교환 / 무결성 / 기밀성으로 나뉜다.

| 구성요소 | 역할 | 보안 3요소 대응 |
|----------|------|----------------|
| **ISAKMP / IKE** (Internet Key Exchange) | 양단이 키 쌍을 생성·교환, 알고리즘 합의 | (사전 준비) |
| **AH** (Authentication Header) | 패킷 단위 **무결성** 보장 (Hash 기반) | **무결(Integrity)** |
| **ESP** (Encapsulation Security Payload) | 전부 암호화 → 키 가진 자만 복호 | **기밀(Confidentiality)** |

> [!note] 보안의 3요소
> **기밀(암호화)** · **무결(변조 판별, Hash)** · **가용**. IPsec은 앞의 두 가지를 ESP/AH로 구현.

---

## 4. 기반 지식 — PKI (공개키 기반 구조)

> [!important] 대칭키 vs 비대칭키
> 보안성 "부여(잠금)"와 "해제(열기)"를 **하나의 키**로 하면 대칭키, **두 개의 키**로 쪼개면 비대칭키.

| 방식 | 키 | 비유 |
|------|----|------|
| **대칭키** | 1개로 잠금·해제 | 열쇠·차키 (열고 잠그고를 한 키로) |
| **비대칭키 (PKI)** | `PUBLIC_KEY` + `PRIVATE_KEY` 쌍 | 잠그는 키 / 푸는 키가 분리 |

- 보통 `PUBLIC_KEY`로 암호화 → `PRIVATE_KEY`로 복호 (반대도 가능), **두 키는 쌍**
- `PUBLIC_KEY`는 **인증서**에 포함되어 배포됨 → 형식은 **X.509** (공인/금융 인증서가 이 부류)
- 양단(클라이언트·서버)이 비밀 통신(터널링)을 하려면 이 **키 쌍을 생성·교환** → 인터넷상 키 교환이 **IKE**, 관련 프로토콜이 **ISAKMP**

## 5. SSL/TLS vs IPsec — 암호화가 일어나는 계층

> [!important] 같은 암호화라도 동작 계층이 다르다
> SSL/TLS는 소켓(L7) 수준, IPsec은 패킷(망) 수준.

| 구분 | **SSL/TLS (HTTPS)** | **IPsec** |
|------|---------------------|-----------|
| **암호화 계층** | 소켓 / L7 | **패킷 레벨 (로우 레벨)** |
| **적용 범위** | HTTP 통신만 암호화 | **앱 종류 무관 — 망 수준 전부 암호화** |
| **앱 관여** | 앱이 SSL 적용 필요 | 환경만 주어지면 자동 |

> [!tip] 핵심 장점
> IPsec은 망 수준에서 암호화하므로, 그 위에서 도는 애플리케이션이 무엇이든 **자동으로 보호**된다.

## 6. VPN 터널링 동작 — 원본 패킷 캡슐화

> [!important] 원본 IP 패킷을 통째 암호화하고 새 IP 헤더를 씌운다
> 엔드포인트 주소는 암호화 안쪽에 숨고, 바깥은 **게이트웨이 간 주소**만 보인다.

```
[PC 3.3.3.10] ─ [GW 3.3.3.1] ===== 인터넷(VPN 터널) ===== [GW 5.5.5.1] ─ [Server 5.5.5.100]

원본 패킷 (PC가 생성)
┌───────────────┬──────────────┐
│ IP: src 3.3.3.10 → dst 5.5.5.100 │ payload │
└───────────────┴──────────────┘
        │  게이트웨이 도착 → 통째 암호화 + 캡슐화
        ▼
캡슐화 패킷 (게이트웨이 간)
┌───────────────┬──────────┬───────────────────────────┐
│ New IP: src 3.3.3.1 → dst 5.5.5.1 │ ESP 헤더 │ [암호화된 원본 IP 패킷] │
└───────────────┴──────────┴───────────────────────────┘
        │  반대편 게이트웨이 도착 → 바깥 헤더 제거·복호
        ▼
원본 패킷 복원 → 5.5.5.100 으로 전달
```

- 바깥에서는 "어느 게이트웨이 → 어느 게이트웨이"만 보이고 **실제 엔드포인트는 알 수 없음**

## 7. MTU / 단편화 문제와 대응

> [!caution] 캡슐화 → 헤더 증가 → MTU 초과 → 단편화
> 원본 패킷이 이미 1500(MTU)이면, 새 IP 헤더 + ESP 헤더가 붙어 **MTU를 초과** → 단편화 발생.

- 암호화 + 단편화가 겹치면 **망이 불안정**해지고 문제가 생김
- **대응**: 경로상(라우터 간) 단편화가 안 나도록 유도
    - **Path MTU**를 계산해 양단이 **MSS/MTU를 미리 축소** (예: 1500 → 1400)
    - 그러면 추가 헤더(IP 헤더 ≈ 20B, ESP 헤더 등) 붙일 여유 확보
- 확인 필요: 옵션에 따라 ESP 헤더 크기·구성이 달라지는 세부

관련: [[Maximum Segment Size]] · [[TTL 과 단편화]]

## 8. NAT와의 차이 + 접근 통제

> [!note] 조작 범위가 다르다
> NAT는 헤더의 IP·포트 정도만 조작. **VPN 터널링은 IP 헤더 자체를 새로 추가**(캡슐화)한다.

| 구분 | NAT (공유기) | VPN 터널링 |
|------|-------------|-----------|
| 조작 대상 | IP 헤더의 IP/포트 | **IP 헤더 자체를 추가 + ESP 헤더** |
| 결과 | 주소 변환 | **원본 캡슐화 + 암호화** |

### 대역 기반 접근 통제

- 서버 앞단 보안 장치에서 **특정 CIDR 대역만 인바운드 허용** (예: `5.5.5.0/24`, `3.3.3.0/24`)
- 본사·지사 대역이 아니면(예: `9.9.9.9`) **IP 주소 레벨에서 차단** → 접속 자체 불가

## 핵심 요약

| 기억할 것 | 내용 |
|-----------|------|
| **터널링** | 사실상 암호화 (내용 안 보이게) |
| **IPsec 배경** | IPv4 보안 한계 보완 → IPv6에 포함, 범용 |
| **3대 구성** | IKE/ISAKMP(키 교환) · AH(무결, Hash) · ESP(기밀, 암호화) |
| **PKI** | 대칭키 vs 비대칭키, `PUBLIC_KEY`/`PRIVATE_KEY` 쌍, 인증서 X.509 |
| **SSL vs IPsec** | SSL=소켓/L7, IPsec=**패킷/망 수준**(앱 무관 전부 암호화) |
| **터널링 동작** | 원본 패킷 암호화·캡슐화 + 게이트웨이 간 새 IP 헤더 |
| **MTU 문제** | 헤더 증가 → MTU 초과 → 단편화 → **MSS/MTU 미리 축소**로 회피 |
| **NAT와 차이** | NAT=IP/포트 조작, VPN=IP 헤더 추가 캡슐화 |
| **접근 통제** | CIDR 대역(`/24`)만 인바운드 허용 |

## 질문 / 헷갈리는 점

- 확인 필요: AH와 ESP를 함께 쓰는 경우 vs ESP만 쓰는 경우의 차이
- 확인 필요: 터널 모드(Tunnel) vs 전송 모드(Transport)의 헤더 구성 차이 (강의는 "중첩 터널링" 언급)
- 확인 필요: ESP 헤더의 정확한 크기·옵션별 변동
- 터널링 = 암호화라는 단순화는 직관용이며, 실제로는 인증·캡슐화도 포함됨

## Knowledge로 승격할 후보

- IPsec VPN 터널링 동작 원리 (캡슐화 + ESP/AH)
- 대칭키 vs 비대칭키 / PKI와 인증서(X.509)
- IPsec과 MTU/단편화 문제 (MSS 축소 대응)
