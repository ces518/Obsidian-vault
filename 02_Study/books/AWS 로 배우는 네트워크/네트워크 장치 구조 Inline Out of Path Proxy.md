# 네트워크 장치 구조 Inline Out of Path Proxy

## 개요

네트워크 장치(어플라이언스)의 **세 가지 구조** — **Inline / Out-of-Path / Proxy** 를 다룬다.
각 구조가 **어떤 데이터 단위(Packet vs Stream)** 를 다루는지, 어떤 동작을 할 수 있는지를 비유로 설명한다.
AWS의 **ALB**, **WAF** 같은 핵심 서비스가 모두 **Proxy 구조**라는 점이 실무 포인트.

---

## 1. 사전 개념 — 다루는 데이터 단위

> [!important] 장치 구조를 가르는 핵심 기준
> "이 장치가 **Packet(조각)** 을 다루는가, **Stream(조립된 전체)** 을 다루는가?"

### Packet vs Stream

```
┌─────────────────────────────────────────────┐
│  User Mode (Application Process)            │
│  ┌──────────┐                                │
│  │  HTTP    │  ← 통신 프로토콜 (L7)          │
│  └────┬─────┘                                │
│       │                                      │
│       ▼  Socket I/O — 여기서는 Stream 데이터  │
├──────────────────────────────────────────────┤
│  Kernel Mode                                 │
│  ┌──────────┐                                │
│  │   TCP    │  ← L4                          │
│  ├──────────┤                                │
│  │   IP     │  ← L3 (여기서 Packet 단위)     │
│  ├──────────┤                                │
│  │ Driver   │                                │
│  └────┬─────┘                                │
├───────┼──────────────────────────────────────┤
│  Hardware                                    │
│  ┌────▼─────┐                                │
│  │   NIC    │                                │
│  └──────────┘                                │
└──────────────────────────────────────────────┘
```

| 단위 | 특징 |
|------|------|
| **Packet** | **조각** (퍼즐 한 조각), 크기 제한(MTU=1,500), 단편적 |
| **Stream** | 조각들을 **모두 모아 조립한 전체 흐름**, 끝이 정해져 있지 않음, 연속적 |

> [!tip] 핵심
> - L3/L4 수준에서 통제 → **Packet 단위** → Inline, Out-of-Path
> - L7(HTTP) 수준에서 통제 → **Stream 단위** → **Proxy**

관련: [[계층별 데이터 단위]] · [[택배와 닮은 Packet]]

## 2. 세 가지 장치 구조 — 한눈에 보기

| 구조 | 비유 | 데이터 단위 | 트래픽 경로 | 차단 가능? |
|------|------|------------|------------|----------|
| **Inline** | 톨게이트 / 바리케이트 | Packet | 통과 (가로지름) | ✅ |
| **Out-of-Path** | 과속 감시 카메라 | Packet | 우회 (옆에서 관찰) | ❌ |
| **Proxy** | 대리 응답 직원 | **Stream** | 종단 (대신 받아 다시 보냄) | ✅ |

---

## 3. Inline — 톨게이트 구조

> [!important] Inline
> 트래픽이 **반드시 장치를 통과**해야 하는 구조 → **필터링(차단)이 가능**

### 비유 — 고속도로 톨게이트 / 인터체인지

```
출발지 ──▶ [Inline 장치] ──▶ 목적지
              │
              ├─ 통과 허용 ✅
              ├─ 통과 차단 (Drop) ❌
              └─ 검사 / 변환
```

```
자동차(Packet)가 톨게이트(Inline 장치)를 반드시 지나감
  → "너는 통과, 너는 차단" 결정 가능
  → 바리케이트 쳐버리면 못 지나감
```

### 특징

| 항목 | 내용 |
|------|------|
| **위치** | 트래픽 경로 **위**에 있음 (반드시 통과) |
| **데이터 단위** | **Packet** |
| **주요 동작** | 통과 / Drop (필터링) |
| **대표 장치** | **방화벽(Firewall)**, 라우터, L3/L4 스위치 |
| **위험** | 장치 다운 시 **트래픽 전체 차단** |

> [!caution] Inline의 트레이드오프
> 강력한 차단 기능을 가지지만, **장치 자체가 단일 장애점(SPOF)** 이 됨.
> → 이중화/HA 구성 필수.

## 4. Out-of-Path — 과속 카메라 구조

> [!important] Out-of-Path
> 트래픽 경로에서 **벗어나(우회)** 있는 구조 → 트래픽을 복사해서 **관찰만** 함

### 비유 — 고속도로 과속 감시 카메라

```
출발지 ──────────────▶ 목적지
   │                      ▲
   │  (실제 트래픽)         │
   │                      │
   │   ┌──────────────────┘
   │   │ 미러링/탭(Tap)
   │   ▼
   ├─[Out-of-Path 장치]   ← 트래픽을 복사받아서 분석만 함
       (관찰자, Sensor)
```

```
과속 카메라(Out-of-Path)는 도로 옆/위에서 차를 보기만 함
  → "이 차 과속이네!" 인지만 가능
  → 차를 멈출 권한은 없음
```

### 특징

| 항목 | 내용 |
|------|------|
| **위치** | 트래픽 경로 **밖** (Mirror/Tap으로 복사 수신) |
| **데이터 단위** | **Packet** |
| **주요 동작** | **읽기만** (탐지/감지/분석) |
| **차단 가능?** | ❌ (실시간 차단 불가) |

### 용도별 명칭

> [!note] 센서(Sensor)의 정체성은 "왜 센싱하는가"로 결정됨

| 목적 | 명칭 |
|------|------|
| **해킹 탐지** | **NIDS** (Network-based Intrusion Detection System) — 보안 센서 |
| **장애/이상 징후 탐지** | 패킷 분석 장애 대응 체계 |
| **트래픽 분석** | 모니터링 / 트래픽 분석기 |

> [!tip] Out-of-Path의 장점
> 장치가 다운돼도 **실제 통신에는 영향 없음** → 장애 부담 낮음.
> 대신 차단 기능 필요하면 별도의 Inline 장치와 연동해야 함.

## 5. Proxy — 대리 처리 구조

> [!important] Proxy
> 클라이언트의 요청을 **대신 받아서**(종단) 새로운 연결로 서버에 **대신 보내주는** 구조
> → **소켓 스트림 단위**에서 L7 콘텐츠 검사/조작 가능

### 동작 구조

```
[Inline/Out-of-Path]
Client ────Packet────▶ [장치] ────Packet────▶ Server
        (그대로 통과)

[Proxy]
Client ──TCP/소켓 연결① ─▶ [Proxy] ──TCP/소켓 연결② ─▶ Server
                          (조립된 Stream 검사/변환)
        ▲                                              │
        │                                              │
        └───────────── 응답도 동일하게 두 단계로 전달 ─────┘
```

> [!important] Proxy의 본질
> Proxy는 **두 개의 독립적인 TCP 연결**을 종단 처리한다.
> 클라이언트가 보낸 패킷들을 **다 모아서 Stream으로 조립**한 후, 
> 새 연결을 만들어 서버로 다시 전송.

### 특징

| 항목 | 내용 |
|------|------|
| **위치** | 트래픽의 **종단점**(End-point)으로 작동 |
| **데이터 단위** | **Stream** (소켓에서 조립된 전체) |
| **L7 처리** | HTTP 헤더/바디 검사, URL 라우팅, SSL 종단 가능 |
| **차단 가능?** | ✅ (Application 레벨 차단) |
| **부하** | 높음 (TCP 종단 + 스트림 처리) |

### 대표적인 Proxy 장치

| 장치 | 역할 |
|------|------|
| **ALB** (Application Load Balancer) | L7 로드밸런싱 — HTTP 헤더/경로 기반 라우팅 |
| **WAF** (Web Application Firewall) | 웹 공격(SQL Injection, XSS 등) 차단 |
| **CDN** (CloudFront 등) | 콘텐츠 캐싱 + Origin 라우팅 |
| **Reverse Proxy** (Nginx 등) | 백엔드 서버 보호, SSL 종단 |
| **Forward Proxy** | 내부 사용자의 외부 접속 통제 |

## 6. 왜 Proxy를 잘 알아야 하는가?

> [!tip] 실무 핵심
> 인터넷 서비스의 **대다수가 웹(HTTP)** → Proxy 구조 장치가 사방에 깔려 있다.
> AWS 사용자는 특히 **ALB / WAF / CloudFront**의 동작 원리를 잘 알아야 함.

### AWS 매핑

| AWS 서비스 | 구조 |
|-----------|------|
| **ALB** | **Proxy** (L7) |
| **NLB** | Inline 유사 (L4 통과) |
| **WAF** | **Proxy** (L7 검사) |
| **CloudFront** | **Proxy** (CDN + WAF 통합 가능) |
| **VPC Traffic Mirroring** | **Out-of-Path** |
| **Security Group / NACL** | **Inline** (필터링) |

## 7. 비교 종합

```
                  Client
                    │
                    ▼
        ┌───────────────────────┐
        │  ① Inline 장치          │  ← 톨게이트
        │  (Packet, 차단 가능)     │
        └─────────┬─────────────┘
                  │ 통과한 패킷
                  │
            ┌─────┼──────────┐
            │     │           │
            ▼     ▼           │
       (실제경로) │            │
                  │       ┌───▼──────────┐
                  │       │ ② Out-of-Path │  ← 과속카메라
                  │       │ (Packet, 관찰만)│
                  │       └───────────────┘
                  ▼
        ┌───────────────────────┐
        │  ③ Proxy                │  ← 대리 직원
        │  (Stream, L7 처리)      │
        │  - TCP 종단 → 재연결      │
        │  - HTTP 헤더 검사 가능    │
        └─────────┬─────────────┘
                  ▼
                Server
```

## 핵심 요약

> [!summary]
> 1. 네트워크 장치 구조 = **Inline / Out-of-Path / Proxy** 3가지
> 2. 구분 기준 = **다루는 데이터 단위**: Packet(L3/L4) vs Stream(L7)
> 3. **Inline** = 톨게이트 — 트래픽이 반드시 통과 → **필터링/차단 가능** (Packet 단위)
> 4. Inline의 약점: 장치 다운 시 **트래픽 전체 차단** → 이중화 필수
> 5. **Out-of-Path** = 과속 카메라 — 트래픽 복사받아 **읽기만**, 차단 불가 (Packet 단위)
> 6. Out-of-Path 활용: **NIDS**(보안 센서), 패킷 분석, 트래픽 모니터링
> 7. **Proxy** = 대리 직원 — 클라이언트 연결을 **종단**하고 서버로 **재연결**, **Stream 단위** 처리
> 8. Proxy는 L7 콘텐츠(HTTP 헤더/바디) 검사 가능 → **차단 + 변환** 모두 가능
> 9. 대표 Proxy: **ALB, WAF, CloudFront, Nginx (Reverse Proxy)**
> 10. AWS 매핑: **ALB·WAF·CloudFront = Proxy** / **VPC Mirroring = Out-of-Path** / **Security Group·NACL = Inline**
