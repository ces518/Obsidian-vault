# TTL과 단편화

## 개요

IP 헤더의 두 가지 중요한 메커니즘인 **TTL(Time To Live)** 과 **단편화(Fragmentation)** 를 다룬다.
TTL은 좀비 패킷 방지 장치이며, 단편화는 경로상 MTU 차이로 인해 발생하는 현상이다. 특히 **VPN 환경**에서 단편화를 주의 깊게 봐야 한다.

---

## 1. TTL (Time To Live)

### 역할

패킷이 목적지에 도달하지 못하고 **좀비화되어 인터넷을 떠도는 것**을 방지하는 안전장치.

- 세포의 **텔로미어**에 비유 가능 — 수명이 정해진 카운터
- 라우터를 **1 hop 지날 때마다 1씩 감소**
- 0이 되면 **패킷 폐기**

### OS별 기본값

| OS | 기본 TTL |
| --- | --- |
| Windows | `128` |
| Linux | `64` (구 `255`) |

> [!note]
> 초기값은 언제든 수정 가능하므로 절대적 기준은 아니다. 다만 패킷 캡처 시 **발신 OS 추정** 용도로 참고할 수 있다.

---

## 2. MTU (Maximum Transmission Unit)

- 인터넷 환경에서 패킷의 **최대 크기 = 기본 1,500 bytes**
- 거의 모든 라우터가 1,500으로 설정됨 (**사실상 최소이자 표준**)

---

## 3. 단편화 (Fragmentation)

### 언제 발생하는가?

경로 중간에 **MTU가 더 작은 라우터**가 하나라도 있으면, 그 지점에서 패킷이 **쪼개진다.**

```
[PC:1500] → [R2:1500] → [R4:1500] → [R5:1400] → [R7:1500]
                              ↑
                       "어? 1400밖에 못 받네?"
                       → 여기서 단편화 발생
                       → 패킷을 둘로 쪼갬
```

### 단편화 과정

```
[원본 패킷]
┌─────────────┬──────────────────────────────────┐
│  IP Header  │  TCP Header + Payload (1480B)    │   총 1500B
└─────────────┴──────────────────────────────────┘
                          │
                          ▼  (MTU 1400 구간 만남)
[단편 1]                             [단편 2]
┌───────┬──────────────────┐         ┌───────┬─────────────┐
│IP Hdr │ TCP Hdr + Data1  │         │IP Hdr │   Data2     │
└───────┴──────────────────┘         └───────┴─────────────┘
  복사                                  복사 + ID/Offset 조정
```

- 원본 IP 헤더를 **복사**하여 두 개의 단편 모두에 붙임
- **Identification** — 같은 원본에서 나온 단편임을 식별
- **Fragment Offset** — 원본에서의 위치 (재조립 순서 결정)
- **MF (More Fragments)** — 뒤에 조각이 더 있음을 표시

### 재조립은 누가?

- **최종 수신 측**에서 재조립 담당
- 조각이 여러 개면 재조립이 **부하의 원인**이 될 수 있음

---

## 4. 단편화가 문제가 되는 이유

### 재조립 오버헤드

- 조각이 많을수록 수신 측 부하 증가
- "월급을 10원짜리로 주는 것"과 같은 비효율

### 보안 이슈 — DDoS 공격에 악용

| 공격 비유 | 실제 네트워크 공격 |
| --- | --- |
| 식당에 허위 주문을 계속 넣기 | 쪼개진 패킷을 대량으로 전송 |
| 배민 주문 → 취소 반복 | 재조립 불가능한 단편 전송 |
| 정상 영업 방해 | 서비스 거부(DoS) 유발 |

- **DDoS** (Distributed Denial of Service) — 동시다발적으로 서비스를 마비시키는 공격
- 의도적 단편화로 **불필요한 재조립 부하**를 유발

### 해결 방법 — Path MTU Discovery

- 통신 경로 전체에서 가장 작은 MTU를 미리 탐지
- 송신 측이 처음부터 그 크기에 맞춰 전송 → **단편화 회피**

---

## 5. VPN 환경에서의 주의사항

### 왜 VPN에서 MTU가 줄어드는가?

- **G2G VPN** (Gateway-to-Gateway, 본사-지사 연동) 등에서 **IPsec** 프로토콜 사용
- IPsec은 원본 패킷에 **추가 헤더를 덧붙임(중첩/캡슐화)**
- 원본 MTU 1,500은 고정인데 헤더가 추가되므로, **유효 페이로드 공간이 줄어듦**

```
[일반 패킷]
┌────────┬──────────────────────────────┐
│ IP Hdr │       Payload                │  MTU 1500
└────────┴──────────────────────────────┘

[VPN(IPsec) 통과 시]
┌───────┬───────┬───────┬──────────────┐
│ IP Hdr│IPsec  │IP Hdr │   Payload    │  ← 추가 헤더로
└───────┴───────┴───────┴──────────────┘     실제 Payload 영역 감소
```

### 운영 관점 시사점

> [!warning] VPN 운영 시 주의
> - 단편화가 **빈번하게 발생** → 재조립 오버헤드 누적
> - VPN 구간이 불안정하면 **네트워크 전체 효율 저하**
> - 장애 징후로 단편화가 감지되면, **경로상 VPN 존재 여부를 의심**해야 함

### 진단 포인트

| 체크 항목 | 확인 방법 |
| --- | --- |
| 단편화가 많이 발생하는가? | Wireshark로 MF 플래그 확인 |
| 통신 경로에 VPN 구간이 있는가? | 네트워크 토폴로지 확인 |
| 해당 구간의 MTU는? | Path MTU Discovery로 추정 |

---

## 한 줄 요약

> **TTL**은 패킷이 영원히 떠도는 것을 방지하는 hop 카운터이고, **단편화**는 경로상 MTU가 작은 지점에서 패킷이 쪼개지는 현상으로, 특히 **VPN(IPsec)** 환경에서 자주 발생하므로 장애 진단 시 경로상 VPN 존재 여부를 의심해야 한다.
