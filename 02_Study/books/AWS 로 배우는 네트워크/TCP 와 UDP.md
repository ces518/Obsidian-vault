# TCP와 UDP

## 개요

L4(전송 계층)의 양대산맥인 **TCP**와 **UDP**를 다룬다.
TCP는 **연결 지향(Connection Oriented)** 으로 송신자가 수신자를 배려하지만, UDP는 그런 배려가 전혀 없다.
이 둘은 항상 **L3 IP**와 짝지어 동작하기 때문에 `TCP/IP`, `UDP/IP`로 표기된다.

---

## 1. L4의 위치와 표기

### 계층 구조

```
┌─────────────────────────────┐
│  L7 HTTP / L5~6 SSL         │  User Mode (Application)
├─────────────────────────────┤
│  L4 TCP / UDP               │  ← 여기 (커널 내부 구현)
│  L3 IP                      │
│  L2 Ethernet                │
└─────────────────────────────┘
```

- L4까지는 **운영체제 커널 안에 구현**되어 있음
- 사용자는 Socket을 통해 접근

### `TCP/IP` 표기법

```
        L4: TCP        ← 전송 계층 (분자)
        ──────
        L3: IP         ← 네트워크 계층 (분모)
```

- L4의 TCP가 L3의 IP 위에 올라타는 구조 → **분수 형태**를 가로로 쓴 것이 `TCP/IP`
- UDP의 경우는 `UDP/IP`

> [!important] 핵심 전제
> L4는 **TCP 또는 UDP 둘 중 하나**가 IP와 조합되어 동작한다.

---

## 2. TCP vs UDP — 한눈에 비교

| 항목 | **TCP** | **UDP** |
| --- | --- | --- |
| **정식 명칭** | Transmission Control Protocol | User Datagram Protocol |
| **연결 개념** | **Connection Oriented** (연결 지향) | Connectionless (연결 없음) |
| **순서 보장** | O (시도) | X |
| **재전송** | O (유실 시 자동) | X |
| **수신자 배려** | O (수신 가능 여부 체크) | X (무조건 송출) |
| **복잡도** | 매우 복잡 | 매우 단순 |
| **상태(State)** | 존재 (연결 전/중/완료/종료) | 없음 |
| **클라이언트/서버 구분** | 명확히 존재 | 모호 |
| **대표 활용** | HTTP, 파일 전송, 로그인, 결제 | IPTV, 게임 위치정보, DNS |

## 3. TCP의 핵심 — 연결과 전송 제어

### 연결(Connection) = 가상회선(Virtual Circuit)

> [!important] 용어 정리
> - **Connection** = 연결 (직역)
> - **Session** = 논리적 의미의 연결 (HTTP 로그인 세션 같은 개념)
> - **Virtual Circuit** = 내부적 본질 (가상회선)
>
> 본 문서에서는 일관되게 **"연결"** 이라는 용어를 사용.

### 연결의 효과 — HTTP Session 비유

```
사용자 → 네이버 로그인
         │
         │  HTTP Session 유지
         │  (탭을 새로 열어도 로그인 상태 유지)
         │
         ↓
TCP 레벨에서도 동일한 "유지되는 상태"가 존재
```

### 전송 제어가 만드는 5가지 현상

| # | 특징 | 동작 |
| --- | --- | --- |
| 1 | **순서 보장 (시도)** | 1, 2, 3 순서대로 도착하도록 |
| 2 | **유실 감지 + 재전송** | 수신자가 "2번 못 받았어" → 재전송 요청 |
| 3 | **수신자 배려** | 수신자가 받을 준비 안 되면 송신 중단 |
| 4 | **혼잡 제어** | 네트워크가 막히면 송출 속도 조절 |
| 5 | **순서 번호 기반 식별** | 32비트 시퀀스 번호로 위치 추적 |

> [!note] "보장"의 진짜 의미
> TCP가 순서·재전송을 **보장한다**는 표현은 "완벽 보장"이 아니라
> **그렇게 되도록 설계된 규약과 메커니즘이 있다**는 뜻이다.

### 시퀀스 번호 (Sequence Number)

- **32비트** 정수 (최대 표현 = 약 4 GB)
- 송신된 세그먼트의 **바이트 수만큼** 증가
- 수업·설명에서는 편의상 **1번, 2번, 3번**으로 표기

### 혼잡 제어(Congestion Control) — 표준 없는 영역

> [!warning] TCP 혼잡 제어는 표준이 없다
> "이렇게 처리하라"는 통일된 표준이 존재하지 않음.
> **TCP를 구현하는 쪽(OS/벤더)에서 알아서 잘해야 하는** 영역.
> 이 부분이 OS별·구현별 성능 차이를 만든다.

## 4. TCP의 상태(State) 전이

연결이라는 개념은 곧 **상태(State)** 를 동반한다.

```
[CLOSED] ── 연결 시도 ──→ [SYN_SENT / LISTEN]
                              │
                              ↓
                        [ESTABLISHED]  ← 송수신 가능
                              │
                              ↓
                       [FIN_WAIT / CLOSE_WAIT]
                              │
                              ↓
                          [CLOSED]
                          
정상 종료 vs 비정상 종료 모두 존재
```

### 상태 전이의 부적절성 = 공격 신호

> [!example] 비정상 시나리오
> "연결이 완료되지도 않았는데 송수신을 먼저 시도한다?"
> → 정상 절차상 불가능한 상태 전이 → **공격이거나 오류**

### Stateful Inspection Firewall

- TCP 세션 개념까지 추적하여 상태 전이의 적절성을 검사
- 부적절한 상태 전이를 **탐지·차단**
- 일반 방화벽보다 한 단계 발전된 보안 솔루션

## 5. TCP에서 클라이언트 vs 서버

> [!important] 클라이언트/서버 구분의 근원
> TCP의 **연결 개념** 때문에 자연스럽게 클라이언트와 서버가 나뉜다.

| 역할 | Socket 종류 | 동작 |
| --- | --- | --- |
| **서버** | **Passive Socket** | 연결을 **기다림(Listen)** |
| **클라이언트** | **Active Socket** | 능동적으로 **연결 시도(Connect)** |

소켓 프로그래밍을 하면 자연스럽게 이 개념을 마주하게 됨.

---

## 6. UDP — "받든 말든"의 단순함

### 특징

- **연결 개념 없음** — 그냥 보냄
- **순서·유실·중복 처리 없음** — 다 무시
- **수신자 상태 무관** — 무조건 송출
- 문제 처리는 **개발자가 애플리케이션 수준에서 직접** 구현

### UDP가 유리한 경우 — 멀티미디어 / 실시간

#### IPTV 시나리오

```
[송출 서버] ──→ [클라이언트 1]  정상 수신
            ──→ [클라이언트 2]  공유기 깜빡 → 일부 유실 (깍두기)
            ──→ [클라이언트 3]  처리 지연 → 끊김
```

- 영상 재생 속도는 **일정해야 함**
- 일부 유실되어도 **다음 프레임으로 진행**하는 것이 더 자연스러움
- 잘 받는 사람은 잘 보고, 못 받는 사람은 어쩔 수 없음
- 재전송 기다리느라 멈추는 것보다 훨씬 나음

#### 게임 — 카트라이더(레이싱) 시나리오

```
서버 5.5.5.5
  ├── 클라이언트 3.3.3.3 (3번 차량)
  ├── 클라이언트 4.4.4.4 (4번 차량)
  └── 클라이언트 7.7.7.7 (7번 차량)

위치 정보: ① ② ③ 순서로 송신
              ↓
          ② 유실
              ↓
   서버 수신: ① ③ (② 누락)
```

| 프로토콜 | 동작 | 결과 |
| --- | --- | --- |
| **TCP** | "2번 다시 보내!" → 재전송 대기 | **느려서 게임 불가** |
| **UDP** | 2번은 버리고 3번 위치로 보정 | 자연스러운 진행 (살짝 점프) |

> [!tip] 게임은 TCP+UDP 혼용
> | 용도 | 프로토콜 | 이유 |
> | --- | --- | --- |
> | 위치 정보·실시간 좌표 | **UDP** | 빠른 처리, 누락 허용 |
> | 아이템 구매·결제·인벤토리 | **TCP** | 한 건도 누락되면 안 됨 |

### UDP의 부수 효과 — 차량이 "뒤로 갔다 다시 오는" 현상

- 다른 플레이어 시점에서 위치 정보 일부 유실 시
- 화면에 차량이 **달달거리며 보정**되는 현상이 발생
- 이는 UDP 특성으로 인한 자연스러운 결과

## 7. UDP로 TCP를 흉내내기

> [!note] 선택지
> "재전송·버퍼링이 필요하긴 한데, TCP는 너무 무겁다"
> → **UDP를 베이스로 애플리케이션 레벨에서 직접 구현**하는 방식 선택 가능

- **고성능 RPC (Remote Procedure Call)** 등에서 활용
- **QUIC** (HTTP/3 기반) 도 이런 철학의 사례
- 개발자가 책임지고 신뢰성을 구현해야 함

## 8. 어떤 개발자가 TCP/UDP를 깊이 알아야 하나?

| 분야 | 깊이 필요한가? |
| --- | --- |
| 일반 웹 개발 (HTTP 위주) | 개념 수준이면 충분 (Vibe Coding 가능) |
| **장애 대응 / 트러블슈팅** | **반드시 필요** |
| **고성능 시스템·RPC 개발** | 반드시 필요 |
| **게임 서버 개발** | 반드시 필요 (TCP+UDP 혼용 설계) |
| **네트워크 보안 (방화벽 등)** | 반드시 필요 (Stateful Inspection) |

> [!important] 왜 알아야 하는가?
> HTTP는 결국 **TCP/IP(또는 UDP/IP)** 위에서 동작한다.
> L4·L3 계층의 특징이 그대로 **HTTP 통신의 전제**가 되기 때문.

## 9. AWS 환경에서의 TCP/UDP

| 항목 | 온프레미스 | AWS |
| --- | --- | --- |
| TCP/UDP 처리 | OS 커널 | OS 커널 (동일) |
| 포트 개방 | 방화벽·iptables | **Security Group** + **NACL** |
| L4 로드밸런서 | F5 BIG-IP 등 | **NLB** (Network Load Balancer) |
| L7 로드밸런서 | HAProxy, Nginx | **ALB** (Application Load Balancer) |
| Stateful Inspection | 별도 방화벽 장비 | Security Group이 기본 제공 |

> [!tip] AWS Security Group
> Security Group은 기본적으로 **Stateful**이다.
> Outbound로 나간 연결의 응답은 자동으로 Inbound 허용 → 일반 방화벽보다 직관적.

## 한 줄 요약

> **TCP**는 연결 지향(Connection Oriented) 프로토콜로 순서 보장·재전송·수신자 배려 등 전송 제어를 수행하지만 그만큼 무겁고 상태(State) 관리가 필요하며, **UDP**는 이런 배려가 전혀 없는 단순한 프로토콜로 멀티미디어·게임 위치정보처럼 **속도와 실시간성이 신뢰성보다 중요한 상황**에 유리하다. HTTP는 이 둘 위에서 동작하므로 모든 개발자에게 기본 개념은 필수다.
