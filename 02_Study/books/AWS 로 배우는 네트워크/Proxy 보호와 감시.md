## 개요

[[Proxy - 우회]] 에서 다룬 **우회용 Proxy**에 이어, 같은 Proxy 구조를 **기업 보안**에 활용하는 두 가지 패턴 — **보호(Inbound)** 와 **감시(Outbound)** 를 다룬다.
- **Proxy 구조 = 데이터를 통과시키며 검사 가능** → 우회뿐 아니라 **방어**에도 동일하게 쓰임
- **바이러스월** = 외부 → 내부 악성코드 차단 (Inbound 검사)
- **DLP** (Data Loss Prevention) = 내부 → 외부 기밀 유출 차단 (Outbound 검사)
- 부가 효과 = **사용자 인터넷 활동 가시화** → 근태관리에 연동 가능
- 핵심 통찰: 같은 구조가 **누가 / 무엇을 / 왜** 보느냐에 따라 전혀 다른 시스템이 된다.

---

## 1. Proxy의 3가지 사용 목적

> [!important] Proxy 구조 = 형태. 목적은 별개.
> Proxy는 "데이터가 통과해서 지나간다"는 **구조**일 뿐, 그 구조 위에서 **어떤 목적을 얹느냐**는 자유.

| 목적 | 방향 | 대표 명칭 |
|------|------|-----------|
| **우회 (Bypass)** | 외부 ↔ 외부 | Forward Proxy ([[Proxy - 우회]]) |
| **보호 (Protect)** | 외부 → 내부 검사 | **바이러스월** / 사내 검사 Proxy |
| **감시 (Monitor)** | 내부 → 외부 검사 | **DLP** (Data Loss Prevention) |

> [!tip] 구조 vs 목적
> - Packet 단위 → Inline / Out-of-Path ([[Inline 구조와 라우터]] · [[Out of Path 구조와 DPI]])
> - Stream 단위 → **Proxy** — 우회/보호/감시 모두 동일 구조에서 파생

## 2. 기업의 강제 Proxy 정책

> [!important] 핵심 정책
> 사내 PC의 **직접 외부 접속을 전부 차단**하고, **회사가 지정한 Proxy만 허용**한다.
> 즉, "인터넷을 못 쓰게" 하는 게 아니라 "**반드시 Proxy를 거치게**" 만드는 것.

### 정책 구성

```
[사내 PC1]                ┌─ 외부 인터넷 ─┐
[사내 PC2] ──Outbound─▶ [IPS/Firewall] ─X─ [Web Server]
[사내 PC3]                   ❌ 모든 직접 접속 차단
   │
   │ (Proxy 설정 필수)
   ▼
[사내 Proxy 192.168.0.200] ─────▶ [IPS/Firewall] ─✅─▶ [Web Server]
                                  (Proxy의 외부 접속만 허용)
```

### 정책 효과

| 항목 | 내용 |
|------|------|
| **PC 직접 Outbound** | ❌ 전부 Drop (Inline 장비) |
| **Proxy 경유 Outbound** | ✅ 허용 |
| **사용자 부담** | 브라우저/OS에 Proxy 설정 1회 |
| **회사가 얻는 것** | 모든 외부 트래픽이 **단일 지점**에 모임 → 검사/통제 용이 |

> [!note] 단일 통제점(Single Control Point) 확보
> 분산된 PC를 직접 통제하기보다, **모든 트래픽이 모이는 Proxy 한 곳**을 통제하는 게 훨씬 효율적.

관련: [[Inline 구조와 라우터]] · [[Proxy - 우회]]

## 3. 보호 ① — 바이러스월 (Inbound 검사)

> [!important] 시나리오
> 임직원이 업무 중 외부 사이트에 접속 → 그 사이트가 악성코드 감염 상태
> → 다운로드되는 파일에 바이러스가 섞여 들어옴
> → **Proxy가 Stream을 검사**해서 악성 실행파일을 미리 차단

### 동작 흐름

```
[감염된 외부 사이트]
        │
        │ ① 응답 데이터(파일 포함) 전송
        ▼
[사내 Proxy] ─── ② Stream 검사
        │            "어, 실행 파일이네?"
        │            "악성코드 검사 시작..."
        │
        ├─ 정상     → ✅ Bypass → [사내 PC]
        └─ 악성코드 → ❌ Drop  → 사용자에게 경고
```

### Proxy → 바이러스월(Virus Wall)

| 항목 | 내용 |
|------|------|
| **방향** | **Inbound** (외부 → 내부) |
| **검사 대상** | 실행 파일, 문서 매크로 등 응답 콘텐츠 |
| **차단 동작** | 악성 콘텐츠 발견 시 Drop + 사용자 알림 |
| **명칭** | Anti-Virus Proxy / Virus Wall |

> [!tip] Stream 단위라서 가능한 일
> "이 파일이 .exe인가?" "이 매크로가 악성인가?" — 이런 판단은 **조립된 Stream**이 있어야 가능.
> Packet 단편으로는 파일의 전체 내용을 알 수 없다. → **Proxy 구조의 강점**.

## 4. 감시 ② — DLP (Outbound 검사)

> [!important] DLP = Data Loss Prevention (정보 유출 방지 체계)
> **내부의 기밀이 외부로 새어 나가는 것을 막는** Proxy.
> 동일 구조, 방향만 반대.

### 동작 흐름

```
[사내 PC]
   │
   │ ① 업로드 시도 (예: docx 파일)
   ▼
[사내 Proxy] ─── ② Stream 검사
   │              "이 파일 내용에 영업기밀 키워드 있나?"
   │
   ├─ 일반 파일 → ✅ Bypass → [외부 사이트]
   └─ 기밀 포함 → ❌ Drop  → 관리자/사용자 알림
                              (감사 로그 기록)
```

### DLP의 특징

| 항목 | 내용 |
|------|------|
| **방향** | **Outbound** (내부 → 외부) |
| **검사 대상** | 업로드 파일, 폼 데이터, 이메일 본문 등 |
| **차단 기준** | 영업기밀 키워드, 특정 패턴, 분류 라벨 |
| **구현 방법** | Proxy 방식 / **PC 에이전트 방식** 등 다양 |

> [!note] DLP는 Proxy 외 다른 형태도 있다
> 꼭 네트워크 Proxy로만 구현하는 것은 아니다.
> 각 PC에 **에이전트 소프트웨어**를 깔아 엔드포인트에서 검사하는 방식도 흔함.
> "어떤 단위 / 어디서 / 무엇을 보고 판단할지" 에 따라 형태가 결정된다.

> [!tip] 한국 반도체 기술 유출 사건들
> 뉴스에 자주 나오는 "반도체 기술 유출" 사건의 대응 체계가 바로 DLP. 기업 기밀 보호의 핵심 도구.

## 5. 부가 효과 — 사용자 활동 가시화

> [!caution] Proxy의 부산물 — 모든 활동이 로그로 남는다
> 보안 검사를 하다 보면 자연스럽게 **누가 / 언제 / 어디에 접속했는지** 가 기록된다.

### 수집 가능한 정보

| 데이터 | 활용 |
|--------|------|
| 접속 URL 이력 | 업무용/사적 사용 구분 |
| 접속 시간 / 시간대 | 업무시간 vs 비업무시간 |
| 트래픽 양 / 빈도 | 이상 사용 패턴 탐지 |
| HTTPS 통신 내역 | (Proxy가 SSL 종단할 경우) 내용까지 |

### 인사관리 시스템과 연동되면?

```
Proxy 로그 ──▶ "업무시간 중 주식 거래 사이트 1시간 접속"
                          │
                          ▼
                   인사관리(HRM) 연동
                          │
                          ▼
                   → 근태관리 체계 작동
```

> [!important] 같은 구조, 전혀 다른 시스템
> Proxy 한 대로 **방어 시스템 + 감시 시스템**이 동시에 만들어진다.
> "기술은 중립이지만, 어떻게 사용하느냐는 정책의 문제"

## 6. 사용자 vs 보안 관리자 — 관점 차이

> [!note] 도감청인가, 정당한 보안 조치인가
> 사용자: "회사가 내 통신을 들여다보는 것 아니냐?"
> 보안 관리자: "보안 목표 달성을 위한 **불가피한 조치**다."

### 양쪽의 정당한 논리

| 관점 | 주장 |
|------|------|
| **사용자 관점** | 사생활 침해 우려, 통신비밀 보호 (정보통신비밀보호법) |
| **보안 관리자 관점** | 외부 위협 차단, 내부 기밀 보호, 단일 통제점 확보 |
| **기업 관점** | 자산 보호 + 컴플라이언스 + 사고 책임 회피 |

> [!tip] 균형 잡힌 시선
> 어느 한쪽이 절대적으로 옳지 않다.
> 회사 네트워크를 쓰는 한, **HTTPS 기반 통신 내역은 회사가 알 수 있다**는 점을 인지하고 사용하는 것이 현실적.

## 핵심 요약

| 기억할 것 | 내용 |
|-----------|------|
| **Proxy 3가지 목적** | 우회 / 보호 / 감시 — 구조는 같고 방향과 정책만 다름 |
| **기업 정책 핵심** | PC 직접 Outbound 차단 + **회사 Proxy만 허용** |
| **단일 통제점** | 모든 트래픽이 Proxy 한 곳에 모임 → 검사/통제 효율 ↑ |
| **바이러스월** | **Inbound** Stream 검사 → 악성 파일 Drop |
| **DLP** | **Outbound** Stream 검사 → 내부 기밀 유출 차단 |
| **Stream의 강점** | 파일 단위, 키워드 단위 판단 가능 (Packet으로는 불가) |
| **DLP의 다양성** | 네트워크 Proxy 외에 **PC 에이전트** 방식도 흔함 |
| **부가 효과** | 사용자 인터넷 사용 기록 전부 가시화 → 근태관리 연동 가능 |
| **관점 차이** | 사용자(도감청 우려) vs 관리자(보안 필수) — 균형 시선 필요 |
| **현실 인식** | 회사 네트워크에서는 **HTTPS 통신 내역도 회사가 알 수 있다** |
