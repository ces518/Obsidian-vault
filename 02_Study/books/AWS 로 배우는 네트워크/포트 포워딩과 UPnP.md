# 포트 포워딩과 UPnP

## 개요

[[공유기 작동 원리]] / [[Symmetric NAT]] 에서 본 NAT의 보안 효과(외부 차단)를 **의도적으로 뚫어야** 하는 상황 — **포트 포워딩(Port Forwarding)** 과 그 자동화 버전 **UPnP**를 다룬다.
- NAT는 Inbound를 기본 차단 → 홈서버를 외부에 공개하려면 **수동으로 NAT Table 규칙 추가** = 포트 포워딩
- Private IP는 외부에서 접속 불가 → **공유기의 Public IP** 를 알려줘야 함
- 포트 포워딩이 필요한 경우: 서버 소켓 `listen()`, **P2P 통신**(UDP)
- **UPnP** = 내부 앱이 공유기에 신호를 보내 포트 포워딩을 **자동 등록**
- UPnP는 편의성 ↑ 이지만 **보안 구멍** → 보안성과 편의성은 반비례

---

## 1. 문제 — 홈서버를 친구에게 보여주고 싶다

> [!note] 시나리오
> 철수가 집 공유기 아래 PC에 Vibe Coding으로 홈페이지를 띄우고, 친구 길동에게 자랑하고 싶다.

```
[철수 홈서버 192.168.0.10:3000]
        │
   [공유기 NAT]  Public IP: 3.3.3.3
        │
   ─── Internet ───
        │
   [길동이 PC] ── "철수야 IP 뭐야?"
```

### Private IP를 알려주면?

| 철수가 알려준 것 | 결과 |
|------------------|------|
| `192.168.0.10` (Private IP) | ❌ 외부에서 통용 안 됨 — 길동 접속 불가 |
| `3.3.3.3` (공유기 Public IP) | ✅ 인터넷에서 도달 가능 |

> [!tip] 내 Public IP 확인 방법
> - `what is my ip` 류 사이트 접속
> - 공유기 관리자 화면에서 할당된 Public IP 확인

---

## 2. Public IP를 알려줘도 안 되는 이유

> [!important] NAT Table에 Inbound 규칙이 없다
> 길동의 패킷이 공유기까지는 도달하지만, "이걸 어느 내부 PC로 보낼지" 매핑이 없어 Drop.

```
[길동 15.15.15.15] ──▶ Dst: 3.3.3.3:3000
                            │
                            ▼
                      [공유기 NAT Table 검색]
                      Remote(길동) + Local(3000) 매핑?
                            │
                            ▼
                      ❌ Not Found
                            │
                            ▼
                      🗑️ Drop (외부 임의 접속 차단)
```

> [!note] NAT Table 규칙은 원래 Outbound로 자동 생성
> [[Symmetric NAT|NAT Table]] 엔트리는 **내부에서 나갈 때(Outbound)** 자동 추가된다.
> 외부에서 먼저 들어오는 트래픽은 매핑이 없으므로 차단되는 것이 정상.

---

## 3. 포트 포워딩 — Inbound 규칙 수동 등록

> [!important] 포트 포워딩 = NAT Table에 수작업 규칙 삽입
> Outbound 없이도 **특정 외부 포트로 들어온 트래픽을 특정 내부 호스트:포트로** 무조건 전달하도록 규칙을 미리 박아둔다.

### 규칙 구성

```
[규칙] 외부 포트 80 → 내부 192.168.0.10:80
       Remote(원격지) = 0.0.0.0 (누구든 상관없음)
```

| 항목 | 값 | 의미 |
|------|-----|------|
| **External Port** | 80 | 외부에서 접속할 포트 |
| **Internal Host** | 192.168.0.10 | 실제 서버 사설 IP |
| **Internal Port** | 80 | 서버가 Listen 중인 포트 |
| **Remote** | `0.0.0.0` | **출발지 무관** — 누가 오든 허용 |

### 동작

```
[누구든] ──▶ 3.3.3.3:80 ──▶ [공유기]
                                │ 포트 포워딩 규칙 참조
                                ▼
                         192.168.0.10:80 (홈서버)
```

> [!tip] 포트 포워딩의 본질
> NAT Table 의 Inbound 항목을 **영구적으로** 하나 만들어두는 것.
> Inbound 패킷 처리 시 NAT Table + 포트 포워딩 규칙을 함께 참조 → 외부 접근 허용.

---

## 4. 포트 포워딩이 필요한 경우

> [!important] 내부에서 외부 접속을 "받아야" 할 때
> 핵심은 **서버처럼 동작**(수동적으로 연결을 기다림)하는 모든 경우.

| 경우 | 설명 |
|------|------|
| **서버 소켓 `listen()`** | 웹서버/게임서버 등 외부 연결 대기 → **반드시** 포트 포워딩 |
| **P2P 통신 (UDP 등)** | 클라-서버 개념이 아닌 Peer 간 직접 통신 — 특정 포트가 열려 있어야 함 |

> [!note] P2P가 까다로운 이유
> [[Symmetric NAT]] 처럼 세션 단위로 포트가 매번 바뀌면, Peer끼리 서로의 포트를 예측·고정하기 어렵다.
> 그래서 P2P 앱은 그때그때 NAT 규칙을 만들어 넣어야 하는데, 이게 일반 사용자에겐 매우 번거롭다.

관련: [[Symmetric NAT]] · [[User Kernel 모드 와 Socket 의 본질]]

## 5. UPnP — 포트 포워딩 자동화

> [!important] UPnP = Universal Plug and Play
> "엄마한테 NAT를 설명하고 포트 포워딩을 시킬 수 있나?" → 불가능.
> 그래서 **내부 앱이 공유기에 신호를 보내 포트 포워딩 규칙을 자동 등록**하게 만든 기술.

### PnP의 뿌리 — Plug and Play

```
USB 장치 꽂음 → PC가 자동으로 드라이버 설치 + 사용 준비
   = Plug and Play
UPnP = 이걸 네트워크(인터넷 너머)로 확장하려는 발상
```

### 원래 의도 (역사)

> [!note] 홈쇼핑 프린터 쿠폰 시나리오
> "인터넷 너머의 서버(A)가 시청자(B)의 프린터를 원격 제어해 쿠폰을 인쇄해준다"
> → 인터넷 너머의 하드웨어를 USB 꽂듯 인지·제어하려던 구상.
> 보안 문제 등으로 원래 의도대로는 잘 안 쓰이게 됨.

### 실제로 살아남은 용도 — 자동 포트 포워딩

```
[내부 앱 실행] ──"이 포트 좀 열어주세요"──▶ [공유기]
                                              │
                                              ▼
                                    포트 포워딩 규칙 자동 추가
                                              │
                                              ▼
                                    외부에서 접속 가능해짐
```

| 항목 | 내용 |
|------|------|
| **트리거** | 내부 앱이 UPnP 신호 전송 |
| **공유기 동작** | 포트 포워딩 규칙 자동 생성 |
| **대표 사례** | **토렌트(P2P)** — UPnP 지원으로 수동 설정 없이 Peer 접속 |
| **공유기 설정** | IPTime 등에서 "UPnP" 기본 활성화된 경우 많음 |

## 6. 보안 vs 편의성 — UPnP의 양면

> [!caution] UPnP는 NAT의 보안 효과를 스스로 무너뜨릴 수 있다
> 내부 앱(또는 악성코드)이 임의로 포트를 열어버리면, NAT의 "외부 차단" 방어선이 자동으로 뚫린다.

| 관점 | 선택 |
|------|------|
| **높은 보안성 원함** | UPnP **비활성화** (수동 포트 포워딩만 허용) |
| **편의성 원함** | UPnP **활성화** (토렌트 등 자동 동작) |

> [!important] 동전의 양면
> **보안성과 편의성은 늘 반비례.**
> 공유기는 본질적으로 보안 장비가 아니다 — NAT의 보안 효과는 부산물일 뿐.
> 극단적 보안이 필요하면 UPnP를 끄는 것이 정석.

## 7. 다음 예고 — NAT를 거꾸로 = 부하분산

> [!note] Reverse NAT
> [[Reverse Proxy 와 WAF|Reverse Proxy]] 처럼, NAT도 **거꾸로 적용**하면 **부하분산 장치**가 된다.
> NAT는 L3~L4 → 여기서 분산하는 부하도 **L3/L4 수준의 네트워크 부하**.
> 이것이 AWS **NLB (Network Load Balancer)** 의 원리.

```
Forward NAT  : 내부 다수 → 하나의 Public IP로 (출구)
Reverse NAT  : 하나의 Public IP → 내부 다수 서버로 분산 (입구)
                                    = L3/L4 Load Balancing
```
