## 개요

[[공유기 작동 원리]] 에서 분류한 NAT 방식 중 **Symmetric NAT** — **TCP 세션 단위**로 주소+포트를 변환하는 가장 정교한 방식.
- **NAPT(Network Address Port Translation)** 가 진정한 의미로 구현되는 형태
- 핵심 자료구조 = **NAT Table** (세션 단위 엔트리)
- 클라이언트와 서버는 **서로 다른 세션 정보**를 보고도 "연결됐다"고 믿는다 → [[연결이라는 착각과 AWS ALB|연결의 본질]] 재확인
- **NAT Table에 매핑이 없는 Inbound = 자동 Drop** → 외부 직접 침입 차단
- AWS의 **보안 그룹(Security Group) 규칙**이 본질적으로 이와 같은 구조

## 1. Symmetric NAT의 본질

> [!important] 단위가 다르다
> - **Cone NAT** = **호스트 단위**로 외부 포트 지정 (PC당 외부 포트 고정)
> - **Symmetric NAT** = **TCP 세션 단위**로 외부 포트 지정 (세션마다 포트 새로 할당)

| 항목 | Symmetric NAT |
|------|---------------|
| **변환 단위** | TCP 세션 (Local IP:Port + Remote IP:Port 조합) |
| **포트 변환** | ✅ 항상 발생 — 진정한 NAPT |
| **정교함** | ★★★ |
| **보안성** | ★★★ (외부에서 External Port 예측 어려움) |
| **P2P 친화성** | ❌ (홀펀칭 매우 까다로움) |

## 2. 동작 시나리오 — 출발지/포트 변환

> [!note] 가정 시나리오
> - 공유기 Public IP = `3.3.3.3`
> - 내부 PC = `192.168.0.10`, 브라우저가 사용하는 임의 포트 = `3000`
> - 목적지 서버 = `15.15.15.15:80` (웹 서버)

### Step 1 — 패킷 생성 (PC)

```
[브라우저] (Active connect)
    ↓
출발지 : 192.168.0.10 : 3000   ← OS가 부여한 난수 포트
목적지 : 15.15.15.15  :   80   ← 서버의 Listen 포트
```

> [!tip] 클라이언트 포트는 난수
> 서버 소켓은 포트를 **특정**해야 하지만, 클라이언트는 OS가 임의 포트(난수)를 부여한다.

### Step 2 — NAT Gateway에서 변환

```
변환 전 (PC → NAT)              변환 후 (NAT → 서버)
─────────────────────           ─────────────────────
Src : 192.168.0.10 : 3000       Src : 3.3.3.3 : 23000   ← IP+Port 모두 변경!
Dst : 15.15.15.15  :   80       Dst : 15.15.15.15 : 80
```

### Step 3 — 서버가 보는 것

| 실제 | 서버의 인식 |
|------|-------------|
| `192.168.0.10:3000` 이 접속 | `3.3.3.3:23000` 이 접속한 것 |
| 클라가 3000번을 연 것 | 클라가 **23000번을 연** 것으로 착각 |

> [!caution] 23000번은 어디에도 안 열려 있다
> - 클라이언트 PC: 실제로는 **3000번**만 열려 있음
> - NAT Gateway: 23000번을 **열지 않음** (단지 헤더만 조작해서 토스)
> - **존재하지 않는 가상의 포트** 가 서버에는 진짜처럼 보인다.

## 3. 연결의 착각 — 양쪽이 다른 세션을 본다

> [!important] 클라이언트 ≠ 서버의 세션 정보
> 같은 "연결" 인데 양쪽이 보는 정보가 **다르다**.

| 관점 | 인식하는 TCP 세션 |
|------|-------------------|
| **클라이언트** | `192.168.0.10:3000` ↔ `15.15.15.15:80` |
| **서버** | `3.3.3.3:23000` ↔ `15.15.15.15:80` |

```
[Client]                          [Server]
  ↓                                  ↓
"내 세션:                          "내 세션:
 192.168.0.10:3000                  3.3.3.3:23000
   ↔ 15.15.15.15:80"                  ↔ 15.15.15.15:80"
                                     ↑
                                  실재하지 않는 포트
                                  (NAT의 위장)
```

> [!tip] 연결의 본질
> "연결"은 **실체가 아니라 프로토콜 규칙에 따라 양쪽이 합의했다고 믿는 논리적 상태**.
> 양쪽이 서로 다른 정보를 보고 있어도, 각자의 규칙이 충족되면 "연결됐다"고 판정한다.
> → [[연결이라는 착각과 AWS ALB]] 의 핵심 통찰이 NAT에서도 동일하게 작동.

관련: [[TCP 세션과 상태 그리고 게임서버]] · [[연결이라는 착각과 AWS ALB]]

## 4. NAT Table — 세션 단위 매핑 데이터베이스

> [!important] NAT의 두뇌
> Outbound 발생 시 엔트리 **추가**, Inbound 응답 시 엔트리 **검색**.

### 엔트리 구조 (예시)

| Local IP | Local Port | External Port | Remote IP | Remote Port | Protocol |
|----------|-----------|---------------|-----------|-------------|----------|
| 192.168.0.10 | 3000 | **23000** | 15.15.15.15 | 80 | TCP |
| 192.168.0.10 | 3001 | **23001** | 15.15.15.15 | 80 | TCP |
| 192.168.0.12 | 3000 | **23002** | 16.16.16.16 | 443 | TCP |
| 192.168.0.11 | 3000 | **23003** | 15.15.15.15 | 80 | TCP |

> [!note] External Port는 NAT Gateway가 unique하게 관리
> 동일한 External Port가 중복되면 Inbound 응답을 누구에게 줄지 결정 불가 → NAT Gateway가 **충돌 없이 유일성 보장**.

### Outbound 시 — 엔트리 추가

```
[PC 192.168.0.10:3000] ──▶ [NAT] ──▶ [15.15.15.15:80]
                              │
                              ├─ NAT Table 에 새 엔트리 추가
                              │  (Local 3000 ↔ External 23000)
                              │
                              └─ 헤더 변환 후 외부 송신
```

### Inbound 응답 — 엔트리 검색

```
[15.15.15.15:80] ──▶ Src: 15.15.15.15:80, Dst: 3.3.3.3:23000
                          │
                          ▼
                  [NAT Table 검색]
                  Remote(15.15.15.15:80) + External(23000) 매칭
                          │
                          ▼
                  매칭 엔트리 발견
                  → Dst를 192.168.0.10:3000 으로 복원
                          │
                          ▼
                  [PC 192.168.0.10:3000]
```

## 5. NAT의 보안 효과 — 매핑 없는 Inbound = Drop

> [!important] 외부가 임의로 들어올 수 없다
> NAT Table 에 **선행 Outbound 매핑**이 없는 외부 패킷은 변환 대상이 없으므로 자동 Drop.

### Drop 시나리오

```
[외부 공격자 9.9.9.9:80] ──▶ [NAT] Dst: 3.3.3.3:30000
                                  │
                                  ▼
                            NAT Table 검색
                            (Remote 9.9.9.9:80 + External 30000)
                                  │
                                  ▼
                            ❌ 매칭 엔트리 없음 (Not Found)
                                  │
                                  ▼
                            🗑️ 패킷 Drop
```

| 상황 | 결과 |
|------|------|
| 내부에서 먼저 나간 적 있는 세션의 응답 | ✅ NAT Table 매칭 → 내부로 전달 |
| 외부에서 임의로 보낸 패킷 | ❌ 매칭 없음 → Drop |

> [!tip] 사설 네트워크 = 자연스러운 방화벽
> NAT를 쓴다는 것 자체가 "외부에서 임의 접근 불가"를 의미.
> 별도 방화벽 없이도 **패킷 필터링 방화벽 유사 효과**.

## 6. AWS 보안 그룹 — NAT Table의 일반화

> [!important] NAT Table ≈ Security Group Rule
> NAT 테이블 엔트리와 AWS 보안 그룹의 Inbound/Outbound 규칙은 **거의 같은 구조**.

### 구조 비교

| NAT Table 컬럼 | AWS Security Group 규칙 |
|----------------|------------------------|
| Local IP : Port | 보호 대상 리소스 자체 |
| External Port | Port (Listen 포트) |
| Remote IP : Port | **Source/Destination** (CIDR 표기) |
| Protocol | Protocol (TCP/UDP/ICMP) |

### NAT vs 보안 그룹의 차이

| 항목 | NAT Table | 보안 그룹 규칙 |
|------|-----------|----------------|
| **단위** | 단일 IP : Port | **CIDR 표기** (예: `10.0.0.0/24`, `0.0.0.0/0`) |
| **생성 방식** | Outbound로 **자동** 추가 | 관리자가 **명시적** 정의 |
| **목적** | 주소 변환 | 접근 통제 |
| **유효기간** | 세션 종료 후 만료 | 명시적 삭제까지 영구 |

> [!tip] 학습 효과
> NAT Table 의 의미를 정확히 이해하면 → AWS Security Group Rule 설정이 자연스럽게 이해된다.
> "어디서 어디로 어떤 프로토콜이 어떤 포트로" 라는 4-tuple 사고가 동일.

## 7. 세션이 늘어나면 — Table도 늘어난다

> [!note] Symmetric의 특징
> TCP 세션마다 새 엔트리 → 한 PC가 여러 탭을 열면 그만큼 엔트리 증가.

### 예시

| 행위 | NAT Table 변화 |
|------|----------------|
| 철수가 네이버에 접속 (브라우저 탭 1) | +1 엔트리 |
| 철수가 네이버에 또 접속 (탭 2) | **+1 엔트리** (별도 세션) |
| 영희가 네이버에 접속 | +1 엔트리 |
| 길동이 구글에 접속 | +1 엔트리 |

> [!caution] 대규모 NAT의 부담
> 호스트가 많고 세션이 많으면 NAT Table 이 빠르게 커진다.
> Symmetric은 정교한 만큼 **리소스 부담**도 큰 편 (대규모 환경에서는 분산/만료 정책 중요).

## 핵심 요약

| 기억할 것 | 내용 |
|-----------|------|
| **Symmetric NAT** | **TCP 세션 단위**로 NAT 적용 — 진정한 NAPT |
| **변환 대상** | IP + **Port 둘 다** 변환 |
| **External Port** | NAT Gateway가 임의로 부여 + **unique 보장** |
| **NAT Table** | Outbound 시 추가, Inbound 응답 시 검색 |
| **테이블 키** | Local IP:Port + External Port + Remote IP:Port + Protocol |
| **연결의 착각** | 클라이언트와 서버가 **서로 다른 세션 정보**를 보면서도 연결됐다고 판정 |
| **보안 효과** | NAT Table 매핑 없는 Inbound = **자동 Drop** (방화벽 효과) |
| **포트는 안 열림** | External Port 는 실제로 열린 게 아니라 헤더만 조작한 **가상 포트** |
| **보안 그룹과 유사** | NAT Table ≈ AWS Security Group Rule (CIDR 표기만 추가) |
| **Cone과의 차이** | Cone = 호스트 단위 / Symmetric = **세션 단위** (더 정교) |
| **P2P 약점** | 세션마다 포트가 달라 외부에서 예측 불가 → 홀펀칭 어려움 |
| **연결의 본질** | 양쪽이 합의한 **논리적 상태**일 뿐 — 실체가 다를 수 있다 |
