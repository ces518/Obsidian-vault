# 사설망과 가상 사설망(VPN)

## 개요

네트워크 보안 인프라의 하나인 **VPN(Virtual Private Network)** 을, 그 토대인 **사설망(Private Network)** 개념부터 풀어가는 강의 정리.
- 보안 인프라 복습: **패킷 필터링 방화벽**(Packet, Inline) vs **WAF**(소켓 스트림, L7, Reverse Proxy)
- **사설망의 본질 = LAN** — 물리적으로 연결된, 그 자체로 보안이 적용된 영역
- 진짜 사설망: **전용회선 임차**(KT 등) → 안전하지만 **비싸고 느림**
- **VPN** = 퍼블릭 인터넷 위에서 **LAN처럼 안전하게** 통신하는 논리적 사설망
- **IPsec VPN** = Gateway-to-Gateway로 **두 망을 하나의 LAN처럼 통합**(망 대 망), 재택근무 접속에도 사용
- 구현은 **패킷 조작** 방식 → 이어서 **MTU/단편화 문제**로 연결 (다음 주제 예고)

## 한 줄 요약

> 사설망의 본질은 LAN(물리적으로 보호된 영역)이고, 서울-부산을 진짜 전용회선으로 묶으면 안전하지만 비싸고 느리다. 그래서 **퍼블릭 인터넷 위에 LAN에 준하는 보안성을 논리적으로 부여**한 것이 VPN이며, 망 대 망 통합에 쓰이는 대표 방식이 **IPsec VPN**(Gateway-to-Gateway)이다. 구현은 패킷 조작 방식이라 **MTU/단편화 이슈**가 따라온다.

---

## 1. 보안 인프라 복습 — 패킷 필터링 방화벽 vs WAF

> [!note] 이미 다룬 두 가지 보안 인프라
> 네트워크 보안 인프라 중 앞서 언급한 두 가지를 복습.

| 구분 | **패킷 필터링 방화벽** | **웹 애플리케이션 방화벽(WAF)** |
|------|----------------------|-------------------------------|
| **다루는 데이터** | **Packet** (조각) | 소켓 **스트림** 데이터 |
| **계층/위치** | Inline 장비 | **L7** (HTTP 트래픽) |
| **작동 방식** | 패킷 단위 필터링 | **Reverse Proxy** 방식 |
| **한계** | 패킷은 조각 → 정보량 제한, 조립해도 한계 | 패킷 자체는 보기 어려움 |

관련: [[Reverse Proxy 와 WAF]]

## 2. VPN — 추가로 알아야 할 보안 인프라

> [!important] VPN, 그 중에서도 IPsec VPN
> 꼭 알아야 할 보안 인프라 중 하나가 **VPN**. 구현 방식은 여러 가지지만 핵심은 **IPsec VPN**.

- **망 대 망(site-to-site) 통합** VPN으로 알려짐
- **재택근무**: 내 PC에 소프트웨어를 설치 → 회사 네트워크에 VPN으로 접속
- **AWS 연계**: EC2는 사설망(Private Network) 안에 있음. 퍼블릭 IP를 주는 대신, **VPN으로 연결**해 EC2의 외부 접근성을 현저히 낮추는 방법도 있음

## 3. 사설망(Private Network)이란? — 본질은 LAN

> [!important] 사설망 = LAN
> VPN의 V는 Virtual. 가상 "사설망"인데, 이 사설망은 NAT의 사설 IP 대역과는 다른 개념이다.
> 본질을 쉽게 말하면 그냥 **LAN** — 물리적 회선으로 연결된 환경.

> [!tip] 비유 — 집에 들어온 상태
> 현관을 지나 집(Secured Area)에 들어오면 안전하다고 여기고 편한 복장을 한다.
> **LAN 환경 자체가 이미 "보안이 적용된 영역"** 이라는 감각.

### 회사가 커지면

```
소규모: L2 스위치 1대 + PC 몇 대 → 게이트웨이로 인터넷만 잘 되면 OK
        │
        ▼ (성장)
대규모: PC n대 → 디스트리뷰션 스위치 → 코어 스위치 → 건물 단위
        │
        ▼ (확장)
서울 본사 ── 인터넷 ── 부산 지사   ← 지리적으로 분리된 망
```

관련: [[L2 스위치]] · [[공유기 작동 원리]]

## 4. 전용회선 임차 — "진짜" 사설망의 비용

> [!important] 문제 상황
> 서울 본사의 중요 DB에 부산 지사 PC가 접속해야 하는데, **인터넷은 기본적으로 퍼블릭**.
> 평문 노출은 그 자체로 보안 사고 → 암호화 + 접근 통제 필요.

> [!caution] 극단적 해법 — 물리적으로 LAN선을 깐다
> "서울 본사 ↔ 부산 지사를 프라이빗으로 묶자" = 서울~부산 LAN선 포설.
> 물리적으로는 가장 안전하지만 **현실성 없음**.

### 전용회선 임차 (KT 등)

- KT처럼 전국에 케이블을 매설한 회사가 회선 일부를 떼어 **A사 전용으로 임대**
- 물리적 접근 통제를 통신사가 보장 → **보안성 매우 높음**

> [!tip] 비유 — 영화관 좌석 통째 구매
> 옆자리에 아무도 없게 하려고 내 주변 좌석을 **몽땅 다 사서** 둘이서만 본다.
> 전용회선도 이처럼 **많은 비용**을 지불해야 한다.

| 전용회선 사설망 | 평가 |
|----------------|------|
| 보안성 | 매우 높음 (물리적 통제) |
| 비용 | **매우 비쌈** |
| 속도 | **저속** |

## 5. VPN — 인터넷 위의 논리적 사설망

> [!important] 인터넷은 빠른데?
> "빠른 인터넷을 쓰면서 사설망처럼 못 쓰나?" → **LAN에 준하는 보안성을 논리적으로만 제공**하면 된다는 발상.

- 퍼블릭 인터넷을 쓰면서도 회사 간 통신을 **마치 로컬 LAN처럼 안전하게**
- 로컬 LAN에 준하는 방화벽/접근 정책을 그대로 적용해도 문제없이 동작
- 그래서 나온 것이 **VPN** (특히 **IPsec VPN**)

---

## 6. IPsec VPN — Gateway-to-Gateway 망 통합

> [!important] 두 망을 하나의 LAN처럼
> 서울 본사망과 부산 지사망을 **Gateway(라우터)-to-Gateway** 수준에서 묶어 하나의 로컬 LAN인 것처럼 통합하는 것이 IPsec VPN.

```
[서울 본사망]                         [부산 지사망]
     │                                     │
 [Gateway/라우터] ===== IPsec VPN ===== [Gateway/라우터]
     │         (퍼블릭 인터넷 위 논리적 사설망)      │
   내부 PC·DB                              내부 PC
```

- 망을 통합(site-to-site)할 때 쓰는 대표 방식
- VPN을 논하기 전에 **"프라이빗 네트워크가 무엇인지"** 를 먼저 이해해야 함

## 7. 구현 — 패킷 조작과 MTU 문제 (예고)

> [!note] 공유기 NAT와 같은 결 — 패킷 조작
> VPN 구현 과정에서도 **패킷을 조작하는 방식**으로 문제를 해결한다 (공유기에서 패킷을 조작하던 것과 마찬가지).

- 패킷 조작 방식 → **MTU** 이야기로 이어지고 → **단편화(Fragmentation)** 문제로 연결
- 확인 필요: IPsec VPN에서 MTU 문제가 구체적으로 왜 발생하는지 (다음 주제에서 상세히)

| **진짜 사설망** | 전용회선 임차(KT) → 안전하지만 **비싸고 느림** (영화관 좌석 통째 구매 비유) |

| **IPsec VPN** | **Gateway-to-Gateway** 망 대 망 통합, 재택근무 접속에도 사용 |
| **AWS 연계** | EC2 외부 접근성을 낮추기 위해 VPN 연결 활용 가능 |
| **구현/이슈** | 패킷 조작 방식 → **MTU/단편화** 문제로 연결 |

## 질문 / 헷갈리는 점

- 확인 필요: IPsec VPN에서 MTU 문제가 발생하는 구체적 원리 (단편화와의 관계)
- 확인 필요: IPsec VPN 외 다른 VPN 구현 방식(SSL/TLS VPN 등)과의 차이
- 사설망(VPN의 Private)과 NAT 사설 IP 대역은 **다른 개념**이라는 점 주의
