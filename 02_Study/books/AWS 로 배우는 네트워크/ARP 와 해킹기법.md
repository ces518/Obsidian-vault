# ARP와 해킹 기법

## 개요

**ARP (Address Resolution Protocol)** 는 IP 주소를 MAC 주소로 변환하는 프로토콜이다.
L2 통신을 위해 반드시 필요한 과정이지만, **무조건적인 신뢰 기반**으로 설계되어 **ARP Spoofing** 같은 중간자(MITM) 공격에 취약하다.

---

## 1. ARP가 필요한 이유

### L2 통신에는 MAC 주소가 필수

패킷이 실제로 전송될 때, **L2 구간별로 MAC 주소가 계속 바뀐다.**

```
[PC 5.5.5.5] ──→ [Gateway 5.5.5.1] ──→ ... ──→ [Naver 7.7.7.7]

• IP:  Src=5.5.5.5, Dst=7.7.7.7  (끝까지 불변)
• MAC: Src=PC, Dst=Gateway      (첫 구간)
       Src=Gateway, Dst=다음라우터 (다음 구간)
       ...
```

### PC가 알아야 하는 것

- 자기 IP (DHCP로 받음)
- Gateway IP (DHCP로 받음)
- **Gateway MAC** ← ❓ 어떻게 알지?

> DHCP는 IP만 주고 MAC은 알려주지 않음. MAC은 변경될 수도 있어서 동적으로 알아내야 함.
> → **이때 쓰는 것이 ARP**

---

## 2. ARP 동작 원리

### Request / Reply

```
[PC: 5.5.5.5]
     │
     │ ARP Request (브로드캐스트)
     │ "5.5.5.1 쓰는 애, MAC 주소 뭐야?"
     ▼
┌────────── 네트워크 전체 전파 ──────────┐
│  [옆 PC] → 무시 (내 IP 아님)           │
│  [Gateway 5.5.5.1] → "내 MAC은 xx:xx"  │
└─────────────────────────────────────────┘
     │
     │ ARP Reply (유니캐스트)
     ▼
[PC] Gateway MAC 학습 → ARP 테이블에 캐싱
```

### ARP 테이블

| IP 주소 | MAC 주소 | 유형 |
| --- | --- | --- |
| 5.5.5.1 | aa:bb:cc:11:22:33 | **Dynamic** |
| 5.5.5.52 | dd:ee:ff:44:55:66 | Dynamic |
| ... | ... | Static |

- 명령어: `arp -a` (Windows/macOS/Linux 공통)
- **Dynamic**: ARP Reply에 따라 수시로 갱신
- **Static**: 수동 고정

### 왜 Dynamic이 기본인가?

- 게이트웨이 장비가 고장 나서 교체 → **MAC 주소가 바뀜**
- PC 1,000대에 일일이 "MAC 바뀌었다" 알려줄 수 없음
- Dynamic이면 ARP 테이블이 자동 갱신 → 문제없이 동작

---

## 3. ARP의 치명적 취약점 — 무조건적 신뢰

> [!danger] ARP의 근본적 결함
> **ARP Reply가 오면 검증 없이 무조건 신뢰한다.**
> Request를 보낸 적이 없어도, 누구든 "내 IP는 X이고 MAC은 Y야"라고 주장하면 받아들임.

---

## 4. ARP Spoofing / MITM 공격

### 공격 시나리오

```
[철수 PC]          [해커]           [서버 192.168.0.100]
192.168.0.10                        MAC: AA:BB:CC:11:22:33

   ①   │ ← 해커가 거짓 ARP Reply 전송
        │   "내가 192.168.0.100이고, MAC은 [해커MAC]이야"
        │
   ②  철수 PC의 ARP 테이블:
        192.168.0.100 → [해커MAC] (변조됨)
        │
   ③  철수가 서버에 보내는 패킷
        → L2 스위치는 MAC 기준으로 해커에게 스위칭
        │
   ④  [해커]가 내용 열람 후, MAC만 바꿔 서버로 전달
        │
   ⑤  서버 응답도 같은 방식으로 해커 경유
```

### 결과

- **양방향 트래픽이 해커를 통과** → 모든 통신 도청·변조 가능
- 이를 **MITM (Man-In-The-Middle) Attack** 이라고 함

---

## 5. MITM이 잘 발생하는 환경

같은 L2 세그먼트에 **이질적인 구성원**이 섞여 있을 때 위험.

| 환경 | 위험도 | 설명 |
| --- | --- | --- |
| 집(가정) | 낮음 | 가족끼리 서로 해킹하지 않음 |
| **PC방** | ⚠️ 높음 | 처음 보는 사람들이 같은 L2에 묶임 — 게임 계정 탈취 사례 多 |
| **아파트 (옛 구조)** | ⚠️ 중간 | 같은 ISP 회선이 한 동의 L2로 묶인 경우 존재 |
| **기업 서버팜** | ⚠️ 높음 | WAS-DB 서버 간 통신을 노리는 내부자 공격 |

### 아파트 공유기 활용 팁

- 벽에서 나오는 LAN 선을 **PC에 직결하지 말 것**
- **공유기를 거쳐** 연결하면 구조적으로 일정 수준의 보안 제공

---

## 6. 방어 수단 — Secure Switch

### 동작 원리

일반 L2 스위치 대신 **Secure Switch**를 사용.

```
[Secure Switch]
┌───────────────────────────────┐
│ Port 1 ↔ MAC: AA:BB:CC:11:22 │  ← 포트-MAC 매핑 고정
│ Port 2 ↔ MAC: DD:EE:FF:33:44 │
│ Port 3 ↔ MAC: ...            │
└───────────────────────────────┘
         │
         ↓ 매핑 불일치 발생 시
     → 스위칭 거부
     → 관리자에게 경보 통지
```

### 적용 대상

- PC방 — 필수
- 기업 서버팜 (WAS ↔ DB 구간) — 필수
- Dynamic ARP Inspection(DAI) 기능 병행

---

## 7. 서버 팜에서의 MITM 사례

### 일반적인 3-tier 구성

```
[Web] ─── [WAS (Spring Boot)] ─── [DB (개인정보)]
                 └── 같은 L2 Access에 묶임 ──┘
```

- 같은 로컬 LAN → MITM 취약
- 보안 강화 시 Web을 DMZ로 분리, WAS-DB만 내부망

### 내부 공격 경로

1. 관리자 PC에 악성코드 심기
2. 서버팜 내부에서 ARP Spoofing 수행
3. WAS ↔ DB 사이의 트래픽을 가로채 **개인정보 유출**

→ 방어: **Secure Switch 필수**

---

## 8. AWS 환경에서는?

> [!tip] AWS를 쓰는 이유 중 하나
> **L2를 아예 신경 쓸 필요가 없다.**
> ARP, MAC, MITM — 모두 AWS가 추상화하여 관리.
> 사용자는 L3 이상만 고민하면 됨.

| 항목 | 온프레미스 | AWS VPC |
| --- | --- | --- |
| ARP 관리 | 직접 필요 | 자동 |
| MAC 신경 쓸 일 | 많음 | 없음 |
| Secure Switch 설정 | 직접 구성 | AWS가 처리 |
| MITM 위험 | 존재 | 크게 낮음 |

비용이 비싸지만, **보안·관리 부담 감소**를 고려하면 클라우드 선택이 합리적인 경우가 많음.

---

## 한 줄 요약

> ARP는 IP → MAC 변환을 위한 필수 프로토콜이지만 **무조건적 신뢰 기반**이라 ARP Spoofing / MITM 공격에 취약하며, 이질적 구성원이 섞인 L2(PC방·서버팜)에서는 **Secure Switch**가 필수이다. **AWS VPC에서는 L2 자체가 추상화**되어 이런 문제에서 해방된다.
