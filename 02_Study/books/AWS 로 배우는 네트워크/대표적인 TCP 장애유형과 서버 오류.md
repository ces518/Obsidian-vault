# 대표적인 TCP 장애유형과 서버 오류

## 개요

네트워크는 본질적으로 **불안정**하며 다양한 형태의 장애를 유발한다.
TCP에서 발생하는 장애를 **네트워크 인프라 원인**과 **애플리케이션 논리 오류** 두 카테고리로 나누어 정리하고,
특히 후자의 대표 주자인 **Zero Window** 현상이 왜 EC2 증설로 해결할 수 없는 본질적 코드 문제인지 다룬다.

---

## 1. 네트워크의 본질 — 불안정함

> [!important] 핵심 인식
> 네트워크는 본질적으로 **불안정의 대명사**.
> 사람 관계처럼 — 오해(왜곡)·전달자 개입(중간 노드)·인지 차이가 항상 존재.

### TCP vs UDP 장애 관점

| 프로토콜 | 장애 인식 | 이유 |
| --- | --- | --- |
| **TCP** | 다양한 장애 유형 존재 | 배려·고민이 프로토콜에 설계되어 있음 |
| **UDP** | 사실상 "장애"라는 개념이 희박 | "받든 말든" → 못 받으면 그냥 끝 |

> [!note] UDP에 장애가 없는 이유
> UDP는 배려가 없으니 고민도 없다. 못 받으면 그만이라 **표면적으로 도드라지는 장애 자체가 적다.**
> ([[TCP 와 UDP]] 참조)

---

## 2. 장애 두 카테고리

| 카테고리 | 원인 위치 | 대상자 |
| --- | --- | --- |
| **A. 네트워크 인프라 장애** | 스위치·라우터·방화벽·회선 | 네트워크 관리자 |
| **B. 애플리케이션 논리 오류** | 서버 코드 (수신 처리 구조) | **서버 개발자** |

> [!warning] 잘못된 진단 = 잘못된 처방
> Zero Window가 났는데 네트워크에서 원인을 찾는다 → 영원히 못 찾음.
> EC2 증설로 우회한다 → 비용만 오르고 본질 미해결.

## 3. AWS의 East-West 트래픽은 거의 안 망가진다

```
┌──────────── AWS VPC 내부 ────────────┐
│                                       │
│  [Web]  ⇄  [WAS / API]  ⇄  [DB]      │
│         ↑              ↑              │
│         East-West 트래픽              │
│         유실 가능성 ≈ 0               │
│                                       │
└───────────────────────────────────────┘
                   │
                   ▼
            외부 인터넷 통신
            ⚠️ 여기서는 장애 가능
```

> [!tip] AWS 내부 트래픽 특성
> SDN 기반 가상 환경이라 **East-West 트래픽 유실은 사실상 0에 수렴**.
> 그래서 AWS 안쪽에서 발생하는 장애는 거의 **애플리케이션 코드 문제**.

---

## 4. 인프라 장애 #1 — 패킷 유실 (Packet Loss)

### 원인 후보

| 원인 | 설명 |
| --- | --- |
| **스위치/라우터 오류** | 스위칭 자체 실패 |
| **회선 문제** | 케이블 결함 / 광신호 불량 |
| **방화벽이 의도적으로 폐기** | 보안 필터에 걸려 Drop ([[RST 가 발생하는 이유]]의 Silent Drop) |

> [!important] 보안 필터를 잊지 말 것
> "패킷 유실"이라고 하면 단순히 회선 문제만 떠올리기 쉽지만,
> **방화벽이 보안 정책상 의도적으로 버린** 경우도 매우 흔하다.

---

## 5. 인프라 장애 #2 — 순서 뒤바뀜 (Out of Order)

### 발생 환경

```
[다양한 출처] → [Aggregation Switch] → [업링크 1개]
                       ↑
            여러 회선을 하나로 합치는 과정에서
            오작동 시 순서가 뒤바뀔 수 있음
```

| 장비 | 특징 |
| --- | --- |
| **L2 Access** | 업링크 하나로 올림 (단순) |
| **Aggregation Switch** | 다양한 회선을 하나의 라인으로 통합 → 오동작 가능 |

### 라우팅 경로 변동

- 동적 라우팅에서 경로가 바뀌면 **늦게 출발한 패킷이 먼저 도착**할 수 있음

---

## 6. 인프라 장애 #3 — 재전송 (Retransmission)

> 위 #1 유실 + #2 순서 뒤바뀜의 **결과적 현상**.

### 시나리오 — 단순 유실

```
[Server]                      [Client]
   1번 ───────────────────→   ✓ 1번 받음
   2번 ───────❌ 유실
   3번 ───────────────────→   "2번 못 받았어! 다시!"
                              │
                              ▼
                          서버가 2번 재전송
```

### 시나리오 — 순서 꼬임 + 조기 재전송 요청

```
[Server]                      [Client]
   1번 ───────────────────→   ✓ 1번
   2번 ───── (지연) ─┐
   3번 ─────────────────→     "2번 안 왔다! 재전송!"
                  │            
                  ▼            
                  ⏰ 뒤늦게 2번 도착
                              "어, 2번 이미 왔네?"
                              그래도 서버는 재요청 받았으니
                              ──> 2번 또 보냄

→ 결과: 1, 3, 2, 2 (중복 ACK / Duplicated)
```

### Selective Acknowledgment (SACK) 의 역할

| 지원 여부 | 동작 |
| --- | --- |
| **SACK 지원** | "2번만 다시" → 효율적 |
| **SACK 미지원** | **2번부터 다시** → 3번도 또 받게 됨 → 톱니바퀴 결 안 맞듯 |

> [!note] SACK는 3-way handshake 시 협상
> SACK 지원 여부는 [[TCP 세션과 상태 그리고 게임서버]]에서 다룬 handshake 옵션 교환 시 결정된다.

### 혼잡 상황 진입

```
ACK 중복 + 송수신 합 안 맞음
   │
   ▼
양쪽 모두 "혼잡 상황(Congestion)" 인식
   │
   ▼
"잠깐 멈추고 처음부터 다시 합 맞추자"
   │
   ▼
송신 속도 일시 감소 → 안정화 후 재개
```

> [!important] 인프라 장애의 책임 소재
> 패킷 유실·순서 꼬임·재전송 → **Endpoint 문제가 아니라 네트워크 인프라 문제**.

## 7. 애플리케이션 논리 오류 — Zero Window

> [!danger] 가장 어려운 장애
> **Zero Window** = 수신 측 버퍼에 여유 공간이 0인 상태
> 90% 이상 **애플리케이션 코드의 논리적 오류**.
> 컴파일 타임이 아닌 **런타임 장애**라서 발견·재현이 매우 어렵다.

### 동작 원리 — 버퍼와 처리의 분리

```
[Network] → [TCP I/O Buffer] → [Application Process]
              ↑                      ↑
        OS가 채워줌           개발자가 비워줘야 함
        (수신)                (read + 처리)
```

### 문제가 발생하는 시나리오

```
[버퍼 상태]
초기:    [          ] (텅 빔)

1번 도착: [1         ] 
서버 read: [          ] ← 1번 퍼올림 (move)
서버 처리 시작: 🕐 1번 처리 중 (2초 소요)

  그동안 데이터가 계속 쏟아짐:
  2번 도착: [2         ]
  3번 도착: [23        ]
  4번 도착: [234       ]
  5번 도착: [2345      ]
  6번 도착: [23456     ]
  7번 도착: [234567    ]   ← 버퍼 꽉 참!

[Zero Window 상태]
   Window Size = 0
   → 송신자에게 "더 보내지 마" 통보
   → 송수신 완전 정지
```

### 핵심 — 누구 탓인가?

| 책임 후보 | 실제 책임? |
| --- | --- |
| OS / 네트워크 / TCP | ❌ |
| **애플리케이션 코드 (수신 구조)** | ✅ |

> [!example] 자주 듣게 되는 어처구니없는 대화
> - 서버 개발자: "**클라이언트가 데이터를 안 보내요**"
> - 클라이언트 개발자: "**서버가 못 받아서 못 보내는 거예요**"
> 
> 둘 다 맞다. TCP는 **수신자가 못 받으면 송신자가 안 보낸다**(Flow Control).
> 그러나 진짜 원인은 **수신 측 처리 구조의 결함**.

## 8. Zero Window 해결 — 수신/처리 Thread 분리

### 잘못된 구조 (단일 Thread)

```
loop {
   data = socket.read();      // 수신
   process(data);              // 처리 (오래 걸림)
}                              // 처리하는 동안 수신 막힘 → Zero Window
```

### 올바른 구조 (Thread + Queue 분리)

```
┌─────────────────┐         ┌──────────┐         ┌─────────────────┐
│  Reader Thread  │ ──put→ │  Queue   │ ──poll→ │  Worker Thread  │
│ (수신만 담당)    │         │          │         │ (처리만 담당)   │
└─────────────────┘         └──────────┘         └─────────────────┘
        ↑                                               │
        │ 빠른 read                              느린 처리도 OK
        │ 버퍼 곧바로 비움                       (Worker는 여러 개)
```

### 핵심 원칙

| 원칙 | 설명 |
| --- | --- |
| **Reader Thread** | 소켓에서 빠르게 read만 → Queue에 즉시 push |
| **Worker Thread (다수)** | Queue에서 꺼내 비즈니스 로직 처리 |
| **Queue 자료구조** | 둘 사이의 완충 장치 |

> [!tip] 결과
> 처리에 시간이 걸려도 **수신 버퍼는 항상 빠르게 비워짐** → Zero Window 회피.

---

## 9. 클라이언트는 이 구조가 필요 없다

> [!note] 비대칭성
> - **서버**: 다수의 클라이언트로부터 데이터가 쏟아짐 → Reader/Worker 분리 **필수**
> - **클라이언트**: 서버 한 대로부터 받을 뿐, 폭주 가능성 낮음 → 단일 Thread로 OK

## 10. EC2 증설로 우회하는 안티패턴

### 흔한 잘못된 처방

```
[증상]  특정 시간대에 서버 응답 느림 / 간헐적 끊김
            │
            ▼
[잘못된 진단]  "사용자 늘었으니 서버 부족!"
            │
            ▼
[잘못된 처방]  ALB + EC2 증설
   EC2 1대 → 5대 → 10대 → 비용 폭증 💸
            │
            ▼
[실제 원인]  Reader/Worker 미분리 → Zero Window
            한 대의 EC2도 충분히 처리 가능했음
```

> [!warning] 증설 ≠ 해결
> 코드 구조 결함을 인스턴스 수로 메우면:
> 1. 비용이 선형적으로 증가
> 2. 근본 원인은 그대로 남음
> 3. 트래픽이 더 늘면 똑같이 또 막힘

### 언제 ALB + 증설이 진짜 필요한가?

| 상황 | 처방 |
| --- | --- |
| 코드 구조는 OK, 트래픽이 단일 EC2 한계 초과 | ✅ ALB + 증설 |
| Reader/Worker 미분리로 Zero Window | ❌ 코드 수정이 정답 |
| CPU 바운드 작업이 진짜 1대 한계 도달 | ✅ 증설 또는 스케일업 |

## 11. 장애 진단 워크플로우

```
[서버 응답 지연 / 간헐적 끊김]
            │
            ├─ 패킷 캡처 (Wireshark)
            │     ├─ 유실·순서꼬임·재전송 다수 → 인프라 문제
            │     └─ Zero Window 빈발          → 애플리케이션 문제
            │
            ├─ AWS 내부 통신인가? (East-West)
            │     └─ YES → 인프라 가능성 ↓ → 코드 의심
            │
            └─ 특정 시간대만 발생?
                  └─ YES → 부하 패턴 + 처리 지연 → Zero Window 가능성 ↑
```

### Wireshark 필터

```
tcp.window_size == 0          # Zero Window 검출
tcp.analysis.retransmission   # 재전송 검출
tcp.analysis.duplicate_ack    # 중복 ACK 검출
tcp.analysis.out_of_order     # 순서 꼬임 검출
```

## 12. 핵심 정리표

| 장애 유형 | 카테고리 | 원인 | 해결 위치 |
| --- | --- | --- | --- |
| **패킷 유실** | 인프라 | 스위치/회선/방화벽 Drop | 인프라 점검 |
| **순서 뒤바뀜** | 인프라 | Aggregation 스위치, 동적 라우팅 | 인프라 점검 |
| **재전송 / 중복 ACK** | 인프라 | 위 둘의 결과 | 인프라 + SACK 활성화 |
| **혼잡 상황 진입** | 인프라 | 송수신 합 안 맞음 | TCP 자체 회복 |
| **Zero Window** | **애플리케이션** | **Reader/Worker 미분리** | **코드 수정** |

## 13. AWS 환경에서의 응용

| 항목 | 적용 |
| --- | --- |
| **VPC 내부 통신** | East-West 유실 ≈ 0 → 인프라 의심도 낮음 |
| **CloudWatch Metrics** | 인스턴스 수신/처리 지연 모니터링 |
| **VPC Flow Logs** | 외부 트래픽 손실 패턴 분석 |
| **VPC Traffic Mirroring** | Wireshark용 패킷 미러 ([[IP 헤더와 AWS ENI]]) |
| **ALB / Auto Scaling** | **코드 결함 우회 X**, 정당한 부하 분산에만 사용 |
| **X-Ray** | 애플리케이션 처리 시간 분석 → Worker 병목 식별 |

> [!tip] AWS 시대의 진단 사고법
> AWS 안쪽 East-West에서 장애가 보인다 → **거의 100% 코드 문제**.
> "네트워크 탓"이라는 변명은 클라우드에서는 점점 통하지 않는다.

## 한 줄 요약

> TCP 장애는 **인프라 문제**(패킷 유실·순서 꼬임·재전송)와 **애플리케이션 논리 오류**(Zero Window)로 나뉘며, AWS East-West에서는 사실상 후자만 의심해야 한다. **Zero Window는 수신 Reader Thread와 처리 Worker Thread의 분리(+Queue)로 해결**해야 하며, 이를 EC2 증설로 우회하는 것은 비용만 늘리고 근본을 못 잡는 안티패턴이다.
