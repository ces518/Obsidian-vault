# RST가 발생하는 이유

## 개요

TCP는 정상적이라면 **3-way handshake → 데이터 송수신 → 4-way handshake**로 우아하게 끝나야 한다.
하지만 실제 운영 환경에서는 **RST(Reset)** 이 빈번히 발생한다.
RST의 발생 원인을 **의도적 발생**과 **결과적 발생** 두 카테고리로 나눠 정리하고, 각각이 무엇을 의미하는지 — 특히 **장애 진단·보안 모니터링** 관점에서 살펴본다.

---

## 1. RST을 두 가지 시각으로 봐야 하는 이유

> [!important] 두 카테고리
> | 분류 | 누가 알아야 하나 |
> | --- | --- |
> | **의도적 RST** | **개발자** (특히 서버 개발자) |
> | **결과적 RST** | **네트워크 관리자** (장애·보안 모니터링) |

- 의도적 RST = "내가 이렇게 처리하려고 한 거야"
- 결과적 RST = "어, 왜 RST이 이렇게 많이 나오지?" → **반드시 원인 규명 필요**

---

## 2. 의도적 RST — 서버가 강제로 끊어야 할 때

### 시나리오

```
[Server]                               [Client #1: 이상행위]
   │                                          │
   │  1번 사용자가 어뷰징 / 핵 / 이상행위 감지  │
   │                                          │
   │  서버 판단: "이 클라이언트 튕겨야겠다"     │
   │                                          │
   │  ❌ FIN으로 정상 종료 (절대 X)            │
   │  ✅ RST으로 강제 종료 (정답)              │
   │                                          │
   │  ── RST ─────────────────────────────→  │  💥 즉시 끊김
```

### 구현 — `SO_LINGER` 옵션

```c
// 1번 클라이언트와 통신 중인 소켓
struct linger so_linger;
so_linger.l_onoff  = 1;          // linger 활성화
so_linger.l_linger = 0;          // 0초 → 즉시 RST
setsockopt(sock, SOL_SOCKET, SO_LINGER, &so_linger, sizeof(so_linger));
close(sock);                      // FIN 대신 RST 발송됨
```

> [!tip] 핵심
> 서버가 먼저 끊어야 한다면 `SO_LINGER` 옵션을 변경한 뒤 `close()` → 즉시 RST 발송.
> [[TCP 세션과 상태 그리고 게임서버]]에서 다룬 **TIME_WAIT 회피**의 정공법.

## 3. 결과적 RST — Case 1: 서버 프로세스 비정상 종료

### 발생 메커니즘

```
[게임 서버 Process]
   │
   │  소켓 풀:
   │   ├── 소켓 (Client #1)   ESTABLISHED
   │   ├── 소켓 (Client #2)   ESTABLISHED
   │   ├── 소켓 (Client #3)   ESTABLISHED
   │   ├── ...
   │   └── 소켓 (Client #300) ESTABLISHED
   │
   │  💥 프로세스 비정상 종료 (크래시)
   ▼
[OS Kernel]
   │
   │  "프로세스가 사라졌네? 소켓 모두 강제 회수!"
   │  TCP Stack: "연결된 클라이언트들에게 알려야지"
   │
   ▼
   ── RST × 300개 ───→ 모든 클라이언트
   "서버 튕겼다!" 동시 발생
```

### 핵심 원리

| 단계 | 설명 |
| --- | --- |
| ① 소켓의 본질 | 파일 → 입출력 권한의 주체는 **프로세스** |
| ② 프로세스 사망 | 주체가 사라짐 |
| ③ OS 회수 | 운영체제가 모든 소켓을 강제 회수 |
| ④ TCP Stack | 연결된 모든 상대에게 **RST 일괄 송출** |

### 운영자 관점에서 본 신호

> [!warning] RST 대량 검출 = 비상 신호
> 특정 시간대에 RST이 **수백 개 동시 발생** → 두 가지 가능성:
> 1. **서버 프로세스가 죽었다** (크래시)
> 2. **비즈니스 로직이 일괄 강제 종료를 수행** (의도적 일괄 튕김)
> → 어느 쪽인지 반드시 규명할 것

## 4. 결과적 RST — Case 2: 바인드된 소켓이 없는 포트로 트래픽 도착

### 시나리오

```
[Host: 3.3.3.3]
   │
   │  현재 열린 소켓:  TCP 80, TCP 22 만 사용 중
   │                  (8080은 아무도 안 씀)
   │
   ↑
   │  외부에서 갑자기:
   │  "TCP 8080으로 데이터 보냄"
   │
[외부 호스트]
```

### TCP Stack의 처리

```
[TCP Stack]
   │
   │  ① 도착한 세그먼트의 목적지 포트 = 8080
   │  ② "8080에 bind된 소켓이 있나?" 검색
   │  ③ "없다!"
   │  ④ "전달할 곳이 없으니 RST 보내야겠다"
   │
   ▼
   ── RST ──→ 송신자
```

> [!note] 포트 번호의 역할 복기
> 포트 번호는 **프로세스 식별자**(개발자 관점)이며, 어떤 프로세스도 bind하지 않은 포트로 트래픽이 오면 운영체제는 받을 데가 없으므로 RST으로 응답한다.
> ([[4계층 TCP 헤더 구조와 Buffered IO]] 6장 참조)

## 5. 결과적 RST — Case 3: 비정상 상태 전이 / 잘못된 패킷

TCP는 **상태 전이의 적정성**을 검사한다. 부적절한 패킷이 오면 즉시 RST으로 응답.

### RST을 유발하는 패턴

| 비정상 패턴 | 설명 |
| --- | --- |
| **연결 안 했는데 FIN** | "끊자"가 갑자기 옴 (handshake 없이) |
| **시퀀스 번호 불일치** | 예상 Seq 번호와 전혀 다른 값 |
| **잘못된 Flag 조합** | SYN+FIN 동시 세트 등 비논리적 조합 |
| **상태 전이 위반** | LISTEN 상태인데 데이터 세그먼트가 옴 |
| **조작된 패킷** | 헤더 필드가 명백히 위조됨 |

### TCP의 반응

```
TCP: "야, 너 뭔가 잘못 알고 있는 것 같아"
   ↓
   ── RST ──→ 송신자
```

> [!important] Stateful Inspection 방화벽의 동작 근거
> 위와 같은 비정상 패턴 검출 → RST 자동 응답.
> 이 메커니즘이 [[TCP 와 UDP]]에서 다룬 **Stateful Inspection 방화벽**의 핵심 작동 원리이다.

## 6. 보안 관점 — 해커 스캔 탐지

### 해커의 포트 스캔 시나리오

```
[Attacker]                               [Target]
   │                                         │
   │  "이 호스트에 어떤 포트가 열려 있지?"    │
   │                                         │
   │  ── SYN to Port 22 ──────────────→     │  열림 → SYN+ACK
   │  ── SYN to Port 80 ──────────────→     │  열림 → SYN+ACK
   │  ── SYN to Port 8080 ────────────→     │  닫힘 → RST
   │  ── SYN to Port 9999 ────────────→     │  닫힘 → RST
   │
   │  → RST 응답으로 "닫힌 포트" 식별
   │  → SYN+ACK 응답으로 "열린 포트" 식별
   │  → 공격 표면(Attack Surface) 매핑 완료
```

### 탐지 신호

> [!warning] RST이 대량 발생 = 스캐닝 의심
> 외부에서 들어오는 다양한 포트로의 SYN → RST 응답 패턴이 짧은 시간에 폭증
> → **포트 스캔 / 해커 정찰 활동** 가능성
> → 공격자 IP 식별 후 차단 조치

---

## 7. 더 좋은 방어 — 방화벽으로 RST조차 안 보내기

### 일반 동작 vs 방화벽 적용

```
[일반]
  Attacker ── SYN → 닫힌 포트 ──→ TCP Stack ── RST ──→ Attacker
                                                     "닫혔구나" (정보 노출)

[방화벽 적용]
  Attacker ── SYN → ┌────────────┐
                    │  Firewall  │  ← 비정상 패킷 차단
                    └────────────┘
                          ✗ TCP Stack까지 도달 못함
                          ✗ RST 응답조차 안 나감
                                                     "응답 없음 = 호스트 존재 자체를 인식 못함"
```

### 효과

> [!tip] Silent Drop
> 방화벽이 패킷을 **조용히 폐기(Silent Drop)** 하면, 공격자는
> - 응답이 아예 없으니 호스트의 존재 자체를 확인하지 못함
> - 스캐닝 결과에 "이 IP는 죽은 것 같음"으로 분류됨
> - 공격 표면이 노출되지 않음

### 방화벽 위치별 명칭

| 위치 | 명칭 |
| --- | --- |
| 엔드포인트(PC·서버 OS 자체) | **PC 방화벽 / 엔드포인트 방화벽** (Windows Defender Firewall 등) |
| 네트워크 경로상 | **네트워크 방화벽** (전용 어플라이언스, AWS Security Group 등) |

## 8. RST 원인 한눈에 보기

| 분류 | 원인 | 누가 봐야 하나 | 정상/이상 |
| --- | --- | --- | --- |
| **의도적** | 서버가 `SO_LINGER`로 강제 종료 | 개발자 | 의도된 처리 |
| **결과적 #1** | 서버 프로세스 비정상 종료 → OS가 일괄 RST | 운영자 | ⚠️ 장애 |
| **결과적 #1'** | 비즈니스 로직이 일괄 강제 종료 수행 | 운영자 | 의도된 처리 |
| **결과적 #2** | 바인드되지 않은 포트로 트래픽 도착 | 운영자·보안 | ⚠️ 의심 |
| **결과적 #3** | 시퀀스/플래그/상태 전이 위반 | 보안 | ⚠️ 의심 |
| **보안** | 외부 포트 스캔 시도 | 보안 | 🚨 공격 정찰 |

## 9. 진단 워크플로우

```
[RST 대량 검출]
       │
       ├─ 발생 위치: 자사 서버에서 송출?
       │        │
       │        ├─ YES → ① 서버 프로세스 헬스 체크 (크래시?)
       │        │       ② 비즈니스 로직 점검 (의도된 일괄 종료?)
       │        │
       │        └─ NO  → 외부에서 우리 서버로 RST?
       │                ③ 포트 스캔 / 정찰 의심
       │
       ├─ 시퀀스 번호 / Flag 패턴이 비정상?
       │        → 조작된 패킷 / 공격 시도 의심
       │
       └─ 진단 도구
              ├─ Wireshark (Flag = RST 필터링)
              ├─ netstat / ss
              └─ AWS VPC Flow Logs / VPC Traffic Mirroring
```

### Wireshark 필터 예시

```
tcp.flags.reset == 1
```

## 10. AWS 환경에서의 응용

| 항목 | 적용 |
| --- | --- |
| **VPC Flow Logs** | RST 패킷 패턴 분석으로 스캔 탐지 |
| **VPC Traffic Mirroring** | 의심 트래픽을 IDS로 미러링 ([[IP 헤더와 AWS ENI]] 참조) |
| **Security Group** | 인바운드 규칙으로 불필요 포트 차단 → Silent Drop |
| **NACL** | 서브넷 단위 추가 차단 |
| **GuardDuty** | 비정상 RST 패턴·포트 스캔 자동 탐지 |
| **AWS WAF / Shield** | 애플리케이션 레벨 보안 보강 |

> [!tip] AWS Security Group은 기본이 Silent Drop
> Security Group은 **명시적으로 허용**된 포트 외에는 모두 조용히 폐기 → RST 응답조차 외부로 나가지 않음 → 자연스러운 스캔 방어.

---

## 한 줄 요약

> RST은 **의도적**(서버가 `SO_LINGER`로 강제 종료)과 **결과적**(프로세스 크래시·미바인드 포트·비정상 상태 전이·해커 스캔)으로 나뉘며, RST이 대량 발생하면 **장애 또는 보안 위협**의 신호이므로 반드시 원인을 규명해야 한다. 가장 좋은 방어는 **방화벽으로 RST조차 응답하지 않는 Silent Drop** — 공격자에게 호스트의 존재 자체를 숨기는 것이다.
