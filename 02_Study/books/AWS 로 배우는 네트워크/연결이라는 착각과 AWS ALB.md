# 연결이라는 착각과 AWS ALB

## 개요

TCP의 **연결(Connection)** 은 실체가 있는 것이 아니라 **소프트웨어적 논리(Virtual Circuit)** 일 뿐이다.
물리적 연결과 논리적 연결은 **다른 도메인**에 속하므로, 한쪽이 끊겨도 다른 쪽은 한동안 그대로다.
이 간극이 만들어내는 **좀비 세션·세션 하이재킹** 같은 문제와, 그 해결책인 **하트비트(Heartbeat)** → 그리고 이것이 **AWS ALB의 Health Check**로 이어지는 흐름을 정리한다.

---

## 1. 연결은 실체가 아니다 — 마우스 포인터 비유

> [!important] 핵심 명제
> **TCP 연결은 Virtual Circuit, 즉 논리적인 가상 회선이다.**
> 전선이 폐회로를 이루는 물리적 연결과는 본질이 다르다.

### 마우스 포인터를 떠올려라

| 질문 | 답 |
| --- | --- |
| 마우스 포인터는 **물리적으로** 존재하는가? | ❌ (중력의 영향을 받지 않음) |
| 마우스 포인터는 **논리적으로** 존재하는가? | ✅ |
| 그럼 진짜 존재하는가? | **소프트웨어적 환영(눈속임)** |

> [!tip] IT 용어 변환
> - `Virtual` ⇄ `Logical` ⇄ `Software`
> - 이 단어가 등장하면 → "물리적 실체 없음, 소프트웨어적 구성"

### 그래서 연결은?

- 3-way handshake = **시퀀스 번호 + MSS + SACK + Window Size 정보 교환 절차**
- 절차가 규칙대로 잘 흘러갔다고 양쪽이 판단 → "연결됐다"라고 **합의**
- 즉 연결의 본질 = **양 통신 주체의 논리적 합의**

> [!example] 연결의 환영을 이용한 트릭
> - 실제 connect()를 안 하고도 **handshake 절차만 흉내**내면 연결된 것처럼 만들 수 있다
> - 반대로 멀쩡한 연결을 **외부에서 끊는 절차만 보내면** 끊어버릴 수도 있다
> - 이 모든 건 **논리적 합의가 흔들렸기 때문**

## 2. 물리 연결 vs 논리 연결 — 두 도메인의 분리

### OSI 계층상 위치

```
┌─────────────────────────────────┐
│  L4: TCP                        │  ← 논리적 연결
│  L3: IP                         │
│ ─────────────────────────────── │
│  L2: Ethernet                   │
│  L1: Physical (LAN 케이블)       │  ← 물리적 연결
└─────────────────────────────────┘

원칙: 아랫집(물리)이 윗집(논리)의 전제 조건이다.
```

### 핵심 질문

> "물리적 연결이 잠시 끊어지면, 논리적 연결도 즉시 끊어질까?"

| 직관 | 실제 |
| --- | --- |
| "당연히 끊어지지 않나요?" | ❌ |
| 답 | **유지된다 (적어도 당분간)** |

## 3. 재전송 타이머 — 끊김을 인지하기까지의 시간

### TCP의 끊김 인지 메커니즘

```
정상 송수신 중
   │
   │  (LAN 케이블 분리 / 스위치 다운 / 기지국 전환)
   ▼
TCP 수신 측: "어? 데이터가 안 오네? 패킷 유실인가?"
   │
   │  ── ACK 재시도 → 응답 없음
   │
   ▼
재전송 타이머 발동
   │
   │  1초 → 2초 → 4초 → 8초 → 16초 ... (지수적 증가)
   │
   │  대부분 5번 이상 재전송 후에도 무응답이면
   ▼
   세션 RESET (논리 연결 종료)
```

### SRTT (Smoothed Round Trip Time)

| 항목 | 설명 |
| --- | --- |
| **언제 결정?** | 3-way handshake 시 |
| **무엇?** | RTT의 평활화된 값 |
| **역할** | TCP 내부의 각종 타이머의 기준 |
| **근삿값** | 약 3초 (대부분의 OS는 1초 미만) |

### 실험적으로 체감하기

```
[파일 다운로드 중]
   │
   ├─ LAN 케이블 1초 뽑았다 꽂기  → ✅ 다운로드 정상 진행
   ├─ LAN 케이블 2초 뽑았다 꽂기  → ✅ 대부분 정상 진행
   ├─ LAN 케이블 8초 뽑았다 꽂기  → ⚠️ 될 수도, 안 될 수도
   └─ LAN 케이블 16초 이상       → ❌ 거의 끊김
```

### 일상적 사례 — 이동통신

```
[지하철 이동 중]
   │
   기지국 A 연결 ──→ (잠시 단절) ──→ 기지국 B 연결
                       ↑
                  물리 연결 단절
                       │
                  논리 연결(TCP)은 그대로 유지됨
                  (handover 동안에도 통신 끊김 안 느낌)
```

> [!note] 결론
> 물리 ≠ 논리. **각자의 도메인이 분리되어 있다.**
> 물리가 흔들려도 논리는 한동안 자기 페이스로 살아있다.

## 4. 좀비 세션 — 연결의 신뢰성 문제

### 무엇이 문제인가?

```
[Server]                              [Client]
   │                                       │
   │  ESTABLISHED 상태로 인지             │
   │  "이 클라이언트는 살아있다"          │
   │                                       │
   │                                       💀 (실제로는 죽음)
   │                                       
   │  소켓은 그대로 점유                   
   │  자원 낭비 + 비즈니스 로직 오작동    
```

> [!warning] 좀비 세션(Zombie Session)
> 실제로는 끊어졌는데 **서버는 살아있다고 믿는** TCP 세션.
> 자원 누수와 잘못된 상태 판단을 유발.

### 절대 규칙

> [!danger] 연결을 신뢰하지 마라
> 서버는 **"클라이언트와 연결되어 있다"는 자기 인식을 절대로 신뢰해서는 안 된다.**
> 물리·외부 환경은 언제든 어긋날 수 있다.

## 5. 해결책 — Heartbeat (하트비트)

### 동작 원리

```
[Server] ────── "야, 살아있어?" ─────→ [Client]
        ←─────── "응, 살아있어" ──────
        
                  (주기적으로 반복)
        
        응답 없음 → "끊어졌구나" 판정 → 세션 정리
```

| 항목 | 설명 |
| --- | --- |
| **목적** | 좀비 세션 탐지 |
| **메커니즘** | 일정 주기로 살아있는지 확인 메시지 송수신 |
| **위치** | **애플리케이션 레벨에서 직접 설계** (User Mode Application Protocol) |

### 주기 설정의 트레이드오프

| 주기 | 장점 | 단점 |
| --- | --- | --- |
| **너무 짧음** (1초) | 빠른 탐지 | 트래픽 오버헤드 ↑ |
| **너무 김** (30초) | 트래픽 절약 | 좀비 세션 인지 지연 |
| **적정** (5~10초) | 균형 | — |

> [!tip] 설계 원칙
> "최대 N초 이내에 끊김을 탐지하겠다" → 하트비트 주기를 **N초 이하**로 설정.
> 즉 SLA에서 출발해 주기를 도출.

### 반드시 넣어야 하는가?

> [!important] YES
> 게임 서버·실시간 통신 서버 등 **장기 연결을 유지하는 모든 시스템**에는
> Heartbeat가 **필수 설계 요소**다. 안 넣으면 위 좀비 세션 함정에 그대로 빠진다.

## 6. TCP 세션 하이재킹 — 위조 패킷의 위협

### 공격 시나리오 (MITM 환경)

```
[Client: 6.6.6.10] ──연결── [Server: 7.7.7.7]
                                  │
            [Attacker: 6.6.6.20]  │  ← 같은 LAN, MITM 수행
                                  │
            오가는 패킷 관찰 가능
                  │
                  ▼
   ① Client인 척 위조 패킷 1개 전송
       (Seq/Ack 번호 일치시켜서)
                  │
                  ▼
   ② Server: "Client가 연결 끊자고 했네 (RST)"
       → 강제 종료
                  │
                  ▼
   ③ Client: 자기는 한 적 없는 종료가 발생
```

### 왜 가능한가?

- TCP는 **시퀀스 번호 + ACK 번호**가 일치하면 정상 패킷으로 처리
- MITM 상황이면 그 번호를 **관찰 가능**
- 일치하는 위조 패킷 1개로 **연결 강제 종료** 가능
- 더 어렵지만, 데이터를 가로채는 **TCP Session Hijacking**도 가능

> [!danger] 시사점
> "연결되어 있다"는 인식은 **외부 위협에 의해서도 흔들릴 수 있다.**
> [[ARP 와 해킹기법]]에서 다룬 MITM 환경이라면 더더욱 위험.

## 7. Heartbeat → Health Check → AWS ALB

### 용어의 진화

```
[애플리케이션 프로토콜 설계]
       하트비트(Heartbeat)
            │
            │  "엔드포인트 간 상호 생존 확인"
            ▼
[인프라 / 로드밸런서 영역]
       헬스 체크(Health Check)
            │
            │  "장치/서버 풀의 가동 상태 확인"
            ▼
[AWS]
       ALB Health Check
```

> [!note] 같은 원리, 다른 이름
> "살아있니?"를 묻는 행위 자체는 동일.
> 다만 **장치(서버)의 상태를 체크하는 인프라 관점**에서는 **Health Check**라고 부른다.

### AWS ALB(Application Load Balancer)의 동작

```
┌─────────────────────────────────────────────────────┐
│              AWS ALB (Application Load Balancer)    │
│                                                     │
│   주기적으로 각 EC2의 Health Check API 호출         │
│   GET /health  → 200 OK?                            │
└──┬──────────────┬──────────────┬───────────────────┘
   │              │              │
   ▼              ▼              ▼
┌────────┐    ┌────────┐    ┌────────┐
│ EC2 #1 │    │ EC2 #2 │    │ EC2 #3 │
│ API    │    │ API    │    │ API ❌ │  ← 응답 실패 시
│ /health│    │ /health│    │        │     자동으로 트래픽 제외
└────────┘    └────────┘    └────────┘
```

### Health Check의 본질

| 단계 | 동작 |
| --- | --- |
| ① ALB | 각 대상(EC2)의 `/health` API를 주기적으로 호출 |
| ② 응답 200 | "살아있다" → 트래픽 분배 대상에 포함 |
| ③ 응답 실패 | "죽었다" → 트래픽 분배 대상에서 제외 |
| ④ 부활 | 다시 정상 응답 → 재투입 |

> [!example] 사장님 비유
> "사장님이 알바들에게 계속 '너 괜찮냐?' 묻는 것"
> → 단순 무식하지만 가장 확실한 생존 확인 방법.

### 부하 분산과의 결합

> [!important] Load Balancing의 전제
> 트래픽을 여러 인스턴스에 분산하려면 **각 인스턴스가 살아있는지** 알아야 한다.
> → **Health Check는 Load Balancing의 필수 동반자**.

## 8. 정리 — 연결이라는 착각과 그 대응

```
[연결의 본질]
    Virtual Circuit (논리적 합의)
           │
           ▼
[문제 인식]
    물리적 단절은 논리적 연결에 즉시 영향 X
    → 좀비 세션 발생 가능
    → 외부 위조 패킷으로 강제 종료 가능
           │
           ▼
[해결책]
    애플리케이션 프로토콜 레벨에서 "살아있니?" 주기적 확인
           │
           ├─ Endpoint 간       →  Heartbeat
           └─ Infrastructure   →  Health Check
                                          │
                                          ▼
                              [AWS ALB Health Check]
                              + Load Balancing
```

## 9. 핵심 정리표

| 항목 | 내용 |
| --- | --- |
| **TCP 연결의 본질** | Virtual Circuit (논리적 합의) |
| **물리 vs 논리** | 다른 도메인 — 즉시 동기화되지 않음 |
| **인지 지연** | 재전송 타이머 (1→2→4→8→16초, 약 5회) |
| **SRTT** | 3-way handshake 시 결정, 타이머 기준값 |
| **좀비 세션** | 실제 끊겼는데 서버가 살아있다고 믿는 세션 |
| **하트비트** | 애플리케이션 레벨 생존 확인 |
| **세션 하이재킹** | MITM + Seq/Ack 일치 위조 패킷 → 강제 종료/탈취 |
| **Health Check** | 인프라/로드밸런서 관점의 하트비트 |
| **AWS ALB** | `/health` API 주기 호출 → 트래픽 분배 자동 조정 |

## 10. AWS 환경에서의 응용

| 항목 | 적용 |
| --- | --- |
| **ALB Health Check** | HTTP/HTTPS 레벨, 응답 코드 기반 |
| **NLB Health Check** | TCP 핸드셰이크 기반 (L4) |
| **Target Group** | Healthy/Unhealthy 임계치 설정 (Threshold) |
| **Auto Scaling** | Health Check 결과에 따라 인스턴스 자동 교체 |
| **Connection Draining** | 종료 인스턴스의 기존 연결을 정상 종료할 시간 부여 |
| **WebSocket / gRPC** | 장기 연결 → Heartbeat 설계 더더욱 중요 |

> [!tip] ALB는 자동, Heartbeat는 직접
> ALB의 Health Check는 AWS가 알아서 해주지만,
> **WebSocket·게임 클라이언트 등 애플리케이션 레벨의 좀비 세션은 ALB가 못 잡는다.**
> → 애플리케이션 프로토콜에 **자체 Heartbeat**를 반드시 설계할 것.

---

## 한 줄 요약

> TCP 연결은 **Virtual Circuit, 즉 논리적 합의**일 뿐이며 물리적 연결과는 도메인이 다르다. 물리가 끊겨도 논리는 한동안 살아있어 **좀비 세션**과 **세션 하이재킹**의 위험이 있으므로, 모든 장기 연결 시스템은 **Heartbeat를 애플리케이션 프로토콜에 반드시 설계**해야 한다. 인프라 영역에서 같은 원리가 **Health Check**이며, 이것이 곧 **AWS ALB의 동작 원리**이자 Load Balancing의 전제 조건이다.
