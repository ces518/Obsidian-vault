# 모던 웹 서비스 구조

## 개요

[[모던 웹과 JWT]]에서 다룬 SPA + JWT를 기반으로,
**모던 웹 서비스의 전체 아키텍처**를 정리한다.
프론트와 API 서버의 분리, Scale-out 방식(수평 vs 기능 분리),
**API Gateway**, **Redis**, AWS 매니지드 서비스까지 다룬다.

---

## 1. 모놀리식 vs 모던 — 통신 구조의 차이

### 모놀리식

```
                  Browser
                    │
                    ▼
              ┌──────────┐
              │ Frontend │  ← 프론트가 게이트웨이 역할
              │ (Web)    │
              └─────┬────┘
                    │
                    ▼
              ┌──────────┐
              │ Backend  │
              │ (WAS)    │
              └─────┬────┘
                    │
                    ▼
                ┌──────┐
                │  DB  │
                └──────┘
```

→ 프론트가 **백엔드로 가는 게이트웨이**처럼 작동.

### 모던 (SPA + REST API)

```
                  Browser (SPA)
                  ╱       ╲
                 ╱         ╲
                ▼           ▼
         ┌──────────┐  ┌──────────┐
         │ Frontend │  │   API    │  ← 둘은 완전히 독립된 서버
         │  Server  │  │  Server  │
         └──────────┘  └─────┬────┘
                              │
                              ▼
                          ┌──────┐
                          │  DB  │
                          └──────┘
```

> [!important] 핵심 차이
> 모던 웹에서는 브라우저가 **프론트 서버와 API 서버를 각각 독립적으로 직접 호출**한다.
> 프론트는 더 이상 백엔드의 게이트웨이가 아님.

---

## 2. HTTPS 필수화 — 양쪽 모두 인증서

> [!important] 모던 웹의 통신 원칙
> 모든 통신은 **HTTPS**. 프론트 서버와 API 서버 **각각 SSL 인증서 필요**.

```
Browser ──HTTPS──▶ Frontend Server  (인증서 필요)
   │
   └────HTTPS──▶ API Server       (인증서 별도 필요)
```

- 두 서버는 각자 다른 도메인일 수도 있음 (예: `www.example.com`, `api.example.com`)
- → [[웹 보안과 SOP CORS]]의 CORS 설정이 필요한 상황

## 3. 프론트엔드의 진화

### Application 화 = SPA

| 측면 | 모놀리식 | 모던 (SPA) |
|------|---------|-----------|
| **브라우저 화면** | HTML 문서 뷰어 | **응용 프로그램 실행 화면** |
| **로그인 방식** | `<form>` POST → CSRF 위험 | JS fetch + Authorization Header |
| **페이지 전환** | 새 URL 이동, 전체 리로드 | 같은 URL 내 부분 갱신 |
| **렌더링** | 서버에서 HTML 생성 | **클라이언트 JS 렌더링** (또는 SSR) |
| **프레임워크** | — | **React, Vue, Angular, Next.js** |

### form 기반에서 스크립트 기반으로

```
[모놀리식]                    [모던]
<form action="/login"        스크립트에서 fetch:
      method="POST">         fetch('/api/login', {
  <input name="email">         method: 'POST',
  <input name="password">      headers: {
  <button>로그인</button>        Authorization: 'Bearer xxx'
</form>                        },
                               body: JSON.stringify({...})
                             })
                             
→ CSRF 노출                  → 보안 대응 가능
```

## 4. 백엔드 — Spring Boot 중심

### Spring vs Spring Boot

| 구분 | 특징 |
|------|------|
| **Spring** | 강력하지만 **설정이 절반**일 정도로 복잡 (의존성, XML, 빌드 설정) |
| **Spring Boot** | Spring의 설정 부담 해소 — **자동 설정 + Embedded 서버 + Starter 의존성** |

### 백엔드의 역할 변화

> [!note] API 서버의 본질
> 모던 백엔드는 더 이상 HTML을 생성하지 않는다.
> **REST API 응답으로 JSON 데이터만 제공**하는 역할.

### 의존성 관리

- 라이브러리 = "내가 안 만든 것을 가져다 씀"
- **모듈 의존성 + 패키지화 + 빌드 설정**이 골치 → Spring Boot가 해결
- JWT 검증, DB 연결, 보안 등 → Spring Boot Starter로 손쉽게 추가

## 5. Scale-Out — 두 가지 방식

### 방식 ① 수평적 양적 팽창 (단순 Scale-Out)

```
                Browser
                   │
                   ▼
            ┌────────────┐
            │    ALB     │  ← Application Load Balancer
            │ (로드밸런서) │     부하 적은 서버로 분산
            └──┬──┬──┬──┘
               │  │  │
        ┌──────┘  │  └──────┐
        ▼         ▼         ▼
   ┌────────┐ ┌────────┐ ┌────────┐
   │API #1  │ │API #2  │ │API #3  │  ← 모두 같은 기능
   └────┬───┘ └────┬───┘ └────┬───┘
        └─────────┼──────────┘
                  ▼
              ┌──────┐
              │  DB  │
              └──────┘
```

- 같은 기능을 하는 서버를 **N대로 복제**
- 앞단에 **ALB**(Application Load Balancer)를 두어 부하 분산
- 한 대가 다운돼도 다른 서버가 처리 → **고가용성**

### 방식 ② 기능 단위 분리 (마이크로서비스)

```
                  Browser
                     │
                     ▼
              ┌──────────────┐
              │ API Gateway  │  ← 요청을 적절한 서비스로 라우팅
              └──┬───┬───┬──┘
                 │   │   │
        ┌────────┘   │   └─────────┐
        ▼            ▼             ▼
   ┌────────┐  ┌──────────┐  ┌──────────┐
   │  Auth  │  │  Order   │  │ Product  │  ← 기능별로 서비스 분리
   │ Service│  │ Service  │  │ Service  │
   └────┬───┘  └─────┬────┘  └─────┬────┘
        ▼            ▼             ▼
    ┌──────┐    ┌──────┐       ┌──────┐
    │Auth DB│   │Order DB│      │Prod DB│  ← DB도 각자 분리
    └──────┘    └──────┘       └──────┘
```

> [!tip] 기능 분리의 장점
> - **부분 장애 대응**: Order 서비스가 다운돼도 Auth는 정상 → 로그인은 가능
> - **독립 배포**: 한 서비스만 업데이트해도 전체 영향 없음
> - **DB 분리**로 부하 분산 (DB는 가장 흔한 병목 지점)

### 두 방식의 조합

```
실무에서는 보통 두 방식을 결합:
  - 마이크로서비스로 기능 분리 (Auth, Order, ...)
  - 각 서비스 내에서 ALB로 수평 확장
```

## 6. API Gateway

> [!important] API Gateway의 역할
> 마이크로서비스 환경에서 클라이언트가 직접 N개의 서비스에 접근하지 않고,
> **단일 엔드포인트**로 모든 API 요청을 받아 적절한 서비스로 라우팅.

### 기능

| 기능 | 설명 |
|------|------|
| **단일 엔드포인트** | `api.example.com` 하나로 모든 API 통합 |
| **라우팅** | `/auth/*` → Auth Service, `/orders/*` → Order Service |
| **인증** | JWT 검증을 한 곳에서 처리 가능 |
| **로드밸런싱** | 각 서비스 내 인스턴스 분산 |
| **요율 제한 (Rate Limiting)** | DDoS 방어 |
| **로깅/모니터링** | 모든 트래픽이 통과하므로 중앙 집중 관찰 |

### ⚠ 단일 장애점 (Single Point of Failure)

> [!caution] API Gateway가 다운되면?
> 뒤의 모든 서비스가 멀쩡해도 **전체 서비스가 끝남**.
> → 반드시 **다중화**(이중화/클러스터)로 운영해야 함.

## 7. Redis — 세션 통제와 즉시 무효화

### 문제 — JWT의 한계 (복습)

> [!caution] JWT의 강제 무효화 어려움
> 토큰을 발급하면 **만료 전까지 강제 무효화 불가능**.
> 사용자가 "지금 즉시 로그아웃!"이라고 해도 클라이언트가 가진 토큰은 다른 서버에서 여전히 통과.

→ 자세한 배경은 [[모던 웹과 JWT]] Section 9 참조.

### 해결 — Redis Blacklist

```
Browser                Service                Redis
  │                       │                    │
  │ ① 즉시 로그아웃 요청    │                    │
  │ ─────────────────────▶│                    │
  │                       │ ② 토큰을 Blacklist  │
  │                       │ ──────────────────▶│
  │                       │                    │
  │ ③ (도용된 토큰으로 요청)│                    │
  │ ─────────────────────▶│                    │
  │                       │ ④ Blacklist 조회    │
  │                       │ ──────────────────▶│
  │                       │                    │
  │                       │ ⑤ "무효화된 토큰"    │
  │                       │ ◀──────────────────│
  │ ⑥ 401 Unauthorized    │                    │
  │ ◀──────────────────── │                    │
```

### Redis 활용 영역

| 용도 | 설명 |
|------|------|
| **JWT Blacklist** | 즉시 무효화된 토큰 목록 관리 |
| **Refresh Token 저장** | 만료 정보 + 사용자별 토큰 관리 |
| **활성 세션 통제** | 동시 로그인 세션 수 제한 |
| **사용자별 활성 디바이스 목록** | "어디서 로그인 중?" 표시 |
| **캐싱 서버 (본래 용도)** | DB 쿼리 결과 캐싱으로 부하 감소 |
| **Rate Limiting** | API 호출 횟수 제한 |

> [!tip] Redis의 본질
> Redis는 **In-Memory DB** = 디스크가 아닌 메모리에서 동작 → 매우 빠름.
> 보통 **Cache 서버**로 부르며, 모던 웹에서는 세션 관리에도 필수적.

## 8. AWS 매니지드 서비스 매핑

> [!important] AWS의 강점
> 위에서 다룬 모든 인프라 요소를 **매니지드 서비스로 제공** → 직접 구축/운영 부담 ❌

| 인프라 요소 | AWS 매니지드 서비스 |
|------------|-------------------|
| **로드밸런서** | **ALB** (Application Load Balancer) |
| **API Gateway** | **API Gateway** |
| **Redis (캐시/세션)** | **ElastiCache for Redis** |
| **JWT Secret Key 관리** | **Secrets Manager** / **Parameter Store** |
| **컨테이너 오케스트레이션** | **ECS** / **EKS**(Kubernetes) |
| **컨테이너 자동 스케일링** | Auto Scaling Group |
| **SSL 인증서** | **ACM** (Certificate Manager) |
| **DB** | **RDS**, Aurora, DynamoDB 등 |

### 가상화 환경에서의 도전

> [!note] 컨테이너 환경의 동적 스케일링
> Docker + Kubernetes 환경에서는 서버 수가 **자동으로 늘었다 줄었다** 함.
> → 새로 뜨는 인스턴스에 자동으로 키/설정을 배포해야 함
> → AWS Secrets Manager + ElastiCache 등 매니지드 서비스가 빛을 발함

```
                         Browser (SPA)
                            ╱   ╲
                           ╱     ╲
                          ╱       ╲
                         ▼         ▼
                  ┌──────────┐ ┌──────────────┐
                  │ Frontend │ │ API Gateway  │
                  │ (Next.js)│ │   (AWS)      │
                  │ via      │ └──┬───────┬──┘
                  │CloudFront│    │       │
                  └──────────┘    ▼       ▼
                              ┌──────┐ ┌──────┐
                              │ALB #1│ │ALB #2│

                                 │        │
                              ┌──┴──┐  ┌──┴──┐
                              │     │  │     │
                              ▼     ▼  ▼     ▼
                           ┌────┐┌────┐┌────┐┌────┐
                           │Auth││Auth││Ordr││Ordr│
                           │ #1 ││ #2 ││ #1 ││ #2 │
                           └─┬──┘└─┬──┘└─┬──┘└─┬──┘
                             │     │    │     │
                             ▼     ▼    ▼     ▼
```

## 10. 모던 웹 서비스의 단점/주의점

| 항목 | 위험 | 대응 |
|------|------|------|
| **API Gateway 단일 장애** | 다운 시 전체 서비스 마비 | 다중화, AWS 관리형 사용 |
| **JWT Secret Key 노출** | 1개 서버 해킹 → 전체 사칭 가능 | RSA 비대칭키 또는 Secrets Manager |
| **JWT 즉시 무효화 불가** | 만료까지 토큰 유효 | **Redis Blacklist** + 짧은 만료 + Refresh Token |
| **컨테이너 동적 스케일링** | 키/설정 배포 부담 | Secrets Manager 등 매니지드 서비스 |
| **분산 추적 어려움** | 요청이 여러 서비스 거침 | 분산 트레이싱 (X-Ray, Jaeger 등) |

## 핵심 요약

> [!summary]
> 1. 모던 웹: **Browser ↔ Frontend / Browser ↔ API Server** — 두 서버가 **완전 독립적으로 직접 호출**됨
> 2. 모든 통신은 **HTTPS** — 프론트/API 각자 SSL 인증서 필요
> 3. 프론트는 **응용 프로그램화(SPA)** — React/Vue/Next.js 등, 화면 전환 ≈ 응용 프로그램 화면 전환
> 4. 백엔드는 **REST API + JSON 응답** 전담 — Spring Boot가 사실상 표준
> 5. **Scale-Out 두 가지**: ① ALB로 수평 확장 / ② **마이크로서비스로 기능 분리** (실무는 둘 결합)
> 6. **API Gateway** = 단일 엔드포인트로 모든 API 통합 — **단일 장애점이라 반드시 다중화**
> 7. **Redis** = JWT 즉시 무효화(Blacklist), 활성 세션 관리, 캐싱의 핵심 — In-Memory DB
> 8. AWS 매핑: **ALB / API Gateway / ElastiCache(Redis) / Secrets Manager / ACM / ECS·EKS**
> 9. 컨테이너+K8s 환경의 동적 스케일링 → AWS 매니지드 서비스로 키/설정 배포 자동화
> 10. JWT의 한계(즉시 무효화 불가)는 **Redis Blacklist + 짧은 Access Token + Refresh Token** 조합으로 해결
