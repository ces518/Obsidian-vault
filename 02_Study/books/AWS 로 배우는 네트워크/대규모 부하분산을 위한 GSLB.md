## 개요

전 지구적으로 서비스되는 환경에서 **네트워크 전송 부하**를 분산하는 방법 — 핵심은 **GSLB(Global Server Load Balancing)**.
- 서버를 한 곳에만 두면 먼 지역 사용자는 느리다 → **전 세계에 서버를 분산 배치**
- GSLB는 **DNS(CNAME 체인)** 를 이용해 사용자를 가까운/빠른 서버로 유도
- 분산된 서버에 동일 콘텐츠를 동기화·자동 배포하는 인프라가 **CDN(Content Delivery Network)**
- 한 데이터센터 안의 [[L4 Proxy L7 Proxy|L4]]·[[연결이라는 착각과 AWS ALB|ALB]] 분산과는 **층위가 다름** (지구 규모 → 지역 서버 선택)
- AWS에서는 **CloudFront**(+ 정적 호스팅 **S3**)로 제공, 프론트 배포 자동화 서비스로 **Vercel / Amplify**

---

## 1. 출발점 — 부하의 종류와 글로벌 서비스의 문제

> [!note] 부하는 어디서 생기느냐에 따라 대응이 다르다
> 웹 서비스 기준으로 부하는 발생 지점에 따라 나뉘고, 그때그때 대응이 달라진다.

| 부하 지점 | 예시 |
|-----------|------|
| **애플리케이션 서버** | API 서버 수준의 부하 |
| **DB** | DB 쪽 부하 |
| **전송단 (웹서버)** | 리소스 송수신 = **네트워크 처리** 부하 |

> [!important] 인터넷은 전 지구적이다
> 내 웹서버가 한국에만 있으면 — 한국 사용자는 "빠르다", 미국 사용자는 거리·네트워크 속도 때문에 "느리다"고 느낀다.
> 글로벌 서비스에서는 **다른 대응**이 필요하고, 그게 GSLB.

---

## 2. GSLB란? — Global Server Load Balancing

> [!important] GSLB
> **G**lobal **S**erver **L**oad **B**alancing — 전 세계에 서버를 분산해 대규모로 부하를 분산하는 방법. **DNS를 많이 이용**한다.

- 특히 **네트워크 전송**에 관한 문제에 대응
- 여기서 "리소스"는 웹에서 가장 흔한 **파일** (이미지·멀티미디어 등)
- 서버를 한국·미국·독일에 따로 두고, 각 지역 사용자를 자기 지역 서버로 접속시킴
- 전제: **모든 서버의 콘텐츠가 동일**하다면 어느 서버로 접속하든 문제없다

## 3. CDN — Content Delivery Network

> [!important] CDN
> 여러 지역 서버를 **논리적 네트워크로 묶어** 콘텐츠를 동기화·관리하는 서비스.
> 관리자가 **한 곳에 업로드하면 CDN이 알아서 전 서버에 배포**한다.

### 왜 필요한가 — 수동 배포의 한계

```
서버 3개  → 홈페이지 업데이트 시 3번 반복 (그나마 할 만함)
서버 30개 → 똑같은 작업 30번... 기계적이고 너무 힘듦
```

> [!tip] CDN의 효용
> 서버를 하나의 네트워크로 묶고 한 번만 업로드 → 자동으로 쫙 배포. 서버가 많을수록 이득이 커진다.

## 4. DNS(CNAME) 기반 서버 선택 동작

> [!important] IP를 바로 주지 않고 Alias(CNAME)를 거친다
> DNS가 지역에 맞는 **Canonical Name** 을 응답하고, 그것을 다시 질의해 최종 IP를 얻는 **체인** 구조.

### 동작 예시 (강의의 `abc.com` 시나리오)

```
[한국 KT망 PC]
   │  "www.abc.com 주소 어디야?"
   ▼
[DNS] ── 응답: IP 아님, CNAME = a.www.abc.com
   │  "a.www.abc.com 주소는?"
   ▼
[DNS] ── 응답: 3.3.3.3
   │
   ▼
[한국(KT망) 서버 3.3.3.3 로 접속]  → 같은 망이면 매우 빠름

[미국 사용자]
   www.abc.com → CNAME c.www.abc.com → 미국 서버 IP → 미국 서버로 접속
```

| 지역 | CNAME 응답 | 접속 서버 |
|------|-----------|-----------|
| 한국(KT망) | `a.www.abc.com` | 한국 서버 (`3.3.3.3`) |
| 미국 | `c.www.abc.com` | 미국 서버 |

> [!note] 게임에서 흔하다
> 게임은 접속 환경에서 **링크 속도가 가장 좋은 지점**으로 항상 유도하도록 되어 있다.

## 5. 기존 L4 / ALB 분산과의 차이

> [!important] 층위가 다르다
> GSLB는 **서버 수준에서 전 세계 단위**로 분산. L4/ALB는 그렇게 나뉜 **서버 내부**의 분산.

```
[전 세계 사용자]
      │  ← GSLB (DNS 기반, 지역 서버 선택)
      ▼
 ┌────────┬────────┬────────┐
[한국]   [미국]   [독일]      ← 각 지역 서버군
   │
   ▼  ← 여기서 다시 ALB / DB 클러스터링 동작
 [웹]·[API]·[DB]
```

관련: [[L4 Proxy L7 Proxy]] · [[연결이라는 착각과 AWS ALB]] · [[AWS ALB NLB 를 이용한 부하분산]]

## 6. 실제 사례 — 네이버 / Akamai / 글로벌 기업

> [!note] 네이버도 이렇게 했다 (과거 한때)
> 구글 DNS에 네이버 주소를 물으면 **Alias** → 다른 주소 → **Akamai**(CDN 서비스) 서버로 연결되는 형태.

- 네이버 정도 규모면 다 이렇게 서비스
- 구글·Meta·Facebook 같이 전 세계 상대 기업은 당연히 사용 → **대규모 서비스는 어쩔 수 없다**

---

## 7. 딜레마 — 비용과 운영 부담

> [!caution] GSLB/CDN은 공짜가 아니다
> 좋은 건 알겠지만 배포 편의성·운영 측면에서 부담이 있다.

| 부담 | 내용 |
|------|------|
| **가입/비용** | CDN 서비스 별도 가입 + 비용 |
| **구축** | 여러 지역에 서버를 두고 직접 구축 |
| **선택** | 직접 구축 vs 관리형, 어떤 게 싸고 좋은지 그때그때 따져야 |

---

## 8. AWS의 CDN — CloudFront (+ S3)

> [!important] AWS의 CDN = `CloudFront`
> 프론트(이미지·멀티미디어 리소스) 코드를 배포하면 **자동으로 전 세계에 퍼뜨려** 준다.

- 사소한 서비스라도 전 세계에 쉽게 퍼뜨려 누구나 빠르게 접속하게 하고 싶다 → CloudFront가 편함
- 정적 호스팅 **S3** 와 **CloudFront를 묶어서** 쓰기도 함 → CDN 구성을 한 방에 처리

---

## 9. 빠른 배포 트렌드 — Vercel / Amplify

> [!note] 만들고 없애기 쉬운 시대
> 마케팅용 한시적 페이지처럼 빨리 만들고 빨리 닫는 흐름(+ 바이브코딩) → **CDN 연결까지 자동화**한 서비스 등장.

| 서비스 | 설명 |
|--------|------|
| **Vercel** | 웹 프론트 배포 시 자동으로 전 세계 배포 (강의 시점 "2024년 2월 기준" 인기) |
| **AWS Amplify** | Vercel 대응 격, 서버리스·백엔드 운영 등도 지원 |

> [!tip] 결론
> 모던 **3-tier**의 **프론트엔드** 배포는 Vercel이든 Amplify든 이런 서비스를 쓰면 앞서 말한 **GSLB가 자연스럽게 적용**된다고 보면 된다.

| 기억할 것 | 내용 |
|-----------|------|
| **GSLB 정식** | Global Server Load Balancing — 전 세계 서버 분산, **DNS 이용** |
| **해결 문제** | 글로벌 사용자별 거리·네트워크 속도 차이 (네트워크 전송 부하) |

| **프론트 배포 자동화** | **Vercel**, **AWS Amplify** → GSLB 자동 적용 |

## 질문 / 헷갈리는 점

- 확인 필요: GSLB의 서버 선택 기준이 "지리적 거리"인지 "실측 링크 속도/RTT"인지 (강의는 둘 다 언급)
- 확인 필요: CNAME 체인 방식 외에 Anycast 기반 GSLB(예: AWS Global Accelerator)와의 차이
