# 개요
분산 메시지 큐(Distributed Message Queue)는 **서로 다른 시스템 컴포넌트 간의 비동기 통신을 위한 중간 계층**이다.

구성 요소는 크게 두 가지이다.

- **Producer** : 메시지를 생성하여 큐에 전달
    
- **Consumer** : 큐에서 메시지를 가져와 처리
    
기본 동작은 매우 단순하다.

실제 시스템에서는 다음과 같은 이유로 **분산 메시지 큐 시스템**이 필요해진다.

- 시스템 간 **결합도 감소**
    
- **트래픽 버퍼링**
    
- **비동기 처리**
    
- **확장성 확보**

## 메세지 큐와 이벤트 스트리밍 플랫폼
|구분|메시지 큐|이벤트 스트리밍|
|---|---|---|
|목적|메시지 전달|이벤트 로그 저장|
|메시지 소비|보통 1회|반복 소비 가능|
|데이터 보관|짧음|장기 보관|
|대표 시스템|RabbitMQ, ActiveMQ|Kafka, Pulsar|
최근에는 경계가 점점 흐려지고 있다.

예:
Kafka → 메시지 큐처럼 사용  
RabbitMQ → 스트리밍 기능 지원

## 대표적인 분산 메세지 큐 시스템
- Apache Kafka
    
- Apache Pulsar
    
- RabbitMQ
    
- ActiveMQ
    
- RocketMQ
    
- ZeroMQ

|시스템|특징|
|---|---|
|Kafka|로그 기반 스트리밍|

# 요구 사항
## 기능 요구사항
1. Producer가 메시지 전송 가능  
2. Consumer가 메시지 수신 가능  
3. 메시지 **반복 소비 가능**  
4. 메시지 **단일 소비 설정 가능**  
5. 메시지 **오래된 데이터 삭제 가능**  
6. 메시지 **순서 보장**  
7. **3가지 전달 보장 방식 지원**

|방식|의미|
|---|---|
|At most once|최대 1번 전달 (유실 가능)|
|At least once|최소 1번 전달 (중복 가능)|
|Exactly once|정확히 1번 전달|
## 비기능 요구사항
1. 높은 대역폭 또는 낮은 지연 선택 가능
2. 규모 확장성
	- Partition
	- Broker cluster
	- Consumer scaling
3. 지속성 및 내구성
	- Disk persistence
	- Replication
> 요구사항 전반을 살펴보았을때, Kafka 설계 문제에 가깝다.
> 전통 MQ 보다는, Event Streaming Platform 설계

# 전통적 메세지 큐와 다른점
이 장에서 설계하는 시스템은 **RabbitMQ 같은 전통적인 메시지 큐와 다르게**  
**이벤트 스트리밍 플랫폼(Kafka/Pulsar)에 가까운 기능**을 포함한다.
> [!note]
> 핵심 차이는 메세지 보관과 소비 방식
## 1. 메세지 보관 방식 차이
### 전통적 메세지 큐
전통적인 메시지 큐는 메시지를 **소비하면 바로 삭제**한다.

특징
- 메시지는 **전달 목적**
- 소비 후 **큐에서 제거**
- 장기 보관을 고려하지 않음
    
대표 시스템
- RabbitMQ
- ActiveMQ
- RocketMQ
- ZeroMQ

### 이벤트 스트리밍 플랫폼
이 장에서 설계하는 메세지큐는 **메세지를 장기간 보관**한다.

특징
- 메시지 **append-only 로그 저장**
- **장기 보관 가능**
- **여러 번 소비 가능**
    
대표 시스템
- Kafka
- Pulsar

## 2. 메세지 반복 소비
### 전통적 메세지 큐
메시지는 **한 번만 소비 가능**

### 이벤트 스트리밍 플랫폼
메시지는 **여러 소비자가 반복 소비 가능** 하다.

## 3. 메세지 순서 보장
### 전통적 메세지 큐
메시지 순서를 **보장하지 않는 경우가 많다**

### 설계 해야하는 이벤트 스트리밍 플랫폼
생산 순서를 보장한다

보통 구현 방식
- **Partition FIFO**
- **Offset 기반 소비**

## 4. 데이터 보관 기간
### 전통적 메세지 큐
- 메모리 중심
- 처리 후 삭제
- 장기 저장 없음
### 이벤트 스트리밍 플랫폼
- 디스크 기반 저장
- **Retention 정책**

# 개략적 설계안
![[Pasted image 20260308154437.png]]
메세지 큐 시스템의 **기본 구성 요소**
1. 생산자
	1. 메세지를 생성
	2. 메세지를 큐에 publish
2. 브로커
	1. 메세지를 저장
	2. 생산자와 소비자를 **비동기적으로 연결**
3. 소비자
	1. 메세지를 구독
	2. 메세지를 소비
## 메시지 모델
메세지 큐에는 대표적으로 2가지 **메세지 전달 모델**이 있다.
1. 일대일 모델
2. 구독-발행 모델

### 일대일 모델
![[Pasted image 20260308154813.png]]
전통적인 메세지 큐에서 많이 사용하는 모델이다
```
Producer → Queue → Consumer
```
특징
- 메시지는 **단 하나의 소비자만 가져감**
- 소비 후 메시지는 **삭제** 한다
### 구독-발행 모델
![[Pasted image 20260308154905.png]]
이 모델에서는 **하나의 메시지를 여러 소비자가 받을 수 있다.**
여기서 등장하는 개념이 **Topic**이다.

### Topic
- 메시지를 **주제별로 분류하는 단위**

```
Topic: order-event  
Topic: payment-event  
Topic: user-event

Producer → Topic → Consumer1
                    Consumer2
                    Consumer3
```

## 토픽, 파티션, 브로커
대규모 메시지 큐 시스템에서는 **토픽만으로는 확장이 어렵다.**
그래서 등장하는 것이 **Partition**이다.

### Topic
메시지의 **논리적 분류 단위**
```
Topic: Order  
Topic: Payment
```
### Partition
토픽을 **여러 개의 작은 로그로 분할한 것**
```
Topic A  
  
Partition 1  
Partition 2  
Partition 3
```
목적
- **수평 확장**
- 병렬 처리
### Broker
파티션을 저장하는 **서버**
```
Broker 1 → Partition 1  
Broker 2 → Partition 2  
Broker 3 → Partition 3

Cluster  
   ├─ Broker 1  
   ├─ Broker 2  
   └─ Broker 3
```

## 메세지 저장 구조
각 파티션은 **FIFO 로그 구조**로 동작한다.
```
Partition

Offset 0 → Message A
Offset 1 → Message B
Offset 2 → Message C
```

특징
- append-only log
- 순서 보장
- offset 기반 접근

## 메세지 파티션 분배
Producer는 메시지를 **특정 파티션으로 전송**한다.
- Key 기반 분배
	- 같은 키 -> 같은 파티션
	- 순서 보장
- Random 분배
	- 키가 없을 경우

## 소비자 그룹
![[Pasted image 20260308155555.png]]
여러 Consumer가 **하나의 Topic을 병렬 처리**할 때 사용하는 개념이다.
```
Topic A

Partition 1
Partition 2
Partition 3

Consumer 1 → Partition 1
Consumer 2 → Partition 2
Consumer 3 → Partition 3
```
특징
- 토픽을 구독한 소비자는 **하나 이상의 파티션에서 메시지를 가져온다.**
- 소비자들은 **토픽의 여러 파티션을 나누어 담당**
- 메시지를 **협력하여 소비**
- **병렬 처리 가능**

장점
- 병렬 처리
- 확장성

### 메세지 순서 보장 문제
같은 파티션을 여러 소비자가 읽으면 **순서가 깨질 수 있다.**
해결 방법은 **한 파티션은 한 소비자만 읽도록 제한** 
- **파티션 내부 순서 보장**
- 병렬 처리 가능
이 규칙이 **Kafka 설계의 핵심 규칙**

소비자 수 ≤ 파티션 수:
```
Partition 1 → Consumer 1
Partition 2 → Consumer 2
Partition 3 → Consumer 3
=> 정상 도작
```

소비자 수 > 파티션 수:
```
Partition 1 → Consumer 1
Partition 2 → Consumer 2
Consumer 3 → Idle
=> 일부 소비자는 토픽에서 데이터를 읽지 못함
```

### 소비자 그룹의 목적 정리
소비자 그룹의 목적은 **확장성과 메시지 모델 지원**이다.

|기능|설명|
|---|---|
|병렬 처리|여러 소비자가 메시지 처리|
|확장성|소비자 수 증가 가능|
|순서 보장|파티션 단위 소비|
|모델 지원|Pub/Sub + Queue|

# 상세 설계
시스템은 **고성능 메시지 처리**를 위해 다음 세 가지 설계 결정
1. 디스크 기반 저장 구조
2. 메세지 복사 최소화
3. 일괄 처리

## 디스크 기반 저장 구조
메시지는 **디스크 기반 자료구조(on-disk data structure)** 에 저장한다.

이유
- 디스크는 **순차 읽기/쓰기 성능이 매우 높다**
- OS의 **디스크 캐시 전략**을 활용할 수 있다

특히 **append-only 로그 구조**가 핵심이다.

특징
- 새로운 메시지는 **파일 끝에 append**
- 수정(update) 없음
- 삭제(delete) 없음

|장점|설명|
|---|---|
|높은 처리량|sequential write|
|간단한 구조|append-only|
|데이터 무결성|로그 기반|
## 메세지 복사 최소화

메시지는 **생산자 → 소비자 전달 과정에서 수정되지 않는다.**
메시지 구조를 **수정 없이 그대로 전달 가능**하도록 설계한다.

목적
- **메모리 복사 비용 감소**
- 네트워크 전송 비용 감소
- 높은 throughput 확보

## 배치 처리
시스템은 **batch 중심으로 동작하도록 설계한다.**

이유:
작은 I/O 요청이 많으면 성능이 급격히 떨어진다.
```
Small IO × 1,000,000
```

보다
```
Batch IO × 1,000
```
가 훨씬 효율적이다.

> [!note]
> 메세지를 batch 로 전송하고, batch 단위로 저장한뒤 batch 단위로 읽도록 설계한다

# 데이터 저장소
## 트래픽 패턴
1. 읽기와 쓰기가 모두 빈번하다
2. 갱신/삭제는 발생하지 않는다
3. 대부분 순차 읽기/쓰기이다

read/write 가 모두 강한 구조이며, append-only 로 추가된다.
장기 보관 가능한 스트리밍 플랫폼이라 update/delete 중심 저장소가 아니다.
random access 보다 sequencial access 중심이다

## 선택지 1: 데이터 베이스
가장 먼저 떠올릴 수 있는 선택지는 **일반 데이터베이스**다.
1. 관계형 데이터 베이스
2. NoSQL 데이터 베이스

기능적으로 저장은 가능하지만, **읽기와 쓰기가 동시에 대규모로 빈번하게 발생**한다
메세지 큐는 **매우 높은 처리량**이 중요한데, 데이터베이스는 이런 패턴에서 **병목**이 되기 쉽다

## 선택지 2: WAL (Write-Ahead Log)
책이 추천하는 실제 선택지는 **WAL**이다.

**WAL**
- **append-only 일반 파일**
- 새 데이터는 파일 끝에 계속 추가
- 기존 데이터를 수정하지 않음
    
대표 사례
- MySQL redo log
- ZooKeeper
- Kafka 로그 저장 구조

## WAL 이 적합한 이유 ?
### 1. 접근 패턴에 잘 맞음
WAL은 읽기/쓰기 모두 **순차적 접근**에 강하다.

- 쓰기: 파일 끝에 append
    
- 읽기: offset 기준 순차 read
    
즉 메시지 큐의 트래픽 패턴과 거의 일치한다.

### 2. 디스크 성능 활용 가능
일반적으로 디스크는 느리다고 생각하기 쉽지만,  
그건 **무작위 접근(random I/O)** 기준이다.

이 장에서는 오히려
- 순차 쓰기
- 순차 읽기
- append-only
    
패턴을 적극 활용하므로  
**회전식 디스크(rotational disk)도 충분히 높은 성능**을 낼 수 있다고 본다.

### 3. 비용 효율적
- 대용량 저장이 필요하고
- 메시지를 장기간 보관해야 하므로
    
메모리 기반보다는 **디스크 기반 저장소가 훨씬 현실적**이다.

## 파티션 로그와 오프셋
WAL은 토픽 전체 하나로 관리하는 게 아니라  
보통 **파티션 단위 로그**로 운영된다.

### 동작 방식

- 새로운 메시지는 항상 **파티션 로그의 꼬리(tail)** 에 추가된다
    
- 메시지가 추가될수록 **offset이 증가**한다

```
Partition-1
offset 0
offset 1
offset 2
offset 3
...
```
- **로그 파일 줄 번호(line number)** 를 offset처럼 볼 수도 있다

![[Pasted image 20260308161359.png]]

## 세그먼트 (segment) 로 나누는 이유
로그 파일 하나를 무한정 키울 수는 없으므로  
**세그먼트 단위로 분리**한다.

### 구조

- 하나의 파티션 = 여러 개의 세그먼트 파일
    
- 새 메시지는 항상 **활성(active) 세그먼트**에 기록
    
- 일정 크기 한계를 넘으면 새 활성 세그먼트 생성
    
- 이전 세그먼트는 **비활성(inactive)** 상태가 됨

![[Pasted image 20260308161601.png]]
### 세그먼트 상태
1. 활성 세그먼트
	1. 현재 append 가 일어나는 파일
2. 비활성 세그먼트
	1. 더 이상 쓰지 않음
	2. 읽기 만 처리
3. 오래된 세그먼트
	1. 보관 기한 만료 또는 용량 한계 초과시 삭제 가능

### 삭제 방식
삭제는 메시지 단건 삭제보다  **세그먼트 단위 삭제**가 핵심이다.
- 메시지 하나를 지우는 것이 아니라
    
- 오래된 세그먼트 파일 전체를 제거
    

이 방식이 좋은 이유는

- 구현이 단순하고
    
- 성능 오버헤드가 적고
    
- append-only 구조를 유지할 수 있기 때문이다.

## 디스크 성능 관련 유의사항
디스크는 **무조건 느리다는 편견**이 있다.

하지만 실제로는

- **무작위 접근**에서는 느리지만
    
- **순차 접근**에서는 매우 강력하다
    

특히

- RAID 기반 현대 디스크
    
- OS page cache / aggressive disk caching
    
를 활용하면  수백 MB/s 수준의 읽기/쓰기 성능도 가능하다고 본다.

즉 메시지 큐처럼

- append-only
    
- sequential I/O
    
- batch-friendly
    
한 시스템에는 디스크 기반 WAL이 매우 잘 맞는다.

# 메세지 자료 구조
메시지 자료 구조는 **생산자(Producer), 메시지 큐(Broker), 소비자(Consumer) 사이의 계약(contract)** 이다
## 메세지 스키마
| 필드        | 설명              |
| --------- | --------------- |
| key       | 메시지 파티션 결정      |
| value     | 실제 메시지 내용       |
| topic     | 메시지가 속한 토픽      |
| partition | 메시지가 저장된 파티션    |
| offset    | 파티션 내 메시지 위치    |
| timestamp | 메시지 생성 또는 저장 시간 |
| size      | 메시지 크기          |
| crc       | 데이터 무결성 검사      |

## 메세지 키
메시지 키는 **어느 파티션에 메시지를 저장할지 결정**할 때 사용된다.
```
partition = hash(key) % numPartitions
```
동일 user-id 메세지는 **항상 같은 파티션으로 이동** 된다
키를 잘 정의하면
- **메시지 순서 보장**
- **데이터 locality 확보**

## 메세지 값
메시지 값은 **실제 데이터(payload)** 이다.

```
{
  "orderId": 1234,
  "userId": 99,
  "amount": 12000
}
```

메시지 값의 형태
- JSON
- Binary
- Avro
- Protobuf
- 압축 데이터

## 메세지 기타 필드
- 메세지 위치 정보
	- topic
	- partition
	- offset (파티션 내 메세지 위치)
- 타임스탬프
	- 메세지 생성 시점 or 저장된 시점
- 메세지 크기
- 무결성 검사
	- CRC

# 일괄 처리
일괄 처리(Batching)는 **여러 메시지를 모아서 한 번에 처리하는 방식**이다.
일괄 처리는 **시스템 성능 개선의 핵심 기술**이다.
1. 네트워크 왕복 비용 감소
2. 디스크 순차 쓰기 성능 향상
3. 운영체제 디스크 캐시 활용

## 처리량 과 지연시간 트레이드 오프
처리량 : 초당 처리 메세지 수
지연시간 : 메세지가 소비되기 까지 걸리는 시간
> 이 둘은 **동시에 최적화하기 어렵다.**

|전략|결과|
|---|---|
|큰 batch|throughput ↑ latency ↑|
|작은 batch|throughput ↓ latency ↓|
**낮은 지연이 중요한 시스템**
- RabbitMQ
- ActiveMQ
> small batch 설정으로 메세지를 빠르게 전달

**높은 처리량이 중요한 시스템**
- Kafka
- Pulsar
> large batch 설정으로 대규모 데이터 처리

### 처리량 보완 방법
일괄 처리 크기를 줄이면 Sequential write throughput ↓ 문제가 발생할 수 있음
이 경우 **Partition 수를 증가 (병렬성) 로 처리량을 확보**해야 한다

# 생산자 측 흐름
생산자가 특정 **토픽의 특정 파티션**으로 메시지를 보내려 할 때  
어떤 브로커로 연결해야 하는지가 문제다.

이를 해결하기 위해 **라우팅 계층(routing layer)** 개념이 등장한다.

생산자는 메시지를 직접 브로커에 보내지 않고  **라우팅 계층을 통해 적절한 브로커로 전달**한다.
![[Pasted image 20260308163409.png]]
중요한점:
> 메시지는 **항상 파티션의 리더(leader) 브로커로 전송**된다.

## 메세지 전송 과정
1. 생상자는 메세지를 라우팅 계층으로 보낸다
2. 라우팅 계층은 메타 저장소를 통해 **사본 분산 계획(replica distribution plan)** 을 읽는다.
	1. 파티션 위치, 리더 브로커, 팔로워 브로커 정보가 포함됨
	2. 이 정보를 캐시에 저장한다
3. 라우팅 계층은 메세지를 **파티션의 리더 브로커로 전송**한다.
4. 리더 브로커가 메세지를 받는다
	1. 메세지를 먼저 저장하고, **다른 팔로워 브로커로 복제** 한다
5. 충분한 수의 사본이 동기화 되면 리더는 메세지를 커밋한다
	1. 커밋 -> 디스크 기록
	2. 이 시점 부터 소비자가 소비 가능하다
6. 생산자 에게 응답을 반환한다

## 기존 설계의 문제
1. 네트워크 홉 증가
	1. 라우팅 계층 때문에 네트워크 홉이 증가해 지연이 증가한다
2. 일괄 처리 고려가 안되어 있다
	1. 라우팅 계층 설계는 배치 처리 고려가 되어 있지 않음

## 개선된 설계 방향
![[Pasted image 20260308163931.png]]
라우팅 계층을 생산자 내부로 이동 시킨다
```
Producer Client Library
   ├ Routing logic
   └ Buffer (Batching)
```
> 이 구조가 실제 **Kafka Producer 아키텍처**

# 소비자 측 흐름
소비자는 **특정 파티션(partition)의 오프셋(offset)을 기준으로 메시지를 가져온다.**
1. 특정 파티션을 담당하고
2. 마지막으로 읽은 offset 이후 메세지를
3. 묶음 (batch) 형태로 조회한다
![[Pasted image 20260308210551.png]]

## 푸시와 풀 모델
메세지 큐에서 중요한 설계 선택 중 하나는 Push vs Pull 이다

### 푸시 모델
브로커가 **메세지를 즉시 전달**한다

**장점**
- 낮은 지연

**단점**
- 소비자 과부하 가능성
	- 생산 속도 > 소비속도
- 처리 속도 제어 불가
	- 데이터 전송 속도가 생산자의 속도에 의해 결정된다
	- 소비자가 항상 최대 처리량 대비 자원 확보를 해야 함

### 풀 모델
소비자가 **필요할 때 데이터를 요청**한다

**장점**
- 소비자가 처리 속도 제어
- 확장성
- 일괄 처리에 유리함
	- fetch(offset, max_messages = 100)

**단점**
- 브로커에 메시지가 없을때도 소비자가 계속 요청한다
	- Long Polling 으로 해결
	- 소비자 요청시 Broker wait (timeout)

### 풀 모델 동작 방식
![[Pasted image 20260308211052.png]]
1. 소비자가 그룹에 참여
2. 코디네이터가 파티션을 할당
3. 소비자가 메세지 fetch
4. 데이터 처리
5. offset 갱신

## 대부분 메세지 큐가 풀 모델 채택 이유
1. 소비자가 처리 속도 제어 가능  
2. batch 처리 가능  
3. backpressure 자연스럽게 구현  
4. 확장성 확보

## 소비자 재조정
**어떤 소비자가 어떤 파티션을 담당**할지 다시 결정하는 과정

### 재조정 발생 상황
1. 새로운 소비자가 합류
2. 기존 소비자가 그룹에서 떠남
3. 소비자 장애 발생
	1. 파티션 재배치 필요
4. 파티션 수 변경
	1. 파티션 재분배 필요

# 상태 저장소
상태 저장소는 메시지 본문을 저장하는 곳이 아니라,  
**소비자 그룹이 어디까지 읽었고 현재 어떤 파티션을 누가 담당하는지** 같은  
**운영 상태(state)** 를 저장하는 저장소다.

메시지 큐 브로커 입장에서 상태 저장소는

- **소비자-파티션 배치 정보**
- **소비자 그룹별 마지막 소비 오프셋**
    
을 저장하는 역할을 한다.

## 상태 저장소에 저장되는 정보
1. 소비자에 대한 파티션 배치 관계
	1. 어떤 소비자가 어떤 파티션을 담당하는지 
2. 소비자 그룹별 마지막 소비 오프셋
	1. 각 소비자 그룹이 각 파티션에서 **마지막으로 읽어간 메시지 위치**를 저장

![[Pasted image 20260308212427.png]]

## 상태 저장소가 중요한 이유
상태 저장소가 중요한 이유는 **소비 재개(resume)** 때문이다.

예를 들어 그룹-1의 소비자가 offset 6까지 읽고 장애가 났다면,  
같은 그룹의 다른 소비자가 그 파티션을 넘겨받아 **offset 7부터 이어서 읽을 수 있어야 한다.**

즉 상태 저장소가 없으면:

- 어디까지 읽었는지 알 수 없고
    
- 중복 소비 또는 메시지 누락이 발생할 수 있다.
    

그래서 상태 저장소는 사실상  
**Consumer Group의 진행 상황 체크포인트(checkpoint)** 역할을 한다.

## 상태 데이터의 접근 패턴
이 부분이 설계상 중요하다
1. 읽기와 쓰기가 빈번하다
2. 데이터 양은 많지 않다
3. 갱신은 빈번하지만 삭제는 거의 없다
4. 읽기/쓰기 패턴이 무작위적이다
5. 일관성이 매우 중요하다

> 상태 저장소는  **고성능도 중요하지만, 그보다 정확한 상태 관리와 일관성 보장**이 훨씬 중요하다.

상태 저장소에는 **주키퍼(Apache ZooKeeper) 같은 키-값 저장소**가 적합하다.
- 데이터 양은 작음
- 읽기/쓰기 빈번
- random access 패턴
- 높은 일관성 요구

# 메타데이터 저장소
메타데이터 저장소는 **메시지 큐 시스템의 설정 정보와 구조 정보**를 저장하는 저장소이다.
메시지 본문이나 소비 상태가 아니라 **토픽과 파티션에 대한 시스템 구성 정보**를 저장한다.
- 토픽 설정
- 파티션 수
- 메시지 보관 기간(retention)
- 사본 분산 계획(replica distribution plan)

## 메타데이터 특성
1. 변경이 자주 발생하지 않는다
2. 데이터 양이 적다
3. 강한 일관성이 필요하다

| 요구사항   | 설명    |
| ------ | ----- |
| 데이터 크기 | 작음    |
| 읽기 빈도  | 높음    |
| 쓰기 빈도  | 낮음    |
| 일관성    | 매우 중요 |
> 이 특성에 맞는 저장소로 **ZooKeeper** 같은 **분산 키-값 저장소**가 적합하다.

![[Pasted image 20260308212900.png]]

## ZooKeeper 의 역할
ZooKeeper는 분산 시스템에서 다음 역할을 한다.
- **분산 설정 저장소**
- **동기화 서비스**
- **이름 서비스**
- **리더 선출 지원**
    
메시지 큐 설계에서는 다음 기능에 사용된다.
1. 메타데이터 저장
2. 상태 저장소 구현
3. 브로커 클러스터 **리더 선출 지원**

**기존 구조**

```
Broker
 ├ Data Storage
 ├ State Storage
 └ Metadata Storage
```

**ZooKeeper 기반 구조**

```
Producer → Broker → Consumer

Broker
 └ Data Storage

ZooKeeper
 ├ Metadata Storage
 ├ State Storage
 └ Coordination Service
```

# 복제

분산 시스템에서는 **하드웨어 장애가 매우 흔하다.**

예

- 디스크 손상
    
- 서버 장애
    
- 네트워크 문제
    

이런 장애가 발생하면 메시지가 저장된 노드의 데이터가 **영구적으로 사라질 수 있다.**

따라서 메시지 큐 시스템은 **높은 가용성(High Availability)** 을 확보하기 위해  
**데이터 복제(replication)** 를 사용한다.

## 파티션 복제 구조
메시지는 **파티션 단위로 복제된다.**

각 파티션은 **여러 개의 사본(replica)** 을 가진다.

![[Pasted image 20260308213648.png]]
> **각 사본은 서로 다른 브로커 노드에 분산 되어 저장**된다.

## 리더와 팔로워
각 파티션의 사본 중 하나는 **리더(Leader)** 이고  
나머지는 **팔로워(Follower)** 이다.

### 리더의 역할
- 생산자로부터 메시지를 받음
- 메시지를 로그에 기록
- 팔로워에게 메시지 복제
> 쓰기 요청은 항상 리더에게만 전달 된다

### 팔로워의 역할
리더의 **메세지를 지속적으로 읽어와 동기화** 한다

## 메세지 전송 흐름

```
Producer
   ↓
Partition Leader
   ↓
Followers replication
```

1. 생산자가 메시지를 **리더 파티션**에 전송  
2. 리더가 메시지를 로그에 기록  
3. 팔로워가 리더에서 메시지를 가져와 복제  
4. 일정 조건이 만족되면 리더가 **ACK 반환**
	- 동기화 된 사본 수가 **특정 임계 값**을 넘을 때

## 사본 분산 계획
각 파티션의 사본이 어떤 브로커에 배치되는지를  
**사본 분산 계획**이라고 한다.

```
Topic-A Partition-1
Leader → Broker-1
Follower → Broker-2
Follower → Broker-3

Topic-A Partition-2
Leader → Broker-2
Follower → Broker-3
Follower → Broker-4

Topic-B Partition-1
Leader → Broker-3
Follower → Broker-4
Follower → Broker-1
```
사본 분산 계획은 **브로커 클러스터의 리더 노드**가 만든다
1. 조정 서비스(ZooKeeper)가 **브로커 리더를 선출**  
2. 리더 브로커가 **Replica Distribution Plan 생성**  
3. 계획을 **메타데이터 저장소에 기록**  
4. 다른 브로커는 해당 계획을 따라 동작

# 사본 동기화
분산 메시지 큐에서 메시지는 **여러 사본(replica)** 으로 복제된다.
> 어떤 사본을 동기화 된 상태로 볼 것인가 ? 라는 문제가 발생한다

이를 해결하기 위해 등장하는 개념 **ISR(In Sync Replicas)**

## ISR(In-Sync Replicas)
리더와 충분히 동기화된 상태의 사본 집합을 의미한다
```
ISR = { leader + follower replicas that are caught up }
```
- **리더는 항상 ISR에 포함**
- 리더와 충분히 가까운 상태의 사본만 ISR로 인정

### 판별 기준
ISR 여부는 **리더와 사본 사이의 메시지 차이(lag)** 로 판단한다.
```
replica.lag.max.messages = 4
```
> 리더와 follower 사이의 메시지 차이가 **4 미만이면 ISR** 이다.

**예시**

```
// 리더
10 11 12 13 14 15

// 사본
Replica-2
10 11 12 13 14

-> 차이 = 1 이므로 ISR
```
![[Pasted image 20260308214738.png]]

## 합의 오프셋
ISR과 함께 중요한 개념이 **합의 오프셋(committed offset)** 이다.

합의 오프셋이 의미하는 것은

> **ISR 집합 내 모든 사본에 복제 완료된 마지막 메시지 위치** 이다

```
Leader
10 11 12 13 14 15

Replica-2 → 14
Replica-3 → 13

Committed offset = 13
```
> 0 ~ 13 메세지는 모든 ISR 에 복제 완료


## ISR 이 필요한 이유 ?
모든 replica 동기화 이후 ACK 를 하면 좋겠지만, 느린 사본 하나 때문에 전체 파티션 성능이 저하될 수 있다

ISR 은 아래 두 가지 사이의 **균형점** 이다.

| 요소          | 설명        |
| ----------- | --------- |
| Durability  | 데이터 손실 방지 |
| Performance | 시스템 처리 속도 |
## ACK 설정과 ISR
생산자는 메시지 수신 확인(ACK)을 **ISR 기준으로 설정**할 수 있다.

### ACK = all
![[Pasted image 20260308215402.png]]
```
ACK after all ISR replicated
```

모든 ISR 이 메세지를 받은 후 ACK
가장 안전하지만, 응답 지연이 증가한다

### ACK = 1
![[Pasted image 20260308215411.png]]
```
ACK after leader write
```

리더가 메세지를 저장하면 ACK
응답이 빠르지만, 리더 장애시 메세지가 유실될 수 있다

### ACK = 0
![[Pasted image 20260308215421.png]]
```
No ACK
```

생산자가 ACK 를 기다리지 않으며, 가장 빠르지만 메세지가 유실 될 수 있다

| ACK 설정    | 안정성   | 성능    |
| --------- | ----- | ----- |
| ACK = all | 가장 안전 | 느림    |
| ACK = 1   | 중간    | 빠름    |
| ACK = 0   | 낮음    | 가장 빠름 |
## 소비자 읽기 전략
가장 단순한 구성은 소**비자가 리더에서 메세지를 읽는 것**이다
- 설계가 단순하다
- 소비자 수가 제한된다
	- 특정 파티션 메세지는 같은 소비자 그룹내에서 한 소비자만 읽을 수 있어 리더에 대한 연결이 많지 않음
	- 인기있는 토픽이 아니라면 리더 사본에 대한 연결 수가 많지 않음
- 파티션 기반 확장이 가능하다
	- 인기있는 토픽의 경우 파티션/소비자 수 늘려 확장

### 예외 상황
소비자가 다른 지역 데이터센터에 있다면, 지역적으로 가까운 ISR 사본에서 메세지를 읽을 수 있다

# 규모 확장성
- 생산자
- 소비자
- 브로커
- 파티션

## 생산자
생산자의 규모 확장성은 새로운 생산자를 추가/삭제 함으로 인해 쉽게 달성 가능하다

## 소비자
**소비자 그룹과 재조정 메커니즘** 덕분에 확장이 가능하다
소비자 그룹끼리 서로 독립적이며, 같은 구룹 내에서 소비자가 늘어나면 재조정이 일어난다.
- 파티션 재할당 과정까지 이뤄짐

## 브로커
![[Pasted image 20260308225651.png]]

**브로커 3 장애 발생**시, 브로커 3에 있는 모든 파티션 사본이 사라진다
**replication factor 가 줄어든 불안정 상태**가 됨
### 브로커 컨트롤러
브로커 컨트롤러는 장애를 감지한 뒤 **새로운 파티션 분산 계획**을 만든다
부족해진 사본수를 메우기 위해 **다른 브로커에 새 replica 를 배치**한다
- 새롭게 추가된 사본은 처음에는 **단순 사본**으로 들어오고
- 리더의 로그를 점점 따라잡으면서 정상 replica 가 된다

### 브로커 결함 내성 고려할 점
1. 몇 개 사본까지 반영 되어야 커밋으로 볼 것인가 ?
	1. 많이 반영될수록 안전하지만, 응답 지연은 증가한다
2. 같은 브로커에 여러 사본을 두면 안된다
	1. 같은 노드에 모든 replica 가 있으면, 노드가 죽는 순간 파티션 전체가 사라진다
3. 가능하면 여러 데이터 센터에 분산하는 것이 안전하다
	1. 복제 비용 증가, 지연 증가, 운영 복잡성 증가를 고려해야 한다

### 브로커 규모 확장성
가장 단순한 방법
- 브로커 추가/삭제 시
- 사본을 재배치 하는 방법

더 나은 방법
- 일시적으로 설정된 replica 보다 더 많은 사본을 허용하고
- 점진적으로 균형을 맞추는 방법
> 브로커를 추가하는 도중에 발생하는 데이터 손실을 피할 수 있음.

![[Pasted image 20260308230222.png]]

> 브로커 확장성은 브로커 추가/삭제 시 **파티션 사본은 재배치 하여 달성**해야 한다

## 파티션
운영 중 다음 이유로 **파티션 수를 조정**할 수 있다.
- 시스템 처리량 증가 필요
    
- 브로커 추가
    
- 트래픽 증가 대응
    
- 가용성 조정
    

이때
- **생산자(producer)** 는 브로커로부터 변경 사실을 통지받는다.
    
- **소비자(consumer)** 는 **rebalance** 를 수행한다.
    

따라서

> 파티션 수 변경은 생산자와 소비자의 안정성에 직접적인 영향을 주지 않는다.

### 파티션 추가시 동작
![[Pasted image 20260308230521.png]]
새로운 파티션을 추가하면 **기존 데이터는 이동하지 않는다**
새로운 메세지만 새로운 파티션 포함 전체 파티션에 분산 저장된다

> 파티션 수를 늘리면 토픽의 처리 규모를 쉽게 확장 할 수 있다

### 파티션 삭제시 동작
![[Pasted image 20260309082815.png]]
파티션을 바로 삭제하지 않고 **퇴역(decommission)** 상태를 거친다.
1. 파티션을 **퇴역 상태로 설정**  
2. **새로운 메시지는 다른 파티션에만 저장**  
3. 기존 소비자가 읽을 수 있도록 **일정 기간 유지**  
4. 이후 **데이터 삭제 및 저장공간 반환**

파티션 삭제 진행중 동작:
1. 생산자는 남은 파티션으로만 메세지 전송
2. 소비자는 기존 파티션 포함 모두 읽음
3. 삭제 완료시 생산자 재할당 발생

### 파티션과 확장성
파티션은 메세지 큐 확장 핵심 메커니즘
```
Throughput ≈ Partition 수 × Broker 수
```
- 파티션 증가 → 병렬 처리 증가
- 브로커 증가 → 저장 용량 증가

# 메세지 전달 방식
## 최대 한 번
![[Pasted image 20260309083642.png]]

메시지가 **최대 한 번만 전달되는 방식**
- 메시지 **유실 가능**
- **중복 전달 없음**
생산자가 메세지를 전송하고 **브로커 응답을 기다리지 않는다**
### 사용 예
데이터 유실이 큰 문제가 되지 않는 시스템
- 지표 모니터링
- 로그 수집
- 메트릭 수집

## 최소 한 번
![[Pasted image 20260309083704.png]]
메시지가 **최소 한 번 전달되는 방식**
- 메시지 유실 없음
- 중복 전달 가능
생산자는 **메세지 전달 성공을 반드시 확인**한다
```
// 메세지 소비 과정에서 중복 발생 가능
process message
↓
consumer crash
↓
offset update 실패
↓
재시작 후 메시지 다시 처리
```
> 일반적으로 Idempotency 로 중복을 방지한다

### 사용 예
대부분의 이벤트 기반 시스템
- 이벤트 처리
- 로그 처리
- 데이터 파이프라인
- ETL
> Kafka 기본 전략도 At-least once

## 정확히 한 번
![[Pasted image 20260309084212.png]]

메시지가 **정확히 한 번만 처리되는 방식**
- 유실 없음
- 중복 없음
가장 이상적인 모델이지만, 구현 난이도가 매우 높다
- Producer 재시도
- Broker 복제
- Consumer 재처리
- 네트워크 오류
모든 상황에서 **중복 없이 처리** 해야 한다

### 요구 기술
```
idempotent producer
transaction
deduplication

// Kafka
Idempotent Producer
Transactional Producer
```

### 사용 예
금융 시스템
- 결제
- 거래
- 회계
- 증권 거래

# 고급 기능
## 메세지 필터링
토픽은 같은 유형의 메시지를 담기 위한 **논리적 개념**이지만,  
모든 소비자가 토픽에 있는 **모든 메시지에 관심이 있는 것은 아니다.**
- 결제 시스템 → `checkout`, `refund`
- 배송 시스템 → `order_created`
처럼 **특정 메시지만 필요할 수 있다.**

### 단순 해결 방법
모든 토픽을 나누는 방식
- 다른 시스템에서도 동일 요구 발생시 토픽이 계속해서 늘어난다
- 같은 메세지를 여러 토픽에 저장함으로 인해 저장 공간 낭비
- 소비자 요구 발생시 마다 생산자 수정이 필요해 결합도가 증가한다

### 메세지 필터 방법
브로커 또는 소비자가 **필터 조건을 기반으로 메시지를 선택**한다.
payload 기반 필터링은 필터를 위해 암/복호화 수행시 성능 문제가 있을 수 있고
민감 데이터 노출 여지가 있기 때문에 **메타데이터 기반 필터링**을 권장한다

## 메세지 지연 전송
메시지를 **즉시 소비하지 않고 일정 시간 후 전달**하는 기능

### 사용 예
주문 생성 이후 30분 이내 결제 안하면 주문 취소
- 결제 확인 메세지를 delay = 30 minutes 으로 발행, 30분 이후 체크 후 로직 수행
지연 메세지는 **즉시 토픽에 저장하지 않는다**
```
Producer
     ↓
Temporary Storage
     ↓ (시간 도달)
Topic
     ↓
Consumer
```


## 메세지 예약 전송
특정 **미래 시점에 메시지를 전달하는 기능**
- 기본 구조는 지연 전송과 동일하다

|구분|의미|
|---|---|
|지연 전송|현재 기준 N초 뒤|
|예약 전송|특정 시간에 전달|
