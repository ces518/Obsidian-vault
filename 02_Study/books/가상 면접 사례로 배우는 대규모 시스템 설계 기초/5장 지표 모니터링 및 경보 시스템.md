# 개요

대규모 시스템에서는 **인프라 상태를 지속적으로 관찰하고 문제를 빠르게 감지**하는 것이 중요하다.

지표 모니터링 시스템의 역할

- 시스템 상태 가시화
- 장애 조기 탐지
- 성능 분석
- 자동 경보(alerting)

대표적인 모니터링 시스템

- Prometheus
- Datadog
- InfluxDB
- Munin

# 요구사항

## 모니터링 대상 규모

|항목|규모|
|---|---|
|일간 활성 사용자(DAU)|1억|
|서버 풀|1000개|
|서버 수|풀당 100대|
|전체 서버|100,000대|

## 수집 지표 규모

서버 하나당 100개의 운영 지표 수집 가징

예시 지표

- CPU 사용률
- 요청 수 (RPS)
- 메모리 사용량
- 메시지 큐 길이
- 디스크 사용량

```bash
100,000 서버 × 100 metrics
= 10,000,000 metrics
```

## 데이터 보관 정책

모니터링 데이터는 시간이 지나면 **해상도를 낮춰 저장**한다

→ Downsampling 이라고 함

- 저장 공간 절약
- 조회 성능 향상
- 장기 데이터 보관 가능

|기간|저장 방식|
|---|---|
|최근 7일|원본 데이터|
|이후 30일|1분 단위 집계 데이터|
|이후 1년|1시간 단위 집계 데이터|

## 모니터링 대상 대표 유형

수집 대상은 **운영 지표(Operational metrics) 이며,** 사업 지표는 포함하지 않는다

### 시스템 지표

- CPU usage
- Memory usage
- Disk usage
- Network usage

### 서비스 지표

- Requests per second
- Active connections
- Queue size
- Worker count

## 경보 시스템 요구 사항

시스템은 이상 상황 발생시 **자동 경보 발생**

지원 채널

- Email
- Phone
- PagerDuty
- Webhook

## 비기능 요구사항

- 확장성
- 낮은 지연
- 안정성
- 유연성

# 개략적 설계

지표 모니터링 및 경보 시스템은 일반적으로 **5개의 핵심 컴포넌트**로 구성된다.

```bash
Metric Source
     ↓
1. Data Collection
     ↓
2. Data Transmission
     ↓
3. Data Storage
     ↓
4. Alerting
     ↓
5. Visualization
```

1. 데이터 수집
    - 각 서버나 애플리케이션에서 **운영 지표(metrics)** 를 수집한다.
2. 데이터 전송
    - 수집된 지표 데이터를 **모니터링 시스템으로 전달** 한다.
3. 데이터 저장
    - 수집된 지표 데이터를 **시계열 데이터베이스(Time Series DB)** 에 저장한다.
4. 경보 시스템
    - 수집된 데이터를 분석하여 **이상 상황 발생 시 경보를 발생**시킨다.
5. 시각화
    - 수집된 지표를 **그래프 및 대시보드 형태로 제공** 한다.

# 데이터 모델

모니터링 시스템에서 사용하는 데이터는 **시계열(Time Series) 데이터**이다.

## 시계열 데이터란 ?

값(value)에 시간(timestamp)이 붙어서 기록되는 데이터

## 시계열 데이터의 구성 요소

|요소|설명|
|---|---|
|metric name|지표 이름|
|labels|지표를 구분하는 태그|
|timestamp|측정 시각|
|value|측정 값|

```bash
metric_name: cpu.load
labels: host=i631, env=prod
timestamp: 1613707265
value: 0.29
```

**metric name + label 조합**은 하나의 시계열을 정의한다.

```bash
cpu.load{host=i631,env=prod}
```

이 값은 하나의 시계열이 되고 시간에 따라 값이 계속 기록된다.

```bash
t1 → 0.21
t2 → 0.34
t3 → 0.29
t4 → 0.31
```

## 데이터 저장 형태

```bash
metric_name
labels
[(timestamp, value), (timestamp, value)...]
```

## 사례 1

서버 **i631의 20:00 시점 CPU 부하** 데이터 표현

```bash
metric_name: cpu.load
labels: host=i631, env=prod
timestamp: 1613707265
value: 0.29
```

## 사례 2

us-west 지역 모든 웹 서버의 CPU 평균

```bash
CPU.load host=webserver01 region=us-west 50
CPU.load host=webserver01 region=us-west 62
CPU.load host=webserver02 region=us-west 43
CPU.load host=webserver02 region=us-west 53
```

이러한 데이터는 **line protocol 형식**으로 표현되기도 한다.

## 시계열 데이터 구조

시계열 데이터는 개념적으로 다음 구조를 가진다

|필드|자료형|
|---|---|
|metric name|문자열|
|labels|key:value 집합|
|values|(value, timestamp) 배열|

## 데이터 접근 패턴
![[Pasted image 20260304193501.png]]
### 시계열 데이터 접근 단위

- **y축 레이블(이름 + 레이블/태그 조합)** = **하나의 시계열(Time Series)**
    - 예: `http_error_count{servicepool="s1", method="GET", machinename="m1"}`
- **x축 레이블** = **시간(Time)**
    - 결국 데이터는 **(timestamp, value)** 가 시간축으로 쌓임

데이터 모델 관점에서 접근 패턴은

- **특정 시계열을 잡고(필터: metric + labels)**
- **특정 시간 구간을 잘라(range query)**
- **값들을 읽고/집계한다**

### 쓰기 패턴

이 시스템의 쓰기 부하는 **막대하고 지속적**임.

- 시점과 무관하게 **많은 시계열 데이터가 계속 기록**
- 책의 가정대로면 **매일 천만 개 운영 지표가 기록**되고,
- 그 중 상당수는 **발생 빈도(샘플링 주기)가 높아** 트래픽이 커짐

트래픽은 **쓰기 중심(Write-heavy)** 이다

### 읽기 패턴

읽기는 **spiky(일시 급증형)** 로 본다.

읽기 트래픽을 만드는 주체는 주로 두 가지:

- **시각화(Visualization)**: 대시보드/그래프 조회
- **경보(Alerting)**: 룰 평가를 위해 주기적으로 구간 데이터를 읽거나 집계

**읽기는 평소엔 낮고, 특정 이벤트에 튀는 패턴**

### 설계 관점

- **Write-heavy + Read-spiky** 이므로
    - 쓰기 경로는 “항상 고성능/안정적”이어야 하고
    - 읽기는 “피크 흡수”가 중요 (캐시/사전 집계/다운샘플링 등)
- 또한 질의가 **labels(태그) 기반**이기 때문에
    - 태그 인덱싱/시계열 식별 방식이 핵심 설계 포인트가 됨

# 데이터 저장소 시스템

## RDBMS

사용하지 않는 것을 권장

1. 시계열 연산에 최적화되어 있지 않음
    - 지수이동 평균 EMA 지속 갱신 등
2. 레이블/태그 질의가 인덱스 지옥이 됨
    - 시계열 데이터는 `metric + labels`로 식별되고 필터링/집계를 많이 하는데
    - 레이블 지원시 태그마다 인덱스를 고민해야하고, 운영 난이도 상승
3. 지속적인 대량 쓰기에서 성능 한계 + 튜닝 비용

## NoSQL

가능은 하지만 차선책

- 시계열 저장/질의는 “스키마 설계” 난이도가 높다
- 이를 위해 전문가 수준의 내부 동작 구조 이해도가 필요함

> 기업 규모 지원하는 TSDB 가 많아 위 두가지 방식을 사용할 이유가 없다

## TSDB

- **대량 쓰기 처리에 최적화**
- **레이블(태그) 기반 집계/분석**을 지원하는 질의 인터페이스 제공
- 보관 정책/집계(aggregation)/다운샘플링(retention, downsampling) 같은 기능을 제공하는 제품도 존재
- **OpenTSDB**: 분산 TSDB지만 **Hadoop/HBase 기반**이라 운영이 복잡
- (사례) X(트위터): **MetricsDB**
- (사례) AWS: **Timestream**
- 시장 인기: **InfluxDB / Prometheus**
    - 공통적으로 **메모리 캐시 + 디스크 저장소**를 함께 사용
    - 영속성(durability)과 성능 요구를 잘 만족
![[Pasted image 20260305201713.png]]
### 레이블 인덱싱

좋은 TSDB는 **레이블 기반 빠른 질의**를 위해

- **레이블별 인덱스**를 구축한다(InfluxDB 사례 언급)

제약조건:

> 레이블 값의 **가짓수(cardinality)**가 낮아야 한다

# 지표 수집

모니터링 시스템에서 수집하는 지표 예:

- Counter (요청 수, 에러 수)
- CPU 사용률
- 메모리 사용량
- 디스크 사용량

특징:

> 지표 데이터는 **일부가 손실**되어도 시스템 운영에 큰 문제가 되지 않는다.

![[Pasted image 20260305201750.png]]
## 풀 모델

지표 수집기가 데이터를 가져온다

- 지표 수집기는 주기적으로 애플리케이션의 **metrics endpoint**를 호출

```bash
웹 서버
DB 서버
캐시 서버
큐 서버
      │
      │  (metrics endpoint)
      ▼
   지표 수집기
      │
      ▼
TSDB 저장
```

### 문제

수집 대상 서버 목록을 어떻게 관리할 것인가 ?

서버가 많아질수록

- 서버가 추가되고
- 서버가 삭제되고
- IP가 바뀌고
- 스케일링이 발생한다.

따라서 **정적인 서버 목록 관리 방식은 불가능**

### 해결책

문제를 해결하기 위해 **서비스 탐색(Service Discovery)** 시스템을 사용한다.

대표 예

- etcd
- Apache ZooKeeper

```bash
서비스 → Service Discovery 등록
                │
                ▼
        지표 수집기
                │
      endpoint 목록 조회
                │
                ▼
      각 서비스 /metrics 호출
                │
                ▼
           TSDB 저장
```

### 장점

1. 중앙 관리
    - 수집기를 통해 모든 지표를 관리할 수 있다
2. 장애 대응
    - 서비스가 죽으면 즉시 탐지 가능하다
3. 네트워크 제어
    - 중앙에서 폴링 주기 제어가 가능하다

### 지표 데이터 수집

수천대 서버가 만들어내는 지표 데이터 수집시 서버 한대로는 부족하다

지표 **수집기 서버 풀**을 만들어야 지표 데이터 규모를 감당할 수 있음

### 안정 해시 링

지표 수집기를 여러 대 운영시 다음 문제가 발생할 수 있다

- **중복 수집 발생**
- 저장소 부하 증가
- 데이터 왜곡 가능

이를 해결하기 위해 안정 해시 링을 사용한다

- 서버와 수집기를 **같은 해시 공간에 배치**
![[Pasted image 20260305201805.png]]
**동작 방식**

1. 서버 ID 를 해시링에 매핑
2. 수집기 노드도 해시링에 매핑
3. 서버 위치에서 **시계 방향으로 가장 가까운 수집기**가 처리

> 특정 서버 지표는 항상 동일한 수집기 하나가 처리한다

**장점**

1. 중복 수집 방지
2. 확장성
    - 컬렉터 추가시 데이터 재분배가 **일부만 발생**
3. 장애 복구
    - 컬렉터 하나가 죽으면, 그 구간 데이터는 **다음 collector가 담당**

> 대규모 분산 시스템에서 **노드 변화 영향**을 최소화 한다

## 푸시 모델
![[Pasted image 20260306225829.png]]
모니터링 대상 서버가 직접 지표를 수집기로 전송한다.

- 일반적으로 **수집 에이전트**를 설치한다
- 단순 전송에 그치지 않고 데이터 집계도 수행 가능

```bash
지표 출처 (Server)
      ↓ push
수집 에이전트
      ↓
지표 수집기
      ↓
TSDB
```

### 문제

푸시 모델에서는 많은 서버가 동시에 메트릭을 푸시할 수 있어 다음 문제가 발생할 수 있다

- 수집기 서버 과부하
- 데이터 처리 지연
- 오류 발생

### 해결 방법

**수집기 클러스터 + 로드밸런서** 구조를 사용한다.

```bash
Servers
   ↓
Collection Agent
   ↓
Load Balancer
   ↓
Metrics Collector Cluster
```

### 데이터 유실

push 모델에서 수집기 장애시 데이터 유실 위험이 있어 local buffer 를 사용해 유실을 방지한다

하지만 Auto scaling 환경에서 다음 상황의 경우 데이터 손실 가능성이 있다

서버가 제거되면

- 에이전트 버퍼 데이터
- 아직 전송되지 않은 metrics

# 데이터 집계 지점

지표 데이터는 다음 **3가지 지점**에서 집계 가능하다

1. 클라이언트 측 (수집 에이전트)
2. 데이터 수집 파이프라인
3. 질의 시점

> 각 방식은 **성능 / 데이터 정확성 / 유연성** 측면에서 트레이드오프가 있다.

## 수집 에이전트 집계

```bash
server
 └ collection agent
      ├ request_count
      ├ error_count
      ↓
  1분 단위 집계
      ↓
collector 전송
```

### 특징

- 단순한 집계만 가능
- 예: **counter 합계, 분 단위 집계**

### 장점

- 네트워크 트래픽 감소
- 수집기 부하 감소

### 단점

- **복잡한 집계 로직 구현 어려움**
- 에이전트 기능이 제한적

## 데이터 수집 파이프라인 집계

```bash
Metrics Collector
       ↓
Kafka
       ↓
Stream Processing (Flink / Storm / Spark)
       ↓
Aggregated metrics
       ↓
TSDB 저장
```

### 장점

- 저장 데이터량 감소
- 처리 효율 증가

### 단점

- 늦게 도착한 데이터 처리 어려움
- 원본 데이터를 보관하지 않음

## 질의시 집계

데이터를 **원본 그대로 저장하고 질의시 집계** 한다

```bash
TSDB (raw data 저장)

Query 요청
      ↓
집계 수행
      ↓
결과 반환
```

### 장점

- 데이터 손실 없음
- 유연한 분석 가능
- 새로운 집계 가능

### 단점

- 전체 데이터셋 대상으로 집계

→ 질의 속도 느림

# 질의 서비스

질의 서비스는 **서버 클러스터 형태**로 구성된다

역할

- 시각화 시스템(Grafana 등) 또는
- 경보 시스템(Alerting system)

에서 들어오는 **질의 요청을 처리**한다.

## 목적

질의 서비스를 두는 가장 큰 목적 → **결합도 감소**

## 캐시 계층
![[Pasted image 20260306225928.png]]

질의 서비스는 **캐시 서버**를 함께 두는 경우가 많다

### 목적

- 질의 응답 속도 향상

# 저장소 계층

## 시계열 데이터 베이스

모니터링 시스템의 저장소는 **시계열 데이터베이스** 를 사용하는 것이 일반적이다

### 사용 패턴

> 운영 데이터 질의의 약 85% 는 **최근 26시간 내 데이터**를 대상으로 한다

따라서 TSDB 는 다음 특징을 활용한다

- **최근 데이터 조회 성능 최적화**
- 최신 데이터를 빠르게 처리할 수 있는 구조

예

- 메모리 캐시
- hot storage 구조

## 저장 용량 최적화

모니터링 시스템은 데이터 규모가 매우 크기 때문에, **저장 공간 최적화 전략**이 필요하다

### 대표 전략

- 데이터 인코딩
- 데이터 압축
- 다운샘플링
- 콜드 스토리지

### 데이터 인코딩 / 압축

시계열 데이터는 **시간이 일정 간격으로 증가하는 특징**이 있다

```bash
1610087371
1610087381
1610087391
1610087400
1610087411
```

일반적으로 타임스탬프를 그대로 저장시 → 32bit 필요

실제 차이:

```bash
10
10
9
11
```

TSDB 는 **기준값 + 차이값 형태**로 저장한다

### 이중 델타 인코딩

위 방식에서 한 단계 더 발전한 방식
![[Pasted image 20260306225945.png]]
```
// 구조
timestamp
→ delta
→ delta of delta

// 예
t0 = 1610087371
t1 = t0 + 10
t2 = t1 + 10
t3 = t2 + 9
t4 = t3 + 11

// 델타 값
10
10
9
11

// 변화값
0
-1
+2
```
변화 값을 저장하여 더 작은 bit 로 저장이 가능하다

### 다운 샘플링

데이터를 **시간이 지날수록 해상도를 낮춰 저장**하는 기법

|기간|저장 방식|
|---|---|
|최근 7일|원본 데이터|
|30일|1분 해상도|
|1년|1시간 해상도|

### 콜드 스토리지

오래된 데이터는 **저비용 저장소로 이동**시킨다

- S3
- HDFS
- Object storage

목적:

- 비용 절감

특징:

- 접근 빈도 낮음
- 분석용 보관

# 경보 시스템

모니터링 시스템의 목적은 단순 지표 저장이 아닌, **문제 발생시 알림**을 보내야 한다
![[Pasted image 20260306230012.png]]
## 경보 규칙

경보 조건은 설정 파일 형태로 관리되며, 보통 **YAML 형식**을 많이 사용한다

```bash
- name: instance_down
  rules:
  - alert: instance_down
    expr: up == 0
    for: 5m
    labels:
      severity: page
```

## 처리 흐름

1. 규칙 로드
2. Alert Manager 가 규칙 조회
3. Query Service 호출
4. 조건 평가
    - 임계값 초과시 이벤트 생성
5. 경보 상태 저장
6. Kafka 로 경보 이벤트 전달
7. 알림 전송

## Alert Manager 기능

1. 경보 필터링
2. 경보 병합
3. 중복 제거
4. 접근 제어
5. 재시도

## 경보 상태 저장소

경보 상태는 **키-값 저장소**에 저장된다.

- Cassandra

저장 목적:

- 경보 상태 관리
- 재전송 보장
- 장애 복구
