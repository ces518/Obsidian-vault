# 개요
구글 맵은 사용자가 **지도 탐색과 경로 탐색을 수행할 수 있도록 하는 서비스**이다.

대표 기능

- 지도 표시 (Map Rendering)
    
- 위치 추적 (Location Update)
    
- 경로 탐색 (Routing)
    
- 도착 예상 시간 (ETA)
    
- 실시간 교통 정보 반영
    

규모

- **DAU: 약 10억 명**
    
- **전 세계 99% 지역 지도 제공**
    
- **매일 약 2,500만 건 지도 업데이트**

# 지도 101
## 측위 시스템
측위 시스템은 **지구 표면상의 위치를 표현하는 방법**이다.
지구는 **구(Sphere)** 형태이기 때문에 특정 위치를 표현하려면 좌표 체계가 필요하다.
![[Pasted image 20260312090314.png]]
### 위도
- 특정 위치가 **북쪽 또는 남쪽으로 얼마나 떨어져 있는지** 나타낸다.
- 기준선: **적도 (Equator)**
### 경도
- 특정 위치가 **동쪽 또는 서쪽으로 얼마나 떨어져 있는지** 나타낸다.
- 기준선: **본초 자오선 (Prime Meridian)**
## 3차원 -> 2차원 변환
지구는 **3차원 구체**지만, 지도는 **2차원 평면**이다.
- 3D 구 -> 2D 지도로 변환하는 과정이 필요하다.
> 변환 방법을 **지도 투영법(Map Projection)** 이라고 한다.
![[Pasted image 20260312090619.png]]
## 구글맵 사용 방식
Web Mercator Projection -> **메르카토르 도법의 변형 버전**
사용 이유:
1. 계산이 단순  
2. 지도 타일 생성이 쉬움  
3. 확대 / 축소 구현이 쉬움  
4. 웹 지도 서비스에 적합
## 지오코딩
**주소를 지리적 좌표(latitude, longitude)로 변환하는 과정**이다.
```
<주소>
1600 Amphitheatre Parkway, Mountain View, CA
<결과>
Latitude  : 37.423021
Longitude : -122.083739
```
### 역 지오코딩
지오코딩의 반대 과정
사용 예
- 지도 앱에서 현재 위치 주소 표시
- GPS 좌표 → 실제 주소 변환
### 구현 방법
지오코딩을 구현하는 대표적인 방법 중 하나는 **Interpolation (보간법)** 이다.
- 도로 위 주소를 좌표 사이에서 계산
```
- 도로구간
100번지 ----------- 200번지

- 주소 150 번지
중간 위치 계산

주소 번호 → 도로 위치 비율 → 좌표 계산

```
### GIS
지오코딩은 보통 **GIS 시스템 데이터와 결합해서 처리한다.**
- 도로 구간
- 주소 범위
- 좌표 정보
데이터를 이용해서 주소를 좌표로 변환한다.

## 지오해싱
![[Pasted image 20260312212244.png]]

지도 위의 **특정 영역을 짧은 문자열(영문자 + 숫자)** 로 표현하는 **공간 인코딩 방식**
```
지리 좌표 (lat, lon)
        ↓
Geohash 문자열

ex)
37.423021, -122.083739
→ 9q9hv
```

지도 영역을 **격자 형태로 계속 분할**하면서 생성된다
- 재귀적 공간 분할
```
1. 전체 지도 영역
2. 4개의 영역으로 분할
3. 각 영역 다시 분할
4. 원하는 크기가 될 때까지 반복
```

## 지도 표시
지도 시스템에서 **지도를 화면에 표시하는 핵심 개념은 “타일(Tile)”** 이다
전체 지도를 **하나의 이미지로 제공하는 것이 아니라**, 작은 조각으로 나눠서 화면에 표시한다

지도의 확대 / 축소 기능 지원을 위해 **줌 레벨 마다 다른 타일 세트**가 존재한다
```
Zoom level 0
→ 전세계 지도 1개

Zoom level 1
→ 4개 타일

Zoom level 2
→ 16개 타일

Zoom level n
→ 4^n 개 타일
```

## 경로 안내 알고리즘을 위한 도로 데이터 처리 정리
대부분의 경로 안내 알고리즘은 **다익스트라(Dijkstra)** 또는 **A*** 계열 알고리즘을 바탕으로 한다.

알고리즘들이 공통으로 가정하는 **데이터 모델**
- 교차로 = 노드
- 도로 = 간선

전 세계 도로망을 하나의 그래프로 두지 않는 이유:
- 메모리 사용량 문제
- 탐색할 그래프가 너무 큼
- 경로 탐색 성능 문제
> 경로 탐색 알고리즘의 성능은 **그래프 크기에 매우 민감** 하므로 비효율적

해결책:
**전 세계 도로망을 더 작은 관리 가능 단위로 분할**해야 한다
지도 표시용 타일 분할과 유사하다
- 지오해싱과 유사한 분할 기술 사용
- 작은 격자로 분할
- 격자 내부 도로망을 별도 그래프로 관리

### 경로 안내 타일
나뉜 각 격자 단위를 **경로 안내 타일(routing tile)** 이라고 한다

각 타일이 가지는 내부 속성:
- 해당 영역의 교차로 노드들
- 노드 사이를 잇는 도로 간선들
- 인접 타일로 이어지는 참조 정보

중요한 점:
- **지도 타일** = PNG 이미지
- **경로 안내 타일** = 도로 데이터가 들어 있는 이진 파일

경로는 한 타일 내에서만 끝나지 않는다
사용자가 먼 거리 이동시 여러 타일을 지나가야 하기 때문에, 각 경로 안내 타일은 **도로로 연결된 다른 타일에 대한 참조(reference)** 를 유지한다

> 필요한 타일만 **동적으로 로딩**하며 **더 큰 도로망 그래프를 점진적**으로 구성 할 수 있음

![[Pasted image 20260312213749.png]]

## 계층적 경로 안내 타일
중요한 포인트는 **타일을 하나의 해상도로만 두지 않는다**
장거리 경로 탐색에서 너무 세밀한 도로 데이터만 사용하면 비효율적이기 때문이다
- 일반적으로 **상 / 중 / 하 3단계 수준**의 경로 안내 타일을 사용한다

### 세계 지도
지도 서비스는 **타일(tile)** 기반으로 구성됨
- 확대 시 타일이 **4개로 분할**
- zoom level 증가 → 타일 수 ×4
```
// 타일수
최대 zoom level = 21
≈ 4.4 trillion (4.4조)

// 타일 크기
256 × 256 PNG
≈ 100KB

// 전체 저장 용량
4.4조 × 100KB
= 440PB 
```

대부분의 지역은
- 바다
    
- 사막
    
- 산
    
- 호수
> 보수적으로 봤을때 8-90% 가량 저장 공간 절감

```
44PB ~ 88PB
≈ 50PB

// 모든 줌레벨 합
50 + 50/4 + 50/16 + ...
≈ 67PB

// 최종 추정치
약 100PB
```


## 서버 대역폭
DAU - 10억
평균 사용시간 - 1인당 주 35분

```
10억 × 35분
= 350억 분 / week

-> 하루 50억분

// GPS 업데이트가 1초마다 위치 전송 가정시
50억 분 × 60
= 3000억 요청 / day

// QPS
3000억 / 86400
≈ 3,000,000 QPS

-> 300만 QPS
```

# 위치 서비스
사용자의 위치 정보를 기록하고 저장 하는 역할

## 위치 데이터 수집 이유 ?
1. 교통 상황 분석
	1. 실시간 교통 상황 분석
	2. 정체 구간 탐지
2. 도로 상태 변화 감지
	1. 새로 생기거나, 폐쇄된 도로 탐지
3. 사용자 행동 분석
	1. 개인화 추천
	2. 이동 패턴 분석
4. ETA 정확도 향상
	1. 위치 데이터가 실시간에 가까울수록 ETA (예상 도착 시간) 정확도가 높아진다

## 데이터 전송 최적화
위치가 매번 바뀔때마다 서버 전송시 요청 수가 너무 많아진다
**일괄 요청**을 활용해 전송 최적화를 수행한다

```
1초마다 클라이언트 위치 측정
15초 마다 서버에 한번 전송
```

![[Pasted image 20260314153539.png]]

## 위치 서비스 설계 특징
|특징|설명|
|---|---|
|쓰기 중심 시스템|위치 업데이트가 매우 많음|
|고QPS|최대 100만 QPS|
|실시간 데이터|교통 분석에 활용|
|스트림 처리 필요|Kafka 같은 시스템|

## 저장소 선정
위치 서비스는 **write-heavy workload** 이므로

```
Cassandra
Bigtable
DynamoDB
```

특징
- 분산 저장
- 높은 write throughput
- 수평 확장

# 경로 안내 서비스
경로 안내 서비스의 역할

```
A 지점 → B 지점까지  
합리적으로 빠른 경로를 계산
```

특징
- 반드시 **최단 시간 경로일 필요는 없음**
- 하지만 **정확도는 보장되어야 함**
- 약간의 **응답 지연은 허용**
> 정확도가 계산 속도 보다 중요하다

## 요청 흐름
```
모바일 사용자
      ↓
로드밸런서
      ↓
경로 안내 서비스
```

> 클라이언트는 출발지와 목적지를 전달

## 계산 예시
```
{
  "distance": {"text": "0.2 mi", "value": 259},
  "duration": {"text": "1 min", "value": 83},
  "start_location": {"lat": 37.4027, "lng": -121.9435},
  "end_location": {"lat": 37.4038, "lng": -121.9410},
  "polyline": {"points": "_fhcFjbhgVuAwDsCal"},
  "html_instructions": "Head northeast on Brandon St",
  "travel_mode": "DRIVING"
}
```

polyline = 지도에 그릴 경로
- 좌표 리스트를 **압축 인코딩**

## 경로 안내 서비스 설계 특징
|특징|설명|
|---|---|
|CPU 중심 시스템|그래프 탐색 필요|
|읽기 중심|DB 조회 많음|
|약간의 지연 허용|수백 ms 가능|
|정확도 중요|잘못된 경로는 문제|
**도로 그래프** 데이터를 사용한다

```
A ---- B ---- C
 \         /
   ------ D
```

## 추후 고려 사항
현재는 교통 상호아 변화, 경로 재탐색, ETA 업데이트는 고려하지 않음.
상세 설계 레벨에서 **Adaptive ETA** 를 통해 해결한다

경로 안내 서비스는
```
출발지와 목적지를 입력받아
도로 그래프 기반으로
합리적으로 빠른 경로를 계산하는 서비스
```

특징
- CPU 중심
- 그래프 알고리즘 사용
- 정확한 ETA 계산 필요

실제 지도 시스템에서 사용하는 기술

```
Graph partition
Hierarchical routing
Contraction hierarchy
Traffic weight
Adaptive ETA
```

# 지도 표시
지도 서비스에서 **모든 지도 데이터를 클라이언트에 저장하는 것은 불가능**하다.
- 지도 데이터 규모
- 확대 수준(zoom level) 별 데이터 존재

## 지도 타일이 필요한 상황
1. 지도 이동 -> 새로운 타일
2. 지도 확대 및 축소 -> 다른 해상도의 타일
3. 경로 안내 중 이동 -> 인접 타일

## 지도 타일 생성 방법

### 1. 동적 타일 생성
- 모든 타일을 실시간으로 생성하기엔 서버 부하가 심각
- 캐시 활용이 어렵다
### 2. 타일을 미리생성
- zoom level 별 지도 타일을 미리 생성한다
- CDN 캐싱 가능

![[Pasted image 20260314154844.png]]
## CDN 트래픽 추정

```
// 가정
50억 분 경로 안내 / day
// 총데이터
50억 × 1.25MB
= 6.25 PB / day

// 초당 트래픽
≈ 62,500 MB/s

// POP 200 개 기준
≈ 수백 MB/s
```

# 데이터 모델
지도 시스템은 4가지 핵심 데이터를 다룬다

| 데이터       | 설명                |
| --------- | ----------------- |
| 경로 안내 타일  | 경로 계산용 도로 그래프 데이터 |
| 사용자 위치    | 사용자 GPS 위치 기록     |
| 지오코딩 데이터  | 주소 ↔ 위도/경도 변환     |
| 지도 타일 이미지 | 지도 렌더링용 이미지       |

## 경로 안내 타일
도로 데이터는 외부 기관 / 사업자 제공을 통한 출처
- OpenStreetMap
- 정부 도로 데이터
- 지도 데이터 제공 업체

문제
- 원본 도로 데이터는 그래프 구조가 아니다
- 경로 탐색 알고리즘에 바로 사용 불가능

# 위치 서비스
위치 서비스는 **사용자의 위치 정보를 수집하고 저장하는 시스템**이다

![[Pasted image 20260314160343.png]]

## 데이터 저장 방식
위치 데이터는 **키-값 저장소(Key-Value Store)** 를 사용하여 저장한다.

이유

- 위치 업데이트가 매우 많음
    
- 초당 **백만 건 이상의 write** 발생 가능
    

따라서 요구되는 DB 특성

- 높은 쓰기 처리량
    
- 수평 확장
    
- 고가용성

대표 예시

- Cassandra

## CAP 관점 설계

사용자 위치 데이터의 특징

- 위치는 계속 변경됨  
- 이전 위치는 금방 쓸모 없어짐

따라서 중요한 것

- Availability > Consistency


CAP 정리 기준 선택

- AP (Availability + Partition tolerance)

설계 목표

- 높은 가용성
    
- 분산 환경에서 안정적인 처리

## 위치 데이터 테이블 구조

- 특정 기간 위치 조회 가능

# 지도 표시
지도는 **이미지를 실시간으로 생성하지 않는다.**
- 지도 타일을 미리 생성(pre-compute)

이유
- 지도 이미지 생성 비용이 큼
    
- 동일한 지도 요청이 매우 많음
    
- 캐싱 효과가 매우 큼
> Pre-rendered map tiles + CDN

## 지도 타일 사전 계산
사용자가 보는 지도는 **확대 수준(zoom level)** 에 따라 다른 해상도를 가진다.

|확대 수준|설명|
|---|---|
|0|세계 지도|
|1|세계를 2×2 타일로 분할|
|2|세계를 4×4 타일로 분할|

## Zoom level 구조

```
확대 수준 **0**

256 × 256 타일 1개

확대 수준 **1**

2 × 2 타일

확대 수준 **2**

4 × 4 타일


// 즉
zoom level 증가  
→ 타일 수 = 4배 증가

// 공식
tile count = 4^zoom_level
```

### 타일 크기

각 타일 크기는 동일하다.

256 × 256 px


### 전체 해상도 변화

|zoom level|전체 해상도|
|---|---|
|0|256×256|
|1|512×512|
|2|1024×1024|

```
zoom level ↑  
→ 해상도 4배 증가
```

- 더 상세한 지도 정보 제공
- 필요한 영역만 다운로드

### 네트워크 최적화 효과
타일 방식의 장점

```
클라이언트는 화면에 필요한 타일만 다운로드
```

- 전체 지도 다운로드 불필요
- 네트워크 사용량 절감

> 화면에 표시되는 타일 수는 항상 일정

# 경로 안내 서비스
경로 안내 서비스의 목적
```
출발지 → 목적지까지
가장 빠른 경로 안내
```

특징
- 단순 거리 최단 경로가 아니라
- **교통 상황 + 도로 상태 + 필터 조건**을 고려

![[Pasted image 20260314161343.png]]

## 주요 구성 요소
### 1. 지오코딩 서비스

역할

- 주소 → 위도/경도 변환

예

```
1600 Amphitheatre Parkway  
→ (37.4224764, -122.0842499)
```

이 결과는 이후 **경로 계산의 입력값**이 된다.

### 2. 경로 계획 서비스
경로 안내 시스템의 **핵심 오케스트레이터**

역할

- 다른 서비스들을 호출하여  최종 경로를 계산

사용하는 정보

- 도로 그래프
    
- 교통 상황
    
- 도로 상태
    
- 사용자 옵션

### 3. 최단 경로 서비스
역할

- 도로 그래프 기반   k개의 최단 경로 계산

특징

- 교통 정보는 고려하지 않음

입력

- 출발지 위/경도
- 목적지 위/경도

동작 과정
1. 좌표 -> 지오 해시 변환
2. 해당 위치의 경로 안내 타일 로드
3. 그래프 탐색 수행
	1. A* 알고리즘 기반

![[Pasted image 20260314161628.png]]
### 4. 순위 결정 서비스
역할
- 후보 경로중 가장 좋은 경로 선택
기준 예

- 거리
    
- 교통량
    
- 통행료
    
- 무료 도로
    
- 고속도로

### 5. 예상 도착 시간 서비스 (ETA)
역할
- 각 경로의 ETA 계산

사용 데이터
- 교통량 데이터 베이스

## 전송 프로토콜
경로 안내중 교통 상황이 계속 변하기 때문에, **경로 변경 또는 ETA 업데이트**를 안정적으로 전달할 방법이 필요하다.

### 고려 가능 방식
|방식|설명|
|---|---|
|Mobile Push Notification|모바일 푸시 알림|
|Long Polling|클라이언트가 지속적으로 요청|
|WebSocket|실시간 양방향 통신|
|Server-Sent Events (SSE)|서버 → 클라이언트 단방향 스트림|

모바일 푸시
- 메세지 크기 제한 문제
	- IOS 최대 4096 바이트
- 웹 애플리케이션 미지원

롱 폴링
- 연결 생성 비용 / 서버 리소스 낭비문제
- 실시간 시스템에서 비효율적

웹 소켓
- 실시간 업데이트 가능
- 서버 부담 적음
- 네트워크 효율적

SSE
- 구현 단순 / HTTP 기반
- 양방향 통신 불가
