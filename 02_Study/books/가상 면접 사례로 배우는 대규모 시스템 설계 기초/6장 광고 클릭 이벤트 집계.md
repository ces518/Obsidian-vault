# 개요

디지털 광고는 **RTB(Real-Time Bidding 실시간 경매)** 기반으로 동작하며

광고 클릭 이벤트는 다음을 위해 반드시 정확히 집계되어야 한다

- 광고 효과 측정
- CTR(Click-Through Rate 클릭율) / CVR(Conversion Rate 전환율) 계산
- 광고 비용 정산
- 광고 전략 최적화

**돈이 직접적으로 걸린 데이터.** 따라서 **속도 + 정확성 + 확장성**이 모두 중요
![[Pasted image 20260302173443.png]]

# 요구사항

- **RTB(실시간 경매)** 프로세스는 보통 **1초 내**로 끝나야 해서 “속도”가 중요함.
- 하지만 **광고 클릭 이벤트 집계**는 주로 **광고 과금/리포팅**에 쓰이므로 **몇 분 지연은 허용**됨.
- 다만 집계 결과가 **광고주 과금/예산 조정/타깃·키워드 변경** 등에 영향을 주므로 **정확성**이 매우 중요.
- 클릭 데이터로 계산하는 대표 지표: **CTR(클릭률), CVR(전환률)**

## 기능 요구 사항

- 지난 **M분 동안 ad_id 클릭 수 집계**
- 매분 **가장 많이 클릭된 상위 100개 광고 ID 반환**
- **다양한 속성 기반 필터링** 지원
- 규모는 **페이스북/구글 급**(자세한 수치는 다음 “개략적 추정” 절 참고)

## 비기능 요구 사항

- **정확성** 중요(과금/RTB 연계)
- **지연/중복 이벤트 처리** 가능해야 함
- **신뢰성(reliability)**: 부분 장애 감내
- **전체 지연 시간**: 최대 **수 분**을 넘지 않아야 함

## 개략적 추정

- **DAU(일간 능동 사용자)**: **10억 명(1 billion)**
    
- **사용자당 클릭 수**: 하루 평균 **1회** 클릭 가정
    
    → **일간 클릭 이벤트 수 = 10억 건**
    
- **평균 광고 클릭 QPS**
    
    - 하루를 초로 환산: **10^5초(≈ 100,000초)** 로 근사
    - 계산:
        - 10^9 이벤트 / 10^5초 = **10,000 QPS**
- **피크(최대) QPS**
    
    - 평균의 **5배**로 가정
    - 50,000 QPS
- **이벤트 1건 크기**: **0.1KB** 가정
    
- **일간 저장량**
    
    - 0.1KB × 10억 = 100,000,000KB
    - = 100,000MB
    - = **100GB/day**
- **월간 저장량**
    
    - 100GB/day × 30일 ≈ **3TB/month**

## 고려할 부분

- **쓰기(ingest)가 핵심 병목**: 평균 1만 QPS / 피크 5만 QPS면 단일 DB로 버티기 어려움
    
- 원시 데이터는 **append-only**이므로,
    
    **로그 → 스트림(큐) → 집계 파이프라인** 구조가 자연스러움
    
- 저장량도 월 3TB 수준이라 **장기 보관/분석용 스토리지 전략**(Hot/Warm/Cold)이 필요해짐

# 데이터 모델

시스템이 다루는 데이터는 크게 두 가지:

- 원시 데이터 (Raw Data)
- 집계 결과 데이터 (Aggregated Data)

## 원시 데이터 (Raw Data)

- 로그 파일에 기록되는 **클릭 이벤트 원본**
- append-only 형태
- 여러 애플리케이션 서버에 **분산 저장**

```bash
[AdClickEvent] ad001, 2021-01-01 00:00:01, user1, 207.148.22.22, USA
```

### 특징

- 이벤트 단위 레코드
- 시간 기반 데이터
- 매우 높은 쓰기 QPS
- 재계산/디버깅/ML 분석 용도

## 집계 결과 데이터 (Aggregated Data)

원시 데이터를 그대로 질의하면 너무 느리기 때문에 **미리 집계된 데이터** 를 따로 저장한다.

### 기본 집계 테이블

광고 클릭을 1분 단위로 집계한다고 가정

|ad_id|click_minute|count|
|---|---|---|

- 특정 광고
- 특정 분(minute)
- 그 1분 동안 발생한 클릭 수

### 필터링 지원 집계 테이블

필터링 기능을 위해 `filter_id` 추가

|ad_id|click_minute|filter_id|count|
|---|---|---|---|

- 같은 ad_id + click_minute라도
- 필터 조건별로 별도 집계

ex):

- US만
- 특정 IP만
- 특정 user 제외 등

### 필터 정의 테이블

|filter_id|region|ip|user_id|
|---|---|---|---|

- region = US
- ip = 특정 값
- user_id = *

### TopN 질의용 테이블

지난 M분 동안 가장 많이 클릭된 광고 목록을 위한 테이블

|필드|설명|
|---|---|
|window_size|분 단위 윈도 크기|
|update_time_minute|마지막 갱신 시각|
|most_clicked_ads|JSON 배열 (광고 ID 목록)|

- Top 100 같은 질의 최적화용
- 매분 갱신
- 읽기 성능 극대화 목적

## 원시 / 집계 둘다 저장하는 이유 ?

원시 데이터만 저장:

- 원본 보존, 재계산이 가능하지만
- 질의가 느리고 용량 문제

집계 데이터만 저장:

- 빠른 질의, 용량 절감이 가능하지만
- 원본 손실 및 버그 발생 시 복구가 어려움

> 둘다 저장하는 것이 권장됨

- Raw = 백업/재계산/ML
- Aggregated = 실시간 질의

## 데이터베이스 선택 관점

### 원시 데이터

- 쓰기 중심 (10k~50k QPS)
- 읽기 거의 없음
- 추천: Cassandra, InfluxDB, S3 + Parquet 등

### 집계 데이터

- 읽기 + 쓰기 모두 많음
- 200만 광고 × 분 단위 조회
- 시계열 특성

## 데이터 모델의 본질

> Event → Time-series aggregation → Materialized View → Dashboard 질의

# 개략적 설계

실시간 빅데이터 처리 시스템처럼

데이터는 **계속 흘러 들어오고,**

집계 결과도 **지속적으로 갱신** 된다

## 초기 단순 모델
![[Pasted image 20260302173523.png]]
- 로그 모니터(watcher)가 클릭 로그를 읽음
- 집계 서비스가 매분:
    - 광고 수 집계
    - 상위 100개 광고 계산
- DB에 저장
- 대시보드 질의 서비스가 조회

⚠️ 하지만 이 구조는 **동기식 처리**라는 문제가 있음.

### 동기식 처리의 문제

- 생산자(로그 수집)와 소비자(집계 서비스)의 처리 속도는 항상 같을 수 없음
- 트래픽 급증 시:
    - 메모리 부족
    - 병목
    - 특정 컴포넌트 장애 → 전체 장애

👉 해결책: **메시지 큐 도입 (Kafka 등)**

## 개선된 설계

생산자와 소비자를 메세지 큐로 분리하여 비동기 처리
![[Pasted image 20260302173535.png]]
### 메세지 큐

첫 번째 메세지 큐의 역할:

- 로그 수집과 집계 서비스 분리
- 버퍼 역할
- 트래픽 흡수
- 확장 가능

입력 데이터:

```bash
ad_id
click_timestamp
user_id
ip
country
```

→ 원시 클릭 이벤트 스트림

두 번째 메세지 큐의 역할:

- 집계 서비스가 계산한 결과를
- **원자적으로 커밋(atomic commit)** 하기 위함
- 중복 처리 방지
- 장애 복구 시 재처리 가능

```bash
// 분 단위 클릭 수
ad_id
click_minute
count

// 분 단위 상위 N 광고
update_time_minute
most_clicked_ads
```

### 집계 결과를 DB에 바로 쓰지 않는 이유

Exactly Once 처리를 위해 두 번째 MQ 를 둠

# 집계 서비스

광고 클릭 이벤트 집계는 **맵리듀스(MapReduce) 프레임워크** 를 활용하는 것이 적합하다.

이때 구조는 **DAG(Directed Acyclic Graph)** 모델로 표현된다.

### DAG 모델의 핵심

- 시스템을 작은 컴퓨팅 단위로 분해
- 각 노드는 한 가지 작업만 수행
- 결과를 다음 노드로 전달
- 순환 없음 (비순환 그래프)

## 집계 서비스 구조
![[Pasted image 20260302173601.png]]
```bash
입력 데이터
    ↓
[분배(Map)]
    ↓
[집계(Aggregate)]
    ↓
[축약(Reduce)]
    ↓
최종 결과
```

## 맵 노드 (Map Node)

### 역할

- 입력 데이터를 필터링/정규화
- 특정 기준으로 분배(sharding)

예시:

```bash
ad_id % 2 == 0 → 집계 노드 1
ad_id % 2 == 1 → 집계 노드 2
```

**카프카 파티션**만 잘 나누면 맵 노드 없이도 되지 않을까?

### 맵 노드가 필요한 이유

1. **입력 데이터 정리/정규화가 필요한 경우**
2. 데이터 생성 방식을 제어할 수 없는 경우
    - 동일 ad_id 이벤트가 서로 다른 Kafka 파티션으로 갈 수 있음
    - 이 경우 집계 정확성 깨질 수 있음

👉 따라서 논리적 분배 계층(Map)이 필요

## 집계 노드 (Aggregate Node)

### 역할

- ad_id별 클릭 수를 **메모리에서 분 단위로 집계**
- 사실상 리듀스의 1단계

설명:

- 각 집계 노드는 자신이 담당하는 ad_id 범위만 처리
- 분 단위 카운터 유지

## 리듀스 노드 (Reduce Node)

### 역할

- 모든 집계 노드의 결과를 모아서
- 최종 결과로 축약

예시:

각 집계 노드가 Top 3를 보낸다면:

```bash
Node1: ad1(12), ad3(5), ad2(3)
Node2: ad7(9), ad10(4), ad8(3)
Node3: ad13(8), ad11(4), ad15(3)

-> Reduce 노드가 최종 Top3 계산
ad1(12), ad7(9), ad13(8)
```

**집계 노드도 부분 리듀스** 이고, 최종 리듀스 노드가 글로벌 리듀스 노드이다

## 아키텍처 모델

```bash
로그 모니터
    ↓
Kafka (원시 이벤트)
    ↓
**집계 서비스 (Map/Aggregate/Reduce)**
    ↓
Kafka (집계 결과)
    ↓
DB 기록 프로세스
    ↓
집계 결과 DB
    ↓
질의 서비스
```

## 사례 : 데이터 필터링

요구사항:

> “미국(USA) 내 광고 ad001에 대해 집계된 클릭 수만 표시”

- 단순 ad_id 기준 집계가 아니라
- **특정 조건(필터)** 을 적용한 집계가 필요

### 해결 방법

**필터링 기준을 사전에 정의**한 뒤 해당 기준에 따라 집계 데이터를 생성해 둔다.

- 질의 시 계산하는 게 아니라
- **집계 단계에서 미리 차원별로 분리하여 저장**

## 스타 스키마

이 접근법을 **스타 스키마(star schema)** 라고 부른다.

### 개념

- 데이터 웨어하우스에서 널리 쓰이는 모델
- 집계 대상(팩트 테이블) + 필터 차원(디멘전 테이블)

여기서:

- 클릭 수 = **fact**
- country, ip, user_id = **dimension**

집계 테이블:

|ad_id|click_minute|country|count|
|---|---|---|---|
|ad001|202101010001|USA|100|
|ad001|202101010001|GPB|200|
|ad001|202101010001|others|3000|
|ad002|202101010001|USA|10|
|ad002|202101010001|GPB|25|
|ad002|202101010001|others|12|

같은 ad_id + click_minute라도 country 기준으로 **별도 bucket 생성**

### 장점

- 이해하기 쉽고 구현이 간단하다
- 빠른 질의
- 추가 컴포넌트가 필요 없다

### 단점

- 버킷과 레코드 수가 폭증한다

필터 기준이 많아질수록:

- 조합 폭발
- 저장 공간 증가
- 집계 비용 증가

예:

- country 200개
- device_type 5개
- campaign 100개

→ 조합 수 급증

# 스트리밍 vs 일괄 처리

## 세 가지 시스템 유형 비교

|구분|온라인 시스템|일괄 처리 시스템|스트리밍 시스템|
|---|---|---|---|
|응답성|클라이언트에 빠르게 응답|응답 필요 없음|응답 필요 없음|
|입력|사용자 요청|유한한 대규모 데이터|무한 스트림|
|출력|API 응답|집계 결과, 구체화 뷰|집계 결과, 지표|
|성능 기준|가용성, 지연 시간|처리량|처리량 + 지연 시간|
|사례|온라인 쇼핑|MapReduce|Flink|

## 스트리밍 처리

### 특징

- 데이터가 들어오는 즉시 처리
- 거의 실시간으로 집계 결과 생성
- 입력은 **끝이 없는 스트림**

### 역할

- 광고 클릭 이벤트를 받자마자 집계
- 분 단위 클릭 수 계산
- Top N 광고 계산

👉 **실시간 집계 담당**

## 일괄 처리

### 특징

- 유한한 크기의 데이터 집합을 한 번에 처리
- 응답성보다 처리량이 중요
- 주기적으로 실행

### 역할

- 원시 데이터 백업
- 이력 데이터 재계산
- 장애 복구 후 재처리

👉 **과거 데이터 재계산 담당**

## 람다 아키텍처 (Lambda Architecture)

스트리밍 + 배치 두 경로를 모두 운영

```bash
Raw Data
   ├── Batch Layer (일괄 처리)
   └── Streaming Layer (실시간 처리)
```

### 장점

- 정확성 + 실시간성 모두 확보

### 단점

- 코드/로직을 두 벌 유지
- 운영 복잡도 증가

## 카파 아키텍처 (Kappa Architecture)

스트리밍 엔진 하나로 모든 것 처리

- 모든 데이터를 로그에 저장
- 재처리도 동일 스트림 엔진 사용

```bash
Raw Data Log → Single Stream Engine → 결과
```

### 장점

- 단일 코드 경로
- 운영 단순화

## 데이터 재계산 흐름
![[Pasted image 20260302173643.png]]
1. 원시 데이터 저장소에서 데이터 추출 (Batch 방식)
2. **전용 집계 서비스**로 전달
3. **집계 결과를 메시지 큐**로 보내 DB 반영

⚠️ 전용 집계 서비스를 두는 이유:

- 실시간 처리와 간섭 방지

## 카파 아키텍처 정리

- **카파의 “기본 철학”**: _배치 레이어(별도 MapReduce 파이프라인)_ 없이, **하나의 스트림 처리 로직(코드/모델)** 으로
    
    - 실시간 처리(online aggregation)
        
    - 과거 데이터 재처리(replay)
        
        를 모두 해결한다.
        
- 그런데 **실무/이 책의 설계(그림 6.11)** 에서는, 재처리를 돌릴 때 대량 리플레이가 **실시간 파이프라인과 간섭**할 수 있으니
    
    - **재계산 전용 집계 서비스 인스턴스(별도 프로세스/별도 배포)** 를 둬서 **자원/영향을 격리**한다.

# 시간

집계를 하려면 **타임스탬프(timestamp)** 가 필요하다.

타임스탬프는 두 위치에서 생성될 수 있다.

## 1. 이벤트 시각

> 광고 클릭이 실제로 발생한 시각

- 클라이언트가 기록
- “현실 세계에서의 시간”

### 장점

- 광고 클릭 시점을 정확히 반영
- 집계 정확도 ↑

### 단점

- 클라이언트 시계 오류 가능
- 악성 사용자가 조작 가능
- 서버와 시간 불일치 가능

## 2. 처리 시각

> 집계 서버가 이벤트를 처리한 시각

- 서버 기준 시간
- 시스템 내부에서 생성

### 장점

- 서버 타임스탬프는 상대적으로 안정적
- 신뢰성 높음

### 단점

- 이벤트가 늦게 도착하면 집계 왜곡 발생
- 실제 발생 시점과 다를 수 있음

## 문제 발생 이유 ?

네트워크 지연 + 메세지 큐 + 비동기 처리 때문에

> 이벤트 발생 시각 ≠ 처리 시각

예시:

- 이벤트 1이 발생
- 5시간 후 집계 시스템 도착

이 경우:

- **이벤트 시각 기준 집계** → 지연 이벤트 처리 문제 발생
- **처리 시각 기준 집계** → 집계 정확도 하락

⚠ 완벽한 방법은 없음

→ 트레이드오프 존재

## 현 시스템의 선택

> 정확도가 매우 중요하므로 **이벤트 발생 시각(event time)** 사용 권장

광고 과금/CTR 계산 등은 돈과 직결되기 때문

## 늦게 도착한 이벤트 처리

이벤트 시각을 사용하면:

> 집계 윈도(window)가 이미 닫힌 뒤 이벤트가 도착할 수 있음

예:

- 1분 단위 텀블링 윈도
- 윈도 1: 00:00~00:01
- 해당 구간 이벤트가 00:01:05에 도착

→ 집계 누락 가능

### 해결 방법

워터마크란:

> 집계 윈도를 “조금 더 연장”하는 개념

예:

- 1분 윈도 + 15초 워터마크

→ 윈도 종료 후 15초 동안 늦게 도착한 이벤트 허용

### 트레이드 오프

|워터마크 길이|장점|단점|
|---|---|---|
|길게 설정|늦은 이벤트 많이 포착|처리 지연 증가|
|짧게 설정|지연 감소|정확도 하락|

> 정확도 ↔ 지연 시간의 trade-off

### 한계

- 아주 늦게 도착한 이벤트는 처리 불가
- 확률 낮은 케이스까지 모두 처리하려 하면 ROI 낮음
- 일부 오류는 일 단위 정산 시 보정 가능

# 집계 윈도

“어느 시간 구간까지를 하나의 집계 단위로 볼 것인가?” 를 정의하는 개념 → **집계 윈도**

마틴 클레프만 기준 윈도 유형은:

- **텀블링 윈도 (Tumbling Window)**
- 호핑 윈도 (Hopping Window)
- **슬라이딩 윈도 (Sliding Window)**
- 세션 윈도 (Session Window)

이 장에서는 **텀블링 + 슬라이딩** 두 가지에 집중한다

## 텀블링 윈도 (Tumbling Window)
![[Pasted image 20260302173700.png]]
### 정의

- 시간을 **고정된 길이**로
- **겹치지 않게 분할**

```bash
[00:00~00:01]
[00:01~00:02]
[00:02~00:03]
```

다음과 같은 요구사항에 적합:

- 매 분 클릭 수 집계
- 분 단위 광고 수 계산

### 장점

- 구현 단순
- 메모리 관리 쉬움
- 집계 결과 명확

### 단점

- 윈도 경계에 민감
- 늦게 도착한 이벤트 누락 가능

## 슬라이딩 윈도 (Sliding Window)
![[Pasted image 20260302173714.png]]
### 정의

- 고정 길이 윈도를 유지
- **일정 간격으로 이동**
- 서로 **겹칠 수 있음**

```bash
[00:00~00:03]
[00:01~00:04]
[00:02~00:05]
```

다음과 같은 요구사항에 적합:

- 지난 M분 동안 가장 많이 클릭된 상위 N개 광고
- 최근 3분은 고정된 구간이 아니라
- 현재 시점 기준 계속 이동하기 때문

### 장점

- 실시간 랭킹 계산에 적합
- “최근 M분” 요구사항 충족

### 단점

- 윈도 간 중복 계산 발생
- 연산 비용 증가
- 상태(state) 관리 복잡

## 텀블링 vs 슬라이딩 비교

|구분|텀블링|슬라이딩|
|---|---|---|
|구간 겹침|없음|있음|
|계산 비용|낮음|높음|
|사용 사례|분 단위 집계|최근 M분 Top N|
|구현 난이도|쉬움|상대적으로 복잡|

이 시스템 요구사항은 두 가지:

1. 광고별 분 단위 클릭 수

→ **텀블링 윈도**

1. 최근 M분 Top N 광고

→ **슬라이딩 윈도**

따라서 집계 서비스는 **두 가지 윈도 전략을 모두 지원**해야 한다.

# 전달 보장 (Delivery Gurantee)

집계 결과는:

- 광고 과금
- CTR 계산
- 정산
- 예산 조정

에 직접 사용된다.

시스템은 다음 고민을 해결해야 한다

- **이벤트 중복 처리를 어떻게 피할 것인가?**
- **모든 이벤트 처리를 어떻게 보장할 것인가?**

## 메세지 큐 전달 방식

|방식|의미|특징|
|---|---|---|
|At-most-once|최대 한 번|유실 가능, 중복 없음|
|At-least-once|최소 한 번|유실 없음, 중복 가능|
|Exactly-once|정확히 한 번|유실 없음 + 중복 없음|

광고 집계 시스템은 **Exactly Once**가 적합

- 몇 % 오차가 수백만 달러 차이로 이어질 수 있음
- “약간의 중복은 괜찮다”는 가정이 성립하지 않음

## 데이터 중복 발생 사례

1. **클라이언트 중복**

- 동일 이벤트를 여러 번 전송
- 네트워크 재시도
- 악성 사용자(광고 사기)

→ 별도의 fraud/risk control 시스템 필요

1. **서버 장애 중복**
    
    1. 집계 서비스가 offset 100부터 110까지 소비
    2. 집계 결과를 downstream으로 전송
    3. 그러나 장애 발생
    4. upstream Kafka에 offset 110을 commit 못함
    
    → 복구 후 offset 100부터 다시 소비
    
    → **중복 집계 발생**
![[Pasted image 20260302173736.png]]
### 해결책

1. HDFS/S3 같은 외부 저장소에 offset 기록
    
    - 집계 결과를 downstream으로 보내기 전에
    - offset을 먼저 저장하면
    
    그 직후 장애 발생 시:
    
    → 이미 offset은 110
    
    → 100~110 이벤트 재처리 안 함
    
    → **데이터 손실 발생**
    
2. 다운스트림에서 “집계 결과 수신 확인(ack)”을 받은 후 offset을 저장
    

```bash
// 다음 순서로 진행 되어야 함
1. 이벤트 소비
2. 집계 수행
3. 집계 결과 downstream 전송
4. downstream ack 수신
5. offset commit
```

## Exactly Once

단순히 Kafka 설정으로 해결되는 문제가 아니다

본질은:

- 상태 업데이트
- 결과 전송
- offset commit

이 세 가지를 **원자적으로 처리**해야 한다는 것

실무에서 사용하는 방식:

1. Kafka transactional producer
2. Idempotent write
3. Upsert 기반 집계 테이블
4. 메시지 + offset을 같은 저장소에 기록

# 시스템 규모 확장

- 사업은 **매년 30% 성장**
- 트래픽은 **3년마다 두 배**

시스템은 처음부터 **수평 확장 가능 구조**여야 한다

## 메세지 큐 규모 확장

### Producer 확장

- Producer 인스턴스 수에 제한 없음
- 단순히 인스턴스를 늘리면 확장 가능
- 비교적 쉬운 영역

### Consumer 확장

- Consumer Group 사용
- 노드 추가/삭제 시 **rebalancing** 발생

### ⚠ 주의점

- 소비자가 수백 개일 경우 rebalancing에 **수 분** 걸릴 수 있음
- 따라서 피크 시간에는 확장 작업 피하는 것이 좋음
![[Pasted image 20260302173753.png]]
## 파티션 전략

### 해시 키

- 같은 `ad_id`를 같은 파티션에 저장해야 함
- → `ad_id`를 해시 키로 사용

이유:

- 같은 광고 이벤트를 한 Consumer가 처리하도록 보장
- 집계 정확성 확보

### 파티션 수

- 파티션 수가 변경되면
- 같은 ad_id가 다른 파티션에 들어갈 수 있음

→ 운영 중 파티션 수 증가 지양

→ 처음에 충분히 크게 설정

### 토픽의 물리적 샤딩

하나의 토픽으로 부족할 수 있음

예:

- 지역 기준
    - topic_north_america
    - topic_europe
    - topic_asia
- 사업 유형 기준
    - topic_web_ads
    - topic_mobile_ads

👉 물리적으로 토픽 분리 가능

## 집계 서비스 규모 확장

집계 서비스는 본질적으로 **MapReduce 구조**
![[Pasted image 20260302173805.png]]
### 수평 확장

- 집계 노드 추가/삭제로 확장 가능
- Map/Reduce 노드 수 늘리면 처리량 증가

### 대역폭 늘리기

- Kafka 파티션 수 증가
- 집계 서버 수 증가
    
    1. ad_id 마다 별도 처리 스레드 두기
    2. 집계 서비스 노드를 아파치 하둡 YARN 같은 자원 공급자에 배포 (다중 프로세싱 활용)
    
    - 두 번째 방안이 더 많이 쓰임

## 데이터베이스 확장

- 카산드라(Cassandra)는 설계 자체가 **노드 추가로 용량/처리량을 늘리는 구조**를 기본으로 지원한다.
- 별도의 “수동 샤딩”을 크게 하지 않아도, 클러스터에 노드를 더 붙여 확장하는 방식이 자연스럽다.

### 데이터 분산 방식 (Consistent Hash와 유사한) 해시 링 기반

- 데이터는 **해시 링(hash ring)** 위에서 특정 해시 범위를 담당하는 노드에 저장된다.
- 목표는 **각 노드에 데이터가 균등하게 분산**되도록 하는 것.

### 가상 노드(virtual node)와 복제(replication)

- 각 물리 노드가 링 위에 **여러 개의 가상 노드(vnode)** 를 가진다고 보면 됨.
- 데이터는 단일 노드에만 있지 않고 **사본(복제본)** 을 여러 노드에 분산 저장한다.
    - 즉, 어떤 노드는 “내가 담당하는 구간 데이터”뿐 아니라 **다른 가상 노드 구간의 사본도 일부 보관**한다.
- 효과:
    - **부하 분산**(특정 노드에 데이터/트래픽 몰림 완화)
    - **장애 내성**(노드 장애 시 복제본으로 서비스 지속)
![[Pasted image 20260302173817.png]]
- 클러스터에 **새 노드를 추가하면**, 가상 노드 단위로 데이터 담당 구간이 재배치되면서
    - **데이터 균형이 자동으로 다시 조정**된다.
- 따라서 운영자가 **수동으로 샤딩을 재조정하는 과정이 필요 없다**는 점이 핵심.

# 결함 내성

- 집계 서비스는 **메모리에서 카운터/윈도 상태를 유지**하며 처리한다.
- 그래서 **집계 노드에 장애가 나면, 그 노드가 들고 있던 집계 상태도 같이 손실**된다.

## Kafka 복원

- 업스트림이 Kafka(커밋 로그)이므로, 이론적으로는 **이벤트를 다시 읽어 집계를 재구성**할 수 있다.
- 하지만 **처음(offset 0)부터 전부 replay** 하면 시간이 너무 오래 걸린다.

## 스냅숏 활용 복원

- 그래서 업스트림 오프셋 같은 **시스템 상태(system state)** 를 **주기적으로 스냅숏(snapshot)** 으로 저장한다.
- 이 설계에서 시스템 상태는 **업스트림 오프셋만**이 아니다.
    - 예: **지난 M분간 가장 많이 클릭된 광고 Top N** 같은 데이터도 **상태로 같이 저장**해야 함.

예시로 스냅숏에 포함되는 것:

- 광고별 최근 구간 카운트(분 단위 카운터 배열/시계열 상태)
    
- “최근 5분 Top 3 광고” 같은 랭킹 상태
    
    → 즉, **집계 결과를 재현하기 위한 최소 상태**를 저장
![[Pasted image 20260302173828.png]]
## 장애 복구 절차
![[Pasted image 20260302173844.png]]
1. 특정 집계 노드 장애 발생
2. 해당 노드를 **새 노드로 교체**
3. **스냅숏 저장소에서 마지막 스냅숏을 로드**해서 상태 복원
4. 스냅숏 이후에 도착한 이벤트는
    - Kafka 브로커에서 **스냅숏 시점 이후 offset부터 다시 읽어서** 재처리

👉 결론: **“스냅숏 + 이후 구간 replay”** 로 복구 절차가 단순해진다.

- 본문에 “점진적 스냅숏(incremental snapshot)” 언급이 있어,
    - 매번 전체 상태를 덤프하기보다
    - **변경분 중심으로 스냅숏을 남기는 방향**을 시사한다.

# 데이터 모니터링 및 정확성

광고 클릭 집계 결과는:

- RTB(Real-Time Bidding)
- 청구서 발행(과금)

에 사용된다.

따라서:

> 시스템이 정상적으로 동작하는지 지속적으로 모니터링하고
> 
> 데이터 정확성을 보장하는 것이 매우 중요하다.

## 지속적 모니터링

다음 지표를 항상 추적해야 한다

### 1. 지연 시간

- 데이터는 여러 단계를 거치면서 처리됨
- 각 단계마다 지연이 누적될 수 있음
- 시스템 주요 지점에 **timestamp 기록**
- 두 timestamp 차이를 지연 시간으로 계산
- 단계별 latency 모니터링

예:

- 로그 수집 → MQ
- MQ → 집계 서비스
- 집계 → DB 기록

### 2. 메세지 큐 크기

- 큐가 갑자기 커지면
    
    → 소비 속도가 생산 속도를 못 따라가는 상태
    

Kafka의 경우:

- 분산 커밋 로그 구조
- **records-lag 지표** 추적 가능

records-lag 증가 시:

- 집계 노드 증설 필요
- 병목 발생 가능성

### 3. 집계 노드 시스템 자원

- CPU
- 디스크 I/O
- JVM 메모리
- GC

메모리 기반 집계이므로 특히:

> 메모리 사용량과 GC pause는 중요

## 대사 (Reconciliation)

대사란:

> 서로 다른 데이터 소스를 비교하여
> 
> 데이터 무결성을 검증하는 과정

은행은:

- 은행 내부 기록 vs 외부 기록 비교

하지만 광고 집계에는:

> 비교할 제3자가 없음

### 해결 방법

**배치 결과와 실시간 결과 비교**

1. 각 파티션의 클릭 이벤트를
2. 이벤트 발생 시각 기준으로 정렬
3. 일괄 처리(batch)로 집계
4. 실시간 집계 결과와 비교

→ 차이가 있는지 확인

### 주의점

- 윈도 크기를 줄이면 정확도 ↑
- 하지만 늦게 도착한 이벤트는 존재
- 따라서 **배치 결과와 실시간 결과가 완전히 동일하지 않을 수 있음**
