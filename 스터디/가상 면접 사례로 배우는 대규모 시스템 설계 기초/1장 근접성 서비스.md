# 개요
**근접성 서비스(Proximity Service)** 란  
-> 사용자 위치 기준으로 가까운 장소를 찾는 서비스

### 대표 예시
- Yelp → 주변 맛집 검색
- Google Maps → 가까운 주유소 / 병원 / 카페 검색
---
# 요구사항
## 기능 요구사항
1. 위치 기반 사업장 검색
	- 입력:
	    - 사용자 위치 `(위도, 경도)`
	    - 검색 반경 (radius)
	- 출력:
	    - 해당 범위 내 사업장 목록
2. 사업장 정보 관리
	- 사업장 소유주가 수행 가능:
	    - 추가 (Create)
	    - 수정 (Update)
	    - 삭제 (Delete)
	- 특징:
	    - **실시간 반영 필요 없음**
	    - → 일정 지연 허용 (ex. 다음날 반영)
3. 사업장 상세 정보 조회
	- 사용자는:
	    - 특정 사업장 선택 후
	    - 상세 정보 확인 가능
	- 포함 정보 예시:
	    - 주소
	    - 설명
	    - (확장 시: 리뷰, 평점 등)

## 비기능 요구사항
1. 낮은 응답 지연 (Low Latency)
2. 데이터 보호 (Data Privacy)
3. 고가용성 및 규모 확장성 (High Availability & Scalability)

## 개략적 규모 추정
- **DAU (일간 능동 사용자)**: 1억 명
- **등록된 사업장 수**: 2억 개
- **사용자 1인당 하루 검색 횟수**: 5회
QPS:
- **1억 명 × 5회 = 5억 회/일**
- **QPS = 5억 / 10^5 = 5,000**

> 대부분 검색 요청이 차지하는 Read 위주 트래픽

# 데이터 모델
## 읽기/쓰기 비율
읽기 연산이 자주 발생하는 이유
- 주변 사업장 검색
- 사업장 정보 확인

반면 쓰기 연산은 상대적으로 적다.
- 사업장 정보 추가
- 사업장 정보 삭제
- 사업장 정보 편집

읽기 연산이 압도적인 시스템에는  **MySQL 같은 관계형 데이터베이스**가 바람직할 수 있다
## 데이터 스키마
이 시스템의 핵심 테이블을 두 개로 본다
### 1) business 테이블

- 사업장의 상세 정보를 저장
### 2) 지리적 위치 색인 테이블

- 위치 기반 검색 성능을 높이기 위한 인덱스 역할

> **상세 정보 저장용 테이블**과  **위치 검색 최적화용 테이블**을 분리하는 구조다.

## business 테이블

business 테이블은 사업장 상세 정보를 담는다.  
기본 키(primary key)는 `business_id` 다.

- `business_id` : PK
- `address`
- `city`
- `state`
- `country`
- `latitude`
- `longitude`

> 사업장 상세 정보는 포함되어 있지만, 검색 처리에 충분하지 않다.
>  `latitude`, `longitude` 컬럼이 있다고 해서  대규모 반경 검색이 자동으로 빨라지는 것은 아니기 때문

## 지리적 위치 색인 테이블

이 테이블은 **위치 정보 관련 연산의 효율성을 높이기 위해** 사용된다.

책에서는 이 부분을 이후 상세 설계에서 지오해시와 함께 더 설명한다.

- 특정 좌표 근처의 사업장을 빠르게 찾기 위한 보조 구조
- 반경 검색 시 전체 business 테이블을 풀스캔하지 않도록 도움

# 개략적 설계
![](images/Pasted%20image%2020260323214326.png)
개략적 설계안에서 시스템은 크게 **두 개의 서비스**로 나뉜다

- **LBS (Location-Based Service)**
    - 위치와 반경을 받아 주변 사업장을 검색
- **사업장 서비스**
    - 사업장 상세 정보 조회
    - 사업장 생성/수정/삭제 처리

그리고 이 둘 앞단에 **로드밸런서**가 있고, 뒤에는 **주-사본(Primary-Secondary) 데이터베이스 클러스터**가 있다

## 전체 흐름

사용자 요청은 먼저 **로드밸런서**로 들어온다.  
로드밸런서는 URL 경로를 보고 어느 서비스로 보낼지 결정한다.

### 경로 기준 분기

- `/search/nearby` → **LBS**
- `/businesses/{id}` → **사업장 서비스**

```
사용자  
  ↓  
로드밸런서  
  ├─ /search/nearby      → LBS  
  └─ /businesses/{id}    → 사업장 서비스  
                              ↓  
                     DB 클러스터(주 DB + 사본 DB들)
```

## 로드밸런서

로드밸런서는 외부에서 들어오는 트래픽을 여러 서비스로 자동 분산하는 진입점이다.

- 단일 DNS 진입점 제공
- URL 경로 분석
- 적절한 서비스로 요청 전달

## LBS (위치 기반 서비스)

LBS는 이 시스템의 핵심 서비스다.  
주어진 **위치(latitude, longitude)** 와 **반경(radius)** 정보를 사용해 주변 사업장을 검색한다.

특징:
- **읽기 요청만 빈번**
- **쓰기 요청 없음**
- **QPS가 높음**
- **무상태(stateless) 서비스**
- 따라서 **수평 확장 용이**

## 사업장 서비스

사업장 서비스는 사업장 관련 요청을 처리한다.

처리 요청:
1. 사업장 소유주의 쓰기 요청
	- 사업장 생성
	- 사업장 갱신
	- 사업장 삭제

2. 고객의 읽기 요청
	- 특정 사업장 상세 정보 조회

특징:
- 쓰기 QPS는 높지 않음
- 읽기 요청은 특정 시간대에 많아질 수 있음
- 무상태 서비스라 수평 확장 가능

## 데이터베이스 클러스터

DB는 **주 데이터베이스 + 사본 데이터베이스들** 구조로 구성된다.

- **주 데이터베이스(Primary)**
    - 쓰기 요청 처리
- **사본 데이터베이스(Secondary / Replica)**
    - 읽기 요청 처리

> LBS와 사업장 서비스 모두 **무상태 서비스**이므로 트래픽 변화에 따라 서버 수를 조절할 수 있다

# 주변 사업장 검색 알고리즘
**Redis Geohash, PostGIS 같은 제품명을 나열하는 것보다**  
지리적 위치 색인이 **어떻게 동작하는지 설명하는 것이 더 중요하다.**

주변 사업장 검색은 결국 다음 문제다.

- 입력:
    - 사용자 위치 `(latitude, longitude)`
    - 반경 `radius`
- 출력:
    - 반경 내에 있는 사업장 목록

## 방안 1 : 2차원 검색
주어진 위치를 중심으로 반경만큼 원을 그리고,  원 안에 포함되는 사업장을 찾는 방식이다.
![](images/Pasted%20image%2020260323215002.png)
```
SELECT business_id, latitude, longitude
FROM business
WHERE latitude BETWEEN my_lat - radius AND my_lat + radius
  AND longitude BETWEEN my_long - radius AND my_long + radius
```

쿼리 의미:
- 먼저 원이 아니라 **사각형 bounding box**를 만든 뒤
- 그 범위 안에 들어오는 후보를 찾는다는 것

> 정확히 원 내부 검색이라기보다는,  먼저 대략적인 후보군을 추리는 방식

비효율적인 이유:
1. 테이블 전체를 읽게 될 가능성이 높다
	- 사업장 수가 매우 많으면
	- 위도/경도 범위 조건만으로도 큰 비용이 든다
> 사실상 **풀스캔에 가까워질 수 있다.**

2.  위도/경도 각각 인덱스를 걸어도 충분하지 않다

예를 들어:
- latitude 인덱스
- longitude 인덱스

를 따로 만들 수는 있다.

> 하지만 문제는 데이터가 **2차원**이라는 점이다.

DB 인덱스는 보통 한 차원의 정렬/탐색에는 강하지만,  

문제는:
- 위도 범위 조건
- 경도 범위 조건
- 두 조건의 **교집합** 을 구해야 한다

데이터베이스의 한계:
> 일반적인 데이터베이스 인덱스로는 **오직 한 차원의 검색 속도만 개선**하기 쉽다.

## 지리적 위치 색인 방식
![](images/Pasted%20image%2020260323215539.png)
### 1) 해시 기반 방식

- 균등 격자 (even grid)
- 지오해시 (geohash)
- 카르테시안 계층 (cartesian tiers)

### 2) 트리 기반 방식

- 쿼드트리 (quadtree)
- 구글 S2
- R 트리 (R-tree)

위 방식들의 공통점:
> **지도를 작은 영역으로 분할하고, 그 영역을 빠르게 찾을 수 있도록 색인을 만든다.**

핵심:
- 매번 모든 사업장을 거리 계산하지 않고
- 먼저 **해당 위치 근처 영역(cell, tile, node)** 만 찾은 다음
- 그 안의 사업장만 후보로 삼는 것
