# 개요
**근접성 서비스(Proximity Service)** 란  
-> 사용자 위치 기준으로 가까운 장소를 찾는 서비스

### 대표 예시
- Yelp → 주변 맛집 검색
- Google Maps → 가까운 주유소 / 병원 / 카페 검색
---
# 요구사항
## 기능 요구사항
1. 위치 기반 사업장 검색
	- 입력:
	    - 사용자 위치 `(위도, 경도)`
	    - 검색 반경 (radius)
	- 출력:
	    - 해당 범위 내 사업장 목록
2. 사업장 정보 관리
	- 사업장 소유주가 수행 가능:
	    - 추가 (Create)
	    - 수정 (Update)
	    - 삭제 (Delete)
	- 특징:
	    - **실시간 반영 필요 없음**
	    - → 일정 지연 허용 (ex. 다음날 반영)
3. 사업장 상세 정보 조회
	- 사용자는:
	    - 특정 사업장 선택 후
	    - 상세 정보 확인 가능
	- 포함 정보 예시:
	    - 주소
	    - 설명
	    - (확장 시: 리뷰, 평점 등)

## 비기능 요구사항
1. 낮은 응답 지연 (Low Latency)
2. 데이터 보호 (Data Privacy)
3. 고가용성 및 규모 확장성 (High Availability & Scalability)

## 개략적 규모 추정
- **DAU (일간 능동 사용자)**: 1억 명
- **등록된 사업장 수**: 2억 개
- **사용자 1인당 하루 검색 횟수**: 5회
QPS:
- **1억 명 × 5회 = 5억 회/일**
- **QPS = 5억 / 10^5 = 5,000**

> 대부분 검색 요청이 차지하는 Read 위주 트래픽

# 데이터 모델
## 읽기/쓰기 비율
읽기 연산이 자주 발생하는 이유
- 주변 사업장 검색
- 사업장 정보 확인

반면 쓰기 연산은 상대적으로 적다.
- 사업장 정보 추가
- 사업장 정보 삭제
- 사업장 정보 편집

읽기 연산이 압도적인 시스템에는  **MySQL 같은 관계형 데이터베이스**가 바람직할 수 있다
## 데이터 스키마
이 시스템의 핵심 테이블을 두 개로 본다
### 1) business 테이블

- 사업장의 상세 정보를 저장
### 2) 지리적 위치 색인 테이블

- 위치 기반 검색 성능을 높이기 위한 인덱스 역할

> **상세 정보 저장용 테이블**과  **위치 검색 최적화용 테이블**을 분리하는 구조다.

## business 테이블

business 테이블은 사업장 상세 정보를 담는다.  
기본 키(primary key)는 `business_id` 다.

- `business_id` : PK
- `address`
- `city`
- `state`
- `country`
- `latitude`
- `longitude`

> 사업장 상세 정보는 포함되어 있지만, 검색 처리에 충분하지 않다.
>  `latitude`, `longitude` 컬럼이 있다고 해서  대규모 반경 검색이 자동으로 빨라지는 것은 아니기 때문

## 지리적 위치 색인 테이블

이 테이블은 **위치 정보 관련 연산의 효율성을 높이기 위해** 사용된다.

책에서는 이 부분을 이후 상세 설계에서 지오해시와 함께 더 설명한다.

- 특정 좌표 근처의 사업장을 빠르게 찾기 위한 보조 구조
- 반경 검색 시 전체 business 테이블을 풀스캔하지 않도록 도움

# 개략적 설계
![](images/Pasted%20image%2020260323214326.png)
개략적 설계안에서 시스템은 크게 **두 개의 서비스**로 나뉜다

- **LBS (Location-Based Service)**
    - 위치와 반경을 받아 주변 사업장을 검색
- **사업장 서비스**
    - 사업장 상세 정보 조회
    - 사업장 생성/수정/삭제 처리

그리고 이 둘 앞단에 **로드밸런서**가 있고, 뒤에는 **주-사본(Primary-Secondary) 데이터베이스 클러스터**가 있다

## 전체 흐름

사용자 요청은 먼저 **로드밸런서**로 들어온다.  
로드밸런서는 URL 경로를 보고 어느 서비스로 보낼지 결정한다.

### 경로 기준 분기

- `/search/nearby` → **LBS**
- `/businesses/{id}` → **사업장 서비스**

```
사용자  
  ↓  
로드밸런서  
  ├─ /search/nearby      → LBS  
  └─ /businesses/{id}    → 사업장 서비스  
                              ↓  
                     DB 클러스터(주 DB + 사본 DB들)
```

## 로드밸런서

로드밸런서는 외부에서 들어오는 트래픽을 여러 서비스로 자동 분산하는 진입점이다.

- 단일 DNS 진입점 제공
- URL 경로 분석
- 적절한 서비스로 요청 전달

## LBS (위치 기반 서비스)

LBS는 이 시스템의 핵심 서비스다.  
주어진 **위치(latitude, longitude)** 와 **반경(radius)** 정보를 사용해 주변 사업장을 검색한다.

특징:
- **읽기 요청만 빈번**
- **쓰기 요청 없음**
- **QPS가 높음**
- **무상태(stateless) 서비스**
- 따라서 **수평 확장 용이**

## 사업장 서비스

사업장 서비스는 사업장 관련 요청을 처리한다.

처리 요청:
1. 사업장 소유주의 쓰기 요청
	- 사업장 생성
	- 사업장 갱신
	- 사업장 삭제

2. 고객의 읽기 요청
	- 특정 사업장 상세 정보 조회

특징:
- 쓰기 QPS는 높지 않음
- 읽기 요청은 특정 시간대에 많아질 수 있음
- 무상태 서비스라 수평 확장 가능

## 데이터베이스 클러스터

DB는 **주 데이터베이스 + 사본 데이터베이스들** 구조로 구성된다.

- **주 데이터베이스(Primary)**
    - 쓰기 요청 처리
- **사본 데이터베이스(Secondary / Replica)**
    - 읽기 요청 처리

> LBS와 사업장 서비스 모두 **무상태 서비스**이므로 트래픽 변화에 따라 서버 수를 조절할 수 있다

# 주변 사업장 검색 알고리즘
**Redis Geohash, PostGIS 같은 제품명을 나열하는 것보다**  
지리적 위치 색인이 **어떻게 동작하는지 설명하는 것이 더 중요하다.**

주변 사업장 검색은 결국 다음 문제다.

- 입력:
    - 사용자 위치 `(latitude, longitude)`
    - 반경 `radius`
- 출력:
    - 반경 내에 있는 사업장 목록

## 방안 1 : 2차원 검색
주어진 위치를 중심으로 반경만큼 원을 그리고,  원 안에 포함되는 사업장을 찾는 방식이다.
![](images/Pasted%20image%2020260323215002.png)
```
SELECT business_id, latitude, longitude
FROM business
WHERE latitude BETWEEN my_lat - radius AND my_lat + radius
  AND longitude BETWEEN my_long - radius AND my_long + radius
```

쿼리 의미:
- 먼저 원이 아니라 **사각형 bounding box**를 만든 뒤
- 그 범위 안에 들어오는 후보를 찾는다는 것

> 정확히 원 내부 검색이라기보다는,  먼저 대략적인 후보군을 추리는 방식

비효율적인 이유:
1. 테이블 전체를 읽게 될 가능성이 높다
	- 사업장 수가 매우 많으면
	- 위도/경도 범위 조건만으로도 큰 비용이 든다
> 사실상 **풀스캔에 가까워질 수 있다.**

2.  위도/경도 각각 인덱스를 걸어도 충분하지 않다

예를 들어:
- latitude 인덱스
- longitude 인덱스

를 따로 만들 수는 있다.

> 하지만 문제는 데이터가 **2차원**이라는 점이다.

DB 인덱스는 보통 한 차원의 정렬/탐색에는 강하지만,  

문제는:
- 위도 범위 조건
- 경도 범위 조건
- 두 조건의 **교집합** 을 구해야 한다

데이터베이스의 한계:
> 일반적인 데이터베이스 인덱스로는 **오직 한 차원의 검색 속도만 개선**하기 쉽다.

## 지리적 위치 색인 방식
![](images/Pasted%20image%2020260323215539.png)
### 1) 해시 기반 방식

- 균등 격자 (even grid)
- 지오해시 (geohash)
- 카르테시안 계층 (cartesian tiers)

### 2) 트리 기반 방식

- 쿼드트리 (quadtree)
- 구글 S2
- R 트리 (R-tree)

위 방식들의 공통점:
> **지도를 작은 영역으로 분할하고, 그 영역을 빠르게 찾을 수 있도록 색인을 만든다.**

핵심:
- 매번 모든 사업장을 거리 계산하지 않고
- 먼저 **해당 위치 근처 영역(cell, tile, node)** 만 찾은 다음
- 그 안의 사업장만 후보로 삼는 것

## 방안 2 : 균등 격자

- 지도를 일정한 크기의 작은 격자로 나눈다
- 하나의 사업장은 하나의 격자에 속한다
- 검색 시 현재 위치가 속한 격자와 주변 격자를 탐색한다

### 장점
- 단순하고 구현이 쉬움

### 문제점
1. 데이터 분포가 균등하지 않다

- 도심에는 사업장이 몰려 있음
- 바다, 사막에는 거의 없음

즉 전 세계를 동일 크기 격자로 나누면,  
격자별 데이터 분포가 심하게 불균형해진다.

2. 인접 격자 찾기가 까다로울 수 있다

- 단순히 격자를 나누는 것만으로는
- 주변 격자를 효율적으로 탐색하는 체계가 부족할 수 있다

## 방안 3 : 지오 해시
2차원 좌표(위도, 경도)를 → 1차원 문자열로 변환하는 방식
- 세계를 계속 쪼개면서
- 각 영역을 **binary → base32 문자열**로 표현

### 동작 방식
1. 최초 분할 (4등분)

- 위도 기준:
    - [-90, 0] → 0
    - [0, 90] → 1
- 경도 기준:
    - [-180, 0] → 0
    - [0, 180] → 1

- 4개의 영역 생성 (00, 01, 10, 11)

1. 재귀적 분할

- 각 영역을 다시 4등분
- 위도/경도 비트를 번갈아가며 추가

반복하면:
- 2D 공간 → 점점 작은 grid → bit sequence

3. 문자열 변환

- binary → base32 변환

예시:
- Google HQ → `9q9hvu`
- Meta HQ → `9q9jhr`

> 공통 prefix 많을수록 → 가까운 위치

### 특징
1. Prefix 기반 거리 근사
```
9q9h → 큰 영역  
9q9hvu → 더 작은 영역
```
2. 2D → 1D 변환 효과
	-  B-Tree 인덱스 활용
	- prefix 검색 (`LIKE '9q9h%'`)
	- range scan 가능
3. 정밀도
	- 지오해시 길이 = 격자 크기

|길이|영역 크기|
|---|---|
|3|~156km|
|5|~4.9km|
|6|~1.2km|
|7|~150m|
> 보통 **길이 4~6 사용**

```
사용자 위치 → geohash 생성

→ 해당 prefix + 인접 prefix 조회

→ 후보 business 추출

→ 실제 거리 계산으로 필터링
```
> geo hash 는 정확한 원 계산이 아님. 
> 격자 기반 근사 검색이기 때문에, 반드시 후처리 필터링 작업이 필요함

### 엣지 케이스 문제
1. 가까운데 prefix가 다를 수 있음
2. 격자 경계 문제
	1. 경계의 경우 놓칠 수 있음

### 장점

1. 단순하고 빠름

- 구현 쉬움
- 문자열 기반

2. DB 친화적

- B-Tree index 사용 가능
- prefix scan 가능

3. 확장성 좋음

- shard key로도 활용 가능


### 단점

1. 정확한 원형 검색 아님

- 사각형 기반

2. edge case 존재

- prefix mismatch
- 경계 문제

3. 데이터 skew 문제

- 도심 vs 시골

## 방안 4 : 쿼드 트리
2차원 공간을 재귀적으로 4등분하면서 분할하는 트리 구조
- 공간을 계속 쪼개되
- **데이터 밀도 기준으로 분할을 멈춤**

균등 격자와 가장 큰 차이:

- 균등 격자 → “크기 기준”
- 쿼드트리 → “데이터 개수 기준”

> “사업장이 많은 곳은 더 잘게 쪼개고, 적은 곳은 크게 유지한다”

### 동작 방식
1. 시작 (루트 노드)

- 전체 세계를 하나의 노드로 시작

2. 분할 조건
```
if (해당 영역 사업장 수 > threshold) {  
    4등분  
}
```

- 예시:
    - threshold = 100개

3. 재귀 분할

- 각 영역을 다시 4개로 분할
- 조건 만족할 때까지 반복

4. 종료 조건

- 한 격자에 포함된 사업장 수 ≤ threshold

> 이 노드를 **leaf node**라고 함

###  구조 예시
```
전체 지도  
 ├─ NW  
 ├─ NE  
 ├─ SW  
 └─ SE  
      ├─ 더 쪼갬 (사업장 많으면)  
      └─ 그대로 유지 (적으면)
```


### 노드 구성

1. Leaf Node

- 포함 데이터:
    - 사업장 ID 목록 (최대 100개)
    - 영역 좌표 (bounding box)

> 약 **832 bytes**

2. Internal Node

- 포함 데이터:
    - 영역 좌표
    - 자식 노드 4개 포인터

> 약 **64 bytes**

### 메모리 계산

- 전체 사업장: 2억 개
- leaf node 수:
    - 약 200만 개
- internal node:
    - 약 67만 개

총 메모리:

> 약 **1.7GB** 메모리 사용량이 생각보다 작아서, 서버 메모리에 충분히 올릴 수 있음.

### 검색 방식

전체 흐름

1. 루트부터 탐색  
2. 해당 좌표 포함된 leaf node 찾기  
3. 해당 node의 business 반환    
4. 부족하면 → 인접 node 확장

### 핵심 포인트

- 처음엔 **하나의 leaf node**
- 부족하면 → **주변 노드 추가**

지오해시와 동일한 패턴:

> “후보 부족 → 범위 확장”


### 장점

1. 데이터 분포 최적화

- 도심 → 작은 cell
- 시골 → 큰 cell

> skew 해결 

2. 빠른 검색
- 트리 탐색 → O(log n)
- 매우 빠름

3. 메모리 효율

- 생각보다 작음 (~1.7GB)

### 단점

1. 메모리 기반

- 서버 재시작 시 재구축 필요

2. 동적 업데이트 어려움

- 사업장 추가/삭제 시:
    - 트리 재구성 필요 가능

3. 분산 관리 필요

- 서버마다 동일 트리 유지 필요
## 방안 5 : 구글 S2
- **구글 S2 geometry 라이브러리**는 위치/지리 정보 색인 분야에서 유명한 솔루션
- 쿼드트리처럼 **메모리 기반(in-memory)** 으로 동작하는 방식
- 핵심 아이디어는 **지구 표면(sphere)을 1차원으로 색인화**하는 것

### 핵심 원리
- S2는 지구 표면을 **힐베르트 곡선(Hilbert curve)** 이라는 **공간 채움 곡선(space-filling curve)** 으로 펼쳐서 **1차원 인덱스**로 변환
- 힐베르트 곡선의 중요한 특징:
    - **2차원 공간에서 가까운 점들이 1차원 인덱스 상에서도 가깝게 배치**된다.
- 그래서:
    - 2차원 좌표 공간에서 직접 검색하는 것보다
    - **1차원 공간에서 검색하는 것이 더 효율적**일 수 있다
![](images/Pasted%20image%2020260329162129.png)

### 장점

#### 1. 지오펜스 구현에 적합

- S2는 **지오펜스(geofence)** 구현에 특히 유리하다.
- 지오펜스는 현실 세계의 특정 지역에 설정한 **가상의 경계**를 의미한다.
- 예:
    - 어떤 지점을 기준으로 반경 몇 km
    - 학교 주변 구역
    - 특정 동네나 행정구역 경계

#### 2. 유연한 영역 지정 가능

- 임의의 지역을 **다양한 수준으로 세밀하게 나눌 수 있다.**
- 따라서 단순한 “주변 검색”뿐 아니라,
    - 특정 영역 진입/이탈 감지
    - 위치 기반 알림  
        같은 더 풍부한 기능 구현이 가능하다.

#### 3. Region Cover Algorithm 제공

- S2의 또 다른 장점은 **영역 지정 알고리즘(Region Cover Algorithm)** 이다.
- 지오해시처럼 고정 정밀도만 사용하는 것이 아니라,
    - **최소 level**
    - **최대 level**
    - **최대 cell 개수**  
        등을 지정할 수 있다.
- 즉, **셀 크기를 유연하게 조절**할 수 있어서 결과를 더 정교하게 만들 수 있다.

# 지오해시 vs 쿼드트리
## 1. 지오해시 (Geohash)

### 특징

- 위도/경도를 **문자열(1차원)** 로 인코딩
- 트리 구조 없이 **단순 key 기반 색인**

### 장점

- **구현이 매우 쉽다**
    - 트리 구조 필요 없음
- **색인 갱신이 간단**
    - (geohash, business_id) row만 추가/삭제
-  **범위 검색 (반경 검색)** 지원

### 단점

-  **격자 크기가 고정됨**
    - 정밀도 = 셀 크기
    - 밀집 지역 / 비밀집 지역 구분 못함
- **KNN (k개 최근접 검색) 부적합**
-  경계 문제 (edge case) 존재
    - 인접 영역이 다른 prefix일 수 있음

## 2. 쿼드트리 (Quadtree)

### 특징

- 2D 공간을 **재귀적으로 4분할하는 트리 구조**
- 밀도에 따라 **동적으로 분할**

### 장점

-  **동적 격자 크기**
    - 밀집 지역 → 더 작게
    - 비밀집 지역 → 더 크게
- **KNN 검색에 강함**
    - “가장 가까운 k개” 찾기 쉬움
-  공간 분포에 최적화된 구조

### 단점

- **구현 복잡**
    - 트리 생성 + 유지 필요
- **갱신 비용 높음**
    - 삭제/삽입 시 트리 탐색 필요 (O(log n))
- **동시성 처리 어려움**
    - 락, 리밸런싱 필요

## 3. 핵심 비교 

|항목|지오해시|쿼드트리|
|---|---|---|
|구조|문자열 기반|트리 구조|
|구현 난이도|매우 쉬움|복잡|
|색인 갱신|매우 쉬움|비용 큼|
|격자 크기|고정|동적|
|밀도 대응|❌|✅|
|KNN 검색|❌|✅|
|운영 난이도|낮음|높음|

## 4. 언제 뭐 쓰냐 

### 지오해시 쓰는 경우

- CRUD 많음 (업데이트 잦음)
- 빠르게 구현해야 함
- 단순 반경 검색이면 충분

👉 예:

- 주변 맛집 검색
- 간단한 위치 기반 서비스

### 쿼드트리 쓰는 경우

- “가장 가까운 k개”가 중요
- 지역 밀도 차이가 큼
- 검색 정확도가 중요

👉 예:

- 주유소 찾기
- 추천 시스템 (nearest N)

- 락 필요 없음

# 캐시 키

## Geohash / Quadtree 기반 캐시 키

```
cache_key = geohash
```

## 왜 Geohash가 좋은가

### 핵심 아이디어

- 좌표를 그대로 쓰지 않고
- **“격자(cell)” 단위로 그룹화**

### 효과

#### 1. 위치 노이즈 제거

- 같은 지역 → 같은 geohash
- GPS 오차 영향 제거

#### 2. 캐시 hit 증가

- 근처 사용자 → 동일 캐시 사용

#### 3. 안정적인 캐시 키

- 작은 이동 → 동일 key 유지


## 실제 캐시 구조

### 1. 주변 사업장 캐시
```
key: geohash  
value: 해당 격자 내 business_id 리스트
```

### 2. 사업장 상세 정보 캐시

```
key: business_id  
value: business 정보 객체
```

## 검색 반경과 캐시 키

### 요구사항

- 500m / 1km / 2km / 5km

### 해결 방법

- geohash precision 조절

|반경|geohash 길이|
|---|---|
|500m|4|
|1km|5|
|2km|5|
|5km|6|

👉 따라서

- **precision별 캐시를 따로 유지**

## 캐시 조회 흐름

```
List<String> getNearbyBusinessIds(geohash) {  
    List ids = Redis.get(geohash);  
  
    if (ids == null) {  
        ids = DB 조회  
        Redis.set(geohash, ids, TTL=1day)  
    }  
  
    return ids;  
}
```

## 캐시 무효화 전략

- 사업장 추가 / 수정 / 삭제 시:
    - DB 업데이트
    - 해당 geohash 캐시 invalidate

👉 업데이트 빈도 낮음 → 단순 invalidate로 충분

# 지역 및 가용성 구역
## 1. 왜 필요한가

위치 기반 서비스(LBS)는  
👉 **전 세계 사용자 대상 + 실시간 응답 요구**

따라서 핵심 목표는:

- **지연(latency) 최소화**
- **고가용성(HA) 확보**
- **트래픽 분산**

## 2. 기본 설계 전략

### Region 단위 배치

- 여러 지역(Region)에 서비스 배포

예:

- US West
- Europe
- Asia (한국/일본 등)

👉 사용자와 가까운 Region으로 라우팅

### AZ (Availability Zone) 활용

- 하나의 Region 안에서도
    - 여러 AZ로 분산

👉 장애 대응 + 부하 분산

## 3. 기대 효과

### 1) 지연 시간 최소화

- 사용자 ↔ 서버 거리 감소

예:

- 미국 사용자 → US West
- 유럽 사용자 → Europe

👉 latency 감소 (10ms vs 100ms급 차이)

### 2) 트래픽 분산

- 인구 밀도 기반 분산 가능

예:

- 한국 / 일본 → 트래픽 많음
    - 별도 Region 분리 가능
    - 또는 여러 AZ로 분산

👉 hotspot 방지

### 3) 고가용성 (HA)

- AZ 장애 발생 시:
    - 다른 AZ로 failover
- Region 장애 시:
    - 다른 Region으로 대응 (DR)

### 4) 법적 요구사항 대응 (중요 ⭐)

- 국가별 **데이터 규제 (privacy law)** 존재

예:

- 어떤 국가는:
    - 데이터를 **해외로 못 보냄**

👉 해결:

- 해당 국가에 Region 따로 구성
- DNS 라우팅으로 해당 Region만 사용

## 4. 라우팅 전략

### 👉 DNS 기반 라우팅

- 사용자 위치 기반으로
- 가장 가까운 Region으로 연결

## 5. 데이터 전략

### 캐시 (Redis 등)

- 각 Region에 동일 데이터 복제

👉 이유:

- cross-region 호출 방지
- latency 감소
