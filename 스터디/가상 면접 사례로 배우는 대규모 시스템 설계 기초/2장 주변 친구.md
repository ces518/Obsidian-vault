# 개요

**“주변 친구(nearby friends)” 기능을 지원하는 백엔드 시스템**이다.

기능
```
사용자가 위치 공유를 허용한 경우  
현재 위치 기준으로  
근처에 있는 친구 목록을 보여준다
```

예시 (페이스북 기능)

- 친구 이름
    
- 현재 거리
    
- 마지막 위치 갱신 시각

# 개략적 설계안
사용자 위치 업데이트발생시 해당 사용자의 친구들에게  **위치 변경 정보를 전달**해야 한다
## P2P 방식
각 친구가 **지속적인 연결을 유지**하면 된다.

하지만 현실적으로 문제

- 모바일 네트워크 불안정
    
- 배터리 문제
    
- 연결 관리 어려움
> P2P 방식은 비현실적이다

## 공용 백엔드 방식
![](images/Pasted%20image%2020260316201936.png)
백엔드 역할

2. 친구 목록 조회  
3. 친구들에게 위치 전달

### 트래픽 규모 문제
가정
- 동시 사용자: **1000만**
- 위치 업데이트: **30초**

```
위치 업데이트 QPS

10,000,000 / 30 ≈ 334,000 QPS

평균 친구수 400명 / 활성 10% 가정

334,000 × 400 × 10%
≈ 14,000,000 events/sec
```

## 주기적 위치 갱신
모바일 클라이언트는 **지속적으로 유지되는 WebSocket 연결**을 통해 주기적으로 위치 정보를 서버로 전송한다.

전송 데이터

- 위도 (latitude)
    
- 경도 (longitude)
    
- 타임스탬프 (timestamp)
    

목적

- 친구에게 최신 위치 전달

### 위치 갱신 처리 흐름
![](images/Pasted%20image%2020260316203225.png)
1. 클라이언트 → 로드밸런서
	모바일 클라이언트가 위치 변경 이벤트를 전송한다.
	Client → Load Balancer

2. 로드밸런서 → WebSocket 서버
	로드밸런서는 해당 사용자가 연결된 WebSocket 서버로 요청을 전달한다.
	Load Balancer → WebSocket Server

3.  위치 이력 저장
	WebSocket 서버는 위치 변경 이벤트를
	Location History Database 에 저장한다.
	
	목적
	
	- 위치 이동 기록 보존
	    
	- 분석 / ML 활용
	    
4. 위치 캐시 업데이트

	WebSocket 서버는 새로운 위치를 Location Cache (Redis) 에 저장한다.
	
	이때 TTL(Time-To-Live) 도 함께 갱신한다.
	
	TTL이 지나면
	
	사용자 → 비활성 상태
	
	로 간주되고 캐시에서 삭제된다.


5. Pub/Sub 이벤트 발행

	WebSocket 서버는 위치 변경 이벤트를
	
	Redis Pub/Sub
	
	채널에 발행한다.

6. 이벤트 브로드캐스트

	Redis Pub/Sub은 해당 채널의 **모든 구독자에게 이벤트를 전달한다.**
	
	구독자
	
	해당 사용자와 친구 관계인 WebSocket 핸들러
	
	즉
	
	친구들의 WebSocket 서버
	
	가 이벤트를 수신한다.

7. 거리 계산

	각 WebSocket 서버는
	
	친구 위치 vs 사용자 위치
	
	를 이용해 **거리를 계산**한다.


8. 검색 반경 판단

	거리 계산 결과 검색 반경 이내
	
	라면
	
	위치 업데이트 전송
	
	반경 밖이면 전송하지 않음

9. 친구 클라이언트로 전달

	조건을 만족하면 WebSocket을 통해 친구의 모바일 앱으로 전달한다.
	
	전송 데이터
	- 위도  
	- 경도  
	- timestamp

### 정리
```
WebSocket 위치 업데이트
        ↓
Redis 캐시 갱신
        ↓
Redis Pub/Sub 이벤트 발행
        ↓
친구 WebSocket 핸들러 전달
        ↓
거리 계산
        ↓
반경 내 친구에게 위치 전달
```

# 데이터 모델
주변 친구 서비스에서 중요한 데이터는 크게 3가지

|데이터|역할|
|---|---|
|사용자 데이터|사용자 정보 + 친구 관계|
|위치 정보 캐시|활성 사용자 최신 위치|
|위치 이동 이력 DB|위치 변경 기록|
## 위치 정보 캐시
활성 상태 친구의 "가장 최근 위치" 저장
**Redis** 를 활용해 캐시한다
- 매우 빠른 읽기/쓰기
- TTL 지원
	- 비활성 사용자 자동 제거
- 캐시 용도에 적합

위치 정보 저장에 DB 를 사용하지 않는 이유 ?
- 현재 위치만 필요

## 위치 이동 이력 데이터베이스
캐시와 별개로 위치이동 이력을 데이터베이스 저장한다

목적
- 위치 이력 활용
- 데이터 분석
- ML
- 사용자 이동 패턴
- 지도 개선

데이터 구조

| 컬럼        | 설명     |
| --------- | ------ |
| user_id   | 사용자 ID |
| latitude  | 위도     |
| longitude | 경도     |
| timestamp | 기록 시각  |

이 데이터베이스는 엄청난 **write workload** 를 처리해야 하기 때문에 Cassandra 권장
- 샤딩키로 user_id 를 사용해서 부하 분산 처리

# 상세 설계
## 중요 구성 요소별 확장성
### API 서버

API 서버는 **무상태(stateless) 서버**다.

특징:

- 친구 추가/삭제
    
- 사용자 정보 갱신
    
- 일반 HTTP 요청 처리
    

확장 방식:

CPU 사용률 / 부하 / I/O 상태에 따라  
클러스터 크기를 자동 확장

일반적인 REST API 서버 스케일링 문제이므로 비교적 단순하다.

핵심 포인트:

- 세션 상태를 서버에 들고 있지 않음
    
- 오토스케일링이 쉬움
    
- 로드밸런서 뒤에 여러 대를 두면 됨

### 웹 소켓 서버

웹소켓 서버는 **유상태(stateful) 서버**다.

이게 상세 설계에서 중요한 차이점이다.

이유:

- 클라이언트와 장시간 지속 연결을 유지함
    
- 연결 상태가 서버 메모리에 걸려 있음
    
- 단순히 서버를 바로 내리면 연결이 끊김
    
웹소켓 서버 확장 시 주의점:

웹소켓 클러스터도 사용량에 따라 늘리는 것은 어렵지 않다.  
문제는 **기존 서버를 제거할 때**다.

처리 방식:

1. 서버를 로드밸런서에서 **draining 상태**로 변경
    
2. 그 서버로는 **새로운 웹소켓 연결을 받지 않음**
    
3. 기존 연결이 모두 종료될 때까지 대기
    
4. 충분한 시간이 지난 뒤 서버 제거
> stateful server는 scale-in이 scale-out보다 어렵다

**웹소켓 서버 배포 시 주의점:**

새 버전 애플리케이션을 배포할 때도 같은 문제가 생긴다.

- 연결을 가진 서버를 바로 교체하면 안 됨
    
- drain 후 점진적으로 교체해야 함
    
**클라이언트 초기화 절차:**

모바일 클라이언트가 시작되면 **웹소켓 클러스터 내 특정 서버와 지속 연결**을 맺는다.

이 연결은 오래 유지되며, 현대 언어/런타임에서는 이런 연결 유지 비용이 아주 크지 않다고 본다.

웹소켓 연결이 만들어진 뒤의 흐름이 상세 설계 핵심이다.

**초기화 시 웹소켓 핸들러가 수행하는 작업:**

1) 내 위치 갱신

클라이언트가 자신의 현재 위치를 전송하면, 서버는

위치 정보 캐시에 사용자 위치 저장/갱신

한다.

2) 핸들러 내부 상태 저장

이 위치 정보는 뒤에서 거리 계산에 쓰이므로

연결 핸들러 내부 변수에도 저장

한다.

> 즉, 현재 연결 세션이 자기 사용자의 최신 위치를 기억한다.

3) 친구 목록 조회

사용자 DB에서

해당 사용자의 친구 목록 전체 조회

를 수행한다.

4) 친구 위치 일괄 조회

위치 정보 캐시에 대해 **batch 요청**으로 친구들의 위치를 한 번에 가져온다.

이때 중요한 점:

- 캐시 항목 TTL = inactivity timeout
    
- 최근 위치 갱신이 없는 비활성 친구는 캐시에 없음
    
> 즉 캐시에 존재하는 친구만 사실상 “현재 활성 상태”로 본다.


5) 거리 계산 후 초기 응답 반환

가져온 친구 위치 각각에 대해

나와 친구 사이 거리 계산 을 수행하고, 검색 반경 이내인 친구만 클라이언트에 내려준다.

반환 정보:

- 친구 상세 정보
    
- 친구 위치
    
- 마지막 위치 확인 시각
    

> 즉 앱 시작 직후 사용자는 **현재 주변 친구 목록의 초기 스냅샷**을 받는다.

6) 친구 채널 구독

웹소켓 서버는 각 친구의 Redis Pub/Sub 채널을 구독한다.

이유:

- 이후 친구 위치가 바뀌었을 때 실시간으로 이벤트를 받기 위해
    

중요한 설계 포인트:

- 친구가 지금 비활성 상태여도 채널은 구독 가능
    
- 채널 유지 비용은 작음
    
- 비활성 친구는 CPU/I/O를 거의 쓰지 않음
    

> 구독을 미리 걸어두고, 실제 이벤트가 올 때만 반응하는 구조다.

7) 내 위치를 친구들에게 발행

마지막으로 현재 사용자의 위치를

자기 전용 Redis Pub/Sub 채널에 publish

한다.

> 이 사용자를 친구로 둔 다른 사람들의 웹소켓 핸들러가 이벤트를 받고, 각자 자기 사용자 기준으로 거리 계산 후 클라이언트에 반영한다.

### 사용자 데이터베이스 설계

사용자 DB에는 크게 두 종류의 데이터가 있다.

**사용자 프로필 데이터**

예:

- 사용자 ID
    
- 사용자명
    
- 프로필 이미지 URL
    

**친구 관계 데이터**

예:

- 사용자 A의 친구 목록
    
- 친구 추가/삭제 관계
    
**확장 방식**

이 정도 규모에서는 단일 관계형 DB 한 대로는 부족하다.  
그래서

사용자 ID 기준 샤딩 을 적용한다.

장점:

- 데이터 분산이 비교적 단순
    
- 운영 관리가 쉬움
    
- 관계형 DB도 수평 확장 가능
    
### 위치정보 캐시 설계
활성 상태 사용자의 최신 위치만 저장 한다.

구조:

key   = 사용자 ID  
value = {위도, 경도, 시각}

Redis를 쓰는 이유:

- 읽기/쓰기 매우 빠름
    
- TTL 지원
    
- 위치 정보 영속성 요구가 낮음
    
시스템은
```
현재 위치 = hot data  
과거 위치 = history DB
```
로 분리한다.

### 위치 이동 이력 데이터베이스
위치 변경 이력은 별도 DB에 저장한다.

스키마 예시:

- user_id
    
- latitude
    
- longitude
    
- timestamp
    

요구사항:

- 막대한 쓰기 부하 감당
    
- 수평 확장 가능
    

적합한 저장소:

Cassandra

이유:

- write-heavy workload에 강함
    
- 샤딩 친화적
    
- 대규모 분산 저장에 적합
    
샤딩 기준도 기본적으로 **user_id** 를 사용한다.

# 얼마나 많은 레디스 펍섭 서버가 필요한가 ?

레디스 펍/섭 서버는 이 시스템에서

- 사용자별 채널 보관
    
- 친구들의 채널 구독 관계 관리
    
- 위치 변경 이벤트 fan-out
    
을 담당한다.

따라서 필요한 서버 수는 크게 두 가지 관점에서 본다.

- **메모리 사용량**
    
- **CPU / 메시지 전달 처리량**

## 메모리 사용량 계산

가정:

- 주변 친구 기능 사용자 수: **1억 명**  
    (전체 10억 사용자 중 10%)
    
- 사용자당 채널 1개
    
- 한 사용자의 활성 친구 중 이 기능을 쓰는 친구 수: **100명**
    
- 구독자 1명을 추적하는 데 필요한 메모리: **20바이트**

모든 채널을 저장하는 데 필요한 메모리:
```
1억 채널 × 100명 친구 × 20바이트  
≈ 200GB
```

최신 서버 한 대가 **100GB 메모리**를 장착할 수 있다고 보면

레디스 펍/섭 서버 2대면  모든 채널 메타데이터 보관 가능

- 채널 수 자체는 매우 많지만
    
- 채널/구독 관계 유지에 드는 메모리는 생각보다 감당 가능

## CPU 사용량 계산
진짜 문제는 메모리가 아니라 **이벤트 전달량**이다.

앞서 계산한 위치 업데이트 fan-out 규모:

- 초당 1,400만 건의 위치 정보 업데이트 전달

이 정도 메시지를 단일 Redis Pub/Sub 서버가 처리하기는 어렵다고 본다.

가정:

최신 서버 한 대가 감당 가능한 구독자 수를 보수적으로

100,000 subscribers

라고 가정한다.

그러면 필요한 서버 수는:

14,000,000 / 100,000 = 140

결론:

필요한 레디스 펍/섭 서버 수 ≈ 140대

책에서도 이 숫자는 **매우 보수적인 추정치**일 수 있다고 본다.  
실제 서버 성능이 더 좋다면 필요한 수는 더 적을 수 있다.

## 결론
메모리가 아닌, CPU 병목이 먼저 온다

단일 Redis Pub/Sub 서버로는 불가능
