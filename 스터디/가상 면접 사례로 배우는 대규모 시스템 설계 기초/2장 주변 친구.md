# 개요

**“주변 친구(nearby friends)” 기능을 지원하는 백엔드 시스템**이다.

기능
```
사용자가 위치 공유를 허용한 경우  
현재 위치 기준으로  
근처에 있는 친구 목록을 보여준다
```

예시 (페이스북 기능)

- 친구 이름
    
- 현재 거리
    
- 마지막 위치 갱신 시각

2. 안정성
3. 최종적 일관성

# 개략적 설계안
사용자 위치 업데이트발생시 해당 사용자의 친구들에게  **위치 변경 정보를 전달**해야 한다
## P2P 방식
각 친구가 **지속적인 연결을 유지**하면 된다.

하지만 현실적으로 문제

- 모바일 네트워크 불안정
    
- 배터리 문제
    
- 연결 관리 어려움
> P2P 방식은 비현실적이다

## 공용 백엔드 방식
![](images/Pasted%20image%2020260316201936.png)
백엔드 역할
1. 위치 업데이트 수신  
2. 친구 목록 조회  
3. 친구들에게 위치 전달

### 트래픽 규모 문제
가정
- 동시 사용자: **1000만**
- 위치 업데이트: **30초**

```
위치 업데이트 QPS

10,000,000 / 30 ≈ 334,000 QPS

평균 친구수 400명 / 활성 10% 가정

334,000 × 400 × 10%
≈ 14,000,000 events/sec
```

## 주기적 위치 갱신
모바일 클라이언트는 **지속적으로 유지되는 WebSocket 연결**을 통해 주기적으로 위치 정보를 서버로 전송한다.

전송 데이터

- 위도 (latitude)
    
- 경도 (longitude)
    
- 타임스탬프 (timestamp)
    

목적

- 친구에게 최신 위치 전달

### 위치 갱신 처리 흐름
![](images/Pasted%20image%2020260316203225.png)
1. 클라이언트 → 로드밸런서
	모바일 클라이언트가 위치 변경 이벤트를 전송한다.
	Client → Load Balancer

2. 로드밸런서 → WebSocket 서버
	로드밸런서는 해당 사용자가 연결된 WebSocket 서버로 요청을 전달한다.
	Load Balancer → WebSocket Server

3.  위치 이력 저장
	WebSocket 서버는 위치 변경 이벤트를
	Location History Database 에 저장한다.
	
	목적
	
	- 위치 이동 기록 보존
	    
	- 분석 / ML 활용
	    
4. 위치 캐시 업데이트

	WebSocket 서버는 새로운 위치를 Location Cache (Redis) 에 저장한다.
	
	이때 TTL(Time-To-Live) 도 함께 갱신한다.
	
	TTL이 지나면
	
	사용자 → 비활성 상태
	
	로 간주되고 캐시에서 삭제된다.


5. Pub/Sub 이벤트 발행

	WebSocket 서버는 위치 변경 이벤트를
	
	Redis Pub/Sub
	
	채널에 발행한다.

6. 이벤트 브로드캐스트

	Redis Pub/Sub은 해당 채널의 **모든 구독자에게 이벤트를 전달한다.**
	
	구독자
	
	해당 사용자와 친구 관계인 WebSocket 핸들러
	
	즉
	
	친구들의 WebSocket 서버
	
	가 이벤트를 수신한다.

7. 거리 계산

	각 WebSocket 서버는
	
	친구 위치 vs 사용자 위치
	
	를 이용해 **거리를 계산**한다.


8. 검색 반경 판단

	거리 계산 결과 검색 반경 이내
	
	라면
	
	위치 업데이트 전송
	
	반경 밖이면 전송하지 않음

9. 친구 클라이언트로 전달

	조건을 만족하면 WebSocket을 통해 친구의 모바일 앱으로 전달한다.
	
	전송 데이터
	- 위도  
	- 경도  
	- timestamp

### 정리
```
WebSocket 위치 업데이트
        ↓
Redis 캐시 갱신
        ↓
Redis Pub/Sub 이벤트 발행
        ↓
친구 WebSocket 핸들러 전달
        ↓
거리 계산
        ↓
반경 내 친구에게 위치 전달
```

# 데이터 모델
주변 친구 서비스에서 중요한 데이터는 크게 3가지

|데이터|역할|
|---|---|
|사용자 데이터|사용자 정보 + 친구 관계|
|위치 정보 캐시|활성 사용자 최신 위치|
|위치 이동 이력 DB|위치 변경 기록|
## 위치 정보 캐시
활성 상태 친구의 "가장 최근 위치" 저장
**Redis** 를 활용해 캐시한다
- 매우 빠른 읽기/쓰기
- TTL 지원
	- 비활성 사용자 자동 제거
- 캐시 용도에 적합

위치 정보 저장에 DB 를 사용하지 않는 이유 ?
- 현재 위치만 필요

## 위치 이동 이력 데이터베이스
캐시와 별개로 위치이동 이력을 데이터베이스 저장한다

목적
- 위치 이력 활용
- 데이터 분석
- ML
- 사용자 이동 패턴
- 지도 개선

데이터 구조

| 컬럼        | 설명     |
| --------- | ------ |
| user_id   | 사용자 ID |
| latitude  | 위도     |
| longitude | 경도     |
| timestamp | 기록 시각  |

이 데이터베이스는 엄청난 **write workload** 를 처리해야 하기 때문에 Cassandra 권장
- 샤딩키로 user_id 를 사용해서 부하 분산 처리
