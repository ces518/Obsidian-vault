# 개요

AWS S3 같은 **대규모 객체(Object) 저장소 시스템** 을 설계한다

---

# 저장소 시스템 101

저장소를 **추상화 레벨** 기준으로 3단계로 구분:

|저장소 타입|특징|예시|
|---|---|---|
|블록 저장소|Raw block 제공 (가장 저수준)|HDD, SSD, EBS|
|파일 저장소|디렉토리 기반 파일 시스템|NFS, SMB|
|객체 저장소|Key 기반 Object 저장|S3, GCS|

## 블록 저장소 (Block Storage)

- 디스크처럼 **원시 블록(raw block)** 제공
- 서버가 직접 파일 시스템을 만들어 사용
- DB나 VM 엔진은 이 블록을 직접 제어 가능
- 가장 유연하지만:
    - 분산 처리
        
    - 확장성
        
    - 메타데이터 관리
        
        를 직접 해결해야 함
        

**고성능은 가능하지만, 운영 부담이 큼**

## 파일 저장소 (File Storage)

- 블록 저장소 위에 구현
- 디렉토리 / 파일 계층 구조 제공
- NFS, SMB 등으로 네트워크 접근 가능

단점:

- 메타데이터 관리 비용이 큼
- 확장성 한계 존재
- 수십억 파일 관리에 부적합

## 객체 저장소 (Object Storage)

### 객체 구성

```jsx
Object
 ├── Key (이름)
 ├── Value (실제 데이터)
 └── Metadata (부가 정보)
```

파일 시스템 처럼 경로 (path) 개념이 없음

**Key 기반 Flat Namespace**

특징:

- **RESTful API 기반 접근**
- HTTP로 CRUD 가능
- 무제한 확장 가능 (수십~수백조 객체)
- 메타데이터 자유롭게 확장 가능
- 내부적으로는:
    - 데이터 + 메타데이터 분리 관리

## 객체 저장소가 필요한 이유

파일 저장소:

- 디렉토리 트리 관리 필요
- inode 관리 필요
- 락 관리 필요

수십억 파일이 필요한 규모에서 **병목이 발생**한다

객체 저장소:

- Key 기반 접근
- 트리 구조 없음
- 락 최소화 가능
- 확장성 중심 설계

**대규모 분산 환경**에 적합하다

## 저장소 유형별 비교

![](images/Pasted%20image%2020260223163457.png)

|항목|블록 저장소|파일 저장소|객체 저장소|
|---|---|---|---|
|저장된 내용 변경 가능성|O|O|**X** (직접 변경 불가, **버전으로 새 객체 추가**는 가능)|
|비용|고|중~고|**저~중**|
|성능|중~고(혹은 최상)|중~고|**저~중**|
|데이터 일관성|강력|강력|강력|
|데이터 접근|SAS / iSCSI / FC|표준 파일 접근 (CIFS/SMB, NFS)|**RESTful API**|
|규모 확장성|중|고|**최상**|
|적합한 응용|VM, DB 같은 고성능 워크로드|범용 파일 시스템 접근|이진/비정형 데이터, 대규모 저장|

<aside> 💡

객체 저장소는 **비용/확장성/내구성**을 얻는 대신 **성능을 일부 희생**하고, 데이터는 **“파일처럼 수정”이 아니라 “교체(새 버전)”**로 다룬다.

</aside>

## 용어 정리

### 버킷 (Bucket)

- 객체를 담는 **논리적 컨테이너**
- **버킷 이름은 전역적으로 유일(globally unique)** 해야 함
- 업로드 전에 **버킷 생성이 선행**

### 객체 (Object)

- 버킷에 저장되는 **개별 데이터 단위**
- 구성:
    - **데이터(payload)**: 실제 내용(바이너리 무엇이든 가능)
    - **메타데이터(metadata)**: 객체를 설명하는 **이름-값 쌍**(key-value)

### 버전 관리 (Versioning)

- 같은 버킷 내에서 **한 객체의 여러 버전**을 저장 가능
- 실수로 삭제/덮어쓰기 했을 때 **복구** 용도
- 보통 **버킷 단위로 설정 가능**

### URI (Uniform Resource Identifier)

- 객체 저장소는 **RESTful API 기반**
- 모든 리소스(버킷/객체) 는 **URI 로 고유하게 식별**

### SLA (Service-Level Agreement)

- 서비스 제공자와 사용자 간의 **품질 보장 계약**

### 객체 저장소의 SLA

1. 데이터 내구성 (Durability)

- 예: **99.999999999% (eleven nines)**
- 여러 AZ에 복제 저장
- 심지어 **하나의 AZ 전체가 소실돼도 복구 가능**하도록 설계

2. 서비스 가용성 (Availability)

- 예: **연간 99.9% ~ 99.99%**

# 설계 범위 확정

## 요구사항

- **버킷 생성**
- **객체 업로드 & 다운로드**
- **객체 버전(Versioning)**
- **버킷 내 객체 목록 조회**
    - `aws s3 ls` 처럼 동작하는 형태
- **아주 큰 객체**: 수 GB 이상
- **다량의 소형 객체**: 수 KB 정도도 많이
- 매년 **100PB** 추가
- **데이터 내구성(Durability): 99.9999% (six nines)**
- **서비스 가용성(Availability): 99.99% (four nines)**
- **높은 안정성과 성능을 보장하되**
- **저장소 비용은 최대한 낮춰야 함**

## 대략적 규모 추정

객체 저장소의 병목:

- **디스크 용량**
- **디스크 I/O(IOPS)**

### 용량 가정

객체 크기가 다음 분포를 따른다고 가정한다.

- **20%**: 1MB 미만 (소형)
- **60%**: 1MB ~ 64MB (중형)
- **20%**: 64MB 이상 (대형)

계산 편의를 위해 각 구간의 **중앙값(median)** 을 사용한다.

- 소형: **0.5MB**
- 중형: **32MB**
- 대형: **200MB**

### 저장 공간 사용률 (헤드룸)

운영상 여유를 두기 위해 **저장 공간 40%만 사용**한다고 잡는다.

### 총 저장 용량 환산

총 저장 용량을 MB 로 환산

- 총 용량: **100PB**
    
- 환산:
    
    **100PB = 100 × 1000 × 1000 × 1000 MB = 10¹¹ MB**
    

### 저장 가능한 객체 수 계산

평균 객체 크기(분포 가중 평균):

- `0.2×0.5MB + 0.6×32MB + 0.2×200MB`

저장 가능 객체 수:

- `(10¹¹ MB × 0.4) / (0.2×0.5 + 0.6×32 + 0.2×200)`

결과:

- **약 6억 8천만 개(0.68 billion) 객체**

### 메타데이터 저장 용량 추정

- 모든 객체의 메타데이터를 **1KB**로 가정하면,
- 0.68 billion 객체의 메타데이터 총량은
    - **약 0.68TB**

### IOPS 가정

IOPS:

- 초당 디스크 IO

SATA 인터페이스 + 7200rpm HDD 1개가 **100~150 IOPS** (임의 탐색) 정도 지원한다고 가정

- 정확한 계산 값 보다는, 시스템 규모 예측 수준으로 설계에서 직접 사용하진 않는다.

# 개략적 설계

## 객체 저장소 속성

- **객체 불변성(Object immutability)**
    
    객체는 **점진적 수정이 불가**. 삭제 후 새 버전으로 **완전 대체**만 가능.
    
- **키-값 저장소 관점(Key-Value store)**
    
    객체는 **URI로 접근**하고, URI가 키 / 데이터가 값이므로 KV 저장소로 볼 수 있음.
    
- **저장은 1회, 읽기는 여러 번(Write once, read many)**
    
    요청의 상당수가 **읽기(예: 95%)** 라는 조사 결과도 언급.
    
- **소형/대형 객체 동시 지원**
    
    수 KB부터 수 GB까지 다양한 크기를 문제 없이 저장해야 함.
    

## 객체 저장소 설계 철학

객체 저장소는 UNIX 파일 시스템과 비슷하다는 비유를 통해 구조를 제시함.

- UNIX:
    
    파일 이름/메타데이터는 **inode**, 데이터는 **디스크 다른 블록**, inode가 블록 포인터를 가짐
    
- 객체 저장소:
    
    **메타데이터 저장소**(inode 역할) + **데이터 저장소**(디스크 역할)로 분리
    
    - 이를 분리하면 설계가 단순해짐.
    
    메타데이터에는 “블록 포인터” 대신, 네트워크로 데이터 저장소에서 객체를 가져오기 위한 **객체 ID(식별자)** 가 들어감.
    
![](images/Pasted%20image%2020260223163653.png)

### 위 구조 선택 이유

- **대용량 데이터(Blob)** 는 메타데이터 저장소에 두면 비효율적이므로 데이터 저장소로 분리
    
- **읽기 비중이 높고**, 조회 시작점이 URI이므로
    
    “URI로 빠르게 찾을 수 있는 얇은 메타데이터 계층”이 필요
    
- **불변성/버전**을 지원하기 쉬움
    
    (버전이 늘면 메타데이터에 동일 name의 여러 object_id를 관리하는 식으로 확장 가능)
## 개략적 설계안

![](images/Pasted%20image%2020260223163728.png)

### 주요 컴포넌트

**1) 로드밸런서**

- RESTful API 요청을 **여러 API 서버로 분산**

**2) API 서비스 (무상태)**

- 내부의 여러 서비스 호출을 **조율(orchestration)** 하는 “프론트” 역할
    - IAM, 메타데이터 서비스, 저장소 서비스 호출을 묶어서 처리
- **stateless** 이라서 **수평 확장 가능**

**3) IAM 서비스 (Identity & Access Management)**

- **인증(authentication)**: 호출 주체가 누구인지 확인
- **권한 부여(authorization)**: 어떤 작업을 수행할 수 있는지 검증
- **접근 제어(access control)**: 정책 기반 접근 통제

**4) 메타데이터 서비스 + 메타데이터 저장소(DB)**

- 메타데이터 저장소는 객체의 “inode” 역할
- 저장 정보 예시(그림 9.3):
    - 버킷: `Bucket Name`, `Policy`, `Life Cycle` …
    - 객체: `Object Name`, `Version ID`, `Expiration`, `Access Control` …
- “객체 이름(URI)”로 들어온 요청을 **객체 ID(UUID)로 해석**해서 다음 단계로 넘기는 핵심 계층

**5) 데이터 저장소(스토리지 서비스 + 스토리지 노드)**

- 실제 바이너리 데이터를 저장
- 모든 데이터 연산의 키는 **객체 ID(UUID)** 를 사용
- 고가용성을 위해
    - **주(primary) 저장소 노드**
        
    - **부(secondary) 저장소 노드들**
        
        로 복제 구성을 둠(그림 9.4에 primary/secondary 표현)
        

### 메타데이터와 데이터 분리 의도

- 데이터 저장소의 데이터는 **불변(immutable)**
    
- 메타데이터 저장소의 데이터는 **변경 가능(mutable)**
    
    → 분리하면 두 컴포넌트를 **독립적으로 구현/최적화**할 수 있어 설계가 단순해진다
    
- 메타데이터/데이터 저장소는 “논리적 분리”일 뿐 구현은 다양할 수 있고,
    
- 예로 Ceph RGW는 별도 메타데이터 저장소 없이 **Rados 객체로 함께 저장**하는 방식도 언급됨.

## 객체 업로드 플로우

![](images/Pasted%20image%2020260223163800.png)

업로드는 반드시 **버킷 안에 객체를 저장**하는 형태로 진행됨.

예시:

- 버킷: `bucket-to-share`
- 객체: `script.txt`

### 전체 과정

1. **버킷 생성 요청**
    
    클라이언트 요청 후, API Service 로 전달
    
2. **권한 검증 (IAM)**
    
    API Service는 IAM Service 호출:
    
    - 사용자 신원 확인 (Authentication)
    - 해당 버킷에 대한 **WRITE 권한** 확인 (Authorization)
3. **버킷 메타데이터 생성**
    
    권한 문제가 없으면:
    
    - API Service → Metadata Store 호출
    - 버킷 메타데이터 생성(DB 등록)
    
    생성 완료 후 클라이언트에 응답.
    
4. **객체 업로드 요청**
    
    클라이언트가 실제 객체 업로드 요청
    
5. **객체 업로드 권한 확인**
    
    API Service가 다시:
    
    - 사용자 신원 확인
    - 해당 버킷에 대한 WRITE 권한 검증
6. **데이터 저장**
    
    검증 통과 시:
    
    - HTTP PUT body에 실린 **객체 데이터**를
    - **Data Storage Service** 로 전달
    
    Data Storage는:
    
    - 객체를 저장하고
    - 해당 객체의 **UUID(object_id)** 를 생성 후 반환
    - 생성된 UUID 가 실제 Blob 의 Pointer 역할
7. **객체 메타데이터 등록**
    
    API Service는 Metadata Store에 아래 항목을 저장:
    
| 필드          | 설명         |
| ----------- | ---------- |
| object_id   | UUID       |
| bucket_id   | 소속 버킷      |
| object_name | script.txt |
## 객체 다운로드 플로우
![](images/Pasted%20image%2020260223180328.png)
1. 클라이언트 요청
    
2. IAM 권한 확인
    
    API 서비스는:
    
    - 사용자의 신원(Authentication)
    - 해당 버킷에 대한 **READ 권한(Authorization)**
    
    을 IAM 서비스에 질의한다.
    
3. 메타데이터 조회
    
    권한이 확인되면:
    
    - API 서비스는 **메타데이터 저장소(DB)** 를 조회하여
        
    - `object_name = script.txt`
        
        에 해당하는 object_id 를 조회한다
        
4. 데이터 저장소에서 실제 객체 조회
    
    - API 서비스는 해당 `UUID` 를 사용하여
    - **데이터 저장소(Data Storage Service)** 에 요청한다.
    - 데이터 저장소는 UUID → binary data 를 반환한다.
5. 클라이언트에 응답 반환
    
    API 서비스는:
    
    - HTTP GET 응답 바디에
    - 실제 객체 데이터를 담아 클라이언트에 전달한다.

# 상세 설계

개략 설계에서 합의한 구조를 어떻게 컴포넌트로 쪼갤지 살펴본다

## 데이터 저장소

![](images/Pasted%20image%2020260223180405.png)

- API 서비스는 업로드/다운로드 요청을 처리할 때 **데이터 저장소를 호출**한다.
    
- 데이터 저장소는 **객체 이름을 모르고**, 오직 **ObjectID(UUID)** 로만 연산한다.
    
    → 업/다운로드의 공통 키는 UUID.
    

### 데이터 저장소 설계

![](images/Pasted%20image%2020260223180416.png)

데이터 저장소는 **3개의 컴포넌트**로 쪼갠다

1. **데이터 라우팅 서비스(Data Routing Service)**
    - 데이터 노드 클러스터 접근을 위한 **REST/gRPC 엔드포인트**
    - **무상태(stateless)** 로 수평 확장 가능
    - 역할
        - 배치 서비스에 “어디 저장할지” 질의
        - 데이터 노드에서 읽어 API 서비스로 반환
        - 데이터 노드에 기록
2. **배치 서비스(Placement Service)**
    - “어느 데이터 노드에 저장할지” 결정
    - 내부적으로 **가상 클러스터 지도(virtual cluster map)** 를 유지
        - 데이터센터/호스트/파티션 같은 물리 토폴로지 정보를 보관
    - 핵심 목표: **복제본(replica)이 물리적으로 서로 다른 위치**에 놓이게 해서 내구성을 확보
    - 운영 메커니즘
        - 모든 데이터 노드와 **박동(heartbeat)** 교환으로 상태 모니터링
        - 예: **15초 grace period** 동안 응답 없으면 down 처리
    - 중요 서비스라서
        - **5~7대**로 클러스터 구성하고
        - **Paxos/Raft** 같은 합의 프로토콜로 고가용성 보장(과반 생존 시 서비스 유지)
3. **데이터 노드(Data Node)**
    - 실제 객체 바이너리를 저장하는 노드
    - 여러 노드에 복제 저장하는 단위를 **다중화 그룹(replication group)** 으로 부름
    - 노드에는 데몬이 돌며 배치 서비스로 heartbeat(상태/용량 등)를 주기적으로 보냄

## 데이터 저장 흐름 (Write Path)

![](images/Pasted%20image%2020260223180443.png)

**1) API → 데이터 저장소로 포워딩**

- **API 서비스가 객체 데이터를 데이터 저장소로 전달**한다.

**2) 라우팅 서비스: UUID 발급 + 배치 서비스 질의**

- **데이터 라우팅 서비스가 UUID(ObjectID)를 할당**하고,
- 그 UUID를 입력으로 **배치 서비스에 “어느 노드에 저장할지” 질의**한다.
- 배치 서비스는 **가상 클러스터 지도(virtual cluster map)** 를 보고 **주(primary) 데이터 노드**를 반환한다.

> 이때 배치 결과는 **결정적(deterministic)** 이어야 하고, 노드 추가/삭제가 있어도 유지돼야 하므로 보통 **consistent hashing**을 쓴다고 언급.

**3) 라우팅 서비스 → 주 노드로 데이터 전송**

- 라우팅 서비스가 **UUID와 함께 실제 데이터를 주 데이터 노드에 직접 전송**한다.

**4) 주 노드: 로컬 저장 + 부 노드로 복제**

- **주 노드는 데이터를 자기 노드에 저장**하고,
- 동시에 **2개의 부(secondary) 데이터 노드로 복제(replication)** 한다.
- **모든 부 노드에 복제가 성공한 뒤**에야 주 노드가 라우팅 서비스에 성공 응답을 보낸다.

→ 즉, 이 기본 흐름은 **강한 일관성(Strong consistency)** 을 택한 형태.

**5) ObjectID(UUID) 반환**

- 라우팅 서비스는 **객체 UUID(ObjectID)를 API 서비스에 반환**한다.
- (그리고 API 서비스는 이 UUID를 메타데이터 저장소에 등록해서 name→UUID 매핑을 완성)
## 데이터는 어떻게 저장되는가

### 단순한 방식 : 객체 = 파일 하나

```jsx
object1 → file1
object2 → file2
object3 → file3
```

실제 운영에서는 거의 사용하지 않는다.

**문제점**

1. 디스크 블록 낭비
    
    파일 시스템은 데이터를:
    
    > 고정 크기 블록 단위로 저장
    > 
    > (보통 **4KB**)
    
    작은 객체가 많아질수록 디스크 공간 낭비가 기하급수적으로 증가함
    
2. inode 고갈
    
    파일 시스템은:
    
    - 파일 위치 정보 등을
    - **inode** 라는 메타 블록에 저장함
    - inode 개수는 디스크 초기화시 고정된다
    
    문제는:
    
    - 수백만 ~ 수억개의 small object가 생기면
    - inode가 먼저 고갈됨
    - OS는 inode 메타데이터를 캐싱하긴 하지만
    - inode가 너무 많으면 캐싱도 실패

**해결책**

작은 객체들을 하나의 큰 파일에 append 하는 방식으로 해결 가능하다

**WAL (Write-Ahead Log)** 처럼 동작

![](images/Pasted%20image%2020260223180502.png)

**또다른 문제**

append 방식은 반드시 순차 쓰기가 필요하다

여러 CPU 코어가 동시에 write 하면 내용이 뒤섞일 수 있다

이 처리를 위해 **쓰기 대역폭이 크게 감소**하는 문제가 있음

    - SSTable 기반 (LSM-tree 계열)
    - write 성능 👍

## 데이터 내구성

- 객체 저장소는 목표로 **99.9999%(six-nines) 내구성**을 요구한다.
- 단일 디스크/단일 노드로는 **원하는 내구성을 달성할 수 없고**, 장애 케이스를 고려해 **다중화**가 필요하다.

### 하드웨어 장애는 피할 수 없다

- 저장 매체(HDD/SSD) 종류와 관계없이 **디스크 장애는 발생**한다.
- 따라서 “드라이브 1개”만으로는 내구성 목표 달성 불가능.

### 복제

가장 검증된 방법

- 내구성을 높이는 대표적 방법은 **데이터를 여러 드라이브에 복제**해서,
    - 한 드라이브 장애가 전체 데이터 가용성/복구 가능성에 영향을 주지 않게 하는 것.
- 본 설계안은 **3중 복제(3 replicas)** 를 사용한다.

### 연간 장애율 (AFR) 기반 개략 계산

- 회전식 드라이브의 연간 장애율을 **0.81%** 라고 가정.
- 3중 복제 시 내구성(대략):
    - `1 - 0.0081^3 ≈ 0.999999`
- 책에서도 “아주 개략적인 추정”이며, 더 정확한 계산은 참고문헌을 보라고 한다.

## 장애 도메인

복제만 한다고 끝이 아니라, **복제본이 서로 같은 장애 도메인에 있으면 같이 죽는다**는 점을 강조한다.

### 장애 도메인이란?

- 어떤 중요 서비스에 문제가 생겼을 때 **같이 영향을 받는 물리/논리 구획**

### 예시(작은 도메인 → 큰 도메인)

- **서버 단위**: 같은 서버의 CPU/PSU/HDD 등 공유 → 서버 장애는 해당 서버 전체 영향
    
- **랙(rack) 단위**: 같은 랙의 서버들은 보통 **네트워크 스위치/전원**을 공유 → 랙이 장애 도메인
    
- **AZ(가용성 구역) 단위**: 물리 인프라(전원/네트워크)가 다른 독립 DC 수준
    
    → 더 큰 장애(정전/냉방/자연재해)에도 견딤
    

### 결론

- 데이터를 **여러 AZ에 복제**해두면 장애 여파를 최소화할 수 있다(그림 9.14).
- “어떤 수준의 장애 도메인을 선택하느냐”가 극단적 상황에서의 안정성을 크게 좌우한다.

### 소거 코드 (Erasure Coding)

- 3중 복제로도 목표 내구성을 달성 가능하지만,
- 내구성을 달성하는 또 다른 방법으로 **소거 코드(erasure coding)** 를 소개한다.
- 아이디어:
    - 데이터를 **작은 조각으로 분할**해 여러 서버에 배치하고,
    - 일부 조각이 사라져도 **복구 가능하도록 중복 정보를 추가**하는 방식

## 정확성 검증

- 소거 코드는 디스크 장애 등으로 **데이터가 손상/소실됐을 때 패리티로 복구**할 수 있게 해준다.
- 그런데 대규모 시스템에서는 손상이 디스크에만 국한되지 않음:
    - **메모리 데이터 훼손**(process 내부/전송 경계에서의 bit flip 등)도 자주 발생
- 그래서 “복구”뿐 아니라 **정확성(무결성) 검증** 메커니즘이 필요.

### 체크섬 (checksum)

- 프로세스 경계에서 데이터가 이동할 때 **체크섬으로 검증**한다.
- 체크섬이란:
    - 원본 데이터로부터 계산한 **짧은 데이터(요약 값)** 이고
    - 수신측에서 다시 계산해 **같으면 정상, 다르면 훼손**으로 판단

**체크섬 알고리즘**

- MD5, SHA1, HMAC 등 언급
- 이 장에서는 **MD5처럼 간단한 알고리즘을 사용**한다고 가정

**체크섬 처리**

- 본 설계안에서는 **객체 데이터 끝에 체크섬을 붙인다.**
- 그리고 **파일(세그먼트)을 read-only로 전환하기 직전에**
    - **파일 전체 체크섬을 계산**
    - 파일 말미에 저장
- 그림 9.20이 그 배치(객체들이 쌓인 뒤 마지막에 checksum)

## 메타데이터 데이터 모델
메타데이터 저장소는 “inode” 역할. 크게 **버킷 메타데이터**와 **객체 메타데이터**를 다룬다.

- 버킷: bucket name, policy, lifecycle 등 “버킷 단위 설정/정책”
- 객체: object name, version id, expiration, access control 등 “객체 단위 속성”

가장 핵심 매핑은:

- **(bucket, object_name, version?) → object_id(UUID)**
    
    데이터 plane으로 내려가기 위한 포인터가 됨.
    

### 버킷 내 객체 목록 설계

- `aws s3 ls` 같은 “리스트”는 생각보다 까다롭다:
    - 객체 수가 많아질수록 **pagination**, **prefix 기반 조회(폴더 흉내)**, **정렬/필터** 요구가 생김
- 그래서 목록은 보통
    - `(bucket, object_name)` 을 **정렬 가능한 형태**로 저장하거나
    - prefix를 키로 하는 인덱싱 전략을 둬서
    - “특정 prefix 하위”를 빠르게 page 단위로 가져오는 방향으로 설계가 이어짐

## 객체 버전

- 객체는 **immutable**이라 “수정” 대신 **새 버전 생성**으로 처리
    - 삭제시 **삭제 표식(delete marker)** 만 추가한다
- 설계 포인트는:
    - 같은 `(bucket, object_name)`에 대해 **여러 version**을 어떻게 보관/조회할지
    - 최신 버전 조회 vs 특정 버전 조회 API/모델을 어떻게 나눌지
- 데이터 plane은 어차피 UUID로 저장하니,
    - 버전 관리는 **메타데이터 plane에서 ‘name → (version → UUID)’** 형태로 해결하는 그림으로 간다.

## 대용량 파일 업로드 최적화

대형 객체(GB급)를 “한 번에 PUT” 하면:

- 네트워크 중단/재시도 비용이 큼
- API 서버 경유 시 서버가 병목이 됨

그래서 최적화 방향은 보통:

- **멀티파트 업로드(분할 업로드)** 로 재전송 비용을 줄이고,
- 업로드 트래픽이 API 계층을 과하게 타지 않도록 **데이터 plane 직행**(또는 라우팅 계층을 통해 스트리밍) 형태를 고려하게 됨.

## 쓰레기 수집 (Garbage Collection)

버전/삭제가 들어가면 필연적으로:

- 메타데이터에서는 삭제됐는데 데이터 노드에는 blob이 남거나
- 최신 버전 갱신으로 **구버전 데이터가 고아(orphan)** 가 됨

그래서 GC는 보통:

- “현재 메타데이터에서 참조되지 않는 UUID”를 찾아
    
- 데이터 노드에서 제거하는 방식으로 설계/운영 플로우가 잡힌다
    
    (중요 포인트: 실시간 삭제보다 **비동기/배치**로 처리)
