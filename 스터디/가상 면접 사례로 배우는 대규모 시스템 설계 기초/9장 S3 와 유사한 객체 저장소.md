# 개요

AWS S3 같은 **대규모 객체(Object) 저장소 시스템** 을 설계한다

---

# 저장소 시스템 101

저장소를 **추상화 레벨** 기준으로 3단계로 구분:

|저장소 타입|특징|예시|
|---|---|---|
|블록 저장소|Raw block 제공 (가장 저수준)|HDD, SSD, EBS|
|파일 저장소|디렉토리 기반 파일 시스템|NFS, SMB|
|객체 저장소|Key 기반 Object 저장|S3, GCS|

## 블록 저장소 (Block Storage)

- 디스크처럼 **원시 블록(raw block)** 제공
- 서버가 직접 파일 시스템을 만들어 사용
- DB나 VM 엔진은 이 블록을 직접 제어 가능
- 가장 유연하지만:
    - 분산 처리
        
    - 확장성
        
    - 메타데이터 관리
        
        를 직접 해결해야 함
        

**고성능은 가능하지만, 운영 부담이 큼**

## 파일 저장소 (File Storage)

- 블록 저장소 위에 구현
- 디렉토리 / 파일 계층 구조 제공
- NFS, SMB 등으로 네트워크 접근 가능

단점:

- 메타데이터 관리 비용이 큼
- 확장성 한계 존재
- 수십억 파일 관리에 부적합

## 객체 저장소 (Object Storage)

### 객체 구성

```jsx
Object
 ├── Key (이름)
 ├── Value (실제 데이터)
 └── Metadata (부가 정보)
```

파일 시스템 처럼 경로 (path) 개념이 없음

**Key 기반 Flat Namespace**

특징:

- **RESTful API 기반 접근**
- HTTP로 CRUD 가능
- 무제한 확장 가능 (수십~수백조 객체)
- 메타데이터 자유롭게 확장 가능
- 내부적으로는:
    - 데이터 + 메타데이터 분리 관리

## 객체 저장소가 필요한 이유

파일 저장소:

- 디렉토리 트리 관리 필요
- inode 관리 필요
- 락 관리 필요

수십억 파일이 필요한 규모에서 **병목이 발생**한다

객체 저장소:

- Key 기반 접근
- 트리 구조 없음
- 락 최소화 가능
- 확장성 중심 설계

**대규모 분산 환경**에 적합하다

## 저장소 유형별 비교

|항목|블록 저장소|파일 저장소|객체 저장소|
|---|---|---|---|
|저장된 내용 변경 가능성|O|O|**X** (직접 변경 불가, **버전으로 새 객체 추가**는 가능)|
|비용|고|중~고|**저~중**|
|성능|중~고(혹은 최상)|중~고|**저~중**|
|데이터 일관성|강력|강력|강력|
|데이터 접근|SAS / iSCSI / FC|표준 파일 접근 (CIFS/SMB, NFS)|**RESTful API**|
|규모 확장성|중|고|**최상**|
|적합한 응용|VM, DB 같은 고성능 워크로드|범용 파일 시스템 접근|이진/비정형 데이터, 대규모 저장|

<aside> 💡

객체 저장소는 **비용/확장성/내구성**을 얻는 대신 **성능을 일부 희생**하고, 데이터는 **“파일처럼 수정”이 아니라 “교체(새 버전)”**로 다룬다.

</aside>

## 용어 정리

### 버킷 (Bucket)

- 객체를 담는 **논리적 컨테이너**
- **버킷 이름은 전역적으로 유일(globally unique)** 해야 함
- 업로드 전에 **버킷 생성이 선행**

### 객체 (Object)

- 버킷에 저장되는 **개별 데이터 단위**
- 구성:
    - **데이터(payload)**: 실제 내용(바이너리 무엇이든 가능)
    - **메타데이터(metadata)**: 객체를 설명하는 **이름-값 쌍**(key-value)

### 버전 관리 (Versioning)

- 같은 버킷 내에서 **한 객체의 여러 버전**을 저장 가능
- 실수로 삭제/덮어쓰기 했을 때 **복구** 용도
- 보통 **버킷 단위로 설정 가능**

### URI (Uniform Resource Identifier)

- 객체 저장소는 **RESTful API 기반**
- 모든 리소스(버킷/객체) 는 **URI 로 고유하게 식별**

### SLA (Service-Level Agreement)

- 서비스 제공자와 사용자 간의 **품질 보장 계약**

### 객체 저장소의 SLA

1. 데이터 내구성 (Durability)

- 예: **99.999999999% (eleven nines)**
- 여러 AZ에 복제 저장
- 심지어 **하나의 AZ 전체가 소실돼도 복구 가능**하도록 설계

2. 서비스 가용성 (Availability)

- 예: **연간 99.9% ~ 99.99%**

# 설계 범위 확정

## 요구사항

- **버킷 생성**
- **객체 업로드 & 다운로드**
- **객체 버전(Versioning)**
- **버킷 내 객체 목록 조회**
    - `aws s3 ls` 처럼 동작하는 형태
- **아주 큰 객체**: 수 GB 이상
- **다량의 소형 객체**: 수 KB 정도도 많이
- 매년 **100PB** 추가
- **데이터 내구성(Durability): 99.9999% (six nines)**
- **서비스 가용성(Availability): 99.99% (four nines)**
- **높은 안정성과 성능을 보장하되**
- **저장소 비용은 최대한 낮춰야 함**

## 대략적 규모 추정

객체 저장소의 병목:

- **디스크 용량**
- **디스크 I/O(IOPS)**

### 용량 가정

객체 크기가 다음 분포를 따른다고 가정한다.

- **20%**: 1MB 미만 (소형)
- **60%**: 1MB ~ 64MB (중형)
- **20%**: 64MB 이상 (대형)

계산 편의를 위해 각 구간의 **중앙값(median)** 을 사용한다.

- 소형: **0.5MB**
- 중형: **32MB**
- 대형: **200MB**

### 저장 공간 사용률 (헤드룸)

운영상 여유를 두기 위해 **저장 공간 40%만 사용**한다고 잡는다.

### 총 저장 용량 환산

총 저장 용량을 MB 로 환산

- 총 용량: **100PB**
    
- 환산:
    
    **100PB = 100 × 1000 × 1000 × 1000 MB = 10¹¹ MB**
    

### 저장 가능한 객체 수 계산

평균 객체 크기(분포 가중 평균):

- `0.2×0.5MB + 0.6×32MB + 0.2×200MB`

저장 가능 객체 수:

- `(10¹¹ MB × 0.4) / (0.2×0.5 + 0.6×32 + 0.2×200)`

결과:

- **약 6억 8천만 개(0.68 billion) 객체**

### 메타데이터 저장 용량 추정

- 모든 객체의 메타데이터를 **1KB**로 가정하면,
- 0.68 billion 객체의 메타데이터 총량은
    - **약 0.68TB**

### IOPS 가정

IOPS:

- 초당 디스크 IO

SATA 인터페이스 + 7200rpm HDD 1개가 **100~150 IOPS** (임의 탐색) 정도 지원한다고 가정

- 정확한 계산 값 보다는, 시스템 규모 예측 수준으로 설계에서 직접 사용하진 않는다.

# 개략적 설계

## 객체 저장소 속성

- **객체 불변성(Object immutability)**
    
    객체는 **점진적 수정이 불가**. 삭제 후 새 버전으로 **완전 대체**만 가능.
    
- **키-값 저장소 관점(Key-Value store)**
    
    객체는 **URI로 접근**하고, URI가 키 / 데이터가 값이므로 KV 저장소로 볼 수 있음.
    
- **저장은 1회, 읽기는 여러 번(Write once, read many)**
    
    요청의 상당수가 **읽기(예: 95%)** 라는 조사 결과도 언급.
    
- **소형/대형 객체 동시 지원**
    
    수 KB부터 수 GB까지 다양한 크기를 문제 없이 저장해야 함.
    

## 객체 저장소 설계 철학

객체 저장소는 UNIX 파일 시스템과 비슷하다는 비유를 통해 구조를 제시함.

- UNIX:
    
    파일 이름/메타데이터는 **inode**, 데이터는 **디스크 다른 블록**, inode가 블록 포인터를 가짐
    
- 객체 저장소:
    
    **메타데이터 저장소**(inode 역할) + **데이터 저장소**(디스크 역할)로 분리
    
    - 이를 분리하면 설계가 단순해짐.
    
    메타데이터에는 “블록 포인터” 대신, 네트워크로 데이터 저장소에서 객체를 가져오기 위한 **객체 ID(식별자)** 가 들어감.
    
![](images/Pasted%20image%2020260223163653.png)

### 위 구조 선택 이유

- **대용량 데이터(Blob)** 는 메타데이터 저장소에 두면 비효율적이므로 데이터 저장소로 분리
    
- **읽기 비중이 높고**, 조회 시작점이 URI이므로
    
    “URI로 빠르게 찾을 수 있는 얇은 메타데이터 계층”이 필요
    
- **불변성/버전**을 지원하기 쉬움
    
    (버전이 늘면 메타데이터에 동일 name의 여러 object_id를 관리하는 식으로 확장 가능)
## 개략적 설계안

![](images/Pasted%20image%2020260223163728.png)

### 주요 컴포넌트

**1) 로드밸런서**

- RESTful API 요청을 **여러 API 서버로 분산**

**2) API 서비스 (무상태)**

- 내부의 여러 서비스 호출을 **조율(orchestration)** 하는 “프론트” 역할
    - IAM, 메타데이터 서비스, 저장소 서비스 호출을 묶어서 처리
- **stateless** 이라서 **수평 확장 가능**

**3) IAM 서비스 (Identity & Access Management)**

- **인증(authentication)**: 호출 주체가 누구인지 확인
- **권한 부여(authorization)**: 어떤 작업을 수행할 수 있는지 검증
- **접근 제어(access control)**: 정책 기반 접근 통제

**4) 메타데이터 서비스 + 메타데이터 저장소(DB)**

- 메타데이터 저장소는 객체의 “inode” 역할
- 저장 정보 예시(그림 9.3):
    - 버킷: `Bucket Name`, `Policy`, `Life Cycle` …
    - 객체: `Object Name`, `Version ID`, `Expiration`, `Access Control` …
- “객체 이름(URI)”로 들어온 요청을 **객체 ID(UUID)로 해석**해서 다음 단계로 넘기는 핵심 계층

**5) 데이터 저장소(스토리지 서비스 + 스토리지 노드)**

- 실제 바이너리 데이터를 저장
- 모든 데이터 연산의 키는 **객체 ID(UUID)** 를 사용
- 고가용성을 위해
    - **주(primary) 저장소 노드**
        
    - **부(secondary) 저장소 노드들**
        
        로 복제 구성을 둠(그림 9.4에 primary/secondary 표현)
        

### 메타데이터와 데이터 분리 의도

- 데이터 저장소의 데이터는 **불변(immutable)**
    
- 메타데이터 저장소의 데이터는 **변경 가능(mutable)**
    
    → 분리하면 두 컴포넌트를 **독립적으로 구현/최적화**할 수 있어 설계가 단순해진다
    
- 메타데이터/데이터 저장소는 “논리적 분리”일 뿐 구현은 다양할 수 있고,
    
- 예로 Ceph RGW는 별도 메타데이터 저장소 없이 **Rados 객체로 함께 저장**하는 방식도 언급됨.

## 객체 업로드 플로우

![](images/Pasted%20image%2020260223163800.png)

업로드는 반드시 **버킷 안에 객체를 저장**하는 형태로 진행됨.

예시:

- 버킷: `bucket-to-share`
- 객체: `script.txt`

### 전체 과정

1. **버킷 생성 요청**
    
    클라이언트 요청 후, API Service 로 전달
    
2. **권한 검증 (IAM)**
    
    API Service는 IAM Service 호출:
    
    - 사용자 신원 확인 (Authentication)
    - 해당 버킷에 대한 **WRITE 권한** 확인 (Authorization)
3. **버킷 메타데이터 생성**
    
    권한 문제가 없으면:
    
    - API Service → Metadata Store 호출
    - 버킷 메타데이터 생성(DB 등록)
    
    생성 완료 후 클라이언트에 응답.
    
4. **객체 업로드 요청**
    
    클라이언트가 실제 객체 업로드 요청
    
5. **객체 업로드 권한 확인**
    
    API Service가 다시:
    
    - 사용자 신원 확인
    - 해당 버킷에 대한 WRITE 권한 검증
6. **데이터 저장**
    
    검증 통과 시:
    
    - HTTP PUT body에 실린 **객체 데이터**를
    - **Data Storage Service** 로 전달
    
    Data Storage는:
    
    - 객체를 저장하고
    - 해당 객체의 **UUID(object_id)** 를 생성 후 반환
    - 생성된 UUID 가 실제 Blob 의 Pointer 역할
7. **객체 메타데이터 등록**
    
    API Service는 Metadata Store에 아래 항목을 저장:
    
    |필드|설명|
    |---|---|
    |object_id|UUID|
    |bucket_id|소속 버킷|
    |object_name|script.txt|
