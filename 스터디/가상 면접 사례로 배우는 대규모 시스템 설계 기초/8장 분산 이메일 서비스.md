# 개요

- Gmail/Outlook/Yahoo Mail 같은 **대규모 이메일 서비스**
- 인터넷 성장으로 이메일 트래픽/데이터가 폭발했고, 사용자도 매우 큼(예: Gmail 활성 사용자 18억+ 언급)

# 요구사항

## 기능 요구사항

인증은 제외

- 집중 기능:
    - **이메일 발송/수신**
    - **모든 이메일 가져오기(목록/조회)**
    - **읽음 여부에 따른 필터링**
    - **제목/발신인/본문 기반 검색**
    - **스팸 및 바이러스 방지**
- **첨부파일 지원 포함** (중요: 메일 본문과 스토리지/전송이 달라짐)

현실에서는 SMTP/POP/IMAP 같은 레거시 프로토콜도 많이 사용되지만, 단순화를 위해 HTTP 접속만 가정

## 비기능 요구사항

- **안정성(Reliability)**: 이메일 데이터는 소실되면 안 됨
- **가용성(Availability)**: 사용자/이메일 데이터를 여러 노드에 **자동 복제**, 일부 장애에도 서비스 지속
- **확장성(Scalability)**: 사용자/이메일이 늘어나도 성능 저하 없이 감당
- **유연성/확장성(Extensibility)**: 새 컴포넌트 추가로 기능/성능을 쉽게 개선(향후 프로토콜/기능 확장 여지)

## 개략적 규모 추정

- 총 사용자수 : 10억명
- 전송 트래픽:
    - 사용자당 하루 전송 건수 = 10건
    - 10억 * 10 = 100억건 / day
    - QPS = 100억 / (24 × 60 × 60) ≈ 100,000 QPS
- 수신 트래픽:
    - 사용자 1명이 받는 메일수 40건
    - 메타데이터 크기 50KB (첨부파일 제외)
- 메타데이터 저장 용량:
    - 1년 기준
    - 10억 * 일 40건 * 365일 * 50KB = 730PB
- 첨부파일 저장 용량:
    - 첨부파일 포함 메일 비율 = 20%
    - 평균 첨부파일 크기 500KB
    - 10억 * 일 40건 * 365일 * 500KB = 1,460PB

# 이메일 101

## 프로토콜

이메일 시스템은 전송 프로토콜, 수신 프로토콜 두 가지를 사용한다

1. SMTP (Simple Mail Transfer Protocol)
    - 메일 전송 프로토콜의 표준
2. POP (Post Office Protocol)
    - 메일 수신 프로토콜
    - 메일 클라이언트가 **다운로드 이후 서버에서 삭제** 된다
    - 메일을 읽기 위해 전체 다운로드가 필요함
    - 첨부파일이 큰 경우 메일 열기까지 시간이 오래 걸림
3. IMAP (Internet Mail Access Protocol)
    - POP 의 단점을 보완한 수신 프로토콜
    - 메일을 서버에 그대로 유지
    - 메일 클릭시에만 다운로드
    - 다중 디바이스 지원
    - 본문 열기전 헤더만 다운로드
4. HTTPS
    - 메일 전송 프로토콜이 아님
    - 메일 서버간 전송은 SMTP, POP/IMAP 을 사용함
    - 웹 기반 클라이언트에서 사용됨
    - MS Outlook 은 ActiveSync 라는 별도 프로토콜을 사용해 모바일/메일 서버 간 통신을 처리

## DNS

메일 전송시 SMTP 서버는 DNS 질의를 통해 해당 도메인의 **MX 레코드**를 조회한다

### MX 레코드란 ?

특정 도메인의 이메일을 어떤 메일 서버가 처리하는지 나타내는 DNS 레코드

```jsx
gmail.com MX
----------------------------------
Priority 5   gmail-smtp-in.l.google.com
Priority 10  alt1.gmail-smtp-in.l.google.com
Priority 20  alt2.gmail-smtp-in.l.google.com
```

Priority 가 낮을수록 우선순위가 높음

### 메일 전송 흐름

1. DNS Query : [gmail.com](http://gmail.com) MX
2. DNS 가 MX 레코드 반환
3. 송신 SMTP 서버가 해당 메일 서버 연결
4. 메일 전송 수행

<aside> 💡

SMTP 는 “전송” 만 담당하고, “목적지 탐색” 은 하지 않는다

</aside>

## 첨부파일

SMTP 는 ASCII 기반 텍스트 전송 프로토콜이기 때문에 첨부파일과 같은 binary 데이터는 직접 전송이 불가능하다

때문에 Base64 인코딩을 통해 텍스트로 변환후 전송한다

```jsx
binary file
     ↓
Base64 encode
     ↓
text
     ↓
SMTP 전송
```

Base64 인코딩시 문제:

- 데이터 크기가 약 33% 정도 증가함
- 원본 500KB → 665KB
- 네트워크 비용
- 저장 공간
- 트래픽 부담

### MIME (Multi-purpose Internet Mail Extension)

첨부파일 전송을 위한 **메일 표준 규격**

MIME 의 역할:

- 본문에 첨부파일 데이터를 포함시켜 SMTP 로 전송 가능하도록 구조화

```jsx
Email
 ├─ Header
 ├─ Body
 └─ Attachment(Base64)
```

## 전통적 메일 서버
전통적 메일서버는 보통 **단일 서버** 위에서 동작하는 구조이며, 사용자 수가 적을 때는 잘 동작한다

### 메일 전송 처리 흐름
![](images/Pasted%20image%2020260225090440.png)
**1. 메일 작성 및 송신**

- Alice가 Outlook 클라이언트에서 이메일 작성 후 전송
- 클라이언트 → Outlook 메일 서버로 전송

```
Client → SMTP Server
```

> 클라이언트 ↔ 메일 서버 간 통신 프로토콜은 SMTP

**2. 수신 메일 서버 탐색 (DNS)**

- Outlook 메일 서버는 DNS 질의를 통해
- 수신자 도메인의 SMTP 서버 주소 조회

```
gmail.com → gmail SMTP server
```

**3. 메일 서버 간 전송**

- Outlook SMTP 서버 → Gmail SMTP 서버로 메일 전송

```
SMTP → SMTP
```

**4. 메일 수신 및 조회**

- Gmail 서버는 이메일을 저장
- Bob이 로그인하면:

```
IMAP / POP Server
```

를 통해 메일을 가져옴

### 저장소

전통적 메일 서버는 이메일을 파일 시스템의 **디렉터리 구조**로 저장한다

**Maildir 구조**

각 사용자 메일은 다음 과 같은 디렉터리 구조로 저장된다

관례적으로 Maildir 이라는 이름이 사용됨
![](images/Pasted%20image%2020260225090458.png)
**문제점**

1. 디스크 I/O 병목
    - 수십억 개의 이메일 = 수십억 개의 파일
    - 파일 수 증가 → 디렉터리 탐색 비용 증가
    - 검색/백업 시 Disk I/O 폭증
2. 가용성 문제
    - 메일이 로컬 파일시스템에 저장됨
    - 디스크 장애/서버 다운시 데이터 손실 가능
3. 확장성 한계
    - 전통 메일 전송 프로토콜은 수십억 사용자 규모를 고려해 설계되지 않았음

## 분산 메일 서버
전통 메일 서버는 단일 서버 기반 으로 설계 되어 있음

서버를 여러 대로 늘리면, 데이터 동기화 문제 발생

- SMTP reputation 유지
- 스팸 오탐 방지
- 사용자 상태 동기화

같은 문제들이 **멀티 노드 환경에서 매우 어려워짐**

이와 같은 이유로 인해 클라우드 기반 분산 아키텍처 구성이 필요하다
![](images/Pasted%20image%2020260226083440.png)
### 주요 구성요소

1. **웹 메일**
    - 사용자가 브라우저로 메일 송수신
    - HTTPS 기반 접근
2. **웹 서버**
    - 메일 API 진입점
    - 모든 요청이 REST API 로 처리
        - 메일 전송
        - 폴더 조회
        - 메시지 조회
3. **실시간 서버**
    - 새로운 메일 수신 이벤트를 클라이언트에 실시간 전달
    - WebSocket
    - 롱 폴링 (long polling)
    - 기본적으로 웹소켓을 사용하고 롱 폴링은 백업
    - 웹 소켓 기반 JMAP(JSON Meta Application Protocol)
4. **저장소 계층**
    - **메타데이터 DB (RDB / NoSQL)**
        - 발신자
        - 수신자
        - 제목
        - 읽음 여부
        - 폴더 정보
    - **첨부파일 저장소 (Object Storage S3)**
        - 이미지
        - PDF
        - 바이너리
    - **분산 캐시 (Redis)**
        - 자주 조회되는 메일 목록
        - 최근 메일
    - **검색 저장소 (Elasticsearch)**
        - 제목.본문 기반 검색
## 이메일 전송 절차
![](images/Pasted%20image%2020260226083555.png)
1. 사용자 메일 작성
    - 사용자가 웹메일(Webmail)에서 메일 작성 후 전송
    - 요청은 **로드밸런서**로 전달됨
2. 로드밸런서 → 웹서버
    - Rate Limit 범위 내에서
    - 요청을 웹 서버로 전달
3. 웹 서버의 역할
    - 기본 메일 검증
        - 크기 제한
        - 포맷 검사 등 사전 정의 규칙
    - 도메인 검증
        - 동일 도메인 이라면 내부 전송 처리
4. 메세지 큐 처리
    - 외부 전송 대상
        - 기본 검증 통과시 **외부 전송 큐**로 전달
        - 첨부파일 사이즈가 컨 경우 첨부파일은 S3 에 저장
        - 큐 에는 attachment_location 만 포함시켜 payload 최소화
    - 검증 실패시
        - 에러 큐로 전달
5. SMTP Worker 처리
    - 외부 전송 큐에서 메세지 소비
    - 스팸/바이러스 검사
    1. 보낸 편지함 저장
        - 검증 통과 시 저장소 계층의 보낸 편지함에 저장
    2. 외부 메일 서버로 전송

> [!note]
> 외부 전송 SMTP 프로세스를 분리함으로 인해 프로세스 규모를 독립적으로 확장 가능

## 이메일 수신 절차
![](images/Pasted%20image%2020260226083811.png)
1. SMTP 로드밸런서 도착
2. SMTP 서버 분산
	- LB가 트래픽을 여러 **SMTP 서버로 분산**한다.
	- 이때 **이메일 수락 정책**을 적용 가능:
	    - 예: 유효하지 않은 이메일은 **즉시 반송**해서 불필요한 처리 방지
3. 첨부파일이 크면 S3에 저장
	- 첨부파일이 큐에 넣기엔 너무 크면 **첨부파일 저장소(S3)** 에 보관한다.
	- (큐에는 첨부파일 자체 대신 **참조(위치) 정보**를 담는 방향)
4. 수신 메일을 큐에 적재
	- 이메일을 **수신 이메일 큐**에 넣는다.
	- 큐의 목적:
	    - SMTP 서버 ↔ 워커 간 **결합도 낮춤(decouple)**
	    - 워커/SMTP를 **각자 독립적으로 스케일** 가능
	    - 트래픽 폭증 시 **버퍼 역할**
5. 메일 처리 워커가 검증 및 처리
	- 워커가 다음을 수행한다:
	    - 스팸 필터링
	    - 바이러스 차단
	    - (그 외 다양한 처리)
	- 이후 단계는 “검증을 통과한 이메일”을 대상으로 진행
6. 저장소 계층에 저장
	- 이메일을 **메일 저장소**, **캐시**, **객체 저장소**, **검색 저장소** 등에 저장한다.
	    - 메타데이터(DB)
	    - 최근 메일(캐시)
	    - 첨부파일(Object Storage)
	    - 검색 인덱스(Search store)
7. 수신자가 온라인이면 실시간 서버로 전달
8. 실시간 서버가 WebSocket 으로 푸시
	- 실시간 서버는 **웹소켓 서버**이며,
	- 클라이언트가 **새 이메일을 실시간으로 수신**하도록 한다.
9. 오프라인이면 저장소에 보관
	- 오프라인 사용자의 이메일은 **저장소 계층**에 보관한다.
	- 사용자가 온라인이 되면 웹메일 클라이언트가 **웹 서버에 REST API로 연결**한다.
10. 웹 서버가 저장소에서 가져와 반환
	- 웹 서버는 저장소 계층에서 새 이메일을 조회해 클라이언트에 반환한다.

## 메타데이터 데이터베이스

### 이메일 메타데이터 특성

|구분|특징|
|---|---|
|헤더|작고 자주 조회됨|
|본문|크기 다양, 조회 빈도 낮음|
|사용 패턴|사용자 단위로 격리 필요|
|접근 패턴|최근 데이터 집중|
|신뢰성|데이터 손실 절대 불가|

조회 패턴이 핵심:

- 생성된 지 **16일 이하 이메일이 전체 읽기 질의의 82%** 차지 한다
- 데이터 신선도(Data Freshness)가 접근 패턴에 직접 영향

## 올바른 데이터베이스 선정

이메일 시스템 규모가 커지면 **IOPS 자체가 병목**이 된다
- Gmail/Outlook 같은 서비스는 맞춤 DB 를 사용하기도 한다

일반적으로 RDB 를 선택하는 이유:
- 메일 검색을 효율적으로 수행 가능
- Header / Body 에 Index 생성 가능

이메일은 BLOB 성격 데이터 이기 때문에 RDB 에서 이를 처리하려면 **BLOB 타입**을 사용해야 한다
- 내부 저장 방식 → 고정 크기 페이지를 연결하는 구조
- 큰 데이터 접근시, 여러 페이지를 조회하고 디스크 I/O 가 발생한다

> [!note]
> 전통적 RDB는 메일 본문 저장용도로 적합하지 않음

분산 객체 저장소는 백업 데이터 보관하기엔 좋지만, 검색 등 다양한 부가 기능 구현시 좋지 않다

지메일은 구글 빅테이블을 저장소로 사용하고 있어 NoSQL 을 검토해볼만 하지만, 오픈소스로 공개되어 있지 않고, 대안으로 카산드라를 고려해볼만 하다.
- 하지만 대형 이메일 서비스 중에서 카산드라를 사용하는 곳은 없음

**다음 요구사항**을 완벽히 지원하는 데이터베이스는 없다
- 단일 컬럼 크기는 한 자릿수 MB 일수 있음
- 강력한 데이터 일관성 보장
- 디스크 I/O 최소화
- 가용성이 매우 높아야하며 일부 장애를 감내할 수 있어야 함
- 증분 백업이 쉬워야 함

## 데이터 모델

이메일 데이터 계층이 지원해야 하는 질의:
- 특정 사용자의 폴더 목록
- 특정 폴더의 이메일 목록 (최근→과거)
- 이메일 생성/삭제/상세 조회
- 읽은/ 안 읽은 메일 필터링
- 이메일 타래 (thread) (보너스)

### 특정 사용자의 폴더 목록
![](images/Pasted%20image%2020260226084508.png)
키 설계
- **Partition Key = user_id**
- **Clustering Key = folder_id** (정렬 기준)

사용자 단위로 폴더가 한 파티션에 모이므로 조회가 빠름

### 특정 폴더의 이메일 목록
![](images/Pasted%20image%2020260226084543.png)
키 설계
- **Composite Partition Key = (user_id, folder_id)**
    → 같은 사용자의 같은 폴더 메일이 한 파티션에 모이게 함
- **Clustering Key = email_id (TIMEUUID)**, **내림차순(C↓)**
    → 최신 메일부터 자연스럽게 정렬/페이지네이션

목록 화면에 필요한 “요약 필드” 만 둔 **조회 최적화 테이블**

### 이메일 상세
![](images/Pasted%20image%2020260226084621.png)
키 설계
- emails_by_user
    - **Partition Key = user_id**
    - **Clustering Key = email_id (TIMEUUID, C↓)**
- attachments
    - **Partition Key = email_id**
    - **Clustering/Key = filename**

상세 화면에 필요한 모든 필드를 한번에 가져오고, 첨부파일을 S3에 있고 DB 에는 참조 URI 만 둔다

### 읽은 / 안 읽은 메일

NoSQL 은 **파티션키/클러스터키** 기반 쿼리만 효율 적으로 지원한다
- emails_by_folder 의 is_read 로 “읽은/안읽은 전체 조회” 를 하기 어렵다

**해결책:**
- `emails_by_folder`를 두 테이블로 **분할(denormalization)**
- `read_emails`
- `unread_emails`

**상태 변경 방법:**
- “안 읽음 → 읽음” 전환 시:
    - `unread_emails`에서 삭제
    - `read_emails`로 삽입(옮김)

> [!note]
> 애플리케이션 로직은 복잡해지지만, 대규모에서 조회 성능을 얻는다.

### 이메일 타래 (Threads)
타래 재구성에 활용되는 대표 헤더 3종:
- `Message-Id` : 메시지 식별자(클라이언트 생성)
- `In-Reply-To` : 어떤 메시지에 대한 답장인지
- `References` : 타래 관련 메시지 식별자 목록

클라이언트가 이 헤더들을 이용해 “대화 타래”를 복원할 수 있음.

전통적으로 **JWZ 알고리즘**을 통해 구현된다

## 이메일 전송 가능성

메일 서버를 구성해서 이메일을 **전송(send)** 하는 것은 쉽다.

하지만 이메일이 실제로:
- 스팸함이 아닌 Inbox에 도착하고
- ISP(Gmail, Outlook 등)에 의해 정상 메일로 분류되며
- 수신자가 읽을 수 있도록 전달되는 것
은 훨씬 어려운 문제다.

> [!note]
> 실제로 전체 메일중 약 50%가 스팸으로 분류된다
> 
> 특히 신규 메일 서버는 인터넷 상에서 **평판(reputation)** 이 없기 때문에 처음에는 대부분의 메일이 스팸으로 처리된다.

### 전송 가능성 확보를 위한 전략

1. **전용 IP 사용 (Dedicated IP)**
	- 메일 발송 시 공유 IP가 아닌 전용 IP 사용 필요
	- 신규 IP에서 대량 메일 발송 시 ISP가 스팸으로 간주 가능
	- 발신자의 신뢰도는 IP 단위로 평가됨
2. **이메일 유형별 IP 분리**
	- 메일 종류에 따라 발송 IP를 분리해야 함

| 메일 유형   | 예시            |
| ------- | ------------- |
| 트랜잭션 메일 | 인증, 결제, 체결 알림 |
| 마케팅 메일  | 광고, 이벤트       |
3.  **IP Warm-up**
	신규 IP는 발송량을 점진적으로 증가시켜야 함
	- 낮은 빈도로 시작
	- 점진적으로 발송량 증가
	- 평판 축적 필요
	
	AmazonSES 기준:
	- 정상적인 평판 형성까지 약 **2~6주** 소요

4. **스팸 발송자 신속차단**
	- 일부 사용자가 스팸 메일을 대량 발송할 경우
	- 서버 전체 IP 평판이 하락함

5. **ISP 피드백 처리**
	- 메일 전달 실패 또는 사용자 신고시 ISP 로 부터 피드백 수신됨

|유형|의미|
|---|---|
|Hard Bounce|수신 주소 오류 등 영구 실패|
|Soft Bounce|일시적 실패 (서버 과부하 등)|
|Complaint|사용자가 스팸 신고|
- 각 유형별로 큐를 유지해 관리해야 함
![](images/Pasted%20image%2020260226085527.png)
6. 이메일 인증
	피싱 공격 대응 및 신뢰성 확보를 위해 아래 인증 기술 필요:
	- **SPF**: 발신 서버 검증
	- **DKIM**: 메일 위변조 방지
	- **DMARC**: SPF/DKIM 정책 통합
	
	피싱/프리텍스팅은 전체 데이터 유출 사고의 약 **93%** 차지
	
> [!note]
> 이메일 시스템에서 중요한 것은 전송 자체가 아니라 Inbox까지의 도달 가능성

## 검색

기본 검색:
- 제목(Subject)
- 본문(Body)
- 키워드 포함 여부

고급 검색:
- From (발신자)
- 날짜 범위
- 첨부파일 여부
- 읽음 / 안읽음 상태
- Folder
- Time range 등

**메일 검색 vs 구글 검색 차이**

| 구분    | 구글 검색          | 이메일 검색  |
| ----- | -------------- | ------- |
| 검색 범위 | 인터넷 전체         | 사용자 메일함 |
| 정렬 기준 | 관련성(Relevance) | 시간 / 속성 |
| 색인 속도 | 느려도 됨          | 거의 실시간  |
| 정확도   | Best-effort    | 매우 중요   |

구글 검색 : indexing → read 중심
메일 검색 : Write (indexing) 중심

이메일 시스템:
- 메일 전송
- 메일 수신
- 메일 삭제
- 메일 이동
- 읽음 상태 변경

이 **모든 이벤트 발생 시 색인 업데이트**가 필요하다

### 방안 1: 엘라스틱 서치
검색 기능을 메일 저장소와 분리된 별도 검색 클러스터로 구성
```
Email Event 발생
(전송 / 수신 / 삭제)
        ↓
Kafka Publish
        ↓
Indexing Service
        ↓
ElasticSearch Index Update

```

핵심:
- 메일 서비스
- 검색 서비스
를 **느슨하게(Decoupling)** 만드는 것

Partition 전략:
- Partition Key = user_id
- 대부분의 검색은 내 메일함 내에서 수행됨
- 동일 유저 메일을 같은 shard에 저장
- cross-node scan 방지
- network hop 감소
- 검색 latency 개선

### 방안 2: 맞춤형 검색 솔루션
- **대규모 이메일 사업자**는 제품 고유 요구사항을 만족시키기 위해 검색 엔진을 **자체 개발**해 쓰는 경우가 많다.
- 이메일 검색 엔진 설계는 **매우 복잡**해서 이 장의 범위를 넘는다.

**디스크 I/O 병목**
- 이메일 시스템은 매일 저장소에 추가되는 데이터(메타데이터+첨부)가 **PB 단위**로 증가한다.
- 한 계정에 **50만 개 이상 이메일**이 쌓이는 것도 흔치 않은 일이 아니다.
- 그래서 이메일 **색인 서버의 주된 병목은 디스크 I/O**가 되기 쉽다.

**LSM 트리가 적합한 이유**
- 색인 구축은 구조상 **대량의 쓰기 연산**을 유발할 수밖에 없다.
- 따라서 디스크에 저장되는 색인을 **LSM(Log-Structured Merge) 트리**로 구조화하는 것이 바람직하다고 제안한다.
- LSM의 쓰기 경로는 **순차 쓰기(sequential write)** 중심으로 최적화되어 있다(그림 8.11).
- LSM은 **Bigtable, Cassandra, RocksDB** 같은 시스템의 핵심 자료구조이기도 하다.

**LSM 동작 방식**
- 새 이메일이 도착하면 먼저 **메모리 캐시(레벨 0)** 에 쌓인다.
- 메모리에 쌓인 데이터가 임계치를 넘으면 **다음 디스크 레벨로 병합(compaction/merge)** 된다.

![](images/Pasted%20image%2020260227083131.png)

### 비교 정리
- **소규모**: ElasticSearch가 통합이 쉬워 좋은 선택
- **대규모**: ElasticSearch도 가능하지만 운영/개발 **전담 팀**이 필요할 수 있음
- Gmail/Outlook 급이면 “검색 전용 시스템”보다 **DB에 내장된 전용 검색 솔루션**이 더 바람직할 수도 있다

## 규모 확장성 및 가용성
![](images/Pasted%20image%2020260227083205.png)
- 이메일 시스템은 **사용자 간 데이터 접근 패턴이 서로 독립적**임
    
    → A 유저 메일 조회가 B 유저 메일 조회에 영향 없음
    
- 즉, 대부분의 컴포넌트는 다음과 같은 특성을 가짐:
    
    - 상태 공유 필요 없음
    - 사용자 단위로 샤딩 가능
    - Horizontal Scaling 가능

따라서 시스템은 **수평적 확장(scale-out)** 에 매우 적합
