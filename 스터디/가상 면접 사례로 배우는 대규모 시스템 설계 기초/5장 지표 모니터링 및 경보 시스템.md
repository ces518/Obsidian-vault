# 개요

대규모 시스템에서는 **인프라 상태를 지속적으로 관찰하고 문제를 빠르게 감지**하는 것이 중요하다.

지표 모니터링 시스템의 역할

- 시스템 상태 가시화
- 장애 조기 탐지
- 성능 분석
- 자동 경보(alerting)

대표적인 모니터링 시스템

- Prometheus
- Datadog
- InfluxDB
- Munin

# 요구사항

## 모니터링 대상 규모

|항목|규모|
|---|---|
|일간 활성 사용자(DAU)|1억|
|서버 풀|1000개|
|서버 수|풀당 100대|
|전체 서버|100,000대|

## 수집 지표 규모

서버 하나당 100개의 운영 지표 수집 가징

예시 지표

- CPU 사용률
- 요청 수 (RPS)
- 메모리 사용량
- 메시지 큐 길이
- 디스크 사용량

```bash
100,000 서버 × 100 metrics
= 10,000,000 metrics
```

## 데이터 보관 정책

모니터링 데이터는 시간이 지나면 **해상도를 낮춰 저장**한다

→ Downsampling 이라고 함

- 저장 공간 절약
- 조회 성능 향상
- 장기 데이터 보관 가능

|기간|저장 방식|
|---|---|
|최근 7일|원본 데이터|
|이후 30일|1분 단위 집계 데이터|
|이후 1년|1시간 단위 집계 데이터|

## 모니터링 대상 대표 유형

수집 대상은 **운영 지표(Operational metrics) 이며,** 사업 지표는 포함하지 않는다

### 시스템 지표

- CPU usage
- Memory usage
- Disk usage
- Network usage

### 서비스 지표

- Requests per second
- Active connections
- Queue size
- Worker count

## 경보 시스템 요구 사항

시스템은 이상 상황 발생시 **자동 경보 발생**

지원 채널

- Email
- Phone
- PagerDuty
- Webhook

## 비기능 요구사항

- 확장성
- 낮은 지연
- 안정성
- 유연성

# 개략적 설계

지표 모니터링 및 경보 시스템은 일반적으로 **5개의 핵심 컴포넌트**로 구성된다.

```bash
Metric Source
     ↓
1. Data Collection
     ↓
2. Data Transmission
     ↓
3. Data Storage
     ↓
4. Alerting
     ↓
5. Visualization
```

1. 데이터 수집
    - 각 서버나 애플리케이션에서 **운영 지표(metrics)** 를 수집한다.
2. 데이터 전송
    - 수집된 지표 데이터를 **모니터링 시스템으로 전달** 한다.
3. 데이터 저장
    - 수집된 지표 데이터를 **시계열 데이터베이스(Time Series DB)** 에 저장한다.
4. 경보 시스템
    - 수집된 데이터를 분석하여 **이상 상황 발생 시 경보를 발생**시킨다.
5. 시각화
    - 수집된 지표를 **그래프 및 대시보드 형태로 제공** 한다.

# 데이터 모델

모니터링 시스템에서 사용하는 데이터는 **시계열(Time Series) 데이터**이다.

## 시계열 데이터란 ?

값(value)에 시간(timestamp)이 붙어서 기록되는 데이터

## 시계열 데이터의 구성 요소

|요소|설명|
|---|---|
|metric name|지표 이름|
|labels|지표를 구분하는 태그|
|timestamp|측정 시각|
|value|측정 값|

```bash
metric_name: cpu.load
labels: host=i631, env=prod
timestamp: 1613707265
value: 0.29
```

**metric name + label 조합**은 하나의 시계열을 정의한다.

```bash
cpu.load{host=i631,env=prod}
```

이 값은 하나의 시계열이 되고 시간에 따라 값이 계속 기록된다.

```bash
t1 → 0.21
t2 → 0.34
t3 → 0.29
t4 → 0.31
```

## 데이터 저장 형태

```bash
metric_name
labels
[(timestamp, value), (timestamp, value)...]
```

## 사례 1

서버 **i631의 20:00 시점 CPU 부하** 데이터 표현

```bash
metric_name: cpu.load
labels: host=i631, env=prod
timestamp: 1613707265
value: 0.29
```

## 사례 2

us-west 지역 모든 웹 서버의 CPU 평균

```bash
CPU.load host=webserver01 region=us-west 50
CPU.load host=webserver01 region=us-west 62
CPU.load host=webserver02 region=us-west 43
CPU.load host=webserver02 region=us-west 53
```

이러한 데이터는 **line protocol 형식**으로 표현되기도 한다.

## 시계열 데이터 구조

시계열 데이터는 개념적으로 다음 구조를 가진다

|필드|자료형|
|---|---|
|metric name|문자열|
|labels|key:value 집합|
|values|(value, timestamp) 배열|

## 데이터 접근 패턴
![](images/Pasted%20image%2020260304193501.png)
### 시계열 데이터 접근 단위

- **y축 레이블(이름 + 레이블/태그 조합)** = **하나의 시계열(Time Series)**
    - 예: `http_error_count{servicepool="s1", method="GET", machinename="m1"}`
- **x축 레이블** = **시간(Time)**
    - 결국 데이터는 **(timestamp, value)** 가 시간축으로 쌓임

데이터 모델 관점에서 접근 패턴은

- **특정 시계열을 잡고(필터: metric + labels)**
- **특정 시간 구간을 잘라(range query)**
- **값들을 읽고/집계한다**

### 쓰기 패턴

이 시스템의 쓰기 부하는 **막대하고 지속적**임.

- 시점과 무관하게 **많은 시계열 데이터가 계속 기록**
- 책의 가정대로면 **매일 천만 개 운영 지표가 기록**되고,
- 그 중 상당수는 **발생 빈도(샘플링 주기)가 높아** 트래픽이 커짐

트래픽은 **쓰기 중심(Write-heavy)** 이다

### 읽기 패턴

읽기는 **spiky(일시 급증형)** 로 본다.

읽기 트래픽을 만드는 주체는 주로 두 가지:

- **시각화(Visualization)**: 대시보드/그래프 조회
- **경보(Alerting)**: 룰 평가를 위해 주기적으로 구간 데이터를 읽거나 집계

**읽기는 평소엔 낮고, 특정 이벤트에 튀는 패턴**

### 설계 관점

- **Write-heavy + Read-spiky** 이므로
    - 쓰기 경로는 “항상 고성능/안정적”이어야 하고
    - 읽기는 “피크 흡수”가 중요 (캐시/사전 집계/다운샘플링 등)
- 또한 질의가 **labels(태그) 기반**이기 때문에
    - 태그 인덱싱/시계열 식별 방식이 핵심 설계 포인트가 됨
