# 개요

메리어트 인터내셔널 규모의 호텔 체인을 위한

**대규모 호텔 예약 시스템 설계**

- 5,000개 호텔
- 100만 개 객실
- 웹사이트/앱 기반 예약 시스템

이 장의 설계 기법은 다음과 같은 문제로 확장 가능:

- 에어비앤비
- 항공권 예약
- 영화 티켓 예매

# 요구사항

## 기능 요구사항

- 호텔 정보 페이지 표시
- 객실 정보 페이지 표시
- 객실 예약
- 관리자 페이지

    - 수정
    - 삭제
- 예약 취소 가능
- 초과 예약 지원 (10%)

## 제약 조건

**결제 방식**

- 예약 시 전액 선결제

**예약 채널**

- 호텔 웹사이트/앱만 지원

**취소 지원**

- 반드시 가능

**초과 예약 (Overbooking)**

- 실제 객실 수보다 10% 더 판매 가능
- 일부 고객 취소를 전제로 한 전략

**유동 가격 (Dynamic Pricing)**

- 객실 가격은:
    - 날짜마다 다름
    - 잔여 객실 수에 따라 변동
- 실시간 재고 기반 가격 정책

## 개략적 규모 추정

1. 기본 가정
    
    - 호텔 수: **5,000개**
    - 객실 수: **1,000,000개(100만)**
    - 평균 객실 점유율: **70%**
    - 평균 투숙 기간: **3일**
2. 일일 예약 건수 추정
    
    - 하루에 “새로 발생하는 예약”은
        
        **(전체 객실 × 점유율) / 평균 투숙기간**
        
    - 계산:
        
        - 1,000,000 × 0.7 / 3 = **233,333건**
        - 반올림해서 **약 240,000건/일**
3. 예약 TPS 추정
    
    - 하루 초(秒) 수: **10^5초(약 86,400초를 근사)**
    - 계산:
        - 240,000 / 10^5 ≈ **2.4**
        - 즉 **TPS ≈ 3**
    - 결론: **예약 트랜잭션 TPS 자체는 높지 않다**
4. 페이지별 QPS 계산
    
    사용자는 보통 아래 순서로 진행:
    
    1. **호텔/객실 상세 페이지**(조회)
    2. **예약 상세 정보 페이지**(조회)
    3. **객실 예약 페이지**(트랜잭션)
    
    가정:
    
    - 다음 단계로 진행하는 사용자는 **10%**
    - 최종 예약까지 가지 못하고 이탈하는 사용자가 **90%**
    - 다음 단계 화면을 “미리 계산(precompute)”해두는 최적화는 **안 한다**
    
    결과(그림 7.1):
    
    - 객실 예약 페이지: **QPS ≈ 3**
    - 예약 상세 페이지: **QPS ≈ 30**
    - 객실 상세 페이지: **QPS ≈ 300**

# 데이터 모델

## 데이터베이스 선택

관계형 데이터베이스 를 선택한 이유는 3가지:

**1. 읽기 중심 트래픽**

- 예약 시도보다 조회가 훨씬 많음
- 객실 상세 QPS = 300
- 예약 TPS = 3

→ 읽기 위주 워크로드 → RDB 적합

**2. ACID 보장 필요**

예약 시스템은:

- 이중 예약 방지
- 이중 결제 방지
- 잔여 객실 음수 방지

ACID가 보장되지 않으면 애플리케이션 복잡도 폭증

→ RDB는 기본적으로 ACID 보장

**3. 데이터 관계가 명확함**

엔티티 간 관계가 뚜렷함:

- 호텔 ↔ 객실
- 호텔 ↔ 요금
- 객실 ↔ 예약
- 예약 ↔ 투숙객

→ 정형 데이터 + 명확한 FK 관계 → RDB 적합

# 개략적 설계

호텔 예약은 도메인이 크고(호텔/요금/예약/결제/운영), 트래픽 특성이 다르기 때문에 **마이크로서비스**로 분리해서 설계한다.

구성은 크게 4층으로 나뉜다:

- **클라이언트/엣지:** 사용자·관리자, CDN
- **진입 계층:** 공개 API 게이트웨이(비공개/내부 API 포함)
- **도메인 서비스:** 호텔/요금/예약/결제/호텔관리
- **저장소:** 각 서비스별 DB + 캐시(호텔 캐시)
![](images/Pasted%20image%2020260228183039.png)
## 구성 요소

**사용자(User)**

- 모바일/웹에서 호텔/객실 조회 및 예약 수행

**관리자(Admin = 호텔 직원)**

- 환불, 예약 취소, 객실 정보 갱신 등 운영 기능 수행

**CDN**

- JS 번들/이미지/동영상/HTML 같은 **정적 컨텐츠 캐싱**
- 웹 로딩 속도 개선 + 원본 서버 부하 감소

**공개 API 게이트웨이 (Public API Gateway)**

- 외부 트래픽 진입점
- 담당:
    - **Rate limiting(처리율 제한)**
    - **인증(Authentication)**
    - 라우팅(엔드포인트별로 호텔/예약 등 적절한 서비스로 전달)

**내부 API (Internal API)**

- 승인된 직원만 사용
- 보통 **VPN 같은 네트워크 경계**로 외부 공격을 차단

### 도메인별 MSA 구성

**1) 호텔 서비스 (Hotel Service)**

- 호텔/객실 **상세 정보 제공**
- 데이터가 대체로 **정적** → **캐시(호텔 캐시)** 적용이 쉬움

**2) 요금 서비스 (Rate Service)**

- “미래 특정 날짜에 적용될 요금” 제공
- 가격은 **수요에 따라 변동(Dynamic Pricing)** 될 수 있음

**3) 예약 서비스 (Reservation Service)**

- 예약 요청을 받아 **객실 예약 처리**
    
- 예약/취소 시 **잔여 객실(inventory) 갱신** 책임
    
- (실제로는) 총 결제 금액 산정을 위해 **요금 서비스 조회가 필요**
    
    → 책에서도 그림 7.4 단순화를 위해 화살표 생략했다고 언급
    

**4) 결제 서비스 (Payment Service)**

- 결제 처리 담당
- 결제 성공 시 예약 상태를 **결제 완료(paid)** 로 업데이트
- 실패 시 **승인 실패(rejected)** 로 업데이트

**5) 호텔 관리 서비스 (Hotel Management Service)**

- 승인된 직원 전용 운영 서비스
    
- 임박 예약 확인, 고객 대신 예약, 예약 취소 등 제공
    
- 직원이 변경한 데이터는 결국 **각 도메인의 실제 서비스로 전달**되어 반영됨
    
    (그림 단순화를 위해 다수의 연계 화살표 생략
    

### 저장소 설계 원칙

- 서비스별로 **독립 DB**를 둔다
    - 호텔 DB / 요금 DB / 예약 DB / 결제 DB
- 호텔/객실 정보는 캐싱 효율이 좋아서 **호텔 캐시**를 별도로 둠

### 서비스 간 통신

- 상용 환경에서는 서비스 간 통신에 **gRPC 같은 고성능 RPC**를 흔히 사용
- (요금 조회, 예약 상태 변경 등) 서비스 간 연동이 많음

# 개선된 데이터 모델

기존 스키마는 room_id 기반이라 에어비앤비처럼 **특정 방을 예약하는 모델**에 적합하다

하지만 호텔은 보통:

- 예약 시점에는 **특정 객실 번호가 아니라 “객실 유형(room type)”**을 예약
- **객실 번호 배정은 체크인 시점**에 이루어짐

예약 단위를 `room_id` → `room_type_id` 로 변경 해야 한다

## 스키마 변경점

### reservation

- `room_id` 제거 / `room_type_id` 추가
- 예약은 이제 “호텔 + 객실유형 + 날짜 범위”를 대상으로 생성됨

필드(요지):

- reservation_id (PK)
- hotel_id
- room_type_id
- start_date, end_date
- status
- guest_id

### room_type_rate (요금)

- “특정 객실 유형의 특정 날짜 요금”
- (그림상 PK 표기는 hotel_id/date로 보이지만, 개념적으로는 **room_type까지 포함되는 요금 테이블**로 이해하는 게 자연스러움

### room (객실)

- 객실에 대한 정적 정보 보관
- 실제 “객실 번호/층/호텔 소속” 등의 정보는 여기 존재
- 체크인 시점에 room_type에 맞는 room을 배정

### **room_type_inventory (핵심 신규)**

예약 시스템의 핵심 테이블. **(재고 관리를 count 로 수행함)**

“호텔의 특정 객실유형이 특정 날짜에 몇 개 남아있는지”를 **날짜 단위 레코드**로 관리.

컬럼 의미(책에서 자세히 설명한 부분):

- `hotel_id`: 호텔 식별자
    
- `room_type_id`: 객실 유형 식별자
    
- `date`: 일자
    
- `total_inventory`:
    
    총 객실 수에서 **일시적으로 제외한 객실(점검/유지보수 등)** 을 뺀 값
    
    → “판매 가능한 총 재고”
    
- `total_reserved`:
    
    해당 (hotel_id, room_type_id, date) 에 대해 **이미 예약된 객실 수**
    

PK:

- `(hotel_id, room_type_id, date)` 복합 PK

->  날짜별 레코드를 쓰면 **기간(start~end) 예약을 질의/검증/차감**하기가 쉬움.
![](images/Pasted%20image%2020260228183119.png)
## 저장 용량 추정

가정:

- 호텔 5,000개
- 호텔당 객실 유형 20개
- 2년치(365일×2)

레코드 수:

- `5,000 × 20 × 2 × 365 = 약 7,300만 rows`

결론:

- 데이터 양 자체는 **DB 1대로도 저장 가능**
- 하지만 **SPOF 회피/고가용성**을 위해
    - 여러 AZ/Region에 **복제(Replication)** 필요

# 동시성 문제

**이중 예약을 방지** 하는 것이 풀어야할 문제:

1. **같은 사용자가 예약 버튼을 여러 번 누르는 경우**
2. **여러 사용자가 같은 객실을 동시에 예약하려는 경우**

이 둘은 성격이 완전히 다르다.
![](images/Pasted%20image%2020260228183137.png)
## **1. 같은 사용자가 예약 버튼을 여러 번 누르는 경우**

1. 클라이언트 구현
    
    - 버튼을 비활성화
    - 회색 처리
    - 숨김
    
    하지만:
    
    - JS 비활성화
    - 네트워크 재시도
    - API 직접 호출
    
    → 우회 가능
    
2. 서버 측 구현 (멱등)
    
    예약 요청에 **reservation_id**를 포함
    
    - reservation_id = 전역적으로 유일한 값
    - reservation 테이블의 PK로 사용
    
    **동작 방식**
    
    1. 사용자가 예약 주문 생성 → reservation_id 발급
    2. 같은 reservation_id로 예약 제출
    3. 두 번째 요청이 들어오면:
        - PK 유일성 조건 위반
        - INSERT 실패
        - 중복 예약 방지
![](images/Pasted%20image%2020260228183152.png)
## 2. **여러 사용자가 같은 객실을 동시에 예약하려는 경우**

**상황**

- 어떤 room_type에 잔여 객실 1개
- 두 명이 동시에 예약 시도

문제는:

- 둘 다 `SELECT` 시점에는 재고가 남아 있음
- 둘 다 예약 성공 처리하면 → 초과 예약 발생

두 트랜잭션이 동시에 읽으면

- 둘 다 “예약 가능”이라고 판단
- 둘 다 `total_reserved += 1`
- 결과: 재고 초과

<aside> 💡

동시성 문제는 "읽기-검사-쓰기(read-check-write)" 패턴이 **원자적**이지 않기 때문이다

문제 해결을 위해서 어떤 형태로든 락을 활용해야 한다

</aside>

## 비관적 락

“누군가는 반드시 동시에 수정하려 할 것이다”라고 가정하고

**레코드를 수정하려는 순간 즉시 락을 걸어 다른 트랜잭션을 대기시킨다.**

- 먼저 접근한 트랜잭션이
- 해당 row를 점유(lock)
- 다른 트랜잭션은 commit/rollback까지 대기

### MySQL 의 구현

```jsx
SELECT ... FOR UPDATE
```

- SELECT로 읽은 레코드에 **배타적 락(exclusive lock)** 이 걸림
- 다른 트랜잭션은 해당 레코드를 수정 불가
- 락은 **트랜잭션 종료 시점(commit/rollback)** 에 해제
![](images/Pasted%20image%2020260228183205.png)

### 장점

1. 구현이 단순하다
2. 충돌을 완전히 직렬화
3. 데이터 경합이 심한 경우 안정적

### 단점

1. 데드락 문제
    
    특히 호텔 예약처럼
    
    ```
    start ~ end
    ```
    
    기간이 길면 여러 날짜 row를 잠그므로 교착 위험 증가
    
2. 확장성 문제
    
3. 성능 저하
    

<aside> 💡

예약 시스템에 비관적 락 메커니즘은 권장되지 않는다

</aside>

## 낙관적 락

“충돌은 자주 일어나지 않을 것이다”라고 가정하고

**락을 미리 걸지 않고, 충돌이 발생했을 때만 실패 처리 후 재시도하는 방식**

- 여러 사용자가 동시에 같은 데이터를 읽는 것을 허용
- 갱신 시점에 **버전(version)** 을 비교해 충돌 여부 판단

### 구현 방식

```jsx
SELECT total_reserved, version
FROM room_type_inventory
WHERE ...

UPDATE room_type_inventory
SET total_reserved = total_reserved + 1,
    version = version + 1
WHERE ...
AND version = 1;
```

- UPDATE 성공 row = 1 → 성공
- UPDATE 성공 row = 0 → 다른 트랜잭션이 먼저 갱신함 → 실패 → 재시도
![](images/Pasted%20image%2020260228183215.png)
### 장점

1. 락을 점유하지 않음
    - SELECT 시점에 락 없음
    - DB 대기 시간 없음
    - 일반적으로 비관적 락보다 빠름
2. 구현이 단순
    - version 컬럼 하나 추가
    - WHERE 조건만 추가
3. 낮은 충돌 환경에서 효율적

### 단점

1. 충돌이 많으면 성능 급락
    
    호텔 예약처럼:
    
    - 남은 객실 1개
    - 수백 명이 동시에 시도
    
    → 모두 같은 version 읽음
    
    → 오직 1명만 성공
    
    → 나머지 모두 실패 후 재시도
    
    → **폭발적 재시도 트래픽**
    
    이게 낙관적 락의 치명적 한계.
    
2. 재시도 로직 필요
    
    - 실패 시 앱 레벨에서 재시도 처리
    - 사용자 경험 고려 필요

<aside> 💡

호텔 예약 같은 “핫 스팟 재고 시스템”에서는 낙관적 락도 완벽한 해법이 아니다.

</aside>

## 데이터베이스 제약조건

애플리케이션에서 버전 비교를 하지 않고

**DB가 스스로 “재고가 음수가 되지 않도록” 막게 한다.**

- 낙관적 락처럼 “사후 검증”을 하지만
- 검증 주체가 **애플리케이션이 아니라 DB** 라는 점

### 구현 방식

`room_type_inventory` 테이블에 다음 제약 조건 추가:

```jsx
CONSTRAINT check_room_count
CHECK (total_inventory - total_reserved >= 0)
```

- DB가 마지막 방어선 역할을 수행
![](images/Pasted%20image%2020260228183229.png)
### 장점

1. 구현이 단순함
2. 애플리케이션 로직 단순화
3. 경쟁이 낮을때 매우 잘 동작

### 단점

1. 충돌이 많을 경우 실패 폭증
2. 사용자 경험 문제
3. 버전 통제 어려움

# 시스템 규모 확장

호텔 웹사이트/앱 **자체 트래픽만** 받는다면 보통 예약 QPS가 높지 않다.

“[booking.com](http://booking.com), [expedia.com](http://expedia.com) 같은 외부 여행 플랫폼과 연동되면?”

- **QPS가 1,000배**까지 늘 수 있다

병목 지점:

- DB 가 핵심
- 서비스들은 **무상태(stateless)** 라서 서버를 추가하면 수평 확장이 가능
- 하지만 **모든 상태(state)가 DB에 저장**되므로
    - DB는 **서버만 늘린다고 해결 안 됨**
    - DB 자체 확장이 필요

## 데이터베이스 샤딩

- DB를 여러 대로 쪼개고, 각 DB에 **데이터 일부만 저장**
- 즉, DB 부하를 “분산”시킴

### 샤딩 키

- 이 시스템의 대부분 질의는 `hotel_id`로 필터링됨
- 따라서 **`hotel_id`를 샤딩 키**로 쓰는 게 자연스럽다
- 전체 QPS가 **30,000**
- **16개 샤드**로 분산하면
    - 각 샤드 QPS = 30,000 / 16 = **1,875 QPS**
- 이는 **MySQL 단일 서버로 감당 가능한 수준**
![](images/Pasted%20image%2020260228183241.png)
## 캐시

- **과거 데이터는 중요하지 않음**
    - 고객은 과거 날짜를 예약하지 않는다
- 그래서 “오래된 데이터는 자동 소멸”되는 구조가 이상적

**Redis가 적합한 이유**

- TTL(Time-To-Live) 설정 가능
- LRU 캐시 교체 정책으로 메모리 활용 최적화 가능

**캐시를 어디에 두나?**

- DB 앞단에 캐시 계층을 두고
    - **잔여 객실 확인**
        
    - **객실 예약 로직**
        
        을 캐시에서 처리하도록 할 수 있다
        

중요한 주의점:

- 캐시에 “충분”으로 보여도 **DB를 다시 확인할 필요**가 있다
- **최종 진실(source of truth)은 DB**에 있다는 점을 강조
![](images/Pasted%20image%2020260228183251.png)
## 서비스간 데이터 일관성

전통적인 **모노리스(monolith)** 구조에서는 보통:

- 여러 기능(예약/잔여객실/결제 등)이
- **하나의 관계형 DB를 공유**함

그래서 논리적으로 한 번에 끝나야 하는 작업을:

- **단일 트랜잭션**으로 묶어
- **ACID**를 만족시키는 게 가능

→ “원자적 연산”을 DB 트랜잭션이 보장해줌

마이크로서비스 아키텍처를 “정석”으로 보면:

- **각 서비스는 독자적인 DB를 가져야 한다**
    - 예약 서비스 DB
        
    - 잔여 객실 서비스 DB
        
    - 결제 서비스 DB
        
        처럼
        

논리적으로 하나의 원자적 연산이 **여러 DB에 걸쳐 실행될 수밖에 없다**

![](images/Pasted%20image%2020260228183303.png)
### 하이브리드 접근

책은 동시성 문제를 해결하기 위해:

- **예약 서비스가 예약 API + 잔여 객실 API를 함께 담당**
    
- `reservation` 테이블
    
- `room_type_inventory`(잔여 객실) 테이블
    
    을 **같은 RDB에 저장**
    

“예약”과 “재고(잔여 객실)”을 같은 DB 트랜잭션으로 묶어서 ACID를 활용한다

- 이중 예약 방지
- 재고 음수 방지
- read-check-write 경쟁 조건 완화
