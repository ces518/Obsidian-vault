## 개요

네트워크 장치 세 가지 구조([[네트워크 장치 구조 Inline Out of Path Proxy]]) 중 첫 번째인 **Inline 구조**와, 그 대표 장치인 **라우터**의 내부 구조를 다룬다.
- Inline 장치는 **패킷이 반드시 통과**하는 길목에 있어 **필터링(Drop / Bypass)** 이 가능하다.
- 라우터 / 공유기 / 패킷 필터링 방화벽 / IPS 가 모두 같은 Inline 부류.
- 라우터 내부는 사실상 **NIC 여러 개 꽂힌 PC** + 라우팅 소프트웨어이며, 고성능을 위해서는 **패킷을 모아서 한 번에 처리**해야 한다.

---

## 1. Inline 장치 = 트래픽이 "통과"하는 구조

> [!important] Inline 구조의 본질
> 트래픽이 **반드시 장치를 거쳐서** 외부로 나가거나 내부로 들어온다.
> → "통과 vs Drop"을 결정할 수 있는 **필터링 권한**이 생긴다.

```
내부 PC ── [Access Switch] ── [Router / 방화벽] ── 인터넷
                                  ▲
                            모든 패킷이 여기를 통과
                            → 통과 / 차단 결정 가능
```

### 대표적인 Inline 장치

| 장치 | 역할 | 비고 |
|------|------|------|
| **라우터(Router)** | 패킷 경로 결정 및 전달 | 가장 전형적인 Inline 장치 |
| **공유기** | 가정용 라우터 | 라우터와 동일 구조 |
| **패킷 필터링 방화벽(Firewall)** | 보안 정책에 따라 패킷 허용/차단 | 기업 네트워크 앞단 배치 |
| **IPS** (Intrusion Prevention System) | 침입 시도 탐지 + **차단** | 방화벽보다 고급 보안 기능 |

> [!tip] Inline 장치 = 필터링 가능 장치
> "Inline 구조" 라는 말이 나오면 짝꿍처럼 따라오는 키워드가 **필터링(Filtering)**.
> 패킷 단위로 거름질을 하려면 **반드시 트래픽 경로 위에 있어야** 한다 → Inline.

관련: [[네트워크 장치 구조 Inline Out of Path Proxy]] · [[라우터에 대한 최소 이론]]

## 2. Inbound / Outbound 용어 정리

Inline 장치를 기준으로 트래픽의 방향을 부른다.

| 용어 | 방향 | 설명 |
|------|------|------|
| **Inbound** | 외부 → 내부 | 인터넷에서 내부망으로 유입 |
| **Outbound** | 내부 → 외부 | 내부망에서 인터넷으로 유출 |

- Inline 장치를 기준으로 방향을 판단한다.
- 방화벽의 필터링 = 주로 **Inbound 패킷을 Drop** 하는 것.

## 3. Inline 장치가 하는 일 — 세 가지 동작

> [!important] Inline 장치의 행동 패턴
> 패킷을 읽은 뒤 다음 셋 중 하나를 선택한다.
> 1. **Bypass (통과)** — 다른 인터페이스로 write
> 2. **Drop (폐기)** — write 하지 않고 소멸
> 3. (그 사이에서 동작하는 **로직** — 라우팅 / 필터링 검사)

### 패킷 처리 흐름

```
패킷 유입 (NIC①)
   │
   ▼
 Read (패킷 읽기)
   │
   ▼
 목적지 IP 확인 ──── "내 IP(5.5.5.1)인가?"
   │                      │
   │ NO (남의 패킷)        │ YES (내 패킷)
   ▼                      ▼
 라우팅 판단            프로세스에 전달
   │                    (일반 통신과 동일)
   ├── NIC②로 보내면 됨 → Write → ✅ Bypass
   ├── NIC③로 보내면 됨 → Write → ✅ Bypass
   └── 보낼 곳이 없음   → Write 불가 → ❌ Drop
```

### 3가지 동작 정리

| 동작 | 설명 | 결과 |
|------|------|------|
| **Bypass (통과)** | 적절한 NIC으로 Write | 패킷이 다음 목적지로 전달 |
| **Drop (드롭)** | Write하지 않음 | 패킷이 장치 내에서 소멸 |
| **처리 로직** | Bypass/Drop 판단을 위한 SW | 라우팅 / 필터링 규칙 적용 |

### Drop이 발생하는 상황

- 읽은 패킷의 **Destination을 어떤 인터페이스로도 보낼 수 없을 때**
- 또는 **필터 규칙(보안 정책)에 걸렸을 때**

```
NIC#1 ─ read 패킷 ─▶ 분석
  Destination = 9.9.9.x
  내 IP        = 5.5.5.1
  다른 NIC에도 해당 경로 없음
                      → write 불가 → Drop
```

## 4. 라우터 내부 — "사실은 PC다"

> [!note] 핵심 통찰
> 시스코 라우터 = (저성능) **CPU + RAM + NIC 여러 개 + Cisco IOS**
> 즉 구조적으로는 **NIC 많이 꽂힌 PC**와 다르지 않다.

```
┌─────── Cisco Router ───────┐
│  CPU (Intel 등, PC보다도   │
│       오히려 저사양인 경우) │
│  RAM                       │
│  OS: Cisco IOS             │
│                            │
│  ┌────┐ ┌────┐ ┌────┐      │
│  │NIC1│ │NIC2│ │NIC3│ ...  │
│  └────┘ └────┘ └────┘      │
└────────────────────────────┘
```

### 라우터 vs 일반 PC 구성 비교

| 구성요소 | 라우터 | 일반 PC |
|----------|--------|---------|
| **CPU** | Intel 등 (PC보다 저사양인 경우도 많음) | Intel / AMD |
| **NIC** | 여러 개 (3개 이상) | 보통 1개 |
| **OS** | Cisco IOS 등 전용 OS | Windows / Linux |
| **목적** | 패킷 유통 (read → write) | 범용 컴퓨팅 |

### 그 결과 — 이론적으로 가능한 변태 짓 😈

| 시도 | 결과 |
|------|------|
| Cisco Router에서 IOS 지우고 **Windows 설치** | 윈도우즈 라우터(?) |
| **PC에 NIC 여러 개** + Cisco IOS 설치 | 그 PC가 곧 Cisco Router |

> [!tip] 진짜 "라우터"가 되는 조건
> 단순히 NIC만 여러 개 꽂는다고 라우터가 되는 게 아니다.
> 표준 **라우팅 프로토콜(OSPF, BGP, RIP 등)** 을 준수해야 한다.
> 그것만 충족하면 OS와 상관없이 "라우터"로 기능할 수 있다.
> **하드웨어는 본질적으로 같고, 차이는 OS와 소프트웨어가 만든다.**

## 5. 기업 네트워크에서의 Inline 배치

> [!note] 실무 배치 — 외부에서 안쪽으로
> Inline 장치들이 어떤 순서로 줄지어 있는지 한눈에 본다.

```
        [인터넷]
            │
   ┌────────┴────────┐
   │  ISP 라우터       │ ← Inline ①
   └────────┬────────┘
            │
   ┌────────┴────────┐
   │ 기업 라우터       │ ← Inline ②
   └────────┬────────┘
            │
   ┌────────┴────────┐
   │ 패킷 필터링 방화벽 │ ← Inline ③
   └────────┬────────┘
            │
   ┌────────┴────────┐
   │ SSL Termination   │ (선택적)
   │ / SSL Accelerator │
   └────────┬────────┘
            │
   ┌────────┴────────┐
   │ Proxy (WAF / ALB) │ ← 여기서부터 Proxy 구조
   └────────┬────────┘
            │
        [내부 서버]
```

> [!tip] 배치 순서는 가변적
> 라우터와 방화벽의 순서는 조직마다 다르고, 한쪽이 ISP 망 안에 있을 수도 있다.
> 핵심은 **Inline 장치들이 직렬로 줄지어** 패킷을 흘려보낸다는 점.
> **SSL Termination** (또는 **SSL Accelerator**) 은 별도 장비로 분리되는 경우도 있다.

## 6. Inline 장치 내부 데이터 흐름

일반 애플리케이션의 통신과 Inline 장치의 통신은 **목적지가 다르다.**

### 일반 프로세스 (예: Chrome)

```
[Chrome (User mode)]
     │ socket write
     ▼
[ Kernel: TCP / IP ]
     │
     ▼
[ NIC Driver ] ─▶ [NIC] ─▶ 외부 (구글)
```
→ 트래픽의 **목적지가 자기 자신** (혹은 자신이 만든 트래픽).

### Inline 장치 (예: Router)

```
NIC#1 ──read── ┐
               │  ┌──── 로직 ────┐
NIC#2          ├─▶│ Destination을│──▶ NIC#2 write
               │  │ 보고 어느    │     또는
NIC#3 ─────────┘  │ NIC로 보낼지 │──▶ NIC#3 write
                  │ 결정         │     또는
                  └──────────────┘──▶ Drop
```
→ 도착한 패킷의 **목적지가 내가 아님**. 다른 NIC로 **다시 write** 해주는 게 일.

## 7. 성능 팁 — 패킷을 "묶어서" 처리하라

> [!danger] Inline 소프트웨어를 직접 개발한다면
> **패킷 하나당 User mode ↔ Kernel mode 스위칭**은 **성능 자살**.
> PPS(Packet Per Second)가 처참하게 떨어진다.

> [!note] PPS (Packets Per Second)
> 초당 처리 패킷 수. **Inline 장치 성능을 평가하는 가장 중요한 단위.**

### ❌ 나쁜 패턴 — 패킷 1개씩 모드 전환

```
패킷① ─ Kernel ─▶ User mode 검사 ─▶ Kernel ─▶ write
패킷② ─ Kernel ─▶ User mode 검사 ─▶ Kernel ─▶ write
패킷③ ─ Kernel ─▶ User mode 검사 ─▶ Kernel ─▶ write
                  ↑ 매번 모드 전환 = PPS 급락
```

### ✅ 좋은 패턴 — 배치 처리 (Linked List)

```
Kernel: [패킷①] → [패킷②] → [패킷③]   (Linked List로 묶음)
              │
              ▼ 한 번에 User mode로 전달
User mode: [①, ②, ③] 일괄 검사
              │
              ▼ 한 번에 Kernel로 복귀
Kernel: write 3건 일괄 수행
```

### 성능 비교

| 방식 | 모드 전환 횟수 | 성능 |
|------|----------------|------|
| 패킷 1개씩 처리 | **패킷 수 × 2회** | 매우 낮음 |
| 배치 처리 | **단위 시간당 2회** | 높음 |

> [!tip] 핵심 원리
> 컨텍스트 스위칭은 비싸다. **묶어서 한 번에** 처리하면 PPS가 폭발적으로 올라간다.

## 핵심 요약

| 기억할 것 | 내용 |
|----------|------|
| **Inline =** | 패킷이 반드시 통과하는 구조 → 필터링 가능 |
| **핵심 동작** | Bypass(통과) 또는 Drop(소멸) |
| **대표 장치** | 라우터 / 공유기 / 패킷 필터링 방화벽 / IPS |
| **라우터의 본질** | PC + 다중 NIC + 라우팅 소프트웨어 |
| **라우터 자격** | OS가 아니라 **라우팅 프로토콜 준수** 여부 |
| **Drop의 원리** | Read 후 Write할 곳이 없거나 정책 위반 시 소멸 |
| **방향 용어** | Inbound(외부→내부) / Outbound(내부→외부) |
| **목적지의 차이** | 일반 프로세스 = 자신 / Inline = 남 (다른 NIC로 재전송) |
| **기업 배치 순서** | ISP 라우터 → 방화벽 → (SSL Termination) → Proxy → 서버 |
| **개발 핵심** | 패킷별 모드 전환 금지 → 배치(Linked List) 처리 필수 |
| **성능 단위** | **PPS** (Packets Per Second) |
