대부분의 메시지 큐(Message Queue) 시스템이 Push 모델보다 **Pull(Polling) 모델을 기본으로 사용하는 이유는 네 가지 아키텍처적 특성 때문입니다.**

---

### 1. Consumer 제어권 (Flow Control)

Pull 모델에서는 Consumer가 처리 가능한 만큼만 메시지를 가져옵니다.

Consumer -> Queue : 메시지 요청  
Queue -> Consumer : 메시지 전달

Consumer가 메시지를 직접 가져오기 때문에 다음과 같은 제어가 가능합니다.

- 처리량 제어
    
- 자연스러운 Backpressure 구현
    
- Consumer 과부하(OOM, thread 증가 등) 방지
    

예를 들어 Kafka에서는 다음과 같이 배치 단위로 메시지를 가져옵니다.

consumer.poll(10)

즉, 한 번에 10개의 메시지만 가져와 처리할 수 있습니다.

반면 Push 모델에서는

Queue -> Consumer : 메시지 전달

브로커가 메시지를 계속 전달할 수 있기 때문에 Consumer 처리 속도를 초과하면 다음 문제가 발생할 수 있습니다.

- Consumer 과부하
    
- OOM
    
- Thread 증가
    
- 장애 전파
    

---

### 2. Consumer 장애 처리 (Fault Tolerance)

Pull 모델에서는 Consumer가 중단되어도 메시지를 안전하게 재처리할 수 있습니다.

예:

Consumer A poll  
→ 메시지 수신  
→ 처리 중 crash

이 경우 Queue는 다음과 같이 동작합니다.

ack 없음 → 메시지를 다시 큐에 배치

따라서 다른 Consumer가 해당 메시지를 다시 가져와 처리할 수 있습니다.

반면 Push 모델에서는 다음과 같은 문제가 발생할 수 있습니다.

Queue -> Consumer push  
Consumer crash

이 경우

- 메시지 유실 가능성
    
- retry 로직 필요
    
- 별도의 상태 관리 필요
    

Pull 모델은 메시지 재처리 로직을 브로커 수준에서 단순하게 유지할 수 있습니다.

---

### 3. 네트워크 및 연결 관리

Push 모델에서는 브로커가 Consumer로 직접 메시지를 전달해야 합니다.

Queue -> Consumer

따라서 브로커는 Consumer의 네트워크 주소를 알고 있어야 합니다.

하지만 실제 환경에서는 다음과 같은 조건이 존재합니다.

- Consumer autoscaling
    
- Kubernetes 환경
    
- NAT
    
- Private network
    
- Firewall
    

이러한 환경에서는 브로커가 Consumer에 직접 연결하기 어렵습니다.

Pull 모델에서는 연결 방향이 다음과 같습니다.

Consumer -> Queue

따라서

- NAT 문제 없음
    
- Firewall 설정 단순
    
- 연결 관리 단순
    

---

### 4. 메시지 브로커 구현 단순성

Push 모델을 구현하려면 브로커가 다음 상태를 관리해야 합니다.

- Consumer 상태
    
- Consumer 처리량
    
- Backpressure
    
- Retry 로직
    
- Connection 관리
    

즉, 브로커의 복잡도가 크게 증가합니다.

반면 Pull 모델에서는 브로커가 다음 기능만 제공하면 됩니다.

- 메시지 저장
    
- 메시지 반환
    
- ACK 처리
    

따라서 브로커 구조를 단순하게 유지할 수 있습니다.

---

### 5. 실제 메시지 시스템 사례

|시스템|모델|
|---|---|
|Kafka|Pull|
|SQS|Pull|
|Redis Streams|Pull|
|Pulsar|Pull|
|RabbitMQ|Push + Prefetch|

대부분의 분산 메시지 시스템은 Pull 기반 모델을 사용합니다.

---

### 6. Kafka가 Pull 모델을 선택한 이유

Kafka 설계 문서에서도 Pull 모델의 장점을 다음과 같이 설명합니다.

- Consumer가 batch 단위로 메시지를 가져올 수 있음
    
- Consumer가 offset을 직접 관리
    
- Consumer 처리 속도에 맞게 consumption 가능
    

따라서 Kafka Consumer는 다음 API를 사용합니다.

consumer.poll()

---

### 7. Push 모델이 적합한 경우

Push 모델은 **낮은 지연(Low Latency) 이벤트 전달**이 중요한 경우에 사용됩니다.

대표적인 예:

- Webhook
    
- Server-Sent Events (SSE)
    
- gRPC Streaming
    
- RabbitMQ Push Consumer
    

다만 이 경우에도 대부분 다음과 같은 **Flow Control 메커니즘**이 필요합니다.

- Prefetch
    
- Credit
    
- Window 기반 제어
    

---

### 핵심 정리

메시지 큐가 Pull 모델을 선호하는 이유

|이유|설명|
|---|---|
|Flow control|Consumer 속도에 맞게 메시지 소비|
|Fault tolerance|Consumer 장애 시 재처리 용이|
|Network simplicity|NAT / Firewall 환경에서 연결 관리 단순|
|Broker 단순성|상태 관리 감소|
|확장성|Consumer autoscaling에 유리|

따라서 **대규모 분산 시스템에서는 Pull 모델이 더 안정적인 구조를 제공합니다.**
